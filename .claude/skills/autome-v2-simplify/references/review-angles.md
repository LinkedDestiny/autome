# diff 范围的五个清理角度

来源：Claude Code 官方 `/simplify` 与 `/code-review` 的清理角度，做了本地化。
这五个角度只找**质量**问题，不找正确性 bug（那是 code-review 的事）。
每个角度独立过一遍 diff；有子代理就一个角度一个子代理，互不看对方结论。

每条发现记 `file`、`line`、一句话 `summary`、具体代价：重复了什么、浪费了什么、
多维护了什么、违反了哪条书面规则。代价说不出来的不是发现。

## 1. 复用（Reuse）

找 diff 新写的、但仓库里已经有的东西。方法：grep 共享 / 工具模块，以及改动文件相邻的文件，
看有没有同名或同职责的 helper。发现要点名「应该改调用的现成函数」。
常见：又写了一个 `formatDate`、又实现了一遍重试、又拼了一次同样的 SQL 片段。

## 2. 化简（Simplification）

找 diff 引入的不必要复杂度：可推导的冗余状态、带小变化的复制粘贴、深嵌套、留下的死代码、
嵌套三元、把简单事情包成三层调用。发现要点名「做同一件事的更简形式」。
注意：更少行不等于更简单；展开成命名中间变量的三行往往比一行链式调用更简单。

## 3. 效率（Efficiency）

找 diff 引入的浪费：重复计算、重复 I/O、本可并行却串行的独立操作、加到启动路径或热路径上的阻塞工作、
用闭包捕获整个外层作用域构造的长寿对象（会把整个作用域的引用留到对象死亡，大对象时是内存泄漏；
改成只拷贝需要字段的 struct / class）。发现要点名「更便宜的做法」。
这不是性能审计：只标 diff 新引入的浪费，不去优化没动过的代码。

## 4. 高度（Altitude）

检查每个改动是不是在正确的深度修了根因，而不是在表层贴创可贴。
在共享基础设施上叠特例，是修得不够深的信号：优先改底层机制的更通用做法，而不是加分支。
发现要点名「更深一层的修法在哪里」。
反过来也要看：为一个调用点改了公共机制、影响所有调用者，是修得太深。

## 5. 约定（Conventions）

找到管辖被改文件的规则文档：用户级 `~/.claude/CLAUDE.md`、仓库根 CLAUDE.md / AGENTS.md，
以及被改文件祖先目录里的 CLAUDE.md / CLAUDE.local.md / AGENTS.md（目录级规则只管该目录以下）。
逐条对照 diff。**只在能同时引用规则原文与违反行时才算发现**——不报风格偏好，不报「精神上不符」。
发现里写明规则文件路径并引用规则。没有适用规则文档就这个角度为空。

## 输出与取舍

- 去重：指向同一行或同一机制的发现只留代价说得最具体的那条。
- 跳过：修复会改变预期行为的；需要改到 diff 之外很远的；你判断是误报的。跳过要在报告里列出来，不要争论。
- 顺序：约定违反 > 复用 > 高度 > 化简 > 效率，产出上限时按这个序裁。
