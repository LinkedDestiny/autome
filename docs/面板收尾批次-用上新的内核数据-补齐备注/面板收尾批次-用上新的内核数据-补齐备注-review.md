## 可要求再评审的问题

### R1-P01 · 按任务过滤后的分页无法追到全账本水位

- **类别 / 追溯：** 关键事实错误、内部逻辑矛盾；任务 **A-3**、任务 §7 **A-Q3**；设计 **A-3，第 120–124 行**及 **M-01 验收契约**的「分页到 latest_seq、页不前进报错」。
- **证据：** `crates/automed/src/dispatch.rs:3316–3333` 按 `subject` 调 `events_by_subject`，但 `latest_seq` 仍取全账本最大值；`crates/automed/src/store.rs:990–1017` 的 SQL 明确先过滤 subject。旧 `apps/web/server/task-events.ts:13–27` 的水位终止条件适用于全账本扫描，不能原样搬到筛选后的流。
- **具体反例：** T-1 最后事件为 seq=10，T-2 后来产生 seq=20。读 T-1 返回截至 10 的事件和 `latest_seq=20`；下一页正常为空，水位仍为 20。按设计必须报「分页未前进」，正常历史任务的时间线因此无法完整返回。没有事件的 subject 也会触发同样错误。
- **根因与同类检查范围：** 混淆全账本水位与筛选结果的结束条件。已核对 A-3 服务替换、旧事件索引、内核查询和 M-01 契约；C 复用这条历史读取路径，也受影响。空任务、其它任务有更新、恰好整页、全是待过滤噪声的页须按同一规则处理。
- **建议修改落点：** A-3 与 M-01 同步改为按原始 subject 页的短页 / 空页结束，游标在过滤噪声前推进；保留对非空却没有有效前进的异常回包检查，不把正常空页视为错误。无需改内核。

### R1-P02 · 会话滑动窗口会移除用户已展开的日志

- **类别 / 追溯：** 内部逻辑矛盾、违反任务目标；任务 **C-2、验-3、§6 约束 10**；设计 **C-Q1，第 232–235 行**与 **C-Q3，第 245–249 行**。
- **证据：** 方案每次只返回最近 20 个会话，却仅用条目 key 稳定解释为何日志不会折叠。现有 `apps/web/app/components/task-timeline.tsx:15–20` 只渲染返回的条目；`session-log.tsx:45–59` 把展开、日志、滚动状态保存在组件内部，卸载会关闭 controller 并清除滚动引用。
- **具体反例：** 页面缺省展示会话 41–60，用户展开会话 41 的日志并滚到中间；会话 61 到达并重验后，窗口变成 42–61，条目 41 直接从渲染树消失。key 没变也不能保住已被删除的组件；随后点「显示更早」会重新挂载它。违反「新增条目时日志不折叠、滚动位置不丢」。
- **根因与同类检查范围：** 把节点身份稳定等同于节点仍被保留。检查范围为 C-Q1 窗口、C-Q3、M-05 及现有日志组件；`timeline=all` 没有此淘汰问题，不能据此证明缺省窗口正确。窗口边界的非会话条目与滚动锚点也需一起处理。
- **建议修改落点：** 首次响应可以限 20 条；打开页面后固定已加载窗口起点并追加新条目，或明确保留正在展开的会话及其滚动锚点。同步修正 C-Q3 的保证理由与 M-05 的行为场景。

### R1-P03 · Onboarding 已知事件覆盖缺口被直接删除兜底

- **类别 / 追溯：** 违反任务目标；任务 **A-5、§7 A-Q6**明确要求「覆盖不了的如实保留并写明」；设计 **A-5，第 140–155 行**、**R-5，第 493–494 行**及 **M-02 的完全删除检查**。
- **证据：** 设计承认旧内核只读、无人收割时 `onboarding_session` 停在运行中，却规定不保留轮询、不恢复读取。现有 `apps/web/server/onboarding-watch.ts:12–21,23–29` 能直接读退出标记或识别进程消失；`apps/web/app/components/settings-data.ts:17–18` 在页面加载时调用该状态读取。
- **具体反例：** 一个 Onboarding 会话已启动，面板随后因内核比账本旧进入只读状态，且没有其它驱动收割；会话退出并留下 `.exit`。旧版重新加载设置页能显示结束，新方案重新加载仍只能得到账本中的运行中状态。这里只主张可证的页面加载退化：旧版 `onTick` 也受 ticker 条件约束，不能据此声称旧版在只读状态下必有实时推送。
- **根因与同类检查范围：** 用「整个 Loop 不推进、已有只读提示」替代了任务对删除旧能力的明确前提。已检查状态读取、watcher 删除、M-02 文件 / grep 检查与 R-5；普通可收割场景可以继续使用账本事件。
- **建议修改落点：** 对事件不能覆盖的状态保留有限兜底，并在 A-5 写清启用条件；M-02 应验证正常路径已迁移以及保留理由，不再要求无条件删除全部旧能力。若选择取消该能力，必须由裁决处理与 A-5 的冲突，不能只列风险。

### R1-P04 · 存活的 stdio 内核不等于正在循环驱动

- **类别 / 追溯：** 关键事实错误、违反任务目标；任务 **E-3、验-5**的「是否有另一个驱动在推进」确定答案；设计 **E-3，第 304–315 行**。
- **证据：** `crates/automed/src/entry.rs:213–244` 的 `serve_stdio` 阻塞读取请求，收到请求后才 `handle_command`，自身没有周期 tick。设计却让所有 `autome core` / `automed` 的 stdio 服务在整个生命周期登记为「正在循环驱动的进程」，并据此输出「另一个驱动在推进」。
- **具体反例：** 启动另一个 `autome core`，保持 stdin 打开但从不发送 `scheduler.tick`。它会一直持有登记锁，status 因而给出正在推进的确定答案，实际上没有调度循环。设计 **F.4，第 367–368 行**恰好使用了这种阻塞 stdio 服务作为残留进程夹具，所以不是不可达的场景。
- **根因与同类检查范围：** 将 RPC 服务进程存在等同于驱动循环存在。影响所有 stdio 服务登记、`driver.list`、`/api/instance`、status 与环境页；`autome run` 的实际循环不是这个反例。
- **建议修改落点：** E-3 应把驱动身份绑定到真正的驱动生命周期，或区分「核心在线 / 已登记」与「正在驱动」；不能只凭 stdio 进程存活作后一种断言。同步调整 M-08 的语义与可观察结果。

### R1-P05 · TERM 到 KILL 之间只检查 PID，可能杀到复用该 PID 的其它进程

- **类别 / 追溯：** 违反任务目标；任务 **F-2、验-6**的主检出、其它任务与用户进程不碰；设计 **F.1，第 327–330 行**与 **F.2，第 351–354 行**。
- **具体反例：** 扫描时 PID P 属于待删 worktree；发送 TERM 后它退出。等待窗口中系统把 P 分配给主检出或其它任务的新进程。方案只用 `kill(P, 0)` 与非僵尸判断存活，会把这个新进程视为原残留，随后发送 KILL。无需新进程的 exe/cwd 命中本任务，就会被误杀。
- **证据 / 根因：** F.1 已取得进程起始时间，F.2 却没有把它绑定到候选身份，而是明确只用 PID 判断。等待最长 3 秒再升级信号，使一次扫描得出的身份和后续信号目标之间存在变化窗口。
- **同类检查范围：** 扫描到首次 TERM、TERM 等待到 KILL、最终 survivors 判断及事件中 PID / 命令归属，都必须识别是否还是同一个进程；不能只补最终 KILL 那一处。
- **建议修改落点：** F.1/F.2 明确保存并复核候选身份，在发送各次信号前复核身份与必要的路径归属；身份改变或无法确认时停止对该 PID 的处理。M-09 使用替身进程表验证「旧进程退出、PID 被其它任务进程复用」不发送后续信号。不能把一次 `kill(pid, 0)` 成功当成原候选仍存活的证据。

### R1-P06 · 进程比目录早启动，不能证明它后来没进入 worktree

- **类别 / 追溯：** 关键事实错误、违反任务目标；任务 **F-2、验-6**的「判据取不到时不杀并记警告」；设计 **F.1，第 334–336 行**和 **M-09 预期**的「早于创建时不告警」。
- **具体反例：** 先启动长寿命 shell，之后才创建 worktree；shell 可以在同一 PID 下 `exec` worktree 内的程序，或 `chdir` 进入新建目录。进程出生时间没有因此变成目录创建之后。若此后可执行文件被删除，路径查询返回未知而 cwd 又在外部，设计会用出生时间静默排除；但它无法证明该进程与任务无关。
- **证据 / 根因：** 设计实测表第 45 行已记录「可执行文件被删除时 `proc_pidpath` 返回 `ENOENT`」。F.1 进一步断言早启动进程的 exe/cwd「不可能」在新目录内，是把进程出生时间误当作它访问目录或切换程序的时间；M-09 又将这条错误推断固化为通过条件。
- **同类检查范围：** exe 与 cwd 两种判据的未知分支、路径删除后的查询、F.1 年龄过滤及 M-09 对应预期。它与 R1-P05 的 PID 复用是不同根因，需分别处理。
- **建议修改落点：** 删除年龄带来的“不相关”推断。路径无法确定且没有其它有效归属证据时不杀，并按 F-2 记录警告；可合并或去重警告，不能以出生时间免除告警。

## 非阻塞建议

以下均不独立触发复审，由裁决轮决定是否进入 Backlog。

- **N-01 · M-04 负向对照与用例路径不一致。** B-2 的浏览器用例操作「移到最前」即 `top`，契约却声称交换 action 的 `before/after` 会使它失败；该变异不影响 top 路径。让变异与实际操作对应即可，不据此判验收不明确。
- **N-02 · D-1 的序号上界不能证明收到了目标事件。** `data-live-seq >= targetSeq` 在漏掉目标事件、只收到更大的序号时仍成立；另把 drain 分发全关会先破坏离线前的准备事件，未必证明恢复路径被守住。可在浏览器观察目标事件本身，并在完成前置步骤后注入恢复路径变异。这是验收判别力建议，不是当前产品缺陷。
- **N-03 · E-3 登记发布与陈旧清理需协调。** 若实现为先创建 `<pid>.json` 再持锁，查询可能在两者之间取得共享锁并删除文件，登记方随后只锁住已删除的 inode。设计尚未钉死发布顺序，可在实现时用持锁后原子发布等方式解决；不把未展开常规并发细节当成方案已经失效。
- **N-04 · C 的估算体积与真实 SSR 分开表述。** 数据 JSON 加静态标记不是实际响应字节数；设计 R-2 已承认差异。建议实现时用同一临时夹具补充实际 SSR 测量，避免将估算通过写成真实响应已达标；本轮未证明未来实现实际超标，不单独阻塞。
