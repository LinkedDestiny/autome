### 面板现状（与任务文件 §8 一致处不重复）

- 任务详情 loader（`task-detail-data.ts`）返回整份 `task.get`、整份 `config.get`、该任务全部事件、合并段的 `task.changes` 与
  当前文档的节点树；时间线、阶段条在浏览器端用原始事件计算。
- 时间线事件来自 `server/task-events.ts`：从 0 起拉全账本事件、按 subject 分组常驻内存。
- 项目页 `loadBoard` 任一卡片 `task.get` 失败整页报错；「待开始」列按编号倒序；页面 action 只认 `start` / `dismiss`。
- Onboarding 状态来自 `server/onboarding-watch.ts` 读盘与每 tick 轮询，结束时推 `onboarding.ended`。

### A 面板用上 T-95 的内核数据

**A-1 文档（A-Q1）。**

- 首标签合并：内核清单里 `label === '任务卡'` 的条目不再单列，并入固定首标签「任务卡」；首标签内容仍取 `task.get.brief`
  （与卡文件同源，不用读盘），`brief` 为空时退回 `request`。清单为空时首标签照样存在。
- 删除两句过时提示（「任务已完成，工作目录已清理，文档暂不可读。」「内核尚未提供 Bug 文档…」）。新的空清单提示只剩一种：
  `task.state.state === 'cancelled'` 且清单为空 →「任务已取消，文档没有合并到默认分支。」；其它状态清单为空不显示提示。
- `source === 'default_branch'` 时在文档区标题旁显示一个灰色标注「来自默认分支」；`worktree` 不标。
- 默认分支来源的文档读盘失败（主检出里文件被删）时沿用 `task-docs.ts` 现有报错文案；主检出里有未提交改动时显示的是磁盘内容，
  标注写成「来自默认分支（主检出）」，不另做比对（内核给的就是磁盘路径；进 Backlog BL-09 由内核给 blob 内容）。
- 里程碑终态：阶段条与头部已读 `status_block`，合并后内核从默认分支解析，无需改动，只加真实内核用例守住。
- 真实内核用例（验-1）：新 kernel 组文件 `test/task-detail-real.test.ts`，用 `w7-flow.sh` 造数据（与 `task-ops-real` 同法，显式
  `AUTOME_BIN` / `AUTOMED_BIN`）。用例 1：Bug 任务 `loadTaskDetail` 的标签含「Bug 文档」、能读出正文；用例 2：`merge` 两个任务并
  `run --until-idle` 之后，需求任务的文档标签全在、`source` 标注出现、设计文档正文可读、里程碑 2/2 已完成、改动标签显示已合并。

**A-2 改动类型（A-Q2）。**

- `TaskChanges` 类型补 `status`、`from`、`deleted_count`、`merged`、`repos[].files/deleted_count`。
- 每行前加类型标签：新增 / 删除 / 修改 / 改名；改名显示为 `from → path`。
- 「删除文件数异常多」只用内核的 `deleted_count`：`deleted_count >= 5 || (deleted_count >= 2 && deleted_count * 2 >= files.length)`
  （沿用旧阈值，换数据源）；删除 `suspected` 的近似计算。
- 已合并任务也取改动：`loadTaskDetail` 在合并段**或** `state === 'done'` 时请求 `task.changes`；`merged: true` 时标题下显示
  「已合并到默认分支」，不显示合并进度条以外的操作。
- 工作区项目：`repos.length > 1` 时按仓库分组列文件，每组显示各自删除数；提示用顶层 `deleted_count`。

**A-3 按任务读事件与结束方式（A-Q3、A-Q4）。**

- 删除 `server/task-events.ts` 与它的测试；新文件 `server/task-history.ts`，导出
  `readTaskEvents(call, taskId)`：从 `after_seq: 0` 起以 `{subject: taskId, limit: 1000}` 分页读，**结束条件是原始页**
  （过滤噪声之前）的 `events.length < limit`（含空页）：带 `subject` 时回包的 `latest_seq` 仍是**全账本**最大序号
  （`dispatch.rs::events_since`，实测源码），它与「该任务的事件读完了没有」无关，所以不拿它当终止或前进判据，也不回退检查
  `latest_seq < cursor`。游标取原始页最后一条的 `seq`（噪声被过滤前就前进）；页非空但最后一条 `seq` 不大于游标时报错
  「任务事件暂不可用：账本分页未前进」（异常回包，不是正常空页）。过滤 `task.head / integrity_warning / task.lessons`，保留最新
  5000 条并给 `truncated`。空任务（没有事件）、其它任务比本任务新（全账本水位更大）、恰好整页后接空页、整页都是噪声，都按此规则
  正常结束。每次加载都重读，
  不缓存、不增量（单任务事件量为几百到两千条，两页内）。`main.ts` 以 `services.taskEvents = { forTask: id => readTaskEvents(core.call, id) }`
  注入，`load-context.ts` 的类型与 `loadTaskDetail` 的调用形状不变——这样 C 只改「算在哪、返回多少」，不推翻 A 的测试。
- 浏览器仍拿不到 `events.since`（约束 8）：调用走服务端的 `core.call`，不经 `gateway.read`。
- 时间线结束方式：会话条目的结束时刻与方式优先取该会话的 `session.ended` 事件（`end`、`exit_code`、事件 `at`），没有事件
  （T-95 之前的会话）时退回会话行：`lifecycle.state` 为 `killed` → 被停止、`timed_out` 为真 → 超时、`exited` 且退出码非 0 或
  `vanished` → 崩溃、其余 → 正常结束。二者不一致时以事件为准（事件只写一次，写在收割时刻）。文案：`exited`「正常结束」、
  `stopped`「被停止」、`timed_out`「超时」、`crashed`「崩溃（退出码 N）」或 `exit_code` 为空时「崩溃（进程消失）」。结束方式
  进条目的 `details`，摘要里原有的「已被停止」改由它给出。
- 真实内核用例（验-1，`task-detail-real` 用例 3）：一条需求的设计轮正常退出（`exited`）、一条步骤 `exit 3` 的任务（`crashed`、
  退出码 3）、一条持有会话后 `autome stop`（`stopped`），断言时间线条目文案。`timed_out` 在真实内核下要等至少 1 分钟
  （`session_minutes` 最小 1），只在 `task-timeline.test.ts` 用与真实载荷同形的事件覆盖，理由写在测试注释里。

### C 任务详情页瘦身

**C-Q1 量什么、砍哪里。** 量「首次响应」＝ SSR 文档。与项目页 `board-payload.test.ts` 同口径：路由 loader 数据的
`JSON.stringify` 字节数 + 壳层 `loadShell` 数据字节数 + `renderToStaticMarkup` 的 HTML 字节数之和 ≤ 150 KB；重验请求返回同一
loader 的数据，所以「数据部分 ≤ 150 KB」同时约束重验。做法：

- loader 不再返回原始 `task.get`、`config.get` 与事件，改为在服务端算好视图：头部、阶段条、提示、操作所需字段（`task` 的
  标识与状态、`status_block` 的里程碑、`gate`、`retry`、`cost`、`notes`、`after`、`blocked_by`、`queue_position`、未消费的
  `decisions`）；配置只留 `roles` 启用表与 `bug.fix_rounds`；`stageBarView` 与 `timelineEntries` 在服务端执行，返回结果；依赖只读原因也使用完整历史在服务端计算，避免裁掉旧实现会话后错误开放修改入口。
- 时间线窗口：**首次响应**（URL 没有 `from` 与 `timeline`）只返回最近 20 个会话的条目，以及最早那个会话开始之后的非会话条目，
  并返回 `window.from`（窗口里最早那个会话的 id）与 `window.earlier`（更早会话数）。**窗口起点打开后即钉住**：时间线组件
  挂载后若 URL 既没有 `from` 也没有 `timeline=all`，用回调写法 `setSearchParams(prev => withParams(prev, {from: window.from}), {replace: true, preventScrollReset: true})`
  把它写进 URL（对象写法会整体替换查询串，丢掉 `tab` / `doc`；见下一条「查询参数互相独立」）；
  此后的重验（事件触发、刷新）都带 `from=<会话 id>`，loader 返回「从该会话起的全部会话」，窗口只向后增长（新会话追加），
  **不会把已展开日志所在的会话挤出渲染树**。`from` 不是该任务的会话 id 时回退到缺省窗口。更早的折叠成一行「显示更早的 N 个
  会话」，链接到当前查询串加 `timeline=all` 且删掉 `from`（URL 状态，刷新保持；`preventScrollReset`），`timeline=all` 时不设上限（用户主动要的）。
  窗口起点钉住后长时间运行的任务数据会随新会话增长（每轮一个会话，量级与改动前相同、仍远小于 60 会话全量）；M-05 另测「钉住后又
  到 5 个新会话」的数据仍 ≤ 150 KB。
- **查询参数互相独立（D2-P01）。** `tab`、`doc`（既有）与 `from`、`timeline`（新增）共用一个查询串，任何一个导航只能改自己负责的键。
  新增纯函数 `withParams(search, {set, remove})`（新文件 `app/components/task-url.ts`）：从当前 `URLSearchParams` 的**副本**出发，只设置 /
  删除指定键，返回新查询串；主标签链接（`tasks.$id.tsx` 的 `tabLink`，本就复制参数）、文档链接（任务卡 `?`、正文、证据，现在由
  `docsView` 产出的固定 `?doc=…` 再拼 `tab=docs`，会丢 `from` / `timeline`）、「显示更早」链接、窗口钉住的 `setSearchParams` 全部改走它：
  文档链接只设 `doc`（任务卡则删 `doc`）与 `tab=docs`，保留 `from` / `timeline`；「显示更早」只设 `timeline=all`、删 `from`，保留 `tab` / `doc`；
  钉住只设 `from`，保留 `tab` / `doc`。`docsView` 的 `href` 改为只给文档名（`name`），链接由组件用 `withParams` 现拼，不再产出带 `?` 的字符串。
  同类检查范围：`task-docs.tsx`（任务卡、正文、证据三类链接）、`task-changes-model.ts` 与 `tasks.$id.tsx` 的标签链接、时间线的「显示更早」链接、钉住 effect，
  共 4 处出口，实现轮用 `grep -n "?doc=\|tab=\|timeline=\|setSearchParams" apps/web/app` 核对没有第五处硬编码查询串。
- 会话对象只带时间线与 `SessionLog` 用到的字段（`id`、`label`、`round`、`kind`、`runtime`、`model`、`started_at`、`ended_at`、
  `running`、`lifecycle.state`、`metrics.cost_usd`），不带 `log_path` 等绝对路径。
- 文档：清单只带 `{name, label, source}`，读文档时服务端用新取的 `task.get` 找 `absolute`（`pickDocument` 不变）；只有文档标签
  被选中时才读正文与解析。改动：只有「改动与合并」标签被选中时才调 `task.changes`。缺省选中哪个标签的规则不变。
- 不新增 HTTP 接口：「按需加载」就是 URL 参数（`tab`、`timeline`、`from`）驱动同一 loader，所以不涉及新的 Host / Origin 面（约束 8）。

- 记什么：锁按操作取放，「此刻的持有者」对状态查询没有意义；记的是**正在循环驱动的进程的登记**，且「进程存活」与「正在推进」分开
  表达（`serve_stdio` 阻塞读请求、自身没有周期 tick，`entry.rs`，所以只因它活着就断言「在推进」是错的）。`driver_lock.rs` 新增
  `register(db_path, command, interval_secs) -> Registration`、`Registration::touch()` 与 `drivers(db_path) -> Vec<DriverInfo>`：
  登记文件在锁旁边的目录 `<账本>.drivers/<pid>.json`，内容 `{pid, command, started_at, interval_secs}`（`interval_secs` 可为空）；
  登记进程在整个登记期间对自己的登记文件持有 `flock(LOCK_EX)`（`O_CLOEXEC`，会话子进程 exec 后不继承）。**`last_tick_at` 取该文件的
  mtime**：每完成一次 tick 调 `touch()`（`futimens`，不重写内容，读者不会读到半截 JSON）。发布顺序：先在目录里以隐藏名写好内容并
  持锁，再 `rename` 成 `<pid>.json`（同一 inode，flock 随 inode 保留）；查询跳过点开头的文件，所以不会在「建好文件、尚未持锁」的缝隙里
  把它当陈旧删掉。查询时逐个文件 `flock(LOCK_SH|LOCK_NB)`：拿不到＝持有者活着；拿得到＝陈旧，删除。进程崩溃时内核释放 flock，所以不怕
  pid 复用、不需要比对起始时间。不进账本，schema 不变。`DriverInfo` 另带 `last_tick_at`（mtime）与 `driving`：
  `driving = now − last_tick_at ≤ max(30 s, 3 × interval_secs)`（`interval_secs` 为空按 0）。

### F 清理任务时结束它留下的进程

**F.1 判据怎样取得（F-Q1）。** 新模块 `crates/automed/src/residue.rs`，进程表抽象为 trait（真实实现 + 测试替身）：

- 枚举：`proc_listallpids`。逐个取 `PROC_PIDTBSDINFO`（uid、**起始时间 `pbi_start_tvsec` + `pbi_start_tvusec`**、状态、控制终端
  `e_tdev`）：取不到
  （`EPERM`，别的用户）或 uid ≠ 本进程 uid → 跳过，不告警（不是本用户的进程，也发不了信号；任务卡「用户自己的进程不碰」由下面的
  路径判据保证）。`ESRCH` 或僵尸 → 跳过。本进程 pid 跳过。命中的候选记 **身份 `(pid, 起始时间)`**，之后对它的每次处理都按这个身份
  复核（见 F.2）。
- 路径：可执行文件 `proc_pidpath`，工作目录 `proc_pidinfo(PROC_PIDVNODEPATHINFO).pvi_cdir`。二者任一位于任一「根」之内即命中。
  根＝任务布局里每个 `slot.worktree` 与 `layout.cwd`，在删除之前先 `canonicalize`（`/tmp` → `/private/tmp`），同时保留原写法；
  比较用 `Path::starts_with`（按路径组件，`feat` 不会命中 `feat-2`），根本身也算命中。主检出（`<主检出>` 不以
  `<主检出>/.worktree/<slug>` 开头）与其它任务的 worktree 天然不命中。
- **有控制终端的不杀（用户驳回意见第 1 条）**：路径判据命中、但该进程 `e_tdev != NODEV`（`u32::MAX`，即有控制终端；取法见实测表）
  时，不发任何信号，记入 `task.processes_unchecked`，`kind: "tty"`、`reason: "有控制终端，可能是用户自己打开的"`，附终端名
  （`devname`，如 `ttys002`；取不到写设备号）。理由：用户在任务 worktree 里开的终端、在其中启动的 `claude` / `codex`、编辑器集成终端
  里的 shell 都满足路径判据，清理时被结束是误伤；任务卡写了「用户自己的进程一律不碰」。只看 `e_tdev`，不看 `PROC_FLAG_CONTROLT`
  （实测二者一致，取一个即可）。泄漏的后台服务（T-96 的 `autome-web serve` 与它的 `autome core` 子进程）在 launchd 驱动下没有控制
  终端，仍会被结束。代价与实测见 F.6。
- 取不到：本用户进程的 `proc_pidpath` 返回 `ESRCH` 以外的错误（实测是可执行文件被删时的 `ENOENT`）、且另一项路径（cwd）没有命中
  时，记为「无法判断」，**不杀**，进 `task.processes_unchecked`（F.3；`kind: "unknown"`，同一次清理里按 pid 去重，`reason` 写明是哪一项
  取不到与错误）。
  **不用进程起始时间早于 worktree 创建时间来豁免**：进程出生早于目录，不代表它之后没有 `exec` 进来或 `chdir` 进来（实测表已记可执行文件
  被删时路径查询返回 `ENOENT`），所以早启动的进程路径不明同样告警。代价：本机那个可执行文件已被替换的长期应用进程会让每次清理事件里
  多一条「无法判断」警告——它只进账本，不影响清理，接受（Backlog BL-12 可再收窄）。
- 非 macOS：`cfg(not(target_os = "macos"))` 的实现直接返回「无法判断：本平台不支持」，清理不杀进程并记一次警告（只为能编译；
  产品只支持 macOS）。
- T-96 的那个案例：`autome core` 子进程的可执行文件是 worktree 里的 `target/debug/autome` → 命中、会被结束；它的 Node 父进程
  `autome-web … serve` 的可执行文件是系统 `node`，工作目录取决于启动处——在 worktree 里则命中，否则接不住。按任务卡只认路径判据，
  不按进程名或命令行匹配；接不住的部分由 M-11（BL-04，G.2：面板服务在内核二进制消失后自行退出）补上。

**F.2 挂在哪里（F-Q2）。** 只挂任务卡说的两种清理：

- 合并后：`Node::Cleanup` 内核步骤在调用 `cleanup(layout)` 之前执行 `residue::sweep`；
- 取消：`discard_checkout` 开头（文档归档之后、`worktree_remove` 之前）执行；`task.convert` 走同一函数，属于「取消原任务」，一并覆盖。

不挂：定位轮结束时删掉未用到的成员检出（没有会话在里面跑过）、合并验证用的临时检出 `verify_dir`（内核自己的临时目录，门禁进程由
`gate` 模块管）。会话进行中不做（F-3）：两处调用点都在会话已结束（合并）或已被 `stop_running_session` 停掉（取消）之后。

信号：命中的进程先全部 `SIGTERM`，每 50 ms 检查一次，最多 3 s；仍在的 `SIGKILL`，再等最多 1 s。**每一次发信号之前和每一次「还在不在」
判断，都用候选的身份 `(pid, 起始时间)` 复核**：重新取该 pid 的 `PROC_PIDTBSDINFO`，起始时间与扫描时记下的不同（pid 已被别的进程复用）、
`ESRCH` 或变成僵尸 → 视为原候选已退出，**不再对该 pid 发任何信号**，也不记入 `survivors`；起始时间相同还要再确认 exe / cwd 仍有一项
位于根内（进程 `chdir` / `exec` 离开后不再是候选，同样不发）且仍没有控制终端（复核时有了 → 不发，按 F.1 记 `kind: "tty"`）；复核时
路径查询出错且无法确认 → 不发信号，记入 `task.processes_unchecked`（`kind: "unknown"`，`reason: "信号前无法复核身份"`）。`kill(pid, 0)` 成功不当作原候选仍存活的证据。
最坏约 4 s，只在确有残留时发生；它在持有驱动锁的 tick 里同步执行，会让同一 tick 的后续工作晚几秒，可接受（清理本来就含同步的
`git worktree remove`）。仍杀不掉的（如 `EPERM`）记进事件的 `survivors`，**清理照常继续**——残留进程不该让合并后的任务卡在失败。

**F.3 事件（F-Q3）。** subject 是任务 id：

- `task.processes_stopped`：`{checkouts: [根路径…], processes: [{pid, command, matched: "exe"|"cwd", signal: "TERM"|"KILL"}],
  survivors: [{pid, command, error}]}`；`processes` 与 `survivors` 都空时不写。
- `task.processes_unchecked`：`{processes: [{pid, command, kind: "unknown"|"tty", reason, tty?}]}`，有「无法判断」或「有控制终端
  未结束」时写（`tty` 只在 `kind: "tty"` 时有）。面板按 `kind` 区分，不解析 `reason` 文本。
- `command` 是可执行文件路径加参数，参数取自 `sysctl(KERN_PROCARGS2)`，整体截到 120 个字符；取不到参数时只写可执行文件路径。
  账本只在本机，截断降低把长参数（可能含密钥）整段写入的风险；不做内容识别。
- 面板时间线（属 `apps/web/`，在 F 同里程碑做）：两类事件进 `light()`——「清理时结束了 N 个残留进程：pid 命令 …」；

**F.6 「有控制终端不杀」的代价（用户驳回意见第 2 条）。**

- 会话若在带终端的环境里运行，它泄漏的、继承了终端的子进程只会被警告（`kind: "tty"`）、不会被结束。会话由内核以 `process_group(0)`
  无窗口启动（`launcher.rs::run_in_terminal`，现在只有 headless 一种），不调 `setsid`；实测在有终端的会话里 `setpgid` 之后子进程仍带
  该终端。所以：用户在终端里前台跑 `autome run`（或在终端标签页里手动起一轮 `claude`）时，这些会话和它们起的服务都带终端，清理时
  只进 `processes_unchecked`，要用户自己结束——时间线那句「有控制终端…未结束」就是提示。本设计不改会话的启动方式（给会话加 `setsid`
  会改变 Ctrl-C 与停止语义，超出 F 的范围）。
- 本机现状（实测，见实测表）：`com.autome.loop` 由 launchd 启动，驱动进程与它起的会话祖先链全是 `NODEV`，本设计轮会话自身也是 ——
  launchd 驱动下会话及其子进程**没有**控制终端，这条规则不影响 T-96 那类泄漏的清理。
- 另一面：iTerm 里交互运行的 `claude` 自身带终端（不会被结束），但它的 Bash 工具起的 shell 实测是 `NODEV`；用户让这样的 `claude` 在
  任务 worktree 里起的后台服务没有终端，路径命中时仍会被结束。规则保护的是「终端里的 shell 及在 shell 里直接运行的程序」，不覆盖
  这类工具子进程——它们与会话泄漏的服务从进程表上无法区分，按任务卡只认路径判据处理。编辑器集成终端按同一机制（伪终端）判定，未单独
  实测，列入人工验收 H-06。

## 风险与回退

- **R-1 浏览器时间预算。** 新增 7 条浏览器用例（含 M-10 的 BL-01）约 +175 s；`globalTimeout` 调到 360 s 后仍远低于 `ci.yml` 的 15 分钟与宿主 30 分钟。
  若审计实测整步超过 300 s，在当轮把最慢的 B 用例改走 live 实例或合并步骤，不再调上限。
- **R-2 150 KB 的口径差。** 夹具口径（数据 JSON + 静态标记）与浏览器实际收到的 turbo-stream 文档有几 KB 差异；窗口 20 个会话
  留有余量，若真实数据（人工清单 H-02）超标，下调窗口到 12，不改口径。M-13 用生产构建量真实响应字节，把这一差距变成可核对的数。
- **R-3 进程表在沙箱里。** 实现轮沙箱可能连 `proc_listallpids` 也不许；`residue` 的路径比较、选择、信号顺序全部在替身进程表上
  可测，真实进程表用例交审计轮。若审计环境也读不到，按约束 7 记录由宿主门禁执行。
- **R-4 清理拖慢 tick。** 只在确有残留时最多约 4 s；若某个任务 worktree 里进程很多（数百），TERM 是一次性批量发出、等待共用一个窗口，
  不按进程累加。
- **R-5 只读内核时 Onboarding 不收割。** 面板内核「比账本旧」不推进时 Onboarding 状态停在账本里的运行中。已保留的兜底：页面加载 /
  重验时读一次退出标记（A-5），所以刷新页面能看到结束；没有实时推送（旧版的 `onTick` 本来也受 ticker 条件约束，不据此声称退化）。
  回退：删掉 `onboarding-disk.ts` 与设置页的那一次读盘即可，不影响事件路径。
- **R-6 驱动登记目录残留。** 进程崩溃留下的登记文件在下一次查询时因能拿到 flock 被删除（发布走「隐藏名写好 → 持锁 → rename」，查询不会误删刚创建的）；目录本身在 `AUTOME_HOME/state/` 下，
  不影响账本。
- **R-7 有终端的泄漏只告警。** 见 F.6：终端里前台运行的驱动所起会话的泄漏进程不会被结束；本机 launchd 驱动不受影响。回退即删去
  F.1 的终端判断。
- **R-8 面板误退出。** 内核二进制短暂缺失（安装时先删后拷）可能让面板退出；要求连续两次（相隔 3 s）不存在才退出。仍误退出时
  launchd 不会拉起（退出码 0），用户 `autome web start` 即可；回退即在 `runFromEnv` 不传 `onKernelBinaryGone`。
- **回退。** 每个里程碑只动自己列出的文件；E-3 与 F 的内核改动不改 schema、不改协议，回退即还原对应提交。
