## 方案

### 总体结构

一个路由 `tasks/:id`（整页重写 `app/routes/tasks.$id.tsx`，不新增路由文件）：

- `loader` → `loadTaskDetail(services, id, url)`（`app/components/task-detail-data.ts`）一次取齐本页数据；
- `action` → `handleTaskAction(formData, id, services)`（`app/components/task-action.ts`）把表单映射成一次 `gateway.write`；
- `shouldRevalidate` 按本任务的事件重验；
- 视图由纯函数模型生成（`task-*-model.ts`），TSX 只做组合。中文文案放 `app/lib/labels.ts` 或 `.ts` 模型，TSX 不写状态、列、
  阶段的中文字面量（`labels.test.ts` 第 7 条）。

版面（1512×944 下页面本身不滚动）：第一行页头；第二行阶段条（含里程碑 / 修复轮次）；第三行「失败与等待」提示与操作区
（一张卡片，表单在卡片内展开、限高内部滚动）；其下主体两栏、`min-height: 0`：左栏执行时间线（内部滚动），右栏标签卡
「文档 / 改动与合并 / 待你决定」（标签内容内部滚动）。合并相关的标签在合并段（见下）默认选中，其余时候默认「文档」。
标签选中用查询参数 `?tab=`，文档选中用 `?doc=`（见「文档标签页」），都是 GET 链接，不需要客户端状态。

### 服务端取数与接线（M-01）

**任务事件：服务端增量索引（回答待定问题 1）。** 新增 `server/task-events.ts`：

```ts
createTaskEvents({ call }): { forTask(taskId: string): Promise<{ events: TaskEvent[]; truncated: boolean }>; close(): void }
type TaskEvent = { seq: number; kind: string; subject: string; payload: Record<string, unknown>; at: string };
```

- 只走服务端的 `core.call('events.since', …)`，**不经 read-gate**——与 read-gate 对 `events.since` 的注释（账本拉取留给服务端）
  一致，浏览器仍拿不到 `events.since`，read-gate 不改。
- 首次调用从 `after_seq: 0` 起按 `limit: 1000` 翻页到 `latest_seq`，按 `subject` 分组存进内存；之后每次调用只从游标往后补
  （常态 0–1 页）。并发调用共用同一次补齐（一个进行中的 Promise）。`latest_seq` 小于游标（账本被换）时清空重建。
- 丢弃对页面无用且量大的三种：`task.head`、`integrity_warning`、`task.lessons`；每个 subject 最多留最近 5000 条，超出时
  `truncated: true`，时间线顶部注明「更早的内核事件已省略」。按本机 7766 条估算常驻内存在几 MB 量级。
- 失败时 reject 原因文字，游标不前进，下一次重试。
- 接线：`server/main.ts` 创建 `taskEvents = createTaskEvents({ call: (m, p) => core.call(m, p) })`，经 `createHttpServer`
  传给 `createLoadContext`；`app/load-context.ts` 的 `WebServices` 新增可选字段 `taskEvents?: TaskEventSource | null`、
  `taskDocs?: TaskDocReader | null`（类型用 `Pick`，与 `gateway` 同一写法；键仍是 `Symbol.for`，三份实例共享不受影响）。
  `server/http.ts` 只多透传这两项。`close()` 在 `startServer().close()` 里调用。

**文档读取（回答待定问题 7）。** 新增 `server/task-docs.ts`：

```ts
pickDocument(documents, name): { ok: true; entry } | { ok: false; message }   // 纯函数，可在 app 侧复用
createTaskDocs(): { read(absolute: string, maxBytes: number): Promise<{ text; size; truncated } | { error }> }
```

- 浏览器只经查询参数 `?doc=<name>` 传文档名；loader 先用 `looksLikeAPath`（write-gate 已导出，含 `/`、`\`、`..`、`~` 开头、NUL）
  判定，路径形状一律返回「已拒绝：文档名不能是路径」且不读文件；再在**这一次请求内** `task.get` 回包的 `documents` 里按
  `name` **全等**查找，找不到返回「这个任务没有名为 … 的文档」；同名多条时取内核顺序的第一条（固定名在证据之前）。
- `read` 只接收查出来的那条的 `absolute`，不拼接、不规范化；读前 `lstat` 必须是普通文件。读取上限 **200 KB**
  （`DOC_LIMIT_BYTES = 200 * 1024`，设计轮取值：大于 W8 之后协议把证据移出设计文档后的常见大小，又远小于历史上 335KB 的失控文档），
  超出时在最后一个换行处截断，返回 `truncated: true` 与全文 `size`，页面注明「文档共 X KB，只显示前 200 KB」。
- 文件在两次 `task.get` 之间消失（`ENOENT`）→「文档已不在（可能刚被合并清理），刷新后重试」；其它读错误原样显示错误信息。
- 任务卡正文直接用 `task.get` 的 `brief`；`brief` 为 `null`（一句话创建的任务）时显示 `task.request` 并注明「这个任务没有任务卡正文」。

**loader（`loadTaskDetail`）一次请求的读调用：**

1. `task.get {task_id}`（失败：离线 503/504 →「内核离线，暂时拿不到任务」；404 或 `code: not_found` →「找不到任务 <id>」；
   其它 →「无法读取任务：<内核原文>」——沿用占位页的三句话）；
2. 并行：`config.get {project_id}`（角色启用状态与 `resolved.bug.fix_rounds`；失败时降级为「角色状态未知」，操作表按全部启用处理、
   以内核拒绝原文为准）、`taskEvents.forTask(id)`（失败时时间线只列会话并注明「内核事件暂时读不到：…」）、
   有 `retry` 时 `dashboard.get`（取 `cooldowns`，与 W6 `board-data.ts` 同一取法）、处在合并段时 `task.changes {task_id}`；
3. 有 `?doc=` 时按上面的规则读一份文档，并在服务端解析成 Markdown 语法树（见「文档标签页」）。

「合并段」= `active` 且节点是 `await_merge`、`rebase`、`merge_gate`、`merging`、`main_check`、`cleanup` 之一，或 T-70 内核上
`task.merge.authorized` 为真。

### 执行时间线（M-03，R-03；回答待定问题 2、3、13）

`app/components/task-timeline-model.ts` → `timelineEntries(sessions, events, now)`，纯函数；`task-timeline.tsx` 渲染。
条目按事件顺序（`seq` 升序，等价于时间升序）排列，**新条目只追加在末尾**。

**会话条目**：以本任务的 `session.started` 事件为锚，按 `session_id` 关联 `task.get.sessions[]` 取其余字段；没有对应事件的会话
（事件被截断）按 `started_at` 插入。每条：阶段中文（`label`）、第几轮、CLI（`RUNTIME_LABELS`，`model` 非空时附上）、起止时刻、
用时（`ended_at − started_at`；运行中为「已运行 …」）、花费（`metrics.cost_usd` 存在时 `$x.xx`，否则「无计费数据」）、结果摘要。
结果摘要由锚点之后、下一条 `session.started` 之前的事件拼出：

- 有 `task.snapshot`：与上一条快照比较里程碑状态，列出变化，例如「M-01 开放 → 待审」「新增 M-02」；
- `bug.located`：`Located` →「已定位：<root_cause>」，`CannotReproduce` →「无法复现」，`NotABug` →「判定不是 Bug」；
- `bug.reviewed`：`Passed` →「复核通过」，其它 →「复核打回」；
- 紧随其后的 `task.updated`（`trigger` 为 `session_ended` / `bug_session_ended`）若进入 `failed` → `failureText(reason)`
  （如「协议失败：缺少状态字段 `status`」「会话崩溃：会话退出码 3」）；以上都没有时写「→ <taskStatusLine(下一状态)>」；
- `lifecycle.state` 为被终止 →「已被停止」；运行中 →「运行中」。

**内核步骤条目**（较轻的样式）：

- 门禁：**一次执行**合成一条，身份是这次执行的**第一个事件的 `seq`**，不是 `(node, kind, sha)`（排队事件没有后两项，同一提交上
  同因失败重跑会重复出现同一三元组）。合成规则按事件顺序逐条处理，每个 `node` 维护至多一条「未结束的执行」：
  - `gate.queued`（`job === "gate"`）：开一条新执行，状态「排队第 N 位」，此时 `kind`、`sha`、命令都未知；若该 `node` 上已有未结束执行
    （上一次排队后任务被停止 / 取消 / 重跑，没有后续事件），先把它标为「已中断」再开新的。`job === "setup"` 的排队不进门禁条目，
    归入 `setup.*` 的轻条目（「准备命令排队第 N 位」）。
  - `gate.started`：若该 `node` 有仅处于排队状态的未结束执行，绑定到它并补上 `kind`、`sha`、命令、日志，状态「运行中」；否则开新执行。
    若该 `node` 的未结束执行已经在运行（没有 `gate.result` 就又开始，如内核被停后重启 / 重跑），先把旧的标为「已中断」再开新的。
  - `gate.result`：绑定到该 `node` 上处于运行中的那条执行；找不到（事件被截断）时单独成一条。结果写完后该执行结束，下一次
    `gate.started`（哪怕 `sha`、`kind` 完全相同）一定是新条目，旧结果保留。
  - 名称按**节点**决定，`kind` 只用来补充命令种类：需求 `gate`、Bug `fix_gate` 上 `kind: quick` →「快检」（`fix_gate` 上为「修复门禁（复现 + 快检）」）；
    `repro_check` 节点 →「复现检查」；Bug `fix_gate` 节点（无论 `kind` 是 `repro` 还是 `full`）→「修复后回归（修复门禁）」；
    `merge_gate` →「合并前门禁」、`main_check` →「验证 main」、需求 `gate` 的 `full` →「门禁」。
  - 状态：排队第 N 位 / 运行中 / 通过 / 未通过 · 退出码 N / 超时 / 已中断。**`ok: false` 不能自己解释成「符合预期」**：
    仅 `repro_check` 节点才与随后的 `bug.reproduced` / `bug.repro_missed` 关联（关联到该执行之后、下一个 `gate.started` 之前的第一条），
    `bug.reproduced` →「已复现：复现命令失败（符合预期）· 退出码 N」；`bug.repro_missed` 按 `why`：`exited_zero` →「未复现：复现命令通过了」、
    `not_runnable` →「复现命令无法执行」、`timed_out` →「复现检查超时」；业务事件还没到达时只显示原始退出结果（「退出码 N」），不先下结论。
    `fix_gate` 及其它节点的非零退出一律「未通过 · 退出码 N」。
  - 显示命令、短提交号、日志路径（纯文本，不做链接）。`gate.reused` →「沿用已通过的结果」，`gate.skipped` →「跳过：<reason>」（各自单独的轻条目）。
- `rebase.conflicts`：`count: 0` →「rebase 无冲突」；有冲突列文件。`merge.auto`（`active: true`）→「默认分支已前进，自动 rebase 后再合并」；
  `merge.rebased` →「已自动 rebase 到 <onto> @ <短 sha>」；`merge.repo` →「已合并 · <短 sha>」；`merge.after*`、`setup.*` 照 CLI
  `event_line` 的措辞；T-70 的三种合并锁事件各一句。
- 用户操作：`task.updated` 的 `trigger` 为 `approve`、`reject`、`reply`、`merge`、`pause`、`resume`、`stop`、`cancel`、
  `rerun_from`、`extend_budget` 时各一条（「你批准了设计」等）。
- `session.retry`、`session.deferred`、`runtime.cooldown`、`task.protocol_failure`、`guard.warning` 各一条，措辞照 CLI `event_line`。

**稳定键**：会话条目的 key 是会话 id；门禁执行条目是 `gate:<node>:<seq>`，`seq` 是这次执行第一个事件的序号（排队 → 开始 → 结果期间
键不变，同一提交上的重跑得到新键）；其余是 `ev:<seq>`。`bug.reproduced` / `bug.repro_missed` 并入复现检查条目，不另出条目。

**日志（N-04）**：会话条目里放 W8 的 `<SessionLog>`。W8 组件只加一个可选参数 `defaultOpen?: boolean`（`useState(defaultOpen ?? false)`），
缺省时行为与现在完全一样；时间线对 `running` 的会话传 `true`。展开状态在 `SessionLog` 自己的 state 里，靠稳定 key 与「容器不重挂载」
保住：时间线列表始终渲染在同一个元素下，条目 key 不变，loader 重验只更新属性，React 不会重建已有条目，已展开的日志与其内部滚动位置

### 收尾不留进程（A-12，回答待定问题 17）

清理不能绑在「走到最后一个用例」上（`beforeAll` 等目标状态超时、断言失败、`task.stop` 被拒绝或超时都会跳过它；`CoreSupervisor.stop()` 只关
内核的 stdin、必要时杀内核子进程，不会回收假 CLI 与门禁脚本，它们在自己的进程组里）。做法：

- `test/fixtures/process-leak.ts` 除 `leftoverProcesses(root)`（读 `ps -axo pid=,command=`，返回命令行含临时目录路径的进程）外，再导出
  幂等的 `teardown({ root, core?, stopServices?, taskIds? })`：每一步各自 `try/catch`、互不阻断，顺序固定——① 停服务 / ticker（如有）；
  ② 对 `taskIds`（夹具创建过的全部任务）逐个尽力 `task.stop`，被拒绝或超时忽略；③ `core.stop()`（幂等）；④ 对 `leftoverProcesses(root)`
  返回的 pid 逐个 `SIGTERM`，有界等待（`vi.waitFor`，不在钩子里用 `expect`，约 5 秒）后仍在的 `SIGKILL`；⑤ **只有**第 ④ 步复查为空，
  或确认没有任何进程命令行含 `root` 时才 `rmSync(root)`；仍有存活进程时**保留**临时目录并抛出带 pid 与命令行的错误（宁可留目录也不删
  等待文件让子进程永不退出）。
- 每个起子进程的测试文件，`afterAll` 与 `beforeAll` 的 `catch` 都无条件调用 `teardown`（夹具只初始化了一半时同样调用，缺的对象跳过）。
  `taskIds` 取夹具脚本输出的任务 id 清单，夹具在创建任务之后第一时间登记。
- **最后一个用例**仍保留，它断言正常出口：对仍在运行的任务 `task.stop` → 停服务 / ticker → `core.stop()` → `vi.waitFor` 等
  `leftoverProcesses(root)` 为空并断言为空。它不是唯一的清理入口，`teardown` 是。门禁脚本与假 CLI 都在 `root` 下，路径过滤覆盖它们。
- `teardown` 本身写一个单测放进 M-01 的 `task-detail-real.test.ts`（第 4 条「收尾」用例内）：对一个真实起的 `w7-sleep` 子进程与一个会让
  `task.stop` 抛错的假 core，断言它仍杀掉子进程、之后才删目录；子进程杀不掉时不删目录。

- **T-70 内核行为差异（最大的不确定性）。** 实现轮用的是基线内核，合并前门禁用的是 rebase 后的 T-70 内核。处置：页面以 `task.merge`
  键判定内核能力（方案「两个内核版本」）；真实内核测试只断言与内核版本无关的事实（会话顺序、每个条目自身的内容，不断言合并段内核步骤的全局顺序）；
  夹具读 `AUTOME_BIN` / `AUTOMED_BIN`；M-05、M-06 审计做版本兼容复验。设计轮已用 main 内核跑过同一脚本，确认会话与门禁事件形状一致、
  合并段只多三种锁事件。
- **实现轮不能监听端口。** 监听的测试只有三个文件；其余真实内核测试走 stdio 直连，不受影响。
- **全量变慢。** 新增 7 个真实内核文件，全量约 10 分钟；夹具同时推进多个任务、一次 `run --until-idle`，不串行。

  任一状态造不出来时，该行从矩阵里拿掉并在证据里写明原因，纯函数逐行测试仍覆盖它，不算缺陷。
- **手写 Markdown 的覆盖面。** 只承诺本项目文档用到的子集；遇到不支持的写法按原文显示，不会执行或注入任何东西。
