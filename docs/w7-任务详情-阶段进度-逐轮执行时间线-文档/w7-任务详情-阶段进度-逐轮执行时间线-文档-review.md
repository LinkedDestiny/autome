## 六类问题

### P-01 门禁三元组不能关联排队事件，也不能区分同一提交上的多次执行

- **类别：关键事实错误。**
- **违反要求：** R-03（逐轮展示内核步骤及排队/运行/结果）、R-09（更新不破坏已有条目）；设计“执行时间线”的事件合并与稳定键条款；M-03 验收契约中门禁五种状态及稳定键的预期。
- **设计位置：** 设计文档第 282–285、294 行，规定按 `(node, kind, sha)` 合并 `gate.queued / gate.started / gate.result`，并使用 `gate:<node>:<kind>:<sha>` 作为键。
- **源码证据：** `crates/automed/src/gate_queue.rs:183` 的 `gate.queued` 只有 `node/job/checkout/position`，没有 `kind`、`sha`；`crates/automed/src/scheduler.rs:3874–3884` 的 `gate.started` 才提供这两个字段。`crates/autome-domain/src/task.rs:1023–1032` 允许门禁同因失败后从原节点重跑，执行 `DiscardGateRuns`；`crates/automed/src/scheduler.rs:2503–2506` 清除门禁产物，不要求改变提交。
- **具体反例：** 任务在 `merge_gate` 排队，先生成 `(merge_gate, undefined, undefined)` 条目；获得槽位后产生 `(merge_gate, full, S)`。按设计不能把二者归为一条，原排队条目会残留，或者必须改键/移除才能补救。随后提交仍是 S，门禁失败触发熔断，用户从 `merge_gate` 重跑；第二次 `started/result` 与第一次键完全相同，会覆盖旧结果或产生重复 React key，逐轮历史无法保留。
- **根因与检查范围：** 把“检查哪份代码”的属性当作“一次执行”的身份；覆盖所有排队、开始、结果及同 SHA 重跑，需求/Bug 的 `gate/fix_gate/merge_gate/main_check` 均应核对，不能只修单个节点。
- **建议修改：** 以一次执行的事件序号作为稳定身份，写明无 `kind/sha` 的排队记录如何绑定后续开始记录、结果如何绑定最近一次未结束执行；同 SHA 再次开始必须形成新的执行条目。同步修正现状字段说明及 M-03 对应反例，不能虚构排队事件字段。

### P-02 用 `kind: repro` 和 `ok: false` 判断“复现失败符合预期”会反转修复结果

- **类别：违反任务目标。**
- **违反要求：** R-02（复现检查结果）、R-03（内核步骤及结果摘要正确）、A-02；设计“阶段条”区分未复现/超时的条款，以及 M-03 验收契约的 Bug 条目预期。
- **设计位置：** 设计文档第 282–286 行，把 `kind: repro` 命名为“复现检查”，并规定其 `ok: false` 显示“复现命令失败（符合预期）”。
- **源码证据：** `crates/automed/src/scheduler.rs:3686–3694` 的 `legacy_kind` 在 `repro_check` 之外，也会给没有快检的 `fix_gate` 等 Bug 门禁赋 `Repro`；第 3917–3928 行的 `ok` 只是 `exit_code == 0`。第 2026–2033、2053–2066 行另行判定是否真正复现：超时、退出码 126/127 均产生 `bug.repro_missed`，不是 `bug.reproduced`。
- **具体反例：** 配置完整门禁只在合并前运行且没有 quick，Bug 修复结束后 `fix_gate` 执行回归命令，仍以退出码 1 失败。真实含义是修复未通过；按设计却会显示“复现检查／复现命令失败（符合预期）”。同类错误还有最初的 `repro_check` 因命令不存在退出 127，虽然 `ok: false`，内核明确认为未复现。
- **根因与检查范围：** 混淆门禁执行种类、所在流程节点与业务结果。检查所有 `kind: repro` 的节点，以及初始复现的正常非零、0、126、127、超时结果；与阶段条保持同一解释。
- **建议修改：** 名称先依节点区分初始复现与修复后回归；仅初始 `repro_check` 对应的 `bug.reproduced` 能得出“符合预期”。`bug.repro_missed` 按 `why` 显示未复现/不可执行/超时；修复后检查非零仍是失败。业务事件尚未到达时保留原始退出结果，不先宣布符合预期。

### P-03 取消重新排队的任务会把阶段条退回旧阶段

- **类别：违反任务目标。**
- **违反要求：** R-02（已取消停在出事的阶段）、A-01；设计“阶段条”对重新排队使用 `resume` 的规则及 M-02 取消状态的预期。
- **设计位置：** 设计文档第 237–239 行：重新排队使用 `resume`，但取消后只查历史最后一条 `active` 节点。
- **源码证据：** `crates/automed/src/scheduler.rs:2118–2132` 在槽位满时把目标状态改为 `Requeued { resume }`，第 2205–2209 行直接把这个状态写入 `task.updated`，中间不产生目标节点的 active 事件。`crates/automed/src/scheduler_gate_queue_tests.rs:808–869` 已有“批准后等待槽位”的源码测试。`crates/autome-domain/src/task.rs:905–913` 允许从该排队状态取消，取消状态不携带节点。
- **具体反例：** 任务停在 `await_design_approval`；项目槽位被另一任务占满；用户批准后进入 `queued(resume=implement)`，页面按设计已经高亮实现阶段。用户此时取消，最后一个 active 仍是 `await_design_approval`，于是页面跳回批准设计阶段并标已取消。类似问题也出现在从旧阶段失败/停止后重跑到另一节点、尚未取得槽位就取消时。
- **根因与检查范围：** 恢复取消前位置时丢弃了事件里已有的 `resume/at`。检查需求与 Bug 从 active、paused、stopped、failed、带 resume 的 queued 取消的路径；普通草稿/初次排队无节点的情况可保留现有降级。
- **建议修改：** 从取消之前最近的、携带节点的任务状态恢复位置，对 `node/resume/at` 使用与正常阶段条相同的映射，再覆盖“已取消”标记。保留批准→重新排队→取消这一具体回归场景。

### P-04 进程清理依赖最后一个用例，初始化或清理失败后仍会删临时目录

- **类别：内部逻辑矛盾。**
- **违反要求：** A-12、任务硬性约束 8（测试结束不留进程，先停进程再删目录）；设计“收尾不留进程”及所有真实内核测试的收尾预期。
- **设计位置：** 设计文档第 454–456 行，把停止任务、停止服务/ticker、确认无残留放在“最后一个用例”；`afterAll` 仅 `core.stop()` 后 `rmSync(root)`。
- **源码证据：** `apps/web/server/core/supervisor.ts:104–109` 的 `stop()` 只停止 sidecar；`apps/web/server/core/sidecar.ts:266–294` 通过关闭 stdin、必要时杀内核子进程实现停止，没有负责回收假 CLI 的独立进程组。设计第 454 行也已明确“停内核不会带走它们”。
- **具体反例：** `beforeAll` 已启动长等待假 CLI 或 main_check 门禁，但等待目标状态超时，最后一个用例不会执行；`afterAll` 只停内核就删 root，独立会话/门禁仍可存活。即使进入最后一个用例，只要 `task.stop` 拒绝或超时，后续停止服务、无残留检查都会被异常打断，兜底仍然直接删目录。这正是 A-12 要避免的“等待文件先被删除、子进程永不退出”路径。
- **根因与检查范围：** 把资源释放绑定在成功走到某个测试用例上，兜底没有承担同一资源生命周期。覆盖计划新增的全部真实内核测试文件，以及夹具部分初始化成功、正常断言失败、停止 RPC 失败三种出口。
- **建议修改：** 提取幂等清理函数，在 `afterAll/finally` 无条件执行：停止 ticker/服务推进，尽力停止任务，必要时按本夹具记录的 PID/进程组回收子进程，停止内核并有界等待退出，最后删除目录。“最后一个用例”可保留无残留断言，但不能是唯一清理入口；钩子仍可用 `vi.waitFor` 而不使用 `expect`。本项要求修正清理控制流，不要求增加产品范围或每轮运行全量门禁。
