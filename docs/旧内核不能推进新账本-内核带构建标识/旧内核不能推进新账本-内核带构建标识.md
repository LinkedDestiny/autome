## 背景与现状

2026-11-13 12:20，在主检出里用 `npm --prefix apps/web start` 起面板。面板落到了主检出里 11 小时前的
`target/debug/automed`，它和 launchd 驱动（`~/.local/bin/autome run`）轮流拿驱动锁，5 分钟内把 T-59、T-54 判成
「配置问题：…不认识的占位符 `{gate_line}`」，并把新建的 T-81 固定在 `protocol/v3` 上。

代码现状（本轮已核对）：

- **找内核。** `apps/web/server/core/binary.ts` 的顺序是 `AUTOMED_BIN` → `webRoot/../automed` → `~/.local/bin/automed` →
  `target/<profile>/automed`（最后一档不检查存在）。`scripts/install-cli.sh` 只装 `autome`，`package-cli.sh` 的 tar 包里只有
  `autome` 与 `README.md`。所以 `~/.local/bin/automed` 从来不存在，在源码检出里起面板一定落到 cargo 目录。
- **没有构建标识。** 仓库里没有 `build.rs`。`crates/automed/src/entry.rs` 的 `VERSION = env!("CARGO_PKG_VERSION")` 是
  两个二进制共用的唯一版本常量（`automed 0.1.0` / `autome 0.1.0`）。
- **推进入口。** `scheduler::tick` 先 `try_acquire` 驱动锁（拿不到返回 `skipped: true`），然后直接进 `tick_locked`：
  第一步是 `gate_queue::reclaim`，首个 tick 还要跑 `recover()`，之后才收会话、重试、跑内核步骤、填槽位。
  `freeze_protocol` 在开新任务时把**本二进制内置的**协议写进任务目录。`dispatch::handle_command` 对「不是
  `scheduler.tick`、也不在 `READ_METHODS`（17 项）」的方法最多等 120 秒驱动锁，写命令结束前还会 tick 一次。
  CLI 不起子进程：`Client` 在本进程里调 `handle_command`。
- **「我比账本旧」的检查。** 现在只有 `store.rs` 的 `refuse_a_database_that_is_not_ours`：账本 `user_version` 比本
  二进制的 `SCHEMA_VERSION`（7）高就拒绝打开。它只在 schema 变过时才生效。账本里没有键值或元数据表。
- **面板状态。** `CoreSupervisor` 用第一次 `scheduler.tick` 当握手。`CoreStatus.state` 有 `starting / connected /
  restarting / offline / stopped` 五种，`mapCoreStatus` 把它们映射成 `connected | offline`。`liveBanner` 显示
  「内核离线：…，写操作暂不可用」，`writeGate` 只在 `connected` 时放行。`ticker.ts` 每 3 秒 tick 一次，抛错就打一行
  日志。`gateway.ts` 把带 `code` 的内核错误映射为 409。
- **`autome run`。** `drive()` 每 `--interval` 秒（缺省 3，接受小数）tick 一次。任何 `skipped` 它都打一次「另一个驱动…
  正在推进」，tick 报错就以退出码 1 结束。launchd 条目是 `KeepAlive` + `ThrottleInterval 10`。
- **测试夹具。** `end_to_end.rs` 的 `World` 用内存库，但已有用例换成文件库：`w.ctx.store = Store::open(&db)`，
  约 8228 行。`cli.rs` 的 `Sandbox` 跑真实的 `autome`。Web 测试里的真实内核取
  `process.env.AUTOMED_BIN || target/debug/automed`。`ReplyErrorCode` 在仓库里没有穷举它的 TS 消费方。

## 目标与非目标

**目标**（覆盖任务卡「要做什么」6 条）：

1. `automed` 库在构建时嵌入可比较的构建标识。`autome` 与 `automed` 读同一个常量，带出到 `--version`、`env.get`、tick
   返回、启动日志和 `autome doctor`。
2. 账本记下推进过它的最新内核。比账本旧的内核只读：不推进、不判失败、不固定协议，写命令给出同一句话。
3. 显式的逃生口 `AUTOME_ALLOW_OLDER_KERNEL=1`，每个进程最多接管一次，并留下一条事件。
4. 装了 CLI 就有一个与 CLI 同版本、面板找得到的内核（`autome core`）。面板启动时打出内核路径与标识。遇到「内核比
   账本旧」时，横幅显示那句话、写操作置灰、不刷日志。
5. `autome run` 走同一段比较，被拒绝时不刷屏。
6. README、技术设计文档、计划 §7.3 写明这些规则。

**非目标**：

- 账本格式迁移框架（只沿用现有的「`SCHEMA_VERSION` 加一」做法）。
- 多机协调。
- 改协议正文（仓库 `protocol/` 与本任务副本）。
- W10 发布包结构。
- 桌面端（`apps/desktop`）的代码与 `scripts/package.sh`。桌面端带的内核由内核侧比较保护，界面怎样呈现不在本任务内。
- launchd 条目本身。

## 方案

### 1. 构建标识的口径（Q1）

文本形式只有两种，都只含 ASCII：

| 来源 | 文本 | 例 |
|---|---|---|
| git | `<HEAD 的祖先提交数，7 位零填充>-<提交者时间 UTC，YYYYMMDDTHHMMSSZ>-<完整 sha 的前 12 位>` | `0004213-20261113T042058Z-7715d8ed0a1b` |
| 未知 | `unknown-<包版本>-<构建时间 UTC，YYYYMMDDTHHMMSSZ>` | `unknown-0.1.0-20261113T050000Z` |

- **次序键是祖先提交数（`git rev-list --count HEAD`），不是时间。** 任务要求「后来的提交标识更大」。提交者时间做不到：
  同一秒内连续产生的父子提交时间相同（脚本、Autome 的合并提交都会如此），时钟偏差或 `--committer-date-is-author-date`
  还会让子提交的时间比父提交早。祖先提交数没有这个问题：子孙提交的祖先集合严格包含祖先提交的集合，所以**任何提交的
  后继，计数严格更大**，与时钟无关。时间戳仍留在文本里，只给人读，**不参与比较**；它由 sha 决定，所以同一提交构建出
  的文本总是一样（验收 1）。
- **浅克隆视为未知来源。** `git rev-parse --is-shallow-repository` 为 `true` 时计数不可信，按未知来源处理并打构建警告。
- **解析规则**：`^\d{7}-\d{8}T\d{6}Z-[0-9a-f]{12}$` 是 git 来源；`^unknown-.+-\d{8}T\d{6}Z$` 是未知来源；其余都是「解析
  失败」。计数 7 位够用到 999 万个提交；超出时 build.rs 标为未知来源，不让构建失败。
- **比较规则**（当前内核 C 对账本记录 M，函数 `build_id::verdict(C, M)`）：

  | 情形 | 结论 | 账本写不写 |
  |---|---|---|
  | M 不存在 | 可推进 | 写成 C |
  | C 与 M 文本相同 | 可推进 | 不写 |
  | 都是 git，C 的祖先数更大 | 可推进 | 写成 C |
  | 都是 git，C 的祖先数更小 | **更旧，拒绝** | 不写 |
  | 都是 git，祖先数相同、sha 不同 | **不可比，拒绝**（祖先数相同的两个不同提交互不为祖先，先后无法确定；不得双向放行，只能走逃生口） | 不写 |
  | C 是 git，M 是未知来源 | 可推进 | 写成 C |
  | C 是未知来源，M 是 git | **更旧，拒绝** | 不写 |
  | 都是未知来源，文本不同 | **更旧，拒绝**（构建时间不代表代码新旧，只能走逃生口） | 不写 |
  | M 解析失败（例如更新的内核换了格式） | **更旧，拒绝** | 不写 |

  未知来源只在没有 `.git` 的源码包或浅克隆里出现。`install-cli.sh`、`package-cli.sh` 与 CI 都在完整检出里构建，所以对它采取
  保守做法。祖先数只在**同一条历史**上有序：两条分叉的分支（例如任务分支与 main）之间，计数更大的一方被视为更新。这
  与约束 6 一致——任务分支的构建本来就不得接触真实账本。
- **工作区有未提交改动（dirty）不表示，也不参与比较。** 标识的含义是「从哪个提交构建」。要让 dirty 位保持新鲜，
  build.rs 就得在每次改任何源文件后重跑，这一位反而最容易陈旧（约束 5）。所以干脆不放。
- **`--version` 形状**：`autome 0.1.0 (0004213-20261113T042058Z-7715d8ed0a1b)`、`automed 0.1.0 (…)`。前缀与版本号不变，
  标识在括号里。`install-cli.sh` 原样把它印在「已安装」一行，`ci-local.sh --package` 只调用它、不解析它。
- **那句话**（约束 3，全仓唯一来源 `build_id::older_kernel_message(C, M)`）：
  「这个内核（<C>）比推进过账本的内核（<M>）旧，已停止推进；请重新安装或设置 AUTOMED_BIN」，按任务卡原文不改字。
  「不可比」的拒绝也用这一句：对账本而言，无法确认自己不旧，就按旧处理。

### 2. build.rs 怎样保证不陈旧（Q2，约束 4、5）

- 只有 `crates/automed/build.rs` 一份，输出 `cargo:rustc-env=AUTOME_BUILD_ID=<文本>`，库里是
  `pub const BUILD_ID: &str = env!("AUTOME_BUILD_ID")`（`automed::build_id`）。`autome` 链接同一个 rlib，读同一个
  常量。`entry::VERSION` 保留，`--version` 由 `entry::version_line(name)` 统一拼出。
- 取值：在 `CARGO_MANIFEST_DIR` 下运行 `git rev-parse --git-dir --git-common-dir --is-shallow-repository`（相对路径按
  manifest 目录补全）、`git rev-list --count HEAD` 和 `git show -s --format=%H%x20%ct HEAD`。UTC 格式化用 build.rs 与库共用的
  纯函数（见下），不引新依赖。取值整体写成 `build_support::compute(dir)`，build.rs 与测试调同一个函数。
- **重跑条件跟着 HEAD 走，并且在 worktree 里成立。** 选路径的逻辑是纯函数 `watch_paths(git_dir, common_dir, head_text,
  exists)`，规则如下（不假设 `.git/HEAD` 存在，也不假设 `.git` 是目录；worktree 的 git-dir 是
  `<主仓库>/.git/worktrees/<名字>/`）：
  - 始终监视 `<git-dir>/HEAD`；存在时监视 `<git-dir>/logs/HEAD`（每次提交、切换、reset 都会追加）与
    `<common-dir>/packed-refs`。
  - HEAD 是符号引用 `ref: refs/heads/x` 时，监视松散引用 `<common-dir>/refs/heads/x`：
    - 它存在：照常监视；
    - 它**不存在**（引用已被 `pack-refs` 打包）：若 `logs/HEAD` 存在，之后的提交会追加它，已经覆盖；若 `logs/HEAD`
      **也不存在**（`core.logAllRefUpdates=false`），仍然把这个不存在的路径发给 cargo。cargo 把不存在的监视路径视为
      「每次都变」，build.rs 每次构建都重跑——宁可多算一次 git，也不让下一次提交（它会新建这个松散引用，而 HEAD 与
      packed-refs 的内容都不变）漏掉。
  - 游离 HEAD 时，`<git-dir>/HEAD` 里就是 sha，本身已覆盖。
- 选路径的逻辑放在 `crates/automed/build_support.rs`，与 `compute` 一起。build.rs 用 `#[path]` 引入它，库的 `build_id`
  测试也用 `#[path]` 引入它，所以 worktree 布局能被单测钉住。**但「路径集合对」不等于「标识跟上 HEAD」，所以另有
  `crates/automed/tests/build_rerun.rs`：在临时目录里用真实 git 与真实 cargo 做两次构建**（把 `build.rs`、
  `build_support.rs` 复制进一个无依赖的小 cargo 项目，`cargo run --offline`，提交后再跑一次，比较程序打印出的标识与
  测试独立用 git 算出的值），覆盖三种场景：worktree、`pack-refs` 加 `core.logAllRefUpdates=false`、同一秒内的父子提交
  （标识必须严格递增，且 `verdict` 把父提交判为更旧）。
- **退路**：没有 `git` 命令、不是仓库（发布源码包、`cargo install` 自 tar 包）、浅克隆或 git 报错时，标为未知来源，
  并打 `cargo:warning=构建标识：拿不到 git 提交，标为未知来源`。**构建永不因此失败。**
- 代价：每次提交后的第一次构建会重编 `automed` 及其下游（见「风险与回退」）。

### 3. 「最新内核」记在账本哪里（Q3、Q4，约束 9、10）

- **新表，迁移 v8**：`SCHEMA_VERSION` 改为 8，`migrate` 末尾加 `if version < 8`，单个事务：

  ```sql
  BEGIN;
  CREATE TABLE IF NOT EXISTS kernel_mark (
      id INTEGER PRIMARY KEY CHECK (id = 1),
      build_id TEXT NOT NULL,
      updated_at TEXT NOT NULL
  );
  PRAGMA user_version = 8;
  COMMIT;
  ```

  已有迁移块一字不改。版本号以合并时 main 上的 `SCHEMA_VERSION` 为准：rebase 后若被并行任务占用，顺延并同步测试。
  迁移测试照 `deps_store_migration_preserves_queue`：降回 7 再打开，表存在、记录为空、原有任务都在。
- **比较与更新在一个 `BEGIN IMMEDIATE` 事务里完成**（`Store::claim_kernel_mark`）：读记录 → `verdict` → 需要写才写。
  写只在值变化时发生；同一内核反复 tick 不产生写入，也不产生事件。**事务只保证「比较加更新」这一步是原子的，
  它保护不了之后的任务写入**：O 提交标记之后、动手推进之前，N 可以插进来抬高标记并完整推进一轮，O 随后仍会按旧规则
  写入。所以两个驱动交替时「不出现各自都以为自己最新的窗口」靠的是**驱动锁覆盖从 `claim` 到最后一个副作用的全程**，
  不是靠事务：文件账本拿不到驱动锁时一律不推进（方案 4）。
- **没有记录的账本照常推进（约束 10）。** 全新的临时账本 `M` 不存在，任何内核都能推进并写下自己的值。所以现有
  的 e2e（183 个）、`cli.rs`（30 个）和 Web 真实内核测试一行不改就能通过。
- **本任务之前构建的内核（Q4）。** 选择加迁移，后果是：账本一旦被新内核打开过，就升到 v8，本任务之前的内核**再打开**
  它会被 `refuse_a_database_that_is_not_ours` 挡在门外（「schema 版本是 8，这个 automed 只认到 7」）。这正好是 11-13
  现场那种旧构建：它连账本都打不开，自然推进不了。代价是这些旧内核也读不了；它们会反复启动失败，面板转
  `offline`，launchd 每 10 秒记一行。不加迁移则这一批旧内核完全不受保护，这一点更不可接受。
- **这道门只挡新连接。** schema 检查只在 `Store::open` 里执行；迁移之前就已经打开了 v7 账本的旧进程（旧面板的 sidecar、
  旧桌面端、旧的 `autome run`）连接仍然有效，SQLite 对加表无感，它们还能拿驱动锁、按旧规则推进。所以上线顺序必须
  **先让所有接入真实账本的旧进程退出，再迁移、再启动新驱动**（方案 14）。

### 4. 哪些调用算「推进」，在哪里比较（Q5，约束 1、2、7、8）

**口径：`READ_METHODS` 以外的方法一律算推进。** 也就是 `scheduler.tick` 加上全部写方法，包括 `config.set_*`、
`project.add/remove`、`project.onboarding.*`、`project.alert.dismiss`、`rules.*`、`task.*` 的写方法。

依据：

- 这些方法都会按**本二进制的**规则改账本或项目文件。`project.add` / `onboarding.run` 会用旧内核内置的脚手架与协议
  初始化项目，`config.set_*` 会按旧的配置形状改写配置，`task.decide`、`rules.*` 写的是旧规则下的裁决与提案，
  `task.retro` 会启动会话。
- 任务名就是「比账本旧就只读」，按 `READ_METHODS` 划线只有一条判据。若逐类放行，会再造一份需要与内核同步的
  清单。`READ_METHODS` 的名字与内容不动（约束 8）。

检查点：

1. **`scheduler::tick`**：先**不取锁**，只读比较（`kernel_guard::check`）。判为更旧且不走逃生口时，直接返回
   `TickReport { skipped: true, older_kernel: Some(..) }`，不碰驱动锁，也就不跟正在推进的驱动抢锁。通过后照旧取锁，
   再在锁内调 `kernel_guard::claim`（就是方案 3 的事务）；被拒就释放锁返回同样的报告。**取锁本身出 I/O 错误
   （文件账本，例如锁文件无法打开）时不再「不带锁继续」**：直接返回 `skipped: true`，`errors` 里带一行
   「无法取得驱动锁：<原因>，本次不推进」，不调 `claim`。理由见方案 3：没有锁就没有「比较到最后一个副作用」的互斥。
   内存账本的 `try_acquire` 恒返回 `Some`，不受影响。两步都在 `tick_locked`
   **之前**，所以 `gate_queue::reclaim`、首个 tick 的 `recover()`、收会话、重试、`freeze_protocol`、启动会话、门禁、
   worktree 一个都不会执行（约束 1）。`ctx.recovered` 保持 `false`。
2. **`handle_command`**：对「不是 `scheduler.tick`、也不在 `READ_METHODS`」的方法，先只读比较，判为更旧且不走
   逃生口时立刻返回，**不去等 120 秒的锁**；然后取锁，再 `claim`，失败就释放锁返回；取锁出 I/O 错误时同样不继续，返回 `internal` 错误
   「无法取得驱动锁：<原因>」，写命令不执行。错误码是新增的 `ReplyErrorCode::OlderKernel`
   （序列化为 `older_kernel`），消息就是那句话。写命令结束前那次 tick 会再 `claim` 一次，此时值等于自己，不写。
3. **`Store::open` 的 `migrate`**：放在比较之前，按原样执行。比较需要 `kernel_mark` 表，只有不旧于账本 schema 的二进制
   才能打开账本；更旧 schema 的二进制已被现有检查拒绝。
4. **`recover()`**：只在 `tick_locked` 里调用（scheduler.rs 170 行），由检查点 1 覆盖。

**`TickReport` 只增字段（约束 7）**：`skipped` 仍是布尔值。新增 `older_kernel: Option<OlderKernel { message, kernel,
ledger }>`，JSON 里是 `"older_kernel": null | {"message","kernel","ledger"}`。「另一个驱动持锁」的跳过是
`skipped: true, older_kernel: null`；「内核比账本旧」的跳过是 `skipped: true, older_kernel: {...}`，调用方能分开。

**`Ctx` 新增三个字段**（照 `launch_mode` 的写法，测试改字段，不靠进程级开关）：

- `build_id: String`，缺省 `build_id::BUILD_ID`；
- `allow_older_kernel: bool`，缺省 `false`；
- `adopted_older_kernel: bool`，缺省 `false`。

`Ctx::new` 不读环境变量。三个进程入口（`automed` 的 main、`autome` 的 `Client::open`、`autome core`）调
`entry::apply_kernel_env(&mut ctx)` 读环境（方案 5、6）。

### 5. 逃生口（Q6，约束 11）

- **只做环境变量 `AUTOME_ALLOW_OLDER_KERNEL=1`**（值必须是字面量 `1`，其余值一律无效）。不另设命令，理由如下：
  - 同一个开关对三个入口都成立：`AUTOMED_BIN=<旧> AUTOME_ALLOW_OLDER_KERNEL=1 npm --prefix apps/web start`、
    `AUTOME_ALLOW_OLDER_KERNEL=1 autome run`、单条写命令。
  - 命令形式要新增一个写方法，牵动 Web 写白名单与桌面端读白名单的比对测试，任务卡也写的是「或」。
  - 命令形式进 Backlog（B-01）。
- **行为**：`claim` 判为更旧，且 `ctx.allow_older_kernel && !ctx.adopted_older_kernel` 时，在同一事务里把记录改成
  C，追加事件，置 `ctx.adopted_older_kernel = true`，然后照常推进。事件形如：
  `append_event("kernel.adopted", "kernel", {"from": M, "to": C, "via": "AUTOME_ALLOW_OLDER_KERNEL",
  "method": "<触发它的方法，如 scheduler.tick>"})`。
- **常驻时的上限：每个进程最多接管一次。** 新驱动（launchd）与带逃生口的旧内核同时在跑时：
  1. 新驱动看到 M=旧 < 自己，正常推进，把记录写回新值，不记事件；
  2. 旧内核在本进程里已经接管过，于是像没带逃生口一样被拒。

  所以 `kernel.adopted` 的条数不超过「带开关启动的进程数」。想再接管一次，就得重启那个进程。这是显式动作。
- **之后新内核再接上**：`verdict` 判新内核更新，写回新值，回到新的（验收 3）。

### 6. 测试怎样「注入标识」（Q5 后半，约束 11）

- **进程内**（e2e、单测）：直接改 `ctx.build_id`。「接同一个 `AUTOME_HOME`」的写法是：e2e 的 `World` 换成文件库
  （仿 `w.ctx.store = Store::open(&db)`），旧内核是**同一个文件上新建的第二个 `Ctx`**（`recovered = false`）。这样
  「旧内核的首个 tick 不得跑 `recover()`」也能被测到。新增辅助方法 `World::second_kernel(build_id) -> Ctx`。
- **进程级**（`cli.rs` 跑真实 `autome`，Web 测试拉真实 `automed`）：环境变量 `AUTOME_TEST_BUILD_ID=<标识>`，由
  `entry::apply_kernel_env` 读。三道限制：
  1. **只在 `cfg(debug_assertions)` 的构建里编译进去。** `install-cli.sh`、`package-cli.sh`、`package.sh` 产出的都是
     `--release`，里面根本没有这段代码。
  2. **只能把标识往旧改。** 解析失败，或 `verdict` 判它比编译进去的标识新时，忽略并在 stderr 打一行警告。
  3. 它只改「我是谁」，不碰账本。

  为什么不构成第二个逃生口：它只能让进程更受限。把自己改旧之后若再配 `AUTOME_ALLOW_OLDER_KERNEL=1`，能把记录降到
  更旧的值；但这件事逃生口本来就能做（让真正的旧内核带开关启动即可），没有新增能力。用例
  `kernel_guard_test_override_cannot_raise_the_id` 钉住「改不新」。
- **`--version` 也读覆盖后的值**：同一个进程只有一个身份，测试里的「旧内核」从版本号到 tick 都一致。

### 10. 面板怎样表示「内核比账本旧」（Q10）

- **新状态 `outdated`**，不是带原因的 `offline`：内核其实连着、读请求照常可用，语义上不是离线。
  - `CoreStatus.state` 加 `'outdated'`，`reason` 存那句话；
  - `CoreMessage.status` 加 `'outdated'`，`mapCoreStatus` 原样带上 `reason`；
  - `hello` 消息加可选的 `reason`，`live-client` 把它交给 `onCore`。
- **横幅**：`liveBanner` 遇到 `outdated` 返回 `{ tone: 'alert', text: <那句话> }`，**不带**「内核离线：」前缀，也不追加
  「写操作暂不可用」，满足约束 3 的「同一句话」。样式沿用 `live-banner` 的 alert。
- **置灰**：`writeGate` 遇到 `outdated` 返回 `{ allowed: false, reason: <那句话> }`。各写控件经 `useWriteGate` 置灰，
  样式与离线时相同。`needsKernelReload` 不变（只看 `connected`）。
- **读请求**：`CoreSupervisor.activeSidecar()` 放行 `starting / connected / outdated`，读请求在 `outdated` 下照常经网关
  转给内核。
- **状态切换在 `CoreSupervisor.tick()` 里**：返回带 `older_kernel` 时转 `outdated`（启动握手时直接
  `starting → outdated`），不带时从 `outdated` 回到 `connected`。进入时用 `log` 打一行 `[内核] <那句话>`，离开时打
  一行 `[内核] 已恢复推进`，状态与原因都不变时不打。
- **ticker：降频、不打日志。** 新增 `canTick`（`connected` 或 `outdated`）与 `isSlow`（`outdated`）。`isSlow` 为真时，
  每 10 个间隔才 tick 一次（缺省 30 秒），这样仍能发现别处用逃生口降了记录，同时不再每 3 秒刷一次。`skipped` 时本来
  就不打 `errors`。
- **恢复路径**：
  - `core.restart` 在 `outdated` 时不再返回 `already_running`，而是重启：**先停止并回收原 sidecar 子进程，再启动新的**
    （`CoreSupervisor.restart()` 现在直接调 `start()` 覆盖 `this.sidecar`，不会停原进程，实现时补上先停后起）。用户重装 CLI 后，同一路径
    （`~/.local/bin/autome`）上已经是新文件，重启即恢复。
  - 另一种是重启面板。
  - 若有人用逃生口降了账本的记录，慢速 tick 会自动回到 `connected`。
- **直接经网关发来的写请求**：内核回 `older_kernel` 错误，`gateway.ts` 照现有规则映射为 409，`code: 'older_kernel'`，
  `error` 是那句话。网关不做预判，以内核为准。

### 11. `autome run` 被拒绝时（Q11，约束 12）

| 形态 | 行为 | 退出码 |
|---|---|---|
| `autome run`（常驻，launchd 用） | **保持进程，不推进。** 第一次遇到 `older_kernel` 时在 stderr 打一行那句话；之后每个间隔照常 tick（无锁只读比较，开销极小），记录变化（消息文本不同）才再打一次；某次 tick 不再带 `older_kernel` 时，打一行「账本已允许本内核推进，继续驱动」并恢复。 | 不因此退出 |
| `autome run --once` | 打一行那句话后结束 | 1 |
| `autome run --until-idle` | 第一次 tick 就被拒：打一行那句话后结束；中途被拒同样结束 | 1 |

- 常驻不退出，launchd 的 `KeepAlive` 就不会每 10 秒拉起一次。日志里这句话的条数不超过「账本记录变化次数 + 1」。
  用户重装后执行 `launchctl kickstart -k` 换上新进程（README）。
- 遇到 `older_kernel` 时**不打**「另一个驱动…正在推进」那行。那一行只给 `older_kernel == null` 的 `skipped` 用。
- `--json` 模式输出一行 `{"older_kernel": {"message": …, "kernel": …, "ledger": …}}`，打印频率规则同上。恢复时输出
  `{"older_kernel": null}`。
- 测试不用真等几分钟：用 `--interval 0.05` 跑约 2 秒（约 40 次 tick）后发 SIGINT，断言 stderr 总行数上限和那句话
  只出现一次，见 M-04。

### 12. 其它写命令在 CLI 上的呈现（Q12）

沿用 `CliError::Failed(message)` → `autome：<那句话>`、退出码 1。

`task new` 这类在调 `task.create` 之前还读文件、解析项目的命令，这些前置步骤都只读，照常执行，然后由 `task.create`
被拒。不额外提前判断，这样拒绝只有内核这一个来源。用例覆盖 `task new`、`approve`、`merge`、`rerun`。

## 风险与回退

- **构建开销。** build.rs 跟着 HEAD 重跑，每次提交后的第一次构建都会重编 `automed` 与 `autome-cli`。这是约束 5 的
  代价，不设缓存绕过。若门禁时长逼近上限，再考虑把标识挪进一个只被二进制依赖的小 crate（B-02）。
- **提交图被改写。** 标识的次序键是祖先提交数，与时钟无关，所以时钟偏差、同一秒的提交、`--committer-date-is-author-date`
  都不影响次序。会让计数变小的只有改写历史（main 上的 squash、force-push、从浅克隆重建）：之后构建的内核祖先数
  更小，被拒。表现明确（那句话），用逃生口接管即可，之后正常的 main 提交会重新递增。分叉分支之间只比计数，
  这正是约束 6 要避免它们接触真实账本的原因。
- **worktree 构建碰真实账本。** 任务分支通常比已安装的 main 构建多出若干提交，祖先数更大。若有人在 worktree 里用新构建打开
  `~/.autome` 并推进一次，记录就会被抬高，已安装的驱动停下（会打那句话）。约束 6 已禁止这样做，README 也写明。
  事后恢复：用已安装的 CLI 带 `AUTOME_ALLOW_OLDER_KERNEL=1` 跑一次 `autome run --once`。
- **迁移挡住本任务之前的所有内核**，包括旧桌面端包与没重装的 CLI。按上线顺序操作可避免 launchd 刷「打不开账本」。
  迁移**挡不住迁移之前已经打开账本的旧进程**，所以上线顺序把「退出全部旧进程」放在迁移之前（方案 14）。
  回退到本任务之前的版本需要把账本移开，这是 schema 迁移的一贯后果，不在本任务内处理。
- **并行任务占用 v8。** 合并前 rebase 时核对 `SCHEMA_VERSION`，顺延本任务的块号，并同步迁移测试与断言（约束 9）。
- **迁移发生在比较之前。** 一个祖先数更小、schema 却更高的分支构建（并行任务加了 v9）打开真实账本时，会先迁移
  再被拒。同样属于约束 6 禁止的操作，不额外处理。
- **桌面端**：tick 返回的 `older_kernel` 与写命令的 `older_kernel` 错误，在桌面端只会表现为「跳过」和一条错误消息
  （那句话），没有专门的横幅，这超出本任务范围。
- **回退方式**：
  - 不能整体 revert。真实账本一旦迁到 v8，`SCHEMA_VERSION` 退回 7 的构建就打不开它。
  - 要回退行为时，保留 v8 迁移块与 `kernel_mark` 表，只去掉检查点（方案 4）。
  - 临时绕过不需要改代码：带 `AUTOME_ALLOW_OLDER_KERNEL=1` 启动即可。
  - 这一点写进 technical-design §13。
