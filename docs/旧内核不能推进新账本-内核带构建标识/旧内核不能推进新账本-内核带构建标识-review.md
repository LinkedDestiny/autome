## 阻塞问题

### R1-P01（P1）提交时间相同或倒退时，旧提交仍可推进新账本

- 六类归属：**违反任务目标**。
- 追溯：任务 §3.1、§6 约束 4「后来的提交标识更大」；任务 §3.2「自己更旧：不推进」。
- 设计位置：方案 1（第 79–95 行），M-01 单测第 6 项（第 408 行），风险「提交时间不单调」（第 653 行）。
- 根因与范围：把提交者时间当作提交先后关系，并将同秒不同 SHA 明确视为可互相推进。检查范围为整个比较矩阵及其风险说明；同类问题包括同秒父子提交和提交者时间倒退。
- 反例：A 是 B 的父提交，两者 `%ct` 都为 `1794528000`。B 先推进并记下 B，A 再接入。按方案 1 的同秒规则，A 被允许推进且不改标记；因此 A 可以按旧规则固定协议、修改任务。它不需要逃生口，也不会触发横幅。更严重的同类情形是 B 的提交时间比 A 早：B 先记下自身后，实际更旧的 A 被判成「更新」并直接放行。设计风险段只写了「新内核被拒」，漏掉这个反向放行。
- 证据：在隔离的临时 Git 仓库实际生成 A→B，确认父子关系成立、SHA 不同、提交者时间相同。实验输出 `parentIsA=true`，两个时间均为 `1794528000`；按文中比较表即可确定错误结论，无需等待实现。完整输出在 `.autome/output/review-1-probes.log` 的 `git-same-second-parent-child` 项。
- 建议裁决：重新确定能满足后继严格变大的排序口径；至少不能把无法确定先后的不同提交双向放行。若要放宽任务对提交顺序的硬约束，须明确裁决该冲突，不能以风险说明或逃生口代替。同步比较表与 M-01 第 6 项，避免测试把错误放行钉成预期。

### R1-P02（P1）驱动锁出错后继续推进，标记事务无法保护之后的任务写入

- 六类归属：**关键事实错误**。
- 追溯：任务 §3.2、§6 约束 1；任务 §7 Q3 要求两个驱动交替时不能出现「各自都以为自己最新」的窗口；设计方案 3 宣称无驱动锁时事务也能保证这一点。
- 设计位置：方案 3 第 144–146 行；方案 4 的两个检查点。
- 根因与范围：`BEGIN IMMEDIATE` 只覆盖 `claim_kernel_mark` 的读、比较和标记更新，提交后才执行 `tick_locked` 或写方法；设计却保留取驱动锁失败时继续执行。检查了两个生产入口：`crates/automed/src/scheduler.rs:127`（第 143 行无锁继续）和 `crates/automed/src/dispatch.rs:222`（第 259 行无锁继续），两处同受影响。
- 具体交错：
  1. 锁文件无法正常打开，例如 `<db>.driver.lock` 被目录占据；数据库文件仍可读写。旧 O、新 N 都走 `Err` 分支。
  2. O 在事务中比较成功，将标记写为 O 并提交；尚未进入实际任务操作。
  3. N 在另一事务将标记抬到 N 并提交，再完成一次任务推进。
  4. O 恢复执行 `tick_locked` 或已获准的写方法，追加 `task.updated`、固定协议或启动会话。

  此时账本已由 N 推进，O 仍在推进。SQLite 没有并发写事务冲突，因为几次事务完全顺序执行。只对两个 `claim` 做互斥不能消除此窗口。
- 证据：源码确认两个无锁继续分支；隔离 SQLite 双连接模型按上述提交顺序执行后，标记为 `new`，事件顺序为 `new` 后 `old`。输出见 `.autome/output/review-1-probes.log` 的 `claim-then-advance-without-driver-lock` 项。这是事务边界的实际验证，不宣称运行了尚未实现的内核 e2e。
- 建议裁决：对文件账本，无法获得驱动锁时停止本次推进并返回可诊断结果；内存测试库可继续沿用其明确的单进程安排。或者提出覆盖「比较到最后一个副作用」的等价互斥方案。必须同时处理 tick 和全部写命令，不能仅加强标记事务。

### R1-P03（P1）只监视已存在的 Git 文件，会让新源码继续携带旧提交标识

- 六类归属：**违反任务目标**。
- 追溯：任务 §6 约束 5「标识不得陈旧」「重跑条件必须跟着 HEAD 走」；任务 §7 Q2；M-01 声称消除构建缓存不确定性。
- 设计位置：方案 2 第 113–120 行，`watch_paths(..., exists)` 及 M-01 重跑路径用例。
- 根因与范围：监视集合只收录当时存在的 HEAD、logs/HEAD、当前 loose ref、packed-refs；缺少「缺失的 loose ref 后来出现」的触发路径。范围是同一规则用于主检出及 worktree 时的依赖集合，而非 `.git` 文件／目录识别本身。
- 具体反例：仓库设 `core.logAllRefUpdates=false`，把当前分支 `git pack-refs --all` 后首次构建。此时没有 `logs/HEAD` 或该分支 loose ref，设计只监视 HEAD 与 packed-refs。随后在同一分支改源码并提交 B：Git 新建 loose ref，但 HEAD 文本及 packed-refs 均不变；Cargo 编译了新源码，却不重跑只监视前述文件的 build.rs。
- 证据：用独立、无依赖的 Cargo 小项目逐项复现方案 2 的 watch 规则，先构建 A，再修改 `src/main.rs` 并提交 B，执行第二次 `cargo run --offline --quiet`。实际结果为 `firstMatchesA=true`、`secondMatchesB=false`、`secondStillA=true`，HEAD 与 packed-refs 内容均未变化。输出见 `.autome/output/review-1-probes.log` 的 `packed-ref-no-reflog-cache` 项；临时源码在 `.autome/output/review-1-probe/cache/`。
- 建议裁决：让监视策略也能捕捉当前引用从 packed 变成 loose 的创建，不能依赖 reflog 必然存在；可监视适当的现有父目录或采用其他不会漏掉该变化的触发机制。把这个真实的两次构建反例纳入 M-01 的验证范围。仅检查 `watch_paths` 返回了哪些现存文件不能证明标识跟随 HEAD。

### R1-P04（P1）上线顺序先启新驱动、后处理旧面板，仍允许无保护旧进程推进

- 六类归属：**违反任务目标**。
- 追溯：任务 §2 的事故路径及 §3.2；任务 §7 Q4 要求说明本任务前内核的防护后果与上线顺序；任务 §3.6 的 README 文档要求。
- 设计位置：方案 3 第 149–153 行「旧构建连账本都打不开，自然推进不了」；方案 14 第 359–366 行；风险「迁移挡住本任务之前的所有内核」。
- 根因与范围：schema 检查只发生在打开连接时，不会撤销已经打开的旧连接。设计虽然承认旧 launchd 连接在安装到 kickstart 之间继续运行，但没有让**所有**旧驱动在第一次迁移／新驱动启动前退出。检查范围包括既有 CLI 常驻驱动、Web sidecar、桌面端内核；无需修改桌面端实现即可在上线前置步骤中覆盖。
- 反例：旧 Web 或桌面端先打开 v7；按方案 14 第 2 步安装并由 doctor 迁到 v8；第 3 步 kickstart 新 CLI，新驱动推进并写下最新标识。旧面板进程到第 4 步才被处理，此间仍可拿驱动锁并按旧规则推进，因为它既不重新打开账本，也没有本任务的比较逻辑。若「重新打包桌面端」没有退出当前已运行的旧应用，窗口还会持续。新旧进程轮流拿锁正是任务要阻断的事故路径。
- 证据：`Store::open` 在 `crates/automed/src/store.rs:193` 调 `migrate`，版本检查位于 `migrate` 第 234–236 行；旧 tick 路径没有重新检查 schema。隔离 SQLite 双连接实验中，新连接加表并将 `user_version` 升为 8 后，先前已打开的旧连接仍成功写入一条事件（`oldConnectionStillWrote.n=1`）。见 `.autome/output/review-1-probes.log` 的 `migration-existing-connection` 项。这不是对真实账本做迁移。
- 建议裁决：把暂停／退出所有接入该账本的旧驱动作为首次升级前置条件，再执行安装迁移与新驱动启动；README 明确迁移只拒绝旧版本的**新连接**。已有旧面板／桌面进程要先退出，不应排到新驱动启动之后。本轮不操作系统 launchd 或真实进程，仅要求修正上线设计。
