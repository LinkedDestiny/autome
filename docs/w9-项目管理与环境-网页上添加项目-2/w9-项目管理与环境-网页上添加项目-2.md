## 方案

### 1. 总体结构

服务端新增两个模块、改四个接线点：

- `server/paths.ts`（新建）：`$HOME` 守卫与目录补全，纯 Node `fs` 同步调用，无网络、无内核。
- `server/admin.ts`（新建）：`createAdmin({ core, automeHome, userHome, terminal, publish })` 汇总本任务的服务端能力，返回
  `{ paths, register(gateway), onboarding, configPaths, onTick }`。`register` 为 `project.confirm`（M-01）、`env.install`、`env.login`（M-06）
  注册本地处理函数；`onTick` 处理 Onboarding 会话结束与环境探测落地的推送（M-03、M-06）。
- `server/terminal.ts`（M-06 新建）：终端启动器。
- `server/gateway.ts`：新增导出类 `LocalOpError(status, message)`；`execute` 遇到它回 `{ status, body: { ok: false, error: '已拒绝：' + message } }`，
  不再落到 503「内核未连接」（Q-11）。`createGateway` 多收一个可选 `paths`；有它时 `read` 对 `project.probe` 先过守卫（见 §2），
  守卫不过回 400，过了把 `path` 换成守卫给出的 realpath 绝对路径再转给内核。不传 `paths` 时行为与现在完全相同（现有测试据此不变）。
- `server/main.ts`：`startServer` 多收可选 `userHome`（默认 `resolveUserHome(process.env)`）与 `terminal`（默认「打不开终端」的启动器，M-06）；
  建 `admin`，`admin.register(gateway)`，把 `paths` 传给 `createGateway`，把 `admin` 传给 `createHttpServer`，ticker 的 `onTick` 改为先
  `attached.onTick()` 再 `admin.onTick(report)`。`runFromEnv` 是唯一传入真实 macOS 终端启动器的地方（M-06）。
- `server/http.ts`：有 `admin` 时注册 `POST /api/paths`（在 `express.json` 之后，因而在 `securityMiddleware` 之后）；`createLoadContext`
  多透传 `admin`。
- `app/load-context.ts`：`WebServices` 新增可选字段 `admin?: AdminServices | null`。任务文件 §3 没有列出这个文件，但 §5 写明
  「往 context 里加新服务时照这个写法」；设置页 loader 要读 Onboarding 会话状态与配置文件路径，添加页 loader 要做路径守卫，
  都只能从服务端服务拿。改动只有一个可选字段，与 W7 加字段的冲突按「并列保留」解决。

前端新增三条路由 `projects/new`、`projects/:id/settings`、`env`（`app/routes.ts`），文案集中在新建的 `app/lib/admin-labels.ts`
（`.ts` 文件不受 `labels.test.ts` 第 7 条守卫约束；不改 `labels.ts`，避开 W7 的改动）。所有页面数据只来自 loader，写操作只经
action → `gateway.write`，变化靠账本事件或服务端扩展消息让 loader 重新加载（约束 13）；写按钮一律 `disabled={!gate.allowed}`、
`title={gate.reason}`（`useWriteGate()`，R-05）。

### 2. 路径守卫与目录补全（R-01a，Q-4、Q-5）

`resolveUserHome(env)` 返回 `env.HOME`（去掉末尾 `/`）；没有 `HOME` 时守卫的每次调用都回「服务进程没有 HOME 环境变量，不能校验路径」。
`createPathGuard({ home })` 在创建时算一次 `realHome = realpathSync(home)`。

`check(input)` → `{ ok: true, absolute, display, isHome } | { ok: false, message }`，规则依次是：

1. 必须是字符串、长度 1..512、不含 NUL、**不含 `..` 子串**（任务卡原文「拒绝含 `..`、NUL 的输入」，按字面执行）、不含 `\`。
2. 形式只收 `~`、`~/…` 与以 `/` 开头的绝对路径；其它（相对路径）拒绝。`~` 展开为 `home`。
3. 规范化之后找出**最深的已存在祖先**，对它 `realpathSync`，再接上其余（不存在的）段，得到 `absolute`。祖先之外的段不可能含
   `..`（规则 1）也不会是符号链接（不存在），所以这个结果就是将来 `create_dir_all` 的落点。
4. `absolute === realHome` 或以 `realHome + '/'` 开头才放行；否则回「路径不在家目录内：…」。绝对路径逃逸、指向外面的符号链接、
   `HOME` 自身是符号链接（`/var` → `/private/var`）三种情况都由这一步统一处理。
5. `display = '~' + absolute.slice(realHome.length)`（家目录本身为 `~`），`isHome = absolute === realHome`。

`complete(input)` → `{ base, entries: [{ name, path }], truncated } | { error }`：空串与 `~` 视作 `~/`；**转换之后先对完整输入执行 `check`**，
不过就整体回 `{ error }`（含 `..`、NUL、`\`、相对路径、完整输入的 realpath 落在 `$HOME` 之外——例如 `~/a..b`、`~/bad\0`、指向外面的符号链接 `~/escape`，
带不带尾斜杠结果一致）；通过之后才拆分：以 `/` 结尾时列这个目录、前缀为空，否则列父目录、前缀为最后一段。父目录再过一次 `check`；不存在则回空列表。
（输入到一半的前缀如 `~/esc` 不存在，按最深存在祖先判断，照常放行。）读 `readdirSync` 后按名称码点序排序，逐个判断：名称以前缀开头
（区分大小写）；前缀不以 `.` 开头时跳过以 `.` 开头的名字；`realpathSync(子项)` 必须是目录（`statSync().isDirectory()`）且仍在 `realHome`
内（符号链接指到外面的不列）。凑满 50 项后再找到第 51 项就停，置 `truncated: true`，页面提示「还有更多，请继续输入」。`path` 是
`base + name`（字面，不展开符号链接——确认时会再过一次守卫）。

接口：`POST /api/paths`，请求体 `{ input: string }`（多余字段拒绝），成功 200 `{ ok: true, payload: { base, entries, truncated } }`，
拒绝 400 `{ ok: false, error: '已拒绝：…' }`。用 POST 而不是 GET，与现有 `/api/read` 一致，并且同时过 Host 与 Origin 检查
（`securityMiddleware` 对非 GET 查 Origin，约束 6「不放松也不加码」——没有加任何新的检查机制）。只读、只回目录名。

### 3. 添加项目（R-01，Q-2、Q-3、Q-6、Q-17）

**服务端 `project.confirm`**（`admin.ts`，经写入口 `gateway.write` 到达，`/api/write` 与页面 action 走同一条路）：

1. 写白名单形状（`write-gate.ts`，纯函数）：键只能是 `path`、`workspace`、`docs_repo`、`skip_onboarding`；`path` 必填、字符串、
   不含 NUL 与 `..`；`workspace`、`skip_onboarding` 若出现须为布尔；`docs_repo` 沿用现有「名称，不能是路径」。
2. 处理函数：`paths.check(path)`，不过 → `LocalOpError(400)`；`isHome` → `LocalOpError(400, '不能把整个家目录添加为项目')`
   （家目录不是仓库时内核会在里面 `git init`，F-07）。
3. **先 `project.probe`（以 `absolute` 调用），再 `project.add`（同一个 `absolute`，`workspace`，`docs_repo` 仅工作区时传）。**
   这就是 A-02「确认前一定调过 `project.probe`」的服务端保证（计划 §5.5「添加项目先经服务端 `project.probe`」）：不论请求来自页面
   还是直接打 `/api/write`，add 之前一定有一次针对同一路径的 probe。工作区而 probe 回 `members` 为空 → `LocalOpError(400,
   '这个目录下没有仓库，不能按工作区添加')`；其余拒绝（已是项目、嵌套、文档仓库不对）交给内核，原文 409 透传。
4. `skip_onboarding` 为真时在 add 成功后调 `project.onboarding.skip`（与命令行 `--skip-onboarding` 相同，F-07）。skip 抛错**不回滚**
   （项目已经加上了），整体仍 200，回包带 `skip_error: <内核原文>`（Q-6）。
5. 回包 `{ project, init, pending_commit, probe, onboarding, init_commit?, skip_error? }`。

**页面 `/projects/new`**（`routes/projects.new.tsx` + 纯逻辑 `components/add-project-model.ts`）：

- 输入框 + 补全列表：输入停顿 150 ms 后 `fetch('/api/paths')`（`components/path-complete-client.ts`），列表在卡片内部滚动，点选填入。
- 「检查」是 `<Form method="get">`，把 `?path=` 交给 loader。loader：`admin.paths.check` 规范成 `display`，再
  `gateway.read({ method: 'project.probe', params: { path: display } })`（读白名单只收 `~/…`，网关守卫会再 realpath 一次）。
  守卫或内核的拒绝原文显示在检查结果卡里。
- 检查结果卡（Q-2）显示内核规范后的 `probe.path` 与由 probe 字段推出的事实，不另造「拒绝原因」：
  - `exists: false` →「目录不存在。确认后会创建它，并在里面 git init（默认分支 main）」；
  - `exists` 且非仓库、无成员 →「不是 Git 仓库。确认后会在这里 git init（默认分支 main）」；

## 风险与验证安排

**风险**

- **耦合内核的会话文件布局（§4）。** Onboarding 状态读的是 `SessionPaths` 与包装脚本的约定，内核改了布局就会失灵。由 M-03 的真实内核用例
  （假 CLI 跑完整个会话，断言状态从运行中变为已结束并推送）守住；根治需要内核给 Onboarding 会话写 session 行或结束事件（Backlog B-03）。
- **守卫与内核之间的检查—使用间隙（TOCTOU）。** 守卫 realpath 之后、内核 `create_dir_all` / canonicalize 之前，符号链接可能被换掉。
  这是本机单用户场景；守卫把 realpath 后的绝对路径交给内核，内核也再 canonicalize 一次，窗口只剩毫秒级。记录，不处理。

- **监听受限。** 此前实现轮多次遇到 `listen EPERM`。需要监听的用例集中在 `test/w9-http.test.ts` 一个文件；其余集成测试直接组合
  `CoreSupervisor` + `createGateway` + `createAdmin`，调用路由的 loader / action 函数，不监听端口。
