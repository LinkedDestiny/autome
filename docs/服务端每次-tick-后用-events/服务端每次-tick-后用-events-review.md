## 可提请裁决的问题

### P-01（P1）账本回退后旧游标继续过滤新账本事件

- **类别：内部逻辑矛盾。**
- **追溯：**设计「方案 §3 服务端事件总线」第 132、141–156 行（账本回退、连接过滤、续传情形表）与「方案 §4 浏览器端」第 190–193 行；M-02 的用例⑫、⑰；R-01 的续传及 R-04 的事件驱动重新验证。回退行为由设计明确纳入，并非另加数据恢复需求。
- **根因：**设计只重置总线 `cursor`，未定义账本切换时连接 `sentSeq` 与客户端 `lastSeq` 如何共同切换到新序列；`reload` 在客户端仅触发 loader 重验，不改变去重游标。
- **具体反例：**原账本 `cursor = sentSeq = lastSeq = 100`，替换后 `latest_seq = 10`。按第 132 行，总线改为 `cursor = 10` 并发 `reload`，页面重验一次。随后新账本产生 `seq = 11`，仍被服务端第 144 行的 `seq > sentSeq` 条件过滤。即使实现者自行补上服务端重置，浏览器第 192 行仍会以 `11 <= lastSeq(100)` 丢弃它。结果是后续 11..100 的变化不能触发页面更新。
- **同类范围：**同时检查了在线发现回退与重连时发现回退两条路径。后者也有同一问题：新连接收到 `hello.seq = 10`，客户端仍保留 100 并发 `resume(after:100)`；服务端按第 153 行回 `reload`、设置 `sentSeq = 10`，但客户端仍拒收后续 11..100。仅修复其中一端或其中一路不够。
- **需要裁决的修改：**明确新账本序列的重新建立规则，同时遵守「同一连接 event 严格递增」和现有 `{type:"reload"}` 信封。例如让回退结束旧连接，客户端在该 reload 后放弃旧检查点，并在新连接的 hello 上建立新检查点；具体机制由裁决轮确定。对应检查应观察 reload 之后的新事件确实被接收并触发重验，不能止于观察到 reload。
- **证据性质：**上述是按设计逐步推演的确定反例；未声称不存在的 W3 实现已经发生该故障。

### P-02（P1）用 URL 对象恒等判断纯重验，使按事件筛选路径不可达

- **类别：内部逻辑矛盾。**
- **追溯：**R-04「只刷新受影响的路由」；设计「方案 §4」第 203–205 行明确写出的 `currentUrl === nextUrl`；M-03 `live-routes.test.ts` ①及 M-03 验收契约。
- **根因：**`currentUrl` 与 `nextUrl` 是两个 URL 对象。即便地址相同，严格对象比较也为 false，设计会落入返回 `defaultShouldRevalidate` 的分支，绕过事件匹配器。
- **源码及实测：**本 worktree 安装的 React Router 为 **8.5.1**。`apps/web/node_modules/react-router/dist/development/lib/router/router.js:2065–2066` 分别调用 `history.createURL(state.location)` 与 `history.createURL(location)`。本轮用 `createMemoryRouter` 构造项目父路由、任务子路由和计数 loader，在同地址调用 `router.revalidate()`：两路由均观察到对象比较 false、href 比较 true、默认重验 true。按设计原式执行，项目与任务 loader 各运行 1 次；只将条件改为 href 值比较后，项目运行 0 次、任务运行 1 次。
- **影响：**即使每个路由都导出了 `liveShouldRevalidate`，无关路由仍随任务事件重验；M-03 ①的预期无法按当前写定条件实现。这不是要求增加测试，而是现有验收与设计表达式冲突。
- **同类范围及修改：**核对了 `revalidateForEvents`、`revalidateAll` 和 `liveShouldRevalidate` 的入口，问题集中于共用的纯重验判定。将 URL 对象身份比较改为明确的 URL 值比较，保留原有导航、表单提交回退规则；用现有 M-03 ①核验。
- **原始实验结果：**`.autome/output/review-router-result.json`。这是对已安装框架的独立实验，不是对未来 live 模块的测试通过声明。

### P-03（P1）只替换 NUL 无法得到 M-04 写定的历史 numstat 结果

- **类别：内部逻辑矛盾。**
- **追溯：**R-06、任务范围「write-gate.test.ts 只做两处转义改动」、设计 M-04 说明第 318–319 行及 M-04 验收契约第 341–343 行。契约三行完整；本条不是「验收不够明确」。
- **错误前提：**设计认为新版本去掉 NUL 后，`git diff --numstat 30e5d51 -- apps/web/test/write-gate.test.ts` 就会显示 `2\t2`。但比较的旧版本仍含 NUL，Git 的二进制判定仍生效。
- **独立实测：**从 `git show 30e5d51:apps/web/test/write-gate.test.ts` 读取旧 blob，确认其与当前文件逐字节相同；仅在 `.autome/output/` 的副本里将两个 0x00 替换为源码 `\u0000`。新副本 NUL 数为 0，旧副本为 2。Git **2.53.0** 对这两个准确的旧/新内容执行 `git diff --no-index --numstat`，仍输出 `-\t-`。该路径的 `diff`、`text` 属性均为 unspecified。进一步实测，给 numstat 加 `--text` 也仍是 `-\t-`；普通 `git diff --no-index --text` 补丁则能显示两处文本替换。
- **影响：**严格按限定范围完成 R-06 的实现，也不能满足 M-04 的 numstat 预期。该不成立的前提同样来自任务 R-06，不能靠实现轮继续修改两处字符串来满足。
- **同类范围及修改：**核对了 R-06 与设计 M-04 的修改范围、验收命令、预期和负向对照。裁决轮需显式记录任务验收前提与 Git 行为的冲突，并调整这一判据：保留 NUL 为 0、恰好两处字节替换、运行时字符串不变和原 35 个测试的要求；可用强制文本补丁核对两处修改，同时如实记录相对旧二进制基线的 numstat 仍为 `-\t-`。不要为得到数字偷偷增加 `.gitattributes` 或修改基线，二者均不在授权改动范围。
- **原始实验结果：**`.autome/output/review-nul-result.json`、`.autome/output/review-nul-text-diff.txt`；旧/新内容副本同在 `.autome/output/`。原测试文件未改。
