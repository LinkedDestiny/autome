## 背景与现状

- 会话（尤其 Codex）的沙箱没有网络，装不了依赖；宿主 automed 有网络，但今天从不替任务装依赖。T-14 因 worktree 的 `node_modules` 缺 `ws` 白跑 17 个实现轮。
- 宿主门禁是后台作业（`crates/automed/src/gate.rs`）：`Job::at(repo, task, node, key)` 把 `log/pid/exit/started` 四个文件放在 `.autome/output/gates/<task>/<node>-<key>.*`；`start` 用独立进程组跑 wrapper，`poll` 读 exit 标记、超时杀进程组并记 124、无标记无进程判 `Vanished`；`stop_all` 杀该任务目录下所有存活 pid；`discard_node` 按 `<node>-` 前缀杀并删文件。core 重启后靠这些文件接上。
- 调度器（`scheduler.rs`）：
  - worktree 在 `launch_session`（约 2194–2216 行）里懒建，紧接 `write_task_inputs`（`first_time = !docs_root.exists()`）；会话由 `start_session` 发起，它先做 `cooldown_route`，冷却时用 `store.schedule_retry(task, node, until, inject, reason, false)` 推迟本轮，由每个 tick 的 `start_due_retries` 到点重发（`redispatch_with → start_session`），`recover` 跳过有待重试的任务。
  - `run_gate`（2715 行起）统一处理 Gate / MergeGate / MainCheck / ReproCheck / FixGate：前四者之外的检出是 `layout.cwd`；MainCheck 在 `.worktree/_verify-<sha12>` 现建 detached 检出，跑完删掉，失败只 `raise_alert("main_gate_failed")`，任务照常进 Cleanup。MergeGate 在提交未变时复用上次通过结果（`gate.reused`），不启动作业。
  - 状态机（`autome-domain/src/task.rs`）：`Merging → MainCheck → Cleanup` 只在配了 `[gate]` 时经过 MainCheck，否则 `Merging → Cleanup`。即「合并后」唯一必经的内核节点是 Cleanup。
  - 停止/取消走 `dispatch.rs::stop_running_session`，其中调 `gate::stop_all`。
- 配置：`[gate]` 在 `config_io.rs::parse_project` 解析——不是表报错、缺 `command` 报错、`command` 去空白后为空等于没配（`None`）、`timeout_minutes` 缺省 30（`DEFAULT_GATE_TIMEOUT_MINUTES`）且须为正整数；`save_project` 用 toml_edit，不认识的表原样保留。`ResolvedConfig.gate` 由 `config::resolve` 从项目配置拷贝。`ProjectConfig` / `ResolvedConfig` 在测试里只经 `..Default::default()` 或 `resolve()` 构造，加字段不需要改现有测试。
- 基线测试数（2553923，`cargo test --workspace --all-targets`，全绿）：autome-domain 345、automed lib 606、end_to_end 80、prompt_rendering 16、real_cli 7、autome-cli bin 19、autome-cli tests/cli 11，共 1084。现有测试名里没有含 `setup` 的（`resume_setup` 是辅助函数，不是测试），所以本任务新增测试一律以 `setup` 入名，过滤 `setup` 即得新增数。

## 目标与非目标

目标（范围 1–4、验收 1–6）：

1. 项目 `.autome/config.toml` 可写 `[setup]`（`command`、`watch`、`timeout_minutes`）。
2. 宿主在三类时机、按「准备指纹」判断是否运行准备命令：任务检出的每个会话与门禁作业开始前（覆盖时机 a、b）、合并提交检出（MainCheck 前）、合并后的主检出。
3. 准备走门禁同一套后台作业机制；写 `setup.started` / `setup.result`（及工作区的 `setup.skipped`）事件，`autome run` 打印。
4. 任务检出上的准备失败 → 任务 `Failed`，原因 `FailureReason::Setup { command, exit_code, log }`，不退回实现轮；合并后两处的失败只报项目警报。

非目标：

- 不碰会话沙箱、网络与启动参数；不猜包管理器；不改 `protocol/`（这是内核行为，会话无需配合）；不改本仓库 `.autome/`。
- 不支持工作区项目（见方案 §4.4，给出确定行为）。
- 界面不新增展示；桌面端对未知 `reason.kind` / 警报 `kind` 已有回退显示（`labels.js::failureReason` 的 `default`、`dashboard.js` 的 `ALERT_TITLES[kind] || kind`），不会坏，文案改进进 Backlog B-01。
- 不检测准备命令是否改动了被跟踪文件（见风险 R1）。

## 方案

### 1. 配置 `[setup]`（范围 1）

```toml
[setup]
command = "npm ci --prefix apps/web"
watch = ["apps/web/package-lock.json"]
timeout_minutes = 20   # 可省，缺省 30
```

- 类型：`autome-domain/src/config.rs` 新增 `SetupConfig { command: String, watch: Vec<String>, timeout_minutes: u32 }` 与 `DEFAULT_SETUP_TIMEOUT_MINUTES = 30`；`ProjectConfig.setup: Option<SetupConfig>`（`#[serde(default, skip_serializing_if = "Option::is_none")]`）；`ResolvedConfig.setup` 在 `resolve()` 里照 `gate` 拷贝。项目级，全局配置没有这一节。
- 解析（`config_io.rs::parse_project`，与 `[gate]` 对齐）：
  - `[setup]` 不是表 → 报错「[setup] 不是一个表」；
  - 缺 `command` 或不是字符串 → 报错「[setup] 需要 command，例如 command = "npm ci"」；
  - `command` 去首尾空白后为空 → 等于没配（`setup = None`），此时 `watch`、`timeout_minutes` 不再校验；
  - `watch` 可省（= 空列表）；给了就必须是字符串数组，每项去空白后非空、不以 `/` 开头、不含 `..` 路径段，否则报错「[setup] watch 必须是相对检出根目录的文件路径列表」。校验函数 `setup::valid_watch_path` 放 domain（纯函数）；
  - `timeout_minutes` 可省（= 30），给了必须是正整数，否则报错「[setup] timeout_minutes 必须是正整数」。
- `save_project` 不需要改：toml_edit 原样保留 `[setup]`，用测试锁住（C5）。
- `watch` 为空的语义：指纹只含命令，于是每个检出「第一次」跑一次、命令改了再跑一次，此后不再跑。

### 2. 准备指纹与记录（约束 2）

- **指纹**（`autome-domain/src/setup.rs`，纯函数，domain 已依赖 sha2）：`fingerprint(command, files: &[(&str, Option<&[u8]>)]) -> String`，sha256 十六进制，输入依次为 `command\0<command>\n`，再对 `watch` 去重并按字典序排序后逐项 `<path>\0<sha256(content) | "absent">\n`。读文件在 automed：读不到（不存在、是目录、无权限）一律记 `absent`，不报错。命令也进指纹，改命令即重跑。
- **判定**：`needs_run(record: Option<&str>, current: &str) -> bool`——没有记录或不同就要跑。
- **记录**：一个检出一个文件，内容是指纹全文，原子写（写 `.tmp` 再 rename），**只在准备成功后写**：

| 检出 | 记录文件（均在 `<project>/.autome/output/setup/` 下） |
|---|---|
| 任务 worktree（`layout.cwd`） | `<task>/worktree.fp` |
| 合并提交检出 `.worktree/_verify-<sha12>` | `<task>/verify-<sha12>.fp` |
| 主检出（`project.path`） | `main.fp`（项目级，跨任务共享） |

- 绑定到具体检出：**检出被新建时删除它的记录**——任务 worktree 在懒建处、`_verify` 在 `worktree_add_detached` 处；`_verify` 删除时一并删记录。这样 worktree 被删后重建（同一任务）不会沿用旧记录。`.autome/output/` 被 gitignore，不会进提交；文件在磁盘上，core 重启后仍有效。

### 3. 宿主作业（范围 4、约束 3、4）

- 复用 `gate::Job` / `start` / `poll` / `stop_all` / `discard_node`，作业放在门禁同一目录：`Job::at(repo, task, "setup", "<checkout>")`，即 `.autome/output/gates/<task>/setup-<checkout>.{log,pid,exit,started}`，`<checkout>` ∈ `worktree | verify | main`。**作业按检出命名，不含指纹**：一个任务在一个检出上同一时刻至多一个在途作业，作业的身份是「哪个检出」，不是「当前输入算出的指纹」（D1-P01）。放进任务目录的好处：`stop_all`（停止、取消）原样覆盖准备作业；`discard_node(repo, task, "setup")` 按 `setup-` 前缀只清准备作业、不碰 `gate-*`。
- **启动指纹旁记**：启动前先原子写 `.autome/output/setup/<task>/<checkout>.running`，内容是该作业**启动时**的指纹全文，然后才 `gate::start`。读作业结果时归属以这个文件为准，不以重新计算的当前指纹为准。该文件缺失（启动前崩溃、被清理）→ 作业无法归属，只清作业、不写记录。它不在 `gates/` 下，`discard_node` 不管它；留下的陈旧文件无害——只有作业存在时才读它，启动新作业时覆盖。
- `sh -c <command>` 在检出根目录执行（wrapper 不变），环境变量加 `AUTOME_TASK`、`AUTOME_SETUP_CHECKOUT`。
- 超时：`[setup] timeout_minutes`（缺省 30），`poll` 超时杀进程组记 124，按失败处理。**不改 `gate::poll` 的签名**（D1-P03，现有三处测试调用两参数 `poll`）：`gate.rs` 新增 `poll_as(job, timeout_minutes, what: &str)` 承载全部逻辑，`poll(job, timeout_minutes)` 变成 `poll_as(job, timeout_minutes, "门禁")` 的一行转发，门禁调用处与现有测试原文不动，日志文字不变；准备作业调 `poll_as(.., "准备命令")`，日志写「准备命令运行超过 N 分钟，已终止」。
- `gate.rs` 另加只读函数 `running(job) -> bool`：`.started` 存在、没有有效 `.exit` 标记、且（pid 文件指向存活进程，或还没有 pid 文件且启动不到 10 秒）。与 `poll` 判 `Running` 的条件一致，但不杀进程、不改文件，供主检出互斥（下面）与 L4 使用。`.started` 是 `start` 在 spawn 之前同步写下的，所以「wrapper 还没写出 pid」的空窗里 `running` 也为真（D1-P02）。
- 新模块 `crates/automed/src/setup.rs` 提供一个入口：

  `ensure(ctx, task, project, setup, checkout: Checkout { kind, dir, record }, node) -> Result<Ready>`，`Ready = Ready | Pending | Failed { command, exit_code, log, tail }`

  1. **先收在途作业**：`job.exists()` 时无论当前指纹是什么都先 `poll_as`（用 `[setup] timeout_minutes`）：
     - `Running` → `Pending`；
     - `Vanished` → 清作业，进入第 2 步；
     - `Done{n≠0}`（含超时 124）→ 写 `setup.result{ok:false}`（`fingerprint` 为启动指纹）、不写记录、删 `started/pid/exit` 与 `.running`、返回 `Failed`。输入在运行期间变过也一样：失败归属于已经跑过的那一次，任务失败，用户修好后重跑会按新输入重新准备；
     - `Done{0}` → 写 `setup.result{ok:true}`；若 `.running` 存在，把**其中的启动指纹**写进记录（不是当前指纹——运行期间输入变了，旧作业的成功不能算作新输入的成功）；删 `started/pid/exit` 与 `.running`；然后进入第 2 步用最新输入再判一次。
  2. **没有在途作业**：读 `watch` 算当前指纹；`needs_run` 为假 → `Ready`（不写事件）；为真 → （仅 `main`：若**其它任务**目录下存在 `setup-main` 的 `running(job)` 为真的作业，返回 `Pending`，不并发跑主检出准备）写 `.running`、`gate::start`、写 `setup.started`、返回 `Pending`。若第 1 步刚收了一个成功作业而最新指纹仍不同，这一步直接启动第二次准备，`setup.started.reason` 记「变化」。
  3. **作业得出结论（成功或失败）后删掉它的 `started/pid/exit` 三个标记，只留 `.log`**。否则：失败后重跑会读到旧的失败标记直接再失败；`watch` 改回旧内容时会读到旧的成功标记而不重装。
- tick 只轮询：`ensure` 不等待，最坏是读几个 `watch` 文件与 stat 作业文件。
- 主检出互斥的收尾：互斥只看「别人的 `setup-main` 是否还在跑」，作业一旦结束（有 `.exit`、或进程已死）即不再占用，哪怕它的所属任务还没来得及收结果（例如该任务被暂停）。晚到的收集会把**它自己的启动指纹**写进 `main.fp`；若期间另一任务已在更新的输入上成功并写了记录，被覆盖成旧指纹的后果只是下一次合并多跑一次准备（指纹不等就重跑），不会漏跑。一个被暂停任务的在途主检出准备若超过超时，要等它恢复才会被杀——只阻塞别人的主检出准备，不阻塞其它任何事，恢复或停止即解除。

### 4. 时机与检出（范围 2，回答问题 1、2、3、6）

#### 4.1 任务检出：会话开始前（时机 a，兼回答问题 6）

- 把 `launch_session` 里「懒建 worktree + `write_task_inputs` + Bug 补充信息提交」挪到 `start_session` 中 `cooldown_route` 之后、`carry_decisions` 之前的一个函数 `ensure_checkouts`，然后：若配了 `[setup]`、项目不是工作区、任务处于 `Active { node }`，调 `ensure(worktree)`：
  - `Ready` → 照常 `carry_decisions` 与 `launch_session`；
  - `Pending` → `schedule_retry(task, node, now, inject, "等待准备命令", counted=false)`，返回 `Ok`，不启动会话。这正是冷却推迟本轮的同一条路：下一 tick `start_due_retries` 重发，`recover` 跳过，暂停/停止时 `task.resume_input` 记下 inject；决定（Decisions）因为还没被 carry，不需要释放；
  - `Failed` → `advance(Trigger::SetupFailed {..})`，返回 `Ok`。
- 检查放在**每个**会话开始前，而不只「第一个」。理由：「第一个会话」在 core 重启、任务恢复、worktree 重建后无法可靠判断，唯一可靠的判据是记录（问题 6 的建议）；而按记录判断，第一个会话之后只要 `watch` 没变就不会再跑，结果与「只在第一次跑」相同，但多覆盖了一种情况——没有 `[gate]` 时会话改了 lock，下一个会话之前也会补装。
- 不在 `Active` 的会话（失败/停止后手动发起的复盘）不做准备：它只写文档，且没有可推迟的节点。

#### 4.2 门禁前（时机 b，回答问题 1）

在 `run_gate` 中「作业不存在、且未走 `gate.reused` 复用」之后、`gate::start` 之前调 `ensure`；`Pending` → 返回（下一 tick 再进来）；`Failed` → 见 §6。逐一覆盖：

| 门禁节点 | 所在 Loop | 判断哪个检出 | 准备失败时 |
|---|---|---|---|
| Gate | 需求 | 任务 worktree | 任务 Failed（at Gate） |
| MergeGate | 需求、Bug | 任务 worktree（rebase 后） | 任务 Failed（at MergeGate） |
| ReproCheck | Bug | 任务 worktree | 任务 Failed（at ReproCheck） |
| FixGate | Bug | 任务 worktree | 任务 Failed（at FixGate） |
| MainCheck | 需求、Bug | `_verify-<sha12>` 合并提交检出 | 项目警报，MainCheck 跳过 |

- MergeGate 复用路径不做准备：复用的前提是提交与上次通过的门禁相同，那时 `watch` 内容也相同，记录必然匹配。
- 门禁「提交在运行中变了就作废」的判断不受影响：准备期间没有会话在跑。

#### 4.3 合并提交检出 `_verify`（回答问题 2）

- `_verify` 每次现建，没有 `node_modules`；配了 `[setup]` 的项目，其门禁命令正是依赖这些准备才跑得起来——在没准备的检出上跑，MainCheck 会对一个没问题的 main 报警。这是 MainCheck 不误报的必要条件，所以纳入：`_verify` 新建时删它的记录，于是每次 MainCheck 前都会准备一次。
- 本仓库的 `scripts/ci-local.sh` 在 `node_modules` 缺失时会自己 `npm ci`，所以今天的 MainCheck 没误报（`.autome/output/gates/T-14,T-17,T-18,T-20,T-21/main_check-*.exit` 均为 0）；但这是本仓库门禁脚本的特性，不是一般项目的。T-14 的失败恰恰出在 `node_modules` 存在但过期——这种情况 `ci-local.sh` 的「缺失才装」判断不了。
- 与「主检出判断一次」的关系：两件不同的事。`_verify` 是给 MainCheck 跑门禁用的临时检出，主检出是用户自己工作的目录；各自一份记录，互不替代。

#### 4.4 合并后的主检出（时机 c）

- 放在 **Cleanup 节点的前置子阶段**：`run_core_step(Cleanup)` 先（配了 `[setup]` 且非工作区时）`ensure(main)`；`Pending` → 返回、不推进（Cleanup 与门禁节点一样跨 tick）；`Failed` → 报警（§6）后继续；`Ready` → 照旧 `cleanup()`。
- 为什么是 Cleanup：它是合并后唯一必经的内核节点——MainCheck 只在配了 `[gate]` 时存在，而 `[setup]` 不以 `[gate]` 为前提。Merging 不行：`merge_all` 再次进入时会以 `last_commit = None` 改写合并提交。
- 跨任务：`main.fp` 是项目级记录，每个合并了的任务到 Cleanup 都判断一次。主检出第一次（没有记录）会跑——启用 `[setup]` 时主检出的依赖状态未知，跑一次比假定它是新的安全。两个任务先后到 Cleanup 时，后者在前者的 `setup-main` 作业 `running` 期间（含 wrapper 尚未写出 pid 的启动空窗）等待（§3 第 2 步），前者收到成功、写了 `main.fp` 后，后者重新算指纹，相同就不跑。

#### 4.5 工作区项目（回答问题 3）

只支持单仓库。工作区项目（`project.is_workspace()`）配了 `[setup]` 时：三个时机全部不跑，每个任务第一次遇到时写一条 `setup.skipped { reason: "工作区项目不支持准备命令" }`（以 `count_events(task, "setup.skipped") == 0` 去重），任务其余行为与没配完全相同。不在解析时拒绝：解析不知道项目是不是工作区，同一份配置文件也可能被单仓项目复用。

### 5. 在 Loop 状态机里的表示（回答问题 4、约束 5）

- **不新增节点**。准备是调度器在「启动会话 / 启动门禁作业 / 执行 Cleanup」之前的前置步骤；它在等待时任务仍停在原节点（会话节点靠待重试记录、门禁与 Cleanup 靠 tick 重入）。新增节点会改 `Node::ALL`、界面节点图与大量穷举测试，违背约束 1 与范围 4 的界面边界。
- domain 改动（纯类型与迁移）：
  - `FailureReason::Setup { command: String, exit_code: i32, log: String }`（serde `kind: "setup"`）；
  - `Trigger::SetupFailed { command, exit_code, log }`：在 `apply_inner` 顶部的控制触发器段处理（这样 Bug 节点也走得到，`bug_loop::apply_for` 的兜底分支会转发到这里）——`Active { node }` 且 `!node.awaits_user()` → `Transition::fail(node, FailureReason::Setup{..})`；其它状态拒绝；
  - `autome_domain::setup`：`fingerprint`、`needs_run`、`valid_watch_path`、`Checkout { Worktree, Verify, Main }`（`as_str`）。
- automed：`setup.rs`（§3）；`scheduler.rs` 三处调用点与 `trigger_name` 加 `setup_failed`；`dispatch.rs::stop_running_session` 加一行 `discard_node(repo, task, "setup")`；所有对 `FailureReason` 的穷举 `match` 补新变体。autome-cli：`render.rs` 加三种事件的打印。

### 6. 失败语义（范围 3）

- **任务检出**（会话前、Gate/MergeGate/ReproCheck/FixGate 前）：`Trigger::SetupFailed` → `Failed { at: 当前节点, reason: Setup { command, exit_code, log } }`。不进 `Inject::GateFailed`、不退回实现轮，不消耗实现预算，也不启动门禁作业（没有 `gate.started`）。用户修好环境后从失败面板「从某节点重跑」：因为失败作业的标记已删、记录没写，重跑会重新准备。
- **合并提交检出 `_verify`**：`raise_alert(project, "setup_failed", task, detail)` 并写 `project.alert`；删 `_verify`；写 `gate.skipped { node: "main_check", reason: "准备命令失败" }`；按现有 MainCheck 结束方式进 Cleanup。
- **主检出**：`raise_alert("setup_failed")` + `project.alert`，`main.fp` 不更新（下次合并会重试），继续 `cleanup()`，任务 `Done`。
- 与 MainCheck 对齐的理由：合并已发生、不能撤回，把任务标成失败既不准确（任务的产物已经在 main 上）也无从补救（重跑任何节点都不会再合并）；项目警报正是「main 上出了需要人处理的事」的现有通道，用户可在仪表盘看到并忽略。
- 警报 detail：`任务 T-x 合并后，在<主检出|合并提交检出>里准备命令 `<command>` 失败（退出码 n）。日志：<log>\n\n<tail>`。

### 7. 暂停、停止、取消、重跑、重启（回答问题 5）

- **暂停**：会话节点上等准备 = 冷却推迟同一形态，`Pause` 立即生效、作业继续在后台跑；恢复后经 `Reenter → redispatch_with → start_session → ensure` 收结果。门禁节点 / Cleanup 上暂停：恢复后 `run_gate` / `run_core_step` 重入，收同一个作业（同 `paused_gate_resumes_at_gate_without_restarting_job`）。
- **停止 / 取消**：`stop_running_session` 已有 `gate::stop_all`（杀进程组），再加 `discard_node(repo, task, "setup")` 删掉准备作业文件。恢复后重新准备，不会读到被杀那次留下的标记。
- **从某节点重跑**：同上，标记已删、记录未写 → 重新准备。
- **core 重启**：作业是独立进程组，文件都在；会话节点有待重试记录 → `recover` 跳过、tick 重发后 `poll` 接上；门禁 / Cleanup → tick 重入接上。不会重新启动一个已经在跑的准备。

### 8. 事件与 `autome run`（范围 4）

| 事件 | 字段 | `autome run` 打印 |
|---|---|---|
| `setup.started` | `checkout, node, command, fingerprint(12 位), reason("首次"/"变化"), log` | `T-x 准备命令开始（任务检出）：npm ci …` |
| `setup.result` | `checkout, node, ok, exit_code, command, fingerprint, log, tail` | `T-x 准备命令通过（任务检出，退出码 0）  日志：…` / `未通过` |
| `setup.skipped` | `reason` | `T-x 准备命令跳过：工作区项目不支持准备命令` |

检出标签：`worktree` 任务检出、`verify` 合并提交检出、`main` 主检出。事件都写在任务名下（主检出那次写在触发它的任务名下）。日志路径同时出现在 `setup.started`、`setup.result`、`FailureReason::Setup.log` 与警报 detail 里（约束 3）。

### 9. 没配 `[setup]` 时零差异（验收 1、范围「不做」第 2 条）

三个调用点都以 `resolved.setup.is_some()` 为第一个判断；为 `None` 时不读文件、不写事件、不排待重试、不进新分支，Cleanup 同步完成如旧。`ensure_checkouts` 的挪动只改调用位置，不改它做的事，现有用例覆盖它（e2e 全部启动会话的用例）。E5 在一个配了 `[gate]`、跑到 `Done` 的任务上断言没有任何 `setup.*` 事件。

### 10. 否决的做法

- **新增 `Setup` 节点**：改 `Node::ALL`、界面节点图、穷举测试，违背约束 1；且准备要在多个节点之前发生，一个节点表达不了。
- **把哈希记在 SQLite 事件里**：`last_event` 按任务取最后一条、不按检出过滤，主检出又是跨任务的；用文件更直接，且「检出新建时删记录」只需删一个文件。
- **准备失败当门禁失败退回实现轮**：任务明确禁止（会话修不了环境），T-14 正是这样白跑的。
- **主检出准备放进 MainCheck**：没配 `[gate]` 就没有 MainCheck。
- **在 `_verify` 里不准备**：见 §4.3。

## 风险与验证安排

- R1 准备命令改动被跟踪文件（例如 `npm install` 改写 lock）：任务 worktree 里会被会话的扫尾提交带进分支；主检出会变脏，下一次合并被「主工作树不干净」挡住。缓解：README 明示用不改 lock 的命令（`npm ci`），并写清这一后果；不做检测（进 Backlog B-03）。
- R2 主检出上的准备与用户自己的进程（dev server）竞争 `node_modules`：这是任务要求的行为；失败只报警，不影响已合并的结果。
- R3 两个任务同时到 Cleanup：§3 第 2 步以 `running(job)`（`.started` 起算，不依赖 pid 文件）判断别人的 `setup-main` 在跑，覆盖启动空窗，使它们串行；L4（M-02）锁住 `running` 的三种状态，M-04 的 L3 锁住等待行为。
- R3b 准备运行期间 `watch` 内容变了（命令自己改写 lock，或别的任务合并改变主检出）：作业按检出而非指纹识别，先收在途作业、超时与失败照常处理，成功只记启动指纹，然后按最新输入再判（§3 第 1 步）；E14、E15 锁住。
- R4 等准备时任务占着并行槽：与门禁相同，接受。
- R5 借用待重试表做等待：与冷却推迟同一形态，已有暂停/恢复/重启的处理；M-02 的 E3、E4 实测停止与重启。
- R6 本仓库自己的门禁也会受益，但本任务不改 `.autome/config.toml`（验收 6），由用户在合并后自行配置；M-04 的验收命令核对该文件与基线一致。
- 验证安排：每个里程碑的验收命令都跑整个受影响 crate（不只过滤新用例），报总数与基线差；e2e 用真实 git worktree、真实 wrapper、真实 `sh -c`，只替换模型 CLI（约束 6），准备命令是写在仓库外的 shell 脚本：把 `$PWD` 与被监视文件内容追加到 `<sandbox>/setup-runs`，在检出里写被 gitignore 的 `deps/stamp`，按需以指定退出码失败或 `sleep`。最后一个里程碑跑 `sh scripts/ci-local.sh`（fmt、clippy、全部 Rust 测试、desktop、web）。

验收与里程碑的对应：验收 1 → 全部里程碑（每个都跑整 crate）与 M-02 的 E5、M-04 的 ci-local；验收 2 → M-02 E1；验收 3 → M-03 E6；验收 4 → M-02 E2、M-03 E7；验收 5 → M-04 E11；验收 6 → M-04。约束 5 → M-01；约束 6 → M-02、M-03、M-04；约束 7 → M-04。
