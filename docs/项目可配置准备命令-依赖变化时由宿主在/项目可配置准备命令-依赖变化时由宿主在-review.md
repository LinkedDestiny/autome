## 六类问题内的评审意见

### R1-P01（P1）：按每次重新计算的指纹定位作业，会丢失仍在运行的旧作业，超时和结果收集失效

- **类别**：内部逻辑矛盾。
- **违反要求**：任务 §3.3（准备失败／超时须进入确定的失败处理）、§3.4（复用后台作业、超时、重启接续）、§5 约束 4（超时按 124 处理）；设计方案 §3 的 `ensure` 步骤、§6 失败语义、§7 重启接续。
- **设计位置**：方案 §3（设计第 80–90 行）以 `<checkout>-<fp12>` 命名作业，每次 `ensure` 先读取当前文件算指纹，再决定该作业是否存在；仅对找到的作业调用 `poll`。方案 §4.4 / 风险 R3 只对准备作业互斥，没有阻止另一任务合并。风险 R1 又明确允许准备命令改写 lock。
- **具体反例**：
  1. 主检出指纹为 A，准备作业 `setup-main-A` 已启动，超时设为 1 分钟。
  2. 准备命令改写被 watch 的 lock 后长时间挂起；这是风险 R1 明确接受的命令行为。即使使用不改 lock 的命令，另一任务合并改变主检出 lock 也能产生同样的变化。
  3. 下一 tick 算出指纹 B，找不到 `setup-main-B`，扫描到仍存活的 `setup-main-A.pid`，返回 `Pending`。
  4. 后续 tick 都重复第 3 步，从不 `poll(setup-main-A)`；超过 1 分钟也不会杀进程、记录 124 或报警，任务一直停在 Cleanup。
  5. 若 A 自己以非零码退出，wrapper 删除 PID 后，流程会启动 B，A 的失败结果没有被收集，缺失对应的 `setup.result` 与项目报警。
- **源码证据**：`crates/automed/src/gate.rs:144–179` 的超时由调用 `poll` 执行，并非 wrapper 自带计时器；`gate.rs:35–49` 的 wrapper 只执行命令并写退出标记。`scheduler.rs:3003–3078` 的合并路径没有等待准备作业的步骤，设计也未安排此处变更。
- **根因与检查范围**：把「当前输入的指纹」同时当作「在途作业的身份」。检查范围包括 worktree、verify、main 三种检出及重启后的恢复。主检出会发生上述无限等待；worktree / verify 没有 main 的 PID 互斥，会在指纹变化后另启作业，使旧作业脱离轮询。
- **建议裁决落点**：先按检出识别并接续已有在途作业，使用其启动时的指纹收集结果和执行超时，再判断最新输入是否需要下一次准备。设计应明确输入中途变化时的结果归属，不能把旧作业成功登记为新指纹成功。可用「作业启动后改变 watch，旧作业继续挂起／失败」反例核对该规则。

### R1-P02（P1）：存活 PID 扫描存在启动空窗，不能实现设计承诺的主检出准备串行

- **类别**：关键事实错误。
- **违反要求**：设计方案 §3 步骤 2 的「不并发跑主检出准备」、§4.4 跨任务串行、风险 R3；任务 §5 约束 2 的成功准备记录语义依赖这些作业在同一检出上正确执行。
- **设计位置**：方案 §3 第 88 行只扫描 `setup-main-*.pid`；风险 R3 第 185 行据此断言两个任务会串行；M-04 的 L3 只提供一个已经存在的存活 PID。
- **具体反例**：
  1. 同一项目的任务 A、B 都到 Cleanup，主检出没有成功记录。
  2. tick 先处理 A：`gate::start` 写 `.started`、spawn wrapper 后返回；此刻子进程尚未得到调度，没有写 `.pid`。
  3. 同一个 tick 处理 B：扫描不到 A 的存活 PID，于是也 spawn 准备作业。
  4. 两个 wrapper 随后同时执行，例如两个 `npm ci` 同时删除、安装同一个 `node_modules`。可能导致其中一个失败，或者刚成功的安装被另一个作业破坏。
- **源码证据**：`crates/automed/src/gate.rs:111–139` 在宿主写 `.started` 后直接 spawn 并返回；PID 写入在 wrapper 第 35 行。`gate.rs:181–184` 特意将「刚启动、尚无 PID」视为 Running，说明现有作业机制本就承认这个窗口。`scheduler.rs:200–208` 在一次 tick 中顺序处理所有内核节点；驱动锁只串行化宿主调用，无法保证子进程在下一个任务被处理之前已经写出 PID。
- **根因与检查范围**：把异步产生的 PID 当作唯一占用凭据。检查范围为同项目不同任务的 main 准备，包括刚启动、运行中、退出但尚未收集的阶段。当前 L3 能证明「PID 已存在时会等待」，不能反驳上述真实启动顺序。
- **建议裁决落点**：沿用现有作业机制，将宿主同步建立的在途作业记录（包括 `.started` 已存在而 PID 尚未出现的阶段）纳入主检出占用判定，明确收集或清除的时机。无需引入新节点；应确保下一任务在 wrapper 尚未写 PID 时也等待。本条修复启动互斥，R1-P01 修复指纹变化后的接续，二者不可互相替代。

### R1-P03（P2）：直接给 `gate::poll` 增加必填参数，与现有测试一字不改的硬约束冲突

- **类别**：违反任务目标。
- **违反要求**：任务 §4 第 2 条、§5 约束 1、§6 验收 1（未配置 setup 时所有现有测试不改照常通过）；设计方案 §9 也承诺零差异。
- **设计位置**：方案 §3 第 82 行要求 `gate::poll` 新增 `what: &str` 参数；M-02 的 L1 明确调用三参数 `poll(job, 0, "准备命令")`，同时 M-02 要求完整 automed lib 测试通过。
- **源码证据与反例**：`crates/automed/src/gate.rs:341` 的现有测试辅助函数、`:450` 的现有超时测试、`:465` 的现有消失作业测试都调用两参数 `poll`。按设计直接改成三参数函数后，保留这些测试就无法编译；修改这些测试又违反任务的明确边界。这与是否配置 `[setup]` 无关。
- **根因与检查范围**：为新增日志标签改变既有函数调用契约。已检索 `gate.rs` 中全部 `poll` 调用，并核对生产调用处；上述三个测试调用点属于同一根因。
- **建议裁决落点**：保留两参数 `poll` 入口和既有门禁文案，准备作业通过最小内部复用入口传标签；或者取消非必要的日志用词差异。同步调整 M-02 的新增用例调用描述，保留现有测试原文。
