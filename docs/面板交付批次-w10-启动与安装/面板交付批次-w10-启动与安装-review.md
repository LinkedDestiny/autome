## 问题

### R1-P01：发布入口没有固定生产模式，会走到已从包中移除的 Vite

- **类别：内部逻辑矛盾。**
- **违反要求：** A-5「空 PREFIX、空 AUTOME_HOME，从 tar 安装到打开面板走通」、C-5「打包后的 .app 能启动并显示面板」；对应 M-03 的 install-alignment 第 2 条和 M-08 的打包冒烟第 1 条。
- **设计位置：** A1 第 91–92 行、A2 第 118–123 行、A5 第 187–190 行、A7 第 203–205 行、C1 第 397–400 行，以及 M-03 第 755–758 行。
- **证据与根因：** A5 明确规定 `serve → runFromEnv → startServer`。现有 `apps/web/server/main.ts:80` 只有在 `NODE_ENV === 'production'` 时才选生产模式，否则选开发模式；`apps/web/server/http.ts:75–76` 随即导入 `vite`。目前 `apps/web/package.json` 的 `start` 脚本设置了这个变量，但新启动链绕过它。设计的打包契约同时明确不带 `vite`，上述启动参数和环境清单均未补上生产模式。设计 E1 第 28 行的成功实验则显式带了 `NODE_ENV=production`，其前提不能直接外推到新入口。
- **具体反例：** 用户在没有设置 `NODE_ENV` 的正常终端安装精简 tar 包，再运行 `autome web`。依设计给出的调用链，服务进入 development 并尝试加载包中不存在的 Vite，无法打开面板。launchd 与薄壳起服务也有相同问题。
- **检查范围：** CLI 默认/open/start 派生的 serve、launchd 直接 serve、Electron 派生的 serve；三种路径均需一致处理。
- **最小修正：** 明确发布启动器的 `serve` 固定使用生产模式，并规定传给 `runFromEnv`/`startServer` 的方式。M-03 安装用例和 C 的冒烟在未设置外部 `NODE_ENV` 时验证启动成功。此处需要补的是启动行为，不是额外扩大测试范围。

### R1-P02：单实例互斥没有覆盖直接 serve 的创建与登记

- **类别：违反任务目标。**
- **违反要求：** A-2「重复执行时不起第二个服务」，以及 C-4 对已有服务的复用；设计 A5 自身声称可挡住 launchd 与手工同时启动。
- **设计位置：** A5 第 181–189 行；直接入口包括 A7 第 203 行、C1 第 397–400 行。关联 M-01 web-launcher 第 3 条与 M-02 web-service 第 7 条。
- **证据与根因：** 设计让启动器持 `launch.lock` 后检查并派生服务，而 `serve` 只在写入前再检查一次活实例。launchd 直接进入 `serve`，没有约定它与手工启动共用同一个覆盖「判定—监听—登记」的临界区。再次检查不是互斥操作。
- **具体交错：**
  1. 手工 start 持锁，派生 S1；launchd 同时直接启动 S2。
  2. S1、S2 都在尚无 `server.json` 时通过写入前检查。
  3. S1 监听默认端口，S2 按自动换端口规则监听下一端口。
  4. 两者先后写 `server.json`，后写者覆盖前者；两个服务和内核仍同时存活，文件只登记其中一个。
- **同类位置：** 锁文件「超过 60 秒即接管」也不能在持有者仍活着时保证互斥；迟到的持有者可恢复执行。该问题与所有直接 serve 入口一并处理。
- **最小修正：** 选定唯一持锁层，让 start/open、launchd、薄壳的所有服务创建经过同一互斥流程；明确父启动器与 serve 的锁移交及释放所有权，不能让持锁父进程等待同锁子进程。活持有者不能仅因锁年龄被并发接管。现有并发验收应包含一个直接 serve 与一个 start 的交错。

### R1-P03：薄壳退出时可能停止它没有创建的继任服务

- **类别：内部逻辑矛盾。**
- **违反条款：** 设计 C4 第 435–438 行「连上的是别人起的服务，不停；自己起的执行 stop」；A5 的实例 UUID 身份约定；对应 M-07 shell-main 第 3–5 条的服务归属行为。
- **设计位置：** C4 第 431–438 行、A8 第 233–246 行。
- **证据与根因：** C4 只以启动时返回的 `reused` 区分归属，退出时调用普通 `stop --wait 0`。A8 的 stop 会读取当时的 `server.json`，确认它指向一个真实实例后停止该实例；这能证明目标是当前服务，却不能证明它是这个 App 最初创建的服务。
- **具体交错：** App 创建 S1，得到 `reused:false`；用户用 CLI 停掉 S1，又启动 S2；随后退出旧 App。退出逻辑仍认为「自己起的」，普通 stop 读取并验证 S2 的文件，最终停止用户后来启动的 S2。此时 S2 的 pid 和 instance 全部合法，A5 的陈旧文件校验不会阻止误停。
- **检查范围：** C4 的退出路径、A8 的停止与超时清理。A8「超时就 SIGKILL 并删文件」也应绑定原 instance，避免清掉停止过程中出现的继任服务记录。
- **最小修正：** App 保存创建时的 instance；退出时只有当前实例仍与它相同才停止，否则保留新服务。停止命令的信号目标及文件清理同样绑定该次操作确认的实例，不能只依赖过时的 `reused:false`。

## 非阻塞建议

以下不单独触发复审，由裁决轮决定是否调整正文或纳入 Backlog。

- **N-01 薄壳启动调用链表述统一。** C1 第 397–400 行写主进程 spawn serve，C4 第 431–434 行写主进程执行 `start --json`，M-07 第 863–864 行又要求复用时「不 spawn」。明确这里是在观察服务进程还是一次性启动器进程，并按最终调用链统一替身断言。两者可以通过封装层协调，暂不认定必然不可实现。
- **N-02 干净检出的 .app 构建前置。** A2 要求 stage-panel 之前已有 Web 的 npm ci/build；C2 只列出 stage-web。现有 `.github/workflows/ci.yml:118–124` 在独立 package job 中直接执行 `scripts/package.sh`，不会继承 web job 的产物。实现时在 package.sh 或该 job 的 stage-web 之前补齐 Web 安装与构建，避免仅在已有 build 的 worktree 成功。这是已授权打包范围内的依赖补全，不以说明不够完整要求复审。
- **N-03 校正两处验收文案。** M-05 第 819–820 行列出四种日期情形、两个时区，却计 6 条；M-04 第 804 行声称取消默认完成数上限会使 `done=all` 的第 2 条失败，但 B1 已约定该查询返回全部。实现前统一计数与实际对应的负向用例即可，不据此判验收不明确。
- **N-04 通知导航校验最终 origin。** C3 的站内路径要求应落实为解析后与面板同源，不能只做 `startsWith('/')`：`//example.com/x` 和 `/\example.com/x` 都可能解析到外站。若主进程使用 `loadURL`，Electron 的 `will-navigate` 不拦截该调用（[Electron 43.2.0 官方文档](https://raw.githubusercontent.com/electron/electron/v43.2.0/docs/api/web-contents.md)）。设计未定具体导航调用，故不把这个条件性风险当作已成立的漏洞或阻塞。
