## 问题

### R2-P01：健康检查超时被等同于实例消失，启动锁不能保护已经运行的服务

- **类别：违反任务目标。**
- **违反要求：** 任务 A-2「重复执行时不起第二个服务，而是打开已有的那个」；关联 C-4 复用已有服务。对应设计 A5「陈旧判定」「竞争」，M-01 的 web-instance 第 4 条与 web-launcher 第 2、3、8 条所覆盖的实例识别、单实例行为。
- **设计位置：** 设计第 168–173 行要求 PID 存活、两秒内健康响应、身份匹配同时成立，否则「当作没有实例，下次启动时覆盖」；第 191–198 行的启动锁在写完登记后立即释放，link 登记失败时仍按同一陈旧判定删旧文件重试。
- **根因：** 「已确认退出或身份不符」与「无法及时确认健康」被合并成同一种可接管状态。持锁期间的互斥只排斥其它启动者，不能排斥已完成启动、已经释放锁的旧服务。link 的防覆盖也会被“健康超时即陈旧”的删除分支绕过。
- **具体反例（设计交错推演，非已实现启动器的实跑结果）：**
  1. S1 启动完成，监听端口 P，写入自己的 pid/instance，释放 launch.lock，持续运行。
  2. S1 暂时无法处理 HTTP，例如在测试中仅暂停本测试创建的服务进程；PID 仍存活，监听端口仍占用。让暂停覆盖本次启动及登记时的健康检查。
  3. 用户再次执行 start。两秒内没有健康回包，按 A5 判“没有实例”。新 S2 取得空闲的启动锁；锁的活持有者保护不起作用，因为 S1 早已释放锁。
  4. S2 发现 P 被占用，自动换端口 Q。登记时旧 server.json 导致 link 返回 EEXIST；再次健康检查仍超时，按设计删掉旧文件并登记 S2。
  5. S1 恢复响应。S1、S2 和各自的内核都仍存活，server.json 只指向 S2；后续 status/stop 无法经登记找到 S1。A-2 已被破坏，整个过程不要求两个启动者同时进入临界区。
- **检查范围：** start/open/无参数、直接 serve（含 launchd）、薄壳 start --json 共用的判活与登记流程；A8 stop 对同一超时结果清理“过期文件”的分支也要保留未知状态，避免抹掉仍活服务的登记。
- **与 D1-P02 的关系及新证据：** 上轮指出的是两个初次启动者绕过共同互斥和按锁年龄接管，裁决已补唯一 serve 锁、禁止按龄接管活持有者。本轮核对该修正仍在，认可它解决了原交错；这里是 **S1 已完成启动并释放锁之后** 的健康超时接管交错，修正后的协议仍允许它。不重复要求上轮的锁层调整，也不以无新证据的同一主张复提。
- **最小修正：** 陈旧判定区分“确认可接管”与“PID 存活但健康/身份暂无法确认”。后一种状态保留登记、提示服务无响应并拒绝另起服务；只有确认原实例结束或取得足以证明登记失效的证据后才允许接管。统一用于首次判定与 link 失败后的重试。M-01 用自己创建的实例暂时不响应、随后恢复的反例验证服务数量仍为 1；恢复前不得覆盖登记，恢复后再次启动应复用 S1。该建议验证的是已成立的 A-2 反例，不是以测试数量不足要求复审。
