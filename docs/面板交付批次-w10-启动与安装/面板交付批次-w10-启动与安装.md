## 方案

### A（W10）启动与安装

**A1 分工。** 结论：Rust 只做定位与转发，其余都在 Node 里。

- `autome web …` 在 `main()` 开头单独分发，与 `core` 同一位置，新文件 `crates/autome-cli/src/web.rs`。
  - 不经过 `Args::parse`，`argv[1..]` 原样转发，`--force`、`-x` 都不被 CLI 解析。
  - 不打开账本。
  - 它找到 Node 和面板目录，设好 `AUTOME_BUNDLED_CORE=<自身 current_exe>`，然后用 `CommandExt::exec` 换成
    `node <面板>/bin/autome-web.js <参数…>`。信号与退出码由 Node 进程直接承担。
- 找 Node：`AUTOME_NODE`，再找 PATH 上的 `node`。都没有时打印
  「没有找到 Node.js（面板需要 22.22 或更高版本）。安装：`brew install node`，或从 https://nodejs.org 下载。」，退出码 1。
- 版本是否够用不在 Rust 里判断。`bin/autome-web.js` 是纯 JS，第一行沿用 `server/node-version.js`，Node 太旧时以现有中文
  提示退出（A4）。
- 找面板目录：依次试 `AUTOME_WEB_ROOT`、`<exe 目录>/web`（解开的 tar 包）、`<exe 目录>/../lib/autome/web`（安装后）、
  `<exe 目录>/../../apps/web`（检出里的 `target/<profile>/autome`）。取第一个含 `bin/autome-web.js` 的目录。
  都没有时打印「没有找到面板：只装了命令行。装好 Node ≥ 22.22 后重新运行 install-cli.sh」，退出码 1。
- USAGE「其他」组加一行
  `web [start|stop [--force]|status|open|service install|uninstall]  在浏览器里打开面板`。

**启动器**：`apps/web/bin/autome-web.js` 先检查版本，再加载 `server/launcher.ts`。逻辑分在几个文件里：
`server/instance.ts`（server.json 与实例身份）、`server/launcher.ts`（子命令）、`server/service.ts`（launchd）、
`server/login-path.ts`、`server/opener.ts`。它们都在 typecheck / lint 覆盖之内。

| 子命令 | 语义 |
|---|---|
| （无） / `open` | 确保服务在跑（没有就后台起一个），然后用打开器打开它的地址（A-1、A-2） |
| `start` | 确保服务在跑，打印地址，不打开浏览器 |
| `serve` | 前台运行服务并写 `server.json`，**固定生产模式**（见 A5「生产模式」）。launchd、薄壳与 `start` 创建服务都只经它，互斥也只在它里面（A5「竞争」）；已有活实例时打印「已有面板在运行：<地址>」并以 0 退出，launchd 不会因此反复重启 |
| `status [--json]` | 见 A8 |
| `stop [--force] [--wait 秒]` | 见 A8 |
| `service install\|uninstall` | 见 A7 |

**A2 发布包与安装布局。**

- 新脚本 `apps/web/scripts/stage-panel.ts <out>`（按 E1 实测的清单）复制以下内容到 `<out>`：
  - `build/`、`server/`、`bin/`、`app/load-context.ts`、`package.json`；
  - lock 里非 dev、非 devOptional 的包（`fs.cpSync`，不联网）。

  它用的是 `apps/web/node_modules` 里已装的包，所以必须在 `npm ci` 与 `npm run build` 之后运行。缺 `build/server/index.js`
  时报「先 npm run build」。
- `package-cli.sh`：
  - 新增 `--web <已暂存的面板目录>`，原样复制成包内的 `web/`。
  - 不带 `--binary` 时是发布模式：`cargo build --release`，再 `npm ci && npm run build && node scripts/stage-panel.ts`。
  - 带 `--binary` 时必须同时给 `--web`，否则报「--binary 需要配合 --web」。这一模式只用 `cp`、`tar`、`shasum`，
    「`--binary` 不触发构建」继续成立，PATH 里没有 cargo / node / npm 也能跑。
  - 包内结构是 `autome-<版本>-<架构>/{autome, README.md, web/}`。
- `install-cli.sh`：
  - `unpack` 改为取 `<解包目录>/*/autome` 这一确切路径（`web/` 里文件很多，不再用 `find` 按名字找）。
  - 命令行照旧装到 `$PREFIX/autome`。
  - 面板装到 `$(dirname "$PREFIX")/lib/autome/web`：PREFIX 缺省为 `~/.local/bin` 时，即 `~/.local/lib/autome/web`。
    做法沿用「写新再换」：`web.new.$$` 写好后，旧目录先 `mv` 成 `web.old.$$`，再把新目录 `mv` 进来，最后删旧的。
  - Rust 那边按 `<exe 目录>/../lib/autome/web` 找它，所以 PREFIX 叫什么名字都对得上。
- 体积：包约 9 MB（E1 实测 8.3 MB + 二进制）。

**A4 没有 Node ≥ 22.22 时。**

**A5 端口与 `server.json`。**

- **谁写、何时写。** 只有 `serve` 写：`startServer` 新增选项 `instanceFile`，在 listen 成功、内核身份已知之后写入。
  `npm start`、`npm run dev` 与全部现有测试都不写，开发者起的服务不会去抢用户面板的位置。
- **位置。** `$AUTOME_HOME/web/server.json`，权限 0600。
- **内容。** 单行 JSON，含 `port`、`pid`、`instance`（随机 UUID）、`url`、`started_at`、`web_root`、
  `kernel{path, source, build_id}`。内核身份放进来，`status` 在服务没响应时也能说清是哪个内核。
- **原子性与清理。**
  - 先写 `server.json.<pid>.tmp`，再用 `link()` 排他登记（目标已存在即 `EEXIST`，见「竞争」），最后删 tmp；不用 `rename` 覆盖。
  - `close()` 只删 `instance` 等于自己的文件；崩溃后留下的文件由下面的陈旧判定处理。
- **实例判定：三态。** 对一份 `server.json`，判定函数（`instance.ts` 的 `judgeInstance`）返回三种结果之一，所有读者
  （`start` / 无参数 / `open`、`serve` 的临界区、`link()` 失败后的重试、`status`、`stop`）共用它：
  - **活（live）**：`pid` 存活，`GET http://127.0.0.1:<port>/healthz` 在 2 秒内回 `ok: true`，且回包的 `instance` 与 `pid` 都与文件一致。
  - **陈旧（stale）**：有**确认失效的证据**，下列任一条：
    1. `pid` 已不存在（`process.kill(pid, 0)` 报 `ESRCH`）；
    2. 端口没有任何监听者（连接被拒，`ECONNREFUSED`）；
    3. 有回包但不是 `ok: true`，或 `instance` / `pid` 与文件不符（端口换了主人）；
    4. `pid` 存活、端口连得上却不应答，但该进程的命令行（`ps -o command= -p <pid>`）里没有 `autome-web`（pid 被别的进程复用；
       `ps` 读不到时不算这条证据）。
  - **无响应（unresponsive）**：`pid` 存活且命令行未被证伪，端口连得上（内核已接入连接），但 2 秒内没有健康回包。
    典型情形是服务被暂停或卡住，之后会恢复。**这一态不是「没有实例」。**
  - 判定的取舍：**只有「陈旧」允许接管**（覆盖或删除 `server.json`、另起服务）。「无响应」一律保留登记、不另起服务，
    因为服务进程与它的监听都还在，另起第二个会破坏 A-2，也会让 `server.json` 不再指向那个仍在运行的服务。
    「陈旧」的证据都是确认性的，不会把一个仍然存活并持有端口的服务误判成陈旧。
  - 对「无响应」的统一处置（各读者按下表，不各自发明）：

    | 读者 | 处置 |
    |---|---|
    | `start` / 无参数 / `open` | 不 spawn `serve`、不打开浏览器，打印「面板服务（pid N，端口 P）暂时没有响应，没有另起服务。等它恢复后重试，或运行 `autome web stop --force`」，退出码 1，`server.json` 不动 |
    | `serve`（含 launchd，临界区内与等锁期间） | 同样不起服务、不动 `server.json`，打印同一句，**退出码 0**（launchd 的 `KeepAlive.SuccessfulExit=false` 因此不会反复重启它） |
    | `link()` 登记失败后的重试 | 判到「无响应」就关掉自己的监听、按上一行退出，**不删旧文件**；只有判到「陈旧」才删后重试一次 |
    | `status` | 打印「面板服务无响应（pid N，端口 P，启动于 …）」，退出码 4；`--json` 输出 `{ "unresponsive": true, pid, port, instance, url }` |
    | `stop` | 见 A8「无响应」 |

  `/healthz` 的回包加 `instance` 与 `pid` 两个字段，E7 已核实与 `panel-url.sh` 兼容。
- **端口。**
  - 缺省先试 7420，再试 7421…7429，最后取系统分配（`0`），实际端口写进 `server.json`。
  - 测试需要可控的「缺省端口」，加一个 `AUTOME_WEB_DEFAULT_PORT`，只改缺省值；显式端口仍由 `AUTOME_WEB_PORT`
    或 `--port` 给。
  - 显式给的端口被占用时不换，沿用现有的「端口 N 已被占用」并以退出码 1 退出。用户点名要这个端口，偷偷换掉会让
    书签失效。
- **生产模式。**
  - `serve` 固定以 `mode: 'production'` 起服务：`runFromEnv` 新增选项 `{ mode, instanceFile }`，`serve` 传 `'production'`
    与 `true`，**不读 `NODE_ENV`**。精简包里没有 `vite`，所以凡是经 `autome web serve` 起的服务（`autome web`、`start`、
    launchd、薄壳）都不会走到 `http.ts` 里导入 `vite` 的开发分支。
  - 只有 `npm run dev`、`npm start` 仍按原样由 `NODE_ENV` 决定，`runFromEnv` 缺省行为不变。
  - 检出里没有 `build/server/index.js` 时，`serve` 报「先 npm run build」后退出码 1。
  - 启动日志里的「（生产模式）」可被测试读到。
- **竞争。唯一持锁层是 `serve`。**
  - `start`、无参数、`open`、launchd、薄壳创建服务，最终都是一个 `serve` 进程；启动器父进程**不持锁**，只做
    「判活实例 → 没有就 spawn `serve` → 等 `server.json` 变成活实例」，因此不存在父子等同一把锁。两个 `start` 同时
    判到没有实例，会各 spawn 一个 `serve`，由它们在下面的临界区里分出先后。
  - `serve` 在 `$AUTOME_HOME/web/launch.lock` 上用 `O_EXCL` 建锁（内容 `{pid, token}`），临界区覆盖
    「判活实例 → 选端口并监听 → 内核就绪 → 写 `server.json`」，写完立即释放；`serve` 崩溃或退出时也释放（只删 token 相符的锁）。
  - 拿不到锁时每 200 ms 重试，最多 30 秒；其间若判到活实例就按「已有面板在运行」以 0 退出，判到「无响应」就按上表以 0 退出。
  - 这把锁只排斥**同时启动**的 `serve`；已经启动完成并释放了锁的旧服务，靠临界区里的「判活实例」保护，而这一步的结论是三态
    （A5「实例判定」）：旧服务暂时无响应时，新 `serve` 拿到空闲的锁也只会判到「无响应」而退出，不会换端口另起。
  - 持锁者已死才可接管，接管由另一把 `launch.lock.reap`（`O_EXCL`）串行化。**持锁者活着时不因锁文件的年龄接管**：
    迟到的持有者可能仍在临界区里。等满 30 秒仍是活持有者，就报「另一个面板正在启动（pid N）；若它卡住，结束该进程后重试」，退出码 1。
  - 后盾：`server.json` 用 `tmp` 文件加 `link()` 登记（目标已存在即 `EEXIST`），写入不会静默覆盖别人的登记。`link()` 失败时，
    判对方是活实例就关掉自己的监听并按「已有面板」退出，判「无响应」就关掉监听并按上表退出（不删文件），只有判是陈旧文件才删后重试一次。
  - 任一 `serve`、`start` 的并发与交错都经过同一临界区，所以「手工 `start` 与 launchd 同时起」「`start` 与直接 `serve`」不会出现
    两个活服务与一份只登记其中一个的文件。
- **后台方式。**
  - `start` 用 `spawn(process.execPath, [bin/autome-web.js, 'serve'], { detached: true })`，输出追加到
    `$AUTOME_HOME/web/logs/server.log`，然后 `unref`。
  - 等 `server.json` 变成活实例，最多 20 秒。超时就打印日志末尾 20 行并以退出码 1 退出。
  - `start --json` 输出单行 `{ url, pid, instance, reused }`，供薄壳记下自己创建的实例（C4）。
- **安全（约束 7）。** 服务端一律走 `serve` → `runFromEnv`（生产模式）→ `startServer`，只绑 `127.0.0.1`，Host / Origin 检查跟着
  实际端口。

**A8 `stop` 与 `status`（A-7）。**

- **通信。** 服务新增只读接口 `GET /api/instance`，经过同一套 Host / Origin 中间件，返回：
  - `pid`、`instance`、`port`、`started_at`；
  - `kernel{path, source, build_id, may_advance}`；
  - `gates: [{task_id, title, node}]`：`dashboard.get` 的 `running` 里节点属于 `gate | fix_gate | merge_gate |
    repro_check | main_check` 的任务；
  - `other_driver: {skipped_last_minute, last_skipped_at}`：服务记下每次 tick 的 `skipped`，保留最近 60 秒。
- **发信号前的确认。** 每次都先按 A5 的三态判定：**活**且 `instance` 与 `pid` 都对上才给 `pid` 发 SIGTERM；**陈旧**才清理文件；
  **无响应**走下一条。只读本 `AUTOME_HOME` 下的 `server.json`，测试的 `AUTOME_HOME` 都是临时目录。
- **无响应。** 判到「无响应」（A5）时登记是仍在运行的服务的唯一线索，不能当「过期文件」清掉：
  - 不加 `--force`：不发信号、不删 `server.json`，打印「面板服务（pid N）没有响应，没有停止。确认要停掉它就加 --force」，退出码 1；
  - 加 `--force`：对该 `pid` 发 SIGTERM（`pid` 的命令行已在判定里核对过含 `autome-web`），等最多 15 秒，超时再 SIGKILL，
    删文件只删 `instance` 相符的，规则同下面的「停止的收尾」；`--instance` 绑定照常生效；
  - 被暂停的进程不处理 SIGTERM，由 15 秒后的 SIGKILL 兜底；`--force` 之外没有别的办法让「无响应」的登记被清掉或覆盖。
- **绑定实例。** `stop` 接受 `--instance <uuid>`：判到的活实例的 `instance` 不等于它时，不发信号、不删文件，打印
  「当前运行的不是指定的那个面板服务，已保留」，退出码 0。不带它时对判到的当前实例操作。信号目标与后面的 SIGKILL、删文件
  都绑定**这一次确认的 instance**：超时 SIGKILL 前重新核对 `server.json` 的 `instance` 与 `pid` 仍是它，删文件只删 `instance` 相符的。
- **有门禁、没加 `--force`。** 先打印
  「T-x 正在跑宿主门禁（<节点>）。门禁在独立进程里，停掉面板不会杀掉它，但在下一个驱动接手前没人收取结果。
  正在等它结束…（加 --force 立即停止）」，然后每 2 秒查一次 `/api/instance`：
  - 门禁清空后再停；
  - 超过 `--wait` 秒（缺省 1800，与门禁缺省超时同量级）仍有门禁时，打印「门禁还在跑，没有停止；加 --force 立即停止」，
    退出码 1，服务保持运行。
- **加 `--force`。** 立即停止，并打印「门禁 T-x 继续在后台运行，下一个驱动（`autome run` 或再次 `autome web`）会收取
  结果」。E2 证明这句话属实。
- **停止的收尾。**
  - 等进程退出、`server.json` 被删，最多 15 秒；超时就对确认过的那个 `pid` SIGKILL，并只在文件仍是该 `instance` 时删文件。
  - 装了自启动时追加「launchd 会在下次登录时再起它」。
  - 没有活实例（判到「陈旧」或没有文件）时打印「面板没有在运行」。若清理了过期文件，提示一句。退出码 0。
    「无响应」不属于这一档，不清理文件。
- **`status` 输出。**
  - 运行时：地址、pid、启动时间、内核路径 / 来源 / 构建标识（`may_advance` 为假时加「只读：内核比账本旧」）、正在跑的
    门禁、驱动一行。
  - 驱动一行是「有另一个驱动在推进（最近 1 分钟让路 N 次，最近一次 HH:mm:ss）」，或「最近 1 分钟没有发现其他驱动」。
  - 不在运行时打印「面板没有在运行」，退出码 3；「无响应」时退出码 4（A5 表）。
  - `--json` 原样输出 `/api/instance` 的回包。
  - 「另一个驱动」只是推断（E3），README 写明这一点，内核方法进 BL-01。

### C（W11）Electron 薄壳

**C1 运行方式（E4 已消除最大不确定性）。**

- 服务放子进程，不放主进程：主进程只跑一次性的启动器，`spawn(process.execPath, [<web>/bin/autome-web.js, 'start', '--json'],
  { env: { ELECTRON_RUN_AS_NODE: '1', AUTOME_BUNDLED_CORE: <Resources>/core/autome, AUTOME_NODE: process.execPath } })`，读它的单行输出
  `{ url, pid, instance, reused }`。启动器按 A5 判活实例，没有就用继承来的环境 spawn 分离的 `serve`（`process.execPath` 即
  Electron 本身，`ELECTRON_RUN_AS_NODE` 随环境传下去）。主进程观察的是这个一次性进程，不直接持有服务进程。
- 走 A 的启动器有两个好处：`server.json`、单实例、登录 PATH、生产模式全部复用；服务崩溃不会带走窗口。
- 面板目录作为 `extraResources` 复制到 `Resources/web`，不进 asar，路径上没有 `node_modules` 层。
- C-1「不依赖系统 Node」：起服务用的 `process.execPath` 就是 Electron 自己，`.app` 里不找也不需要 `node`。

**C2 .app 里的内核。**

- `package.sh` 改为 `cargo build --release -p autome-cli`，复制到 `apps/desktop/core/autome`，经 `extraResources`
  进入 `Resources/core/autome`；不再带 `automed`。
- `ci-local.sh --package` 的「Bundle carries a runnable core」与 `ci.yml` 的 `package` job 改成执行
  `Resources/core/autome --version`。
- `package.sh` 还要先 `npm --prefix apps/desktop run stage-web`，即调 A 的 `stage-panel.ts`，输出到 `apps/desktop/web`
  （gitignore）。干净检出下 Web 的安装与构建由 M-12 的 `prepare-web.sh` 补在它之前（BL-07）。

**C3 preload 与页面。**

- preload 只 `exposeInMainWorld('autome', { pickDirectory, notify })`。
- `pickDirectory()` 走 `ipcRenderer.invoke('autome:pick-directory')`，返回 `string | null`。路径交给页面现有的输入框，
  再走服务端 `admin.paths.check` 与 `project.probe`，`$HOME` 守卫照常生效。
- `project.pick` **不注册**，继续回 501（W9 的约定）：页面从来不调它。
- `notify({ title, body, href })` 弹系统通知，点击后聚焦窗口并导航到 `href`。`href` 必须解析成与面板同源：用 `new URL(href, <服务 origin>)`
  取得结果后比较 origin，`//example.com/x`、`/\example.com/x` 因此被拒；导航用 `loadURL(<解析后的地址>)`，不依赖 `will-navigate`
  （它不拦截 `loadURL`）。
- 页面侧只改 `bell-system.ts`：`window.autome?.notify` 存在时，`SystemNotifier` 用它代替浏览器 `Notification`，权限
  视为已授予。`native-picker.ts` 已支持 `pickDirectory`，不动。
- 主进程校验每个 IPC 调用方：`event.senderFrame.url` 的 origin 必须等于服务的 `http://127.0.0.1:<端口>`。参数做类型与
  长度检查：标题 ≤ 200、正文 ≤ 1000、`href` ≤ 500。
- 窗口导航：
  - `will-navigate` 只放行同源；
  - `setWindowOpenHandler` 一律 `deny`，其中 `http(s)` 外链交给 `shell.openExternal`；
  - `webPreferences` 保持 `sandbox`、`contextIsolation`、无 `nodeIntegration`。
- `open.path` 与 `open.terminal`：页面没有用处（grep 为空），不注册。

**C4 连上已有服务（C-4）。**

- 启动时主进程跑一次 C1 的 `start --json`（A5 的判定在启动器里），得到 `{ url, pid, instance, reused }`，并**记下 `instance`**。
- `reused: true` 就直接加载那个地址，否则加载自己刚起的那个。自己起的服务也写 `server.json`，之后的 `autome web`
  会复用它。
- 退出时：
  - `reused: true`（连上的是别人起的服务），不停；
  - 自己起的，执行 `stop --instance <记下的 instance> --wait 0`。当前运行的服务若已是别的 instance（用户中途停掉后又起了新的），
    `stop` 不动它（A8「绑定实例」）。若有门禁在跑，服务留在后台，再弹一条通知「门禁还在跑，面板服务留在后台；用
    `autome web stop` 停止」。

  在日志里记一行。
