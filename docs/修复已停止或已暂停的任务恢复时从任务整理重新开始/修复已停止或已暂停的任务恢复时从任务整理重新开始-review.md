## 阻塞问题

### R4-P01 · P1 · 未启动会话的恢复输入无法从历史会话找回

- **类别：违反任务目标。**
- **追溯：**任务 §5 约束 5（恢复节点所需 prompt 输入做全）；设计 §3 R3（第 156–162 行）、M-02「带回 inject」。
- **根因与证据：**R3 只从同节点最近一次会话的 `session.started` 读取 inject，没有当前轮尚未启动会话的来源。`scheduler.rs:1313–1323` 在 `cooldown_route` 返回 Deferred 时直接返回，尚未创建会话；`:1440–1444` 把待启动轮次的 inject 放入重试记录，事件只记 node/runtime/until。与此同时，`:932` 对 Pause、Stop、Resume 等成功转换都执行 `clear_retry`，`store.rs:1625–1630` 删除整条重试记录。
- **反例：**实现轮 S1 结束后门禁失败，转换以 `Inject::GateFailed` 回到 Implement（`autome-domain/src/task.rs:1018–1028`）；该 runtime 正在冷却且不能切换，新的实现轮 S2 尚未启动。用户在此时暂停或停止，重试行被删除。随后恢复按 R3 找到 S1，带回 S1 的旧输入或 None，门禁失败输出永久丢失；若冷却尚未结束，错误输入还会写入新的重试记录。节点虽正确，恢复后的 prompt 不满足约束 5。
- **检查范围：**所有由 `StartRole { inject }` 进入节点、却在 `start_session` 中因冷却延后的路径，包括门禁打回、rebase 冲突、设计反馈和用户表态；不能只覆盖已有 `session.started` 的停止用例。
- **修改方向：**设计需明确如何在暂停/停止清除重试调度前保留当前待启动轮次的输入，以及恢复时如何优先使用它；不能用更早的同节点会话替代当前轮。此项不是要求增加一般性重试功能。

### R4-P02 · P1 · 停在 Retro 时，手动复盘会被当成原 Loop 会话

- **类别：内部逻辑矛盾。**
- **追溯：**设计目标中其它节点回原节点的承诺；§3 R1/R2、§4 暂缓推进、§5 手动复盘互斥；M-03「手动复盘轮在跑时恢复被拒」「暂缓结论交付一次」。
- **根因与证据：**设计第 149–156、168–177、188–191 行都只比较 kind 与 node。`scheduler.rs:2492–2518` 允许在 Paused/Stopped 上手动复盘，使用的也是 `SessionKind::Role { role: Retro }`。同一 kind 不等于同一轮或同一来源。当前手动复盘收尾分支（`:249–259`）不推进 Loop，设计却要求把按 kind 暂缓的判断放在它之前。
- **反例：**Loop 在 Retro 暂停，原会话 S1 成功结束并留下暂缓结论；用户再启动手动 Retro S2。S2 仍在运行时恢复，§5 的 kind 不匹配检查不会拒绝，R1 将 S2 当成 Loop 原会话。若等 S2 结束再恢复，§4 又会把 S2 当成新的暂缓结论，R2 的 latest 选择 S2。两种顺序都使 S1 的原结论失去交付机会；S2 崩溃时还会把本应使用 S1 成功结果的恢复转成重试或失败。
- **检查范围：**恢复节点为 Retro，状态为 Paused/Stopped，手动复盘仍运行和已经结束两种顺序；同步检查 R1、R2、R3 的 latest 选择与 reap 收尾。
- **修改方向：**使用原 Loop 会话身份或明确的来源来区分手动复盘，不能仅比较 kind。手动复盘不得成为暂缓结论的替代来源，停在 Retro 时也须实现 §5 的互斥承诺。

### R4-P03 · P1 · 「停止已经杀掉门禁」并不成立，旧作业可能覆盖恢复后的结果

- **类别：关键事实错误。**
- **追溯：**任务 §5 约束 5；设计 §2 `DiscardGateRuns`（第 138–145 行）；M-02 停止门禁后重跑的验收。
- **根因与证据：**设计以「停止已经杀掉了进程，删文件是安全的」为清理前提。实际 `gate.rs:111,136–140` 先写 started、spawn 后直接返回，pid 由异步 WRAPPER 第一句写入（`:33`）；`stop_all` 只扫描已存在的 pid 文件（`:185–200`）。源码自己也说明刚启动的作业可能没有 pid（`:176–178`）。`Job::at` 使用任务、节点、SHA 命名（`:64–71`；`scheduler.rs:1946–1947`），恢复重跑会沿用同一组路径。
- **反例：**旧 gate 已 spawn，但包装脚本尚未写 pid；停止扫描不到 pid，旧进程存活。恢复按设计删除作业文件并启动同 SHA 的新 gate。旧包装脚本随后运行，写入与新作业共用的 log、pid 和 exit；`poll` 优先读取 exit（`gate.rs:145–151`），可在新门禁尚未结束时收下旧结果，提前通过或错误失败。删除旧标记不能证明今后没有旧写入。
- **检查范围：**gate、merge_gate、main_check 共用的启动、停止、作业命名、删除及结果读取路径。
- **修改方向：**设计必须给出旧作业到恢复作业的可靠交接，例如确保旧进程已登记并终止后才复用路径，或使新运行的结果身份与旧运行隔离。无需改变暂停/停止的产品语义，但不能继续依赖已被源码否定的前提。

### R4-P04 · P2 · CLI idle 修改超出任务明确允许的范围

- **类别：违反任务目标。**
- **追溯：**任务 §4「crates/autome-cli：只在恢复后的显示文字确实需要随之调整时才动」；设计 §1 第 108–112 行及 M-01 的 idle 随动。
- **根因与证据：**设计明确承认 `autome-cli/src/main.rs` 的 idle 改动「不是显示文字」，却用约束 7「所有测试通过」自行认定不算越界。源码 `main.rs:759–777` 是 `--until-idle` 的运行控制判断，不属于显示文字。测试要求没有覆盖或撤销目录内部的职责限制。
- **冲突：**照设计修改 idle 会违反 §4；只删掉这一修改又会保留设计已指出的 Requeued 被误判空闲的问题。二者需在设计层处理，不能留给实现轮暗中选择。
- **检查范围：**设计列出的所有 autome-cli 变更；当前明确要求的越界项只有 idle，显示文字已列入 Backlog。
- **修改方向：**裁决需给出符合现有 CLI 边界的方案，或将这一必要范围例外明确留待任务授权方决定；不得把测试约束写成已获范围授权。

### R4-P05 · P2 · 统一 e2e 判据与排队、复用会话和交付结论不能同时满足

- **类别：内部逻辑矛盾。**
- **追溯：**任务验收 2、3；设计「验证安排」第 233–234 行，§3 R1/R2，M-02/M-03 验收契约中的 `cargo test -p automed --test end_to_end resumes_at`。
- **矛盾与全部同类位置：**统一判据要求恢复调用返回后立即为 active/原节点，随后启动的会话也对应原节点；M-02 第 263 行却要求槽满时返回 queued 且无新会话；M-03 第 267–274 行要求已结束的暂停轮次只交付结论、不再起原节点会话，未结束的暂停轮次复用同一会话，暂停门禁收下已有运行。三组用例按统一判据编写时，正确实现也会失败。
- **修改方向：**按既有分支写判据：槽满先检查 queued/resume、无新增运行，出队后检查对应分支；R3 检查新会话属于原节点；R1 检查原会话被复用；R2 检查原结论仅交付一次并进入后继状态；门禁检查对应运行的启动记录与结果。共同保留「没有新增 Intake 会话」。
- 本项指出确定的互斥断言，不以验收契约缺行或「不够明确」为由阻塞，也不要求新增测试数量。
