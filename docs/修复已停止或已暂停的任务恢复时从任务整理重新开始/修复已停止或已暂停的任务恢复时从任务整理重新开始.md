下文「验收 n」指任务文件 §3 的第 n 条验收标准，「约束 n」指 §5 的第 n 条硬性约束。

## 背景与现状

用户对 `Paused` / `Stopped` 的任务执行恢复（`task.resume`），任务会回到任务整理（`intake`）从头再跑。
命令行早就向用户承诺了别的行为：`render.rs` 把暂停显示成「已暂停（会从 {节点} 继续）」。

根因有两处，都在 `crates/autome-domain/src/task.rs`：

1. `Trigger::Resume` 把 `Paused { resume }` / `Stopped { at }` 一律转成 `TaskState::Queued`（约 621–630 行），
   丢掉了节点；
2. `(Queued, SlotAvailable)` 一律转成 `Active { Intake }` + `StartIntake`（约 636–638 行）。

现有测试没有拦住它：域测试 `resume_re_enters_the_queue_rather_than_jumping_the_parallel_limit`、调度测试
`pause_and_resume_move_through_queued_rather_than_jumping_the_limit` 只断言恢复后是 `Queued`；e2e
`stopping_a_task_leaves_it_resumable` 只断言 `queued | active`。没有一条断言出队后去了哪个节点。

调研中还确认了两个与「回到原节点」直接相关的事实，方案必须处理：

- **暂停期间结束的会话，结果被丢掉。** `Pause` 立即把任务记成 `Paused { resume: 当前节点 }`，会话继续跑
  （T-08）。会话结束后 `reap_session`（`scheduler.rs` 约 219 行）先 `finish_session`、扫尾提交、跑 guard、
  结算表态，最后 `advance(SessionEnded)`——而 `(Paused, SessionEnded)` 落进 `apply` 的兜底分支被拒，
  这一轮的结论没有任何地方记得。若恢复时只是「重跑原节点」：暂停在审计时，第二个审计轮面对已经关掉的里程碑
  表无事可做，协议「没有第四种结论」会让任务停下；暂停在实现或裁决时，会多跑一轮、多扣一轮预算。
  所以对暂停而言，「回到原节点」必须包含「把那个节点已经跑完的一轮的结论交给转换表」。
- **被杀掉的门禁可能留下假结论。** 停止时 `stop_running_session` 调 `gate::stop_all` 杀掉门禁进程组。
  包装脚本（`gate.rs` 的 `WRAPPER`）通常随之死掉、不写退出标记，下次 `poll` 得到 `Vanished` 会重跑；但
  信号到达顺序不受保证，一旦包装脚本先写下 `exit_code=143`，恢复后 `run_gate` 会把它当成一次失败的门禁收下，
  任务带着 `GateFailed` 回到实现。约束 5 明确不允许。

其余相关事实：`store.rs` 以 `serde_json::to_string(&task.state)` 存状态，查询都在 Rust 侧做
（`queued_tasks`、`slots_in_use`、`task_counts` 都是对反序列化后的值 `matches!`），不在 SQL 里比对 JSON 文本；
SAME-MODEL 等配置校验在 `advance` 开头的 `resolve_config` 与 `redispatch_with` 里各跑一次；崩溃重试已有
「带着原来那一轮的 inject 重跑」的机制（`carried_inject` + `redispatch_with`）。

## 目标与非目标

目标（对应验收 1–3）：

- `Paused` 或 `Stopped` 在实现、审计、门禁（`gate`）任一节点的任务，恢复后回到那个节点；
  其它可暂停/停止的节点（任务整理、设计、评审、裁决、复盘、rebase、合并前门禁、合并、验证 main、清理）同样回到原节点，
  不比现在差（约束 4 的「门禁之外不得更差」）。
- 恢复时槽位已满就排队，轮到时仍回原节点；排队顺序与并行上限的语义不变（约束 3）。
- 回到原节点时附带工作做全：角色节点带上那一轮原本带着的 inject；停止过的门禁重跑而不是收下被杀的结果；
  暂停期间跑完的那一轮，结论在恢复时交给转换表（约束 5）。
- 角色开关、SAME-MODEL 在恢复路径上照常生效（约束 6）。
- 新增 e2e 覆盖以上两点（验收 3）。

非目标：

- 不改暂停、停止、取消本身的语义：暂停仍是「当前会话跑完后不再启动下一节点」，停止仍立刻杀会话；
  暂停期间那个会话进程照常不占槽位（现状，不动）。
- 不做 `rerun_from`、`extend_budget` 的任何改动；不做任务类型、任务卡、待开始状态（K1、K2）。
- 不改 `apps/`、`protocol/`、`plugins/`、`scripts/`、`.github/`；不改账本 schema（`SCHEMA_VERSION` 仍是 4）。
- CLI 仅增加恢复排队的节点提示，以及用户已授权的 `idle` 判定例外（M-04、M-05）。

## 方案

### 1. 排队记住恢复节点：`TaskState::Requeued`

在 `autome-domain` 的 `TaskState` 增加一个变体：

```rust
/// Resumed from a pause or a stop and waiting for a slot. Serialised as
/// `{"state":"queued","resume":"<node>"}`: to every reader that branches on
/// `state` it is a queued task, which is what it is.
Requeued { resume: Node },
```

序列化用 `#[serde(from = "TaskStateRepr", into = "TaskStateRepr")]`：`TaskStateRepr` 是现有派生形状的拷贝，
唯一差别是 `Queued { #[serde(default, skip_serializing_if = "Option::is_none")] resume: Option<Node> }`。
转换是一一对应的：`Queued` ⇄ `Queued { resume: None }`，`Requeued { resume: n }` ⇄ `Queued { resume: Some(n) }`，
其余变体原样搬运。

这样做的理由：

- **对外形状不变（约束 1）。** 判别字段 `state` 的取值没有增加；新建任务仍序列化为一字不差的
  `{"state":"queued"}`，恢复排队的任务只多一个 `resume` 字段。桌面端按 `state` 分支，看到的都是排队。
- **旧账本照读（约束 2）。** 已有的 `{"state":"queued"}` 读成 `Queued`，出队仍从任务整理开始；`paused` /
  `stopped` 记录的形状没变。不改 schema，K1 升 v5 时只需保留 `TaskStateRepr` 里的 `resume` 字段。
- **现有测试不必改写（约束 4）。** 保留单元变体 `TaskState::Queued`，几十处构造与断言原样编译；若把 `Queued`
  改成带字段的结构变体，所有测试里的 `TaskState::Queued` 都得改写，违背「不修改就要通过」。

新变体的性质：`node()` 返回 `Some(resume)`（与 `Paused` 一致，`next_role` 因此显示将要运行的角色）；
不占槽位；不在「等待我」；非终态。

所有非穷举匹配 `Queued` 的生产代码必须同步收进 `Requeued`（穷举 `match` 由编译器找出，`matches!` 与带 `_`
的匹配要人工改）。已知的四处：

| 位置 | 现有写法 | 改为 |
|---|---|---|
| `store.rs` `queued_tasks` | `matches!(t.state, TaskState::Queued)` | 也收 `Requeued`，仍按 `created_at` 排序 |
| `store.rs` `task_counts` | `Queued => "queued"` | `Requeued` 也计入 `"queued"` |
| `dispatch.rs` `queue_position` | `!matches!(.., Queued)` 就返回 `None` | `Requeued` 也报队列位置 |
| `scheduler.rs` `start_retro` | 拒绝 `Active \| Queued` | 也拒绝 `Requeued` |

用户已纳入 B-01、B-03：M-04 在 CLI 显示恢复节点，M-05 将 `Requeued` 纳入 `idle` 的待办判断。后者是用户明确授权的任务 §4 例外；其余 CLI 运行控制不变。实现时核对 `TaskState::Queued` 的生产匹配位置。

### 2. 转换表

`Resume`、`SlotAvailable` 以及控制触发器在新状态上的行为（`apply` 仍是纯函数）：

| 当前状态 | 触发 | 结果 |
|---|---|---|
| `Paused { resume: n }` | `Resume` | `Requeued { resume: n }`，`Action::None` |
| `Stopped { at: n }`，n 不是门禁 | `Resume` | `Requeued { resume: n }`，`Action::None` |
| `Stopped { at: n }`，n 是三个门禁之一 | `Resume` | `Requeued { resume: n }`，`Action::DiscardGateRuns { node: n }` |
| `Paused` / `Stopped`，n 的角色已关闭 | `Resume` | 拒绝：「该角色当前已关闭，无法从这里恢复」，状态不变 |
| `Queued` | `SlotAvailable` | 不变：`Active { Intake }` + `StartIntake` |
| `Requeued { resume: n }`，n 是任务整理或角色节点且角色开着 | `SlotAvailable` | `Active { n }` + `Action::Reenter { node: n }` |
| `Requeued { resume: n }`，n 的角色在排队期间被关掉 | `SlotAvailable` | `Failed { at: n, reason: Config { "该角色当前已关闭…" } }` |
| `Requeued { resume: n }`，n 是内核步骤（rebase、合并、清理、三个门禁） | `SlotAvailable` | `Active { n }` + `RunCoreStep { node: n }` |
| `Requeued` | `Resume` / `Pause` / `Stop` / `RerunFrom` / `ExtendBudget` | 拒绝，状态不变 |
| `Requeued` | `Cancel` | `Cancelled` + `RunCancel`（与其它非终态一致） |

可暂停、可停止的节点是全部 15 个节点去掉两个等待用户的停顿点，共 13 个；`Requeued` 只会带这 13 个之一。

两个新 `Action` 变体：

- `Reenter { node }`：任务回到 `node`，由调度器决定是接着等、交付已跑完那一轮的结论，还是重新起一轮（§3）。
  它不经 `start_impl`：恢复不是「新开一个实现轮」，不得重复计算纳入表态带来的预算增量；表态由原来那一轮的
  inject 带回（与崩溃重试同一条路）。
- `DiscardGateRuns { node }`：调度器清掉这个任务该门禁节点的全部旧作业（`gate.rs` 新增
  `discard_node(repo, task_id, node)`）。只在从 `Stopped` 恢复时做；从 `Paused` 恢复时门禁进程可能还在跑或已经
  跑完，它的结果是真的，要收下而不是删掉（删掉会让还活着的包装脚本把标记写到新作业的路径上）。

  **「停止已经杀掉了进程」并不可靠，所以先杀净再删。** `gate::start` 写 `.started` 后 spawn 就返回，pid 由包装脚本
  第一句写入（`WRAPPER`），`stop_all` 只扫描已存在的 `.pid`（`gate.rs` 自己的注释也说刚启动的作业可能没有 pid）。
  停在这个窗口里的门禁会逃过停止；而 `Job::at` 以任务、节点、提交命名，恢复后重跑复用同一组路径，逃掉的旧包装脚本
  之后写下的 `exit` / `log` 会被新作业的 `poll` 当成自己的结果。所以 `discard_node` 的顺序是：
  1. 对该节点 `<node>-*` 的每个作业：有 `.pid` 且进程活着的，杀进程组；
  2. 有 `.started`、既无 `.pid` 也无 `.exit` 的，最多等 3 秒让 pid 出现（包装脚本第一句就写它；停止到恢复是用户
     操作的间隔，远大于此），出现后杀进程组；3 秒内仍没有则放弃等待、照常往下走（残余窗口见下，不再加大）；
  3. 全部杀完后才删除 `<node>-*.{started,pid,exit,log}` 与 `.exit.tmp`、`.exit.code`。
  前缀 `gate-` 与 `merge_gate-`、`main_check-` 互不为前缀，不会误删别的门禁。杀进程组复用 `kill_group`
  （SIGTERM，500ms 后 SIGKILL）。残余窗口：包装脚本在 3 秒内连第一句都没执行（机器被挂起之类），它之后写下的文件
  仍可能落进新作业的路径；这与 `gate::start` 本来就先 `clear` 再 spawn 的既有窗口同类，不在本任务消除。

内核步骤节点出队后照旧由下一次 tick 的「跑内核步骤」执行：rebase、合并、清理按 `recover` 的注释是幂等的；
门禁节点由 `run_gate` 依据作业文件决定是启动、等待还是收结果——停止过的已在恢复时被清掉，所以一定重跑。

### 3. 调度器：`Reenter { node }` 怎么执行

`perform` 收到 `Reenter { node }` 时，按顺序判断（`latest` 指这个任务最近一个 kind 对应 `node`、**且不是手动复盘轮**的会话：
任务整理对 `SessionKind::Intake`，角色节点对 `SessionKind::Role { role }`。手动复盘轮用 `SessionKind::Role { Retro }`，
与 Loop 自己的复盘节点同 kind，所以不能只比 kind，必须按下面的来源标记排除，见 §5）：

| 情形 | 做什么 |
|---|---|
| R1 这个任务有一个仍在运行的非手动复盘会话，且 kind 对应 `node`（暂停后、会话还没跑完就恢复了） | 什么也不起；会话结束时 `reap_session` 照常推进 |
| R2 `latest` 有一条未交付的暂缓结论（§4） | 交付它：标记已交付，然后走 `reap_session` 收尾的同一段逻辑——`Crashed` 先试 `schedule_retry`，否则 `advance(SessionEnded { outcome })` |
| R3 其余情况（停止杀掉了会话、暂停发生在冷却或崩溃退避期间、从未起过会话） | 用 `redispatch_with(node, inject)` 重新起一轮；`inject` 的来源见下 |

**R3 的 inject 来源（按顺序取第一个存在的）：**

1. **挂起时留存的待启动输入。** 一轮已经决定要起、但还没有会话的情形——`cooldown_route` 返回 `Deferred`（CLI 在限流冷却）
   或崩溃退避——其输入只存在重试记录里（`schedule_retry`），而 `advance` 对每次成功的转换都 `clear_retry`，
   `Pause` / `Stop` 也不例外，输入随之永久丢失。所以 `advance` 在 `clear_retry` 之前加一步：触发器是 `Pause` 或
   `Stop`，且 `pending_retry` 有记录、记录的节点等于将要停下的节点时，先追加事件 `task.resume_input`，
   载荷 `{ node, inject }`。这个来源只在**事件序号大于 `latest` 的 `session.started` 事件序号**时有效：之后又起过
   会话，就说明它已被用掉或过期。（`Inject` 已是可序列化类型，重试记录就是这么存它的。）
2. `latest` 自己那条 `session.started` 事件里的 inject（不是任务最后一条 `session.started`，也不是任何手动复盘轮的）；
3. 没有 `latest` 时为 `None`。

这解决的反例：实现轮 S1 结束、门禁失败，转换以 `Inject::GateFailed` 回到实现；CLI 在冷却，S2 尚未启动；
此时暂停或停止，重试记录被清掉。恢复时第 1 条取回 `GateFailed`，而不是退回到 S1 的旧输入。检查范围是所有
「带 inject 进入节点、却因冷却或退避没起会话」的路径：门禁打回、rebase 冲突、设计反馈、纳入的表态都走同一个
重试记录，同一处留存。不为此增加一般性的重试功能。

R3 里的 inject 就是约束 5 说的「该节点应有的 prompt 输入」：设计被驳回时的反馈、rebase 冲突文件、门禁失败的
输出、纳入的表态，都随原来那一轮带回。停止时 `stop_running_session` 已经 `release_decisions`，表态回到待交付，
新一轮带着 `Inject::Decisions` 启动时重新租用——与崩溃重试完全相同。`redispatch_with` 内部重新
`resolve_config`，SAME-MODEL 等校验照常生效；失败由 `advance` 的 `record_failed_action` 记成
`Failed { Config }`，与现在一样可见（约束 6）。

`store.rs` 若没有「按会话 id 取它的 `session.started` 事件」的查询，就新增一个只读方法；不改表结构。

### 4. 暂停期间结束的会话：照常收尾，暂缓推进

`reap_session` 在会话已结束、即将推进之前加一个判断：任务处于 `Paused { resume: n }` 或 `Requeued { resume: n }`，
这个会话的 kind 对应 `n`，**且它不是手动复盘轮**（§5 的来源标记）时——

- 前面的步骤全部照做：`finish_session`、记用量、扫尾提交、`apply_guards`、按结论 `settle` / `release` 表态。
  会话行因此是「已结束」，不留在运行列表里，`autome run --until-idle` 与 e2e 的 `settle` 都能把暂停的任务
  看成空闲。
- 不调 `schedule_retry`、不调 `advance`；改为追加事件 `session.outcome_held`，载荷
  `{ session_id, node, outcome }`（`SessionOutcome` 已是可序列化类型），返回 `Ok(true)`。事件名刻意不叫
  `session.deferred`：`cooldown_route` 已用这个名字记「限流冷却而延后」，载荷不同，同名会让按事件名读账的人混淆。
- 「手动复盘轮」特判（`s.kind.role() == Some(Retro) && !Active`）改为**先看来源标记**：有标记的是手动复盘轮，走原来的
  收尾分支（不推进、不暂缓）；没有标记的 Retro 会话按其余规则走，其中处于 `Paused` / `Requeued` 的走上面的暂缓。
  旧特判的 `!Active` 条件保留作为没有标记的老会话（升级前启动、仍在跑的手动复盘轮）的兜底，只在任务已是终态时命中，
  不再吞掉暂停中的 Loop 复盘会话。

交付时（§3 的 R2）追加 `session.outcome_held_applied { session_id }`。「未交付」的判据：`latest`（已排除手动复盘轮）
的 id 有一条 `session.outcome_held`，且没有以它为 `session_id` 的 `session.outcome_held_applied`。
有了已交付标记，交付后若又在崩溃退避期间被暂停、再恢复，不会把同一个结论交付第二次。

先暂停、会话跑完（结论已暂缓）、再停止：停止没有会话可杀，`Stopped { at: n }`；恢复时 R2 交付暂缓的结论。
那一轮确实跑完并提交了，交付它而不是重跑，与暂停的含义一致。

### 5. 手动复盘轮与恢复

`start_retro` 允许在 `Paused` / `Stopped` 上手动跑一个复盘轮（现状），而手动复盘轮与 Loop 自己的复盘节点同 kind
（`Role { Retro }`），光比 kind 分不开：任务停在 Retro 时，R1 会把手动轮当成原会话，§4 会把手动轮的结论当成暂缓结论，
真正的 Loop 会话的结论就丢了。所以给手动轮一个来源标记：

- `start_retro` 在 `start_session` 成功之后，取 `running_session(task_id)`，追加事件
  `session.manual_retro { session_id }`。核心的 tick 与请求串行，标记先于下一次 `reap_session`。冷却延后而没起会话时
  没有会话、也就没有标记，行为同现状。
- 判「是不是手动复盘轮」只看这条事件。`latest`（§3）、R1、§4 的暂缓、旧特判都用同一个判断，不再各自比 kind。

互斥与 `task.resume` 的派发（`dispatch.rs`）：在应用触发器之前检查，任务有正在运行的**手动复盘轮**时拒绝，提示
「手动复盘轮还在跑，结束后再恢复」。无论恢复到哪个节点都一样；非手动的会话 kind 总是对应恢复节点，没有别的拒绝理由。
`start_retro` 拒绝 `Requeued`（§1 表）。顺序举例（停在 Retro）：Loop 复盘会话 S1 在暂停中结束，结论暂缓；用户起手动
S2——S2 在跑时恢复被拒；S2 结束走手动分支、不暂缓；之后恢复，R2 的 `latest` 是 S1（S2 被排除），交付 S1 的结论。

`task.stop` 同理要先看状态：`task_stop` 现在先 `stop_running_session` 再应用触发器，而 `Requeued` 拒绝 `Stop`——
从暂停恢复、会话还在跑的任务点停止，会得到拒绝却已杀掉会话（门禁也被 `stop_all` 杀了）。所以 `task_stop` 在杀进程之前
先判断任务是 `Requeued` 就直接拒绝，不产生任何副作用。`task_cancel` 不受影响（`Requeued` 可取消）。

### 被修改的现有测试

只改两条，都是直接断言「恢复后进入 `Queued`（无节点）」的，即本缺陷定义为错误的行为（约束 4）：

- `autome-domain` `task::tests::resume_re_enters_the_queue_rather_than_jumping_the_parallel_limit`：
  断言改为 `Requeued { resume: Implement }`。测试名不改——它守的「不越过并行上限」仍然成立。
- `automed` `scheduler::tests::pause_and_resume_move_through_queued_rather_than_jumping_the_limit`：同上。

e2e `stopping_a_task_leaves_it_resumable` 不改：`Requeued` 的 `state` 仍是 `"queued"`，出队后是 `"active"`。
除这两条外，任何现有测试需要改动都说明实现偏离了本设计，实现轮应先回头查实现。

## 风险

- **serde `from`/`into` 的兼容性。** 内部标签枚举里「全部字段可缺省的结构变体」能从 `{"state":"queued"}` 反序列化，
  这是 M-01 第一件要证明的事（M-01 的序列化域测试）。若不成立，退路是给 `TaskState` 手写 `Serialize` /
  `Deserialize`，对外 JSON 不变，方案其余部分不受影响。
- **出队后马上交付暂缓结论是一次嵌套的 `advance`。** `fill_slots` 会把这次出队计为占用一个槽位，即使交付后
  任务走到了不占槽位的节点（如设计停顿点）或失败。误差只存在于这一次 tick 之内，下一次 tick 重新统计；
  与 `run_core_step` 在 tick 内调 `advance` 是同一种结构。
- **暂停期间会话进程不占槽位**是现状（`Paused` 不占），恢复后可能短暂地有超过并行上限的进程。属于暂停语义，
  非目标，不在本任务处理。
- **e2e 的时序。** 「暂停时会话还在跑」「停在门禁时门禁还在跑」需要能被测试放行的阻塞步骤。e2e 用
  「等某个文件出现才退出」的脚本，而不是固定 `sleep`，避免在慢机器上抖动；`settle` 的 90 秒上限不变。
