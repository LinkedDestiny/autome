## 评审问题

### R1-P01 · P2 · 等额费用会被误判为超过预算

- 类别：**内部逻辑矛盾**。
- 违反条款：任务 §6.6「超过是严格大于」；设计方案 §4.1 第 212 行「累计 = 上限，不告警」；M-04 的 `budget_alert_requires_strictly_more_than_the_limit` 约定。
- 设计位置：方案 §4.1 第 203–205 行，公式为 `usd_total * 100.0 > limit_cents as f64`。方案 §1.1 第 117 行规定费用保留原始和，风险表第 263 行仅通过选择测试金额避开浮点误差。
- 具体反例：一个会话报 `$0.07`，预算为 7 美分；Rust `f64` 中 `0.07 * 100.0` 为 `7.000000000000001`，公式返回 `true`。两个会话分别报 `$0.10` 与 `$0.20`，预算为 30 美分时，同样得到 `30.000000000000004 > 30`。用户尚未超过预算就收到告警；该告警还会写入去重历史。
- 证据：本轮用 `rustc` 编译并运行最小表达式验证，两例均返回 `true`；合法对照 `$0.25 + $0.25` 对 50 美分返回 `false`，真实超额 `$0.071` 对 7 美分返回 `true`。源码与输出位于 `.autome/output/review-1-float.rs`、`review-1-float-result.log`。
- 根因及同类检查范围：检查了原始金额聚合、配置美元到美分转换、预算比较与 CLI 格式化。配置转换已有容差，展示取两位小数不能修正生产预算判断；错误落在统一比较函数。
- 建议修改：明确能吸收浮点计算尾差的预算比较规则，并保留真实子美分超额的含义；用上述等额与真实超额对照验证。不要只把测试金额改成二进制可精确表示的数，也不要无说明地把所有会话费用取整到美分。

### R1-P02 · P2 · 警报与去重事件分开提交会重复报警

- 类别：**违反任务目标**。
- 违反条款：任务 §3 验收 3 的补充说明：「一条警报」是字面意思，同一任务超限后继续跑出更多会话，不应再来一条；设计方案 §4.1 的同一上限不重复告警约定。
- 设计位置：方案 §4.1 第 219 行只依据 `task.budget_exceeded` 事件去重；§4.2 第 229–232 行依次写警报、去重事件、通知事件；第 237–238 行规定写库失败只记录日志、继续回收。
- 源码证据：`crates/automed/src/store.rs:1805` 的 `raise_alert` 每次生成新 ID 并独立插入 `project_alerts`；`:531` 的 `append_event` 是另一次独立插入；`:551` 的 `last_event` 仅查询 `events`。设计没有把这些写入包在同一事务内。
- 具体反例：第一次超限回收成功提交警报 A1 → 紧接着写 `task.budget_exceeded` 失败 → 按设计只记日志，任务继续 → 下一带费用会话结束 → `last_event` 仍为空 → 再提交警报 A2 和去重事件 E1。最终同一预算有两条警报、一条去重事件。
- 根因及同类检查范围：检查了告警写入、去重读取、关闭警报和两种事件的顺序。警报与去重标记不能分开提交；仅交换先后顺序又会产生「已有去重标记却没有警报」的窗口。`project.alert` 也在同一写入链中。
- 建议修改：将警报、去重事件及对应通知事件放进一次 SQLite 事务；失败仍只记录日志，不影响任务继续。无需新增表、重试系统或补偿流程。
- 证据边界：这是由现有独立写入方法和设计顺序推出的跨语句失败反例；未声称对尚未实现的预算逻辑完成故障注入。这里要求的是既有“一条警报”语义，不是扩展容灾范围。

### R1-P03 · P2 · 指定的项目会话查询直接拼接会报列名歧义

- 类别：**内部逻辑矛盾**。
- 违反条款：设计方案 §1.4 第 147–150 行指定的查询与 M-02 验收结果不能同时成立；对应验收命令为 `cargo test -p automed --lib cost_rollup_`，要求项目和看板的 3 个用例通过。
- 设计位置：`sessions_in_project` 被明确指定为 `SESSION_SELECT_BASE` 加 `JOIN tasks ON tasks.id = sessions.task_id WHERE tasks.project_id = ?1`。
- 源码证据：`crates/automed/src/store.rs:1877` 的 `SESSION_SELECT_BASE` 中 `id`、`kind`、`protocol_ref`、`rules_hash` 没有表名前缀；同文件 `:1873` 的任务查询显示 `tasks` 也具有这些列。
- 具体反例：在含同名列的 SQLite 内存表上执行该拼接查询，prepare 阶段即报 `ambiguous column name: id`；完整最小验证输出位于 `.autome/output/feasibility-sql-join.txt`。按指定查询实现时，`project.get`、`project.list`、`dashboard.get` 的新增取数路径都受影响。
- 根因及同类检查范围：检查了共享 SELECT 的列名及三个项目级调用入口；单任务 `list_sessions` 没有 JOIN，不存在此歧义。不是要求重做聚合架构，也不是认为验收不明确。
- 建议修改：将查询写成 `SESSION_SELECT_BASE` 加 `WHERE task_id IN (SELECT id FROM tasks WHERE project_id = ?1)`，或明确 JOIN 版本对所有会话列加 `sessions.` 限定；均可保留一条查询和纯函数聚合。
