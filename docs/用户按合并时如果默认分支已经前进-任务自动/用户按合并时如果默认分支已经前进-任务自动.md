下文「验收 n」指任务文件 §3 的第 n 条验收标准，「约束 n」指 §5 的第 n 条硬性约束。代码位置以本 worktree 的基线提交 `2cca95b` 为准。

## 背景与现状

第 1 轮 T-8、T-9 同时停在「等你合并」。先合并 T-8 之后，T-9 的合并被拒（「不在最新的 main 之上，需要先 rebase」），退回等你合并。而等你合并的任务不能停止也不能重跑，只能手工 rebase。

现状链路（均已对照源码核实）：

- **按合并。** `task.merge`（`dispatch.rs:397`）→ `Trigger::Merge`。`(Active{AwaitMerge}, Merge)`（`task.rs:969`）在没有新纳入的 Backlog 项时进入 `Active{Merging}` + `RunCoreStep{Merging}`。这一步**不检查槽位**；`Merging` 占槽位，但它只在下一个 tick 跑一次。
- **合并。** `merge_all`（`scheduler.rs:2250`）按代码仓在前、文档仓最后的顺序处理。`is_ancestor(branch, base)` 为真的仓跳过；其余仓逐个调 `git::merge_task_branch`，被拒的仓不阻止后面的仓继续合并，最后汇总成 `CoreStepResult::Blocked{detail}`。
- **被拒的三类原因。** `merge_task_branch`（`git.rs:712`）按固定顺序检查：①主工作树有与本次合并冲突的未提交改动；②主工作树不在默认分支；③`!is_ancestor(default, branch)`，即「不在最新之上」。另有 `git merge` 本身失败。四种情况都只产出一个 `Blocked{detail}` 字符串，**没有机器可读的区分**。现有测试 `merge_is_blocked_when_the_branch_is_behind_the_default_branch`（`git.rs:1370`）断言第③类的返回是 `MergeOutcome::Blocked`。
- **状态机。** `(Merging, Blocked)` → `AwaitMerge`（`task.rs:1039`），现有测试 `a_blocked_merge_returns_to_the_stopping_point_rather_than_failing` 用 `Blocked` 断言这一点。`(Rebase, Ok)` 在配置了门禁时进 `MergeGate`，否则进 `AwaitMerge`。`(MergeGate, Passed)` → `AwaitMerge`；`(MergeGate, Failed)` 与 `(Rebase, Conflict)` 都退回实现。
- **槽位。** `Rebase`、`MergeGate`、`Merging` 占槽位（`Node::occupies_slot`）。`fill_slots`（`scheduler.rs:891`）只把 `Queued`/`Requeued` 任务按提交顺序放进空槽位。`Requeued{resume}` 是 K0 加的，对外仍是 `state: queued` 带 `resume`，拿到槽位后核心步骤节点会 `RunCoreStep`（`task.rs:717`）。
- **合并面板。** `task_changes`（`dispatch.rs:1898`）逐仓给出 `mergeable = 无冲突脏文件 && on_top`，不在最新之上时给 `blocked_by:{kind:"needs_rebase"}`。桌面端 `apps/desktop/renderer/screens/task.js` 第 928、1266 行在 `!changes.mergeable` 时**禁用合并按钮**，所以桌面端用户在默认分支前进之后按不到合并。命令行 `autome merge` 不看 `mergeable`。
- **事件打印。** `render.rs::event_line` 不认识的种类返回 `None`。`autome run`（`main.rs:726`）对每条新事件调用它。
- **账本。** schema v4。任务状态以 `TaskState` 的 JSON 存在 `tasks.state` 列；`events` 表按 `(subject_id, seq)` 建了索引。已有用事件当状态位的先例：`run_gate` 用 `last_event(task,"gate.result")` 决定沿用门禁，`session.outcome_held` / `session.outcome_held_applied` 用一对事件表达「挂起 / 已处理」。

## 目标与非目标

**目标。**

1. 任务在 `await_merge` 时用户按合并。如果任一仓的任务分支不在其默认分支最新提交之上，且没有别的被拒原因，内核自己走 rebase →（配置了门禁时）合并前门禁 → 合并，不再回到 `await_merge`（验收 1）。
2. 合并这一步才发现分支落后（按下合并到真正合并之间默认分支又动了）时，走同一条路径（验收 3 前半）。
3. 自动路径上 rebase 冲突、门禁失败，都按现有路径退回实现，并作废这次按合并的授权。之后照现有流程再次停在 `await_merge`（验收 4）。
4. 记录事件 `merge.rebased`，`autome run` 能打印出来（验收 6）。
5. 桌面端在默认分支前进后仍能按到合并：合并面板不再把「需要 rebase」当成阻挡（这是让验收 1 在桌面端可达的唯一途径，因为 `apps/` 不能改）。

**非目标。**

- 不让「等你合并」可以停止、重跑；不做没有用户按合并的自动合并；不改主工作树脏、不在默认分支等其它前置条件的处理（仍退回 `await_merge`）。
- 不新增 JSON-RPC 方法，不改已有方法的参数（约束 1）。不改 schema（约束 8）。不新增节点名。
- 不改 `apps/`、`protocol/`、`plugins/`、`scripts/`、`.github/`、`docs/development/`。桌面端文案的跟进记在 Backlog。

## 方案

### 1. 合并前置条件分类（`crates/automed/src/git.rs`）

新增：

```rust
pub enum BlockKind { DirtyConflict, NotOnDefault, Behind, MergeFailed }
pub enum MergeCheck { Ready, Blocked { kind: BlockKind, detail: String } }
pub fn check_merge(repo: &Path, default_branch: &str, task_branch: &str) -> Result<MergeCheck>
/// 与 merge_task_branch 同一次尝试，但被拒时带回类型化的原因。
pub enum MergeAttempt { Merged { .. }, Blocked { kind: BlockKind, detail: String } }
pub fn try_merge(repo: &Path, default_branch: &str, task_branch: &str, message: &str) -> Result<MergeAttempt>
```

`check_merge` 按现有的①②③顺序检查，`detail` 文本与现在逐字相同；`MergeFailed` 只由真正的 `git merge` 失败产生（`merge --abort` 之后）。`try_merge` 是现在 `merge_task_branch` 的函数体：先调 `check_merge`，被拒就带着 `kind` 返回，否则执行 `git merge`，失败返回 `kind = MergeFailed`。`merge_task_branch` 缩成 `try_merge` 的薄包装，把 `MergeAttempt` 映射回原来的 `MergeOutcome`（`Blocked` 只取 `detail`）。它的签名、`MergeOutcome` 的形状与所有文本都不变，`merge_is_blocked_when_the_branch_is_behind_the_default_branch` 等现有测试原样通过。

**拒绝原因必须随实际合并尝试返回，不能事后重建。**被拒之后再去查一次状态，看到的是新状态，不能说明刚才为什么被拒（脏文件在两次之间被清掉，或主工作树被切回默认分支，旧的拒绝会被误读成「落后」而升级成自动 rebase，违背验收 3）。所以第 3 节阶段二的汇总只用 `try_merge` 当场给出的 `kind`，不再调 `check_merge`。

①先于③的顺序是有意保留的。分支落后同时主工作树有冲突的脏文件时，结果仍是「脏」，即退回等你合并（验收 3 后半）；用户清理后再按，才走自动路径。

### 2. 状态机（`crates/autome-domain/src/task.rs`）

**新的核心步骤结果。**

```rust
/// Merging only: every repository that refused did so only because its task
/// branch is behind its default branch.
CoreStepResult::Behind { repos: Vec<String>, detail: String }
```

`Blocked` 的含义收窄为「除落后之外的前置条件不满足」，转换不变。这里新增变体而不是给 `Blocked` 加字段，因为现有测试用 `Blocked{detail}` 字面量构造。

**授权位作为转换的输入与输出。** 「用户已经按过合并、这段 rebase/门禁是在替这一下补齐前置条件」需要跨越几个转换。它进入领域层的方式如下：

- 新增 `pub fn apply_with_merge_request(state, trigger, ctx, merge_requested: bool) -> Result<Transition, Rejected>`。现有的 `apply(state, trigger, ctx)` 签名不变，等价于 `apply_with_merge_request(.., false)`。所有现有测试走 `apply`，结果逐字不变。
- `Transition` 新增 `pub merge_requested: bool`，表示**这次转换之后**授权位的值。`Transition` 只由领域层的私有构造函数生成，没有外部字面量。

授权位不放进 `Context`、`TaskState` 或新列，理由见第 5 节「否决的做法」。

**转换表的变化**（`r` 为传入的授权位）。只有这三处读 `r`：

| 当前 | 触发 | `r` | 结果 |
|---|---|---|---|
| `Active{Merging}` | `CoreStepDone{Merging, Behind}` | 任意 | `Requeued{resume: Rebase}`，`Action::None`，授权位置为真 |
| `Active{Rebase}` | `CoreStepDone{Rebase, Ok}`，未配置门禁 | 真 | `press_merge(ctx)` |
| `Active{MergeGate}` | `GateDone{MergeGate, Passed}` | 真 | `press_merge(ctx)` |
| 上两行 | 同上 | 假 | 与现在相同：进 `MergeGate` / `AwaitMerge` |

- `press_merge(ctx)` 是从现有 `(AwaitMerge, Merge)` 分支抽出的函数：有本停顿点新纳入的 Backlog 项时 `start_impl`，否则进 `Active{Merging}` + `RunCoreStep{Merging}`。`(AwaitMerge, Merge)` 改为调用它，行为不变。自动路径因此与按一下合并完全一致，包括「自动路径期间被标纳入的 Backlog 项先回实现」。
- `(Rebase, Ok)` 在配置了门禁时，不论 `r` 都进 `MergeGate`。门禁照常跑在 rebase 后的 head 上；同 sha 沿用的规则在 `run_gate` 里，不改（约束 4）。
- `(Rebase, Conflict)`、`(MergeGate, Failed)`、`(Rebase, Failed)` 的转换不变（验收 4）。授权位按下面的延续规则被清除。
- `(n, Behind)` 中 `n ≠ Merging` 时拒绝（`Rejected`），因为只有合并会报告落后。

**授权位延续规则**（`apply_with_merge_request` 末尾统一计算，单测覆盖）：

```
after = 触发是 CoreStepDone{Merging, Behind}
        || (r && in_stretch(当前状态) && in_stretch(下一状态))
in_stretch(s) = s 是 Active / Requeued / Paused，且节点 ∈ {Rebase, MergeGate}
```

由此得到：

- 排队（`Requeued{Rebase}`）、暂停后恢复（`Paused` → `Requeued` → `Active`）都保留授权；恢复回到原节点，与 K0 一致。
- 离开 rebase/门禁这一段就清除授权：冲突、门禁失败退回实现，进入 `Merging`，`Stop`、`Failed`、`Cancelled` 都属于离开。`Stop` 被视为用户收回这一下合并，恢复后照常停在 `await_merge`。
- 从这一段之外进入 `Rebase`，比如复盘之后，或「从 rebase 重跑」，永远不带授权。所以即使账本里留着一个过期的真值，也不可能在用户没按合并时合并。

### 3. 调度器（`crates/automed/src/scheduler.rs`）

- **`merge_all` 两阶段。**
  - 阶段一：对每个还没并入的仓（`is_ancestor(branch, base)` 为假）调 `check_merge`。如果被拒的仓**全部**是 `Behind`，且至少有一个，就直接返回 `CoreStepResult::Behind{repos, detail}`，一个仓都不合并。
  - 阶段二：其余情况（全部 `Ready`，或有非 `Behind` 的被拒）走**现有循环，代码不变**。
  - 阶段二的循环对每个未并入的仓调 `try_merge`，**记下它当场返回的 `kind`**，不在汇总时重新查询。被拒的仓全部是 `Behind` 时返回 `Behind`，只要有任何一个是 `DirtyConflict`、`NotOnDefault` 或 `MergeFailed` 就返回 `Blocked`。`Behind` 的出现来自两处：阶段一与真正合并之间默认分支又动了（验收 3 前半）；工作区项目里部分仓已合并而其余仓只因落后被拒。一个仓当场被拒的原因是脏，之后被清理，它仍按「脏」计，任务退回 `await_merge`，用户再按一次才走自动路径。
- **授权位持久化**，不改 schema。`advance` 读 `before = last_event(task,"merge.auto")["active"] == true`（没有这类事件时为假，旧账本即如此），调用 `apply_with_merge_request`。`after != before` 时写事件 `merge.auto`：
  - 置真写在 `set_task_state` **之后**，payload `{active:true, repos, detail}`；
  - 置假写在 `set_task_state` **之前**，payload `{active:false}`。

  这样任一时刻崩溃，留下的都是更保守的那一边：丢了置真，任务会走回 `await_merge` 等再按一次；而延续规则保证一个没被清掉的真值不会在别处生效。
- **`merge.rebased` 事件。** `run_core_step(Rebase)` 在 `rebase_all` 返回 `Ok` 且授权位为真时，在 `advance` 之前写 `merge.rebased`。payload 为 `{repos:[{repo, onto, head}]}`，其中 `head` 是 rebase 之后各检出的 head。没有授权的 rebase，即正常复盘之后那一次，不写这个事件。
- **槽位（约束 5）。** `Behind` 让任务以 `Requeued{resume: Rebase}` 交还槽位，由 `fill_slots` 在有空位时按提交顺序重新放进去。同一个 tick 的第 3 步就会尝试；`Rebase` 之后的 `MergeGate`、`Merging` 沿用同一个槽位。槽位已满时，任务对外显示为排队中（resume = rebase），等任一占槽任务停到等你、完成、失败或暂停后自动继续，不需要再按合并。自动路径因此不会越过并行上限。`(AwaitMerge, Merge)` → `Merging` 本来就不查槽位，这一步保持原样（约束 3）。

  按下合并到 `Behind` 之间，任务以 `Active{Merging}` 短暂占着一个槽位，这一段**不会让并行上限被越过**。依据是 tick 的顺序（`scheduler.rs:152` 起 `tick_locked`）：第 2 步执行核心步骤，第 3 步才 `fill_slots`。`Merging` 是纯 Git 步骤，不启动会话、不跑门禁，在第 2 步里一次做完并经 `Behind` 转成 `Requeued{Rebase}`，让出槽位，到 `fill_slots` 数槽位时它已不占。第 1、1b 步启动的只是已占槽位任务自己的下一轮，不新增占用。按下合并与下一次 tick 之间没有任何代码会为别的任务启动会话。因此约束 5 守护的资源（并行的会话与门禁）在任何一个可观察的时刻都不超过上限。要在按下的那一瞬就查槽位，必须让领域层在 `(AwaitMerge, Merge)` 就知道是否落后，这是 I/O，会改变默认分支没动时的行为（约束 3），所以不做。
- **工作区项目与部分合并（约束 7）。**
  - 阶段一保证在「只因落后被拒」时一个仓都不先合并。
  - 部分合并只可能来自阶段二：①某仓因脏或不在默认分支被拒、其它仓已合并，这是现有行为，任务退回 `await_merge`；②竞态，阶段二汇总为 `Behind`，任务进自动路径。
  - 之后的 `rebase_all` 对所有成员仓执行 `git rebase base`。已并入的仓，其任务分支已包含于 base，rebase 只做快进。
  - 再次合并时，这些仓被 `is_ancestor(branch, base)` 跳过。所以不会产生第二个合并提交，也不会丢合并。

### 4. 合并面板与命令行

- **`task_changes`（`dispatch.rs`）。**
  - 逐仓：`mergeable` 改为 `blocking.is_empty()`；`blocked_by` 只在有冲突脏文件时给 `dirty_worktree`；新增 `behind: !on_top`。
  - 顶层：`mergeable`、`blocked_by` 的汇总逻辑不变；新增 `rebase_first`，即有未合并的仓 `behind` 时为真。

  这改变了 `mergeable` 在「只落后」时的取值，`needs_rebase` 也不再出现。按约束 2，理由与受影响读者如下：
  - **为什么必须改。** 不改的话，桌面端在默认分支前进后禁用合并按钮，验收 1 在桌面端不可达，而本任务不能改 `apps/`。
  - **字段含义没变。** 该字段的既定含义，见代码注释「The same judgement `merge_task_branch` makes … the panel must not tell the user a merge is blocked that the core would happily perform」与 e2e `the_merge_panel_reports_what_the_core_would_actually_do`，是「按下合并内核会不会被前置条件挡回」。本任务之后，内核对「只落后」会补齐并合并，所以按原含义它就应为真。变的是内核行为，不是字段含义。
  - **受影响的读者：**
    - 桌面端 `task.js:928`、`:1266`：按钮不再禁用，这是期望的结果；
    - `task.js:968` `repoSummary`：显示「可以合并」，与事实一致；
    - `task.js:980` 的 `needs_rebase` 文案：不再可达，无害；
    - `task.js:1281` 弹窗的「满足 · 主工作树干净且分支在最新默认分支之上」：只落后时与事实不符，记为 B-01；
    - `apps/desktop/test/fixtures.js`：没有 `needs_rebase` 夹具，不受影响；
    - 命令行 `render.rs` 与 `apps/web`：不读 `task.changes` 的这些字段（已 grep 核实）。
- **`render.rs::event_line`。**
  - `merge.auto` 且 `active:true` → `T-9 按合并时默认分支已前进（<仓>），自动 rebase 后再合并`；`active:false` → `None`。
  - `merge.rebased` → `T-9 已自动 rebase：<仓或任务分支> → <onto> @ <head 前 10 位>`，多仓以「；」连接。
  - 具体措辞由实现轮定，测试断言关键词「默认分支已前进」「自动 rebase」与短 sha。

### 5. 否决的做法

- **授权位放进 `Context` 新字段。** `task.rs` 测试里有 5 处 `Context{..}` 完整字面量（第 1211、1921、1950、2075、2093 行），加字段就要改已有测试（约束 3）。
- **授权位放进 `TaskState::Active{node}` 新字段。** 所有测试里的 `TaskState::Active{node: …}` 字面量都要改（约束 3）。
- **新增一个 `TaskState` 变体。** 需要在约 15 处非测试的匹配点逐一补分支，漏一处就是静默错误。而且排队和暂停也要带这一位，变体会成倍增加。
- **在 `tasks` 加列。** 需要 schema v5，与 K1 计划的 v5 冲突（约束 8）。
- **新增节点（如「自动 rebase」）。** 会改变对外节点集合，桌面端不认识（约束 2）。
- **由调度器在到达 `await_merge` 后自动重放一次 `Merge`。** 任务会短暂进入 `await_merge`，触发「等待我」，违背验收 1 的「中途不再停下来」。

### 6. 旧账本与兼容（约束 8）

- 不改 schema。
- 已停在 `await_merge` 的旧任务：按合并后按新行为走。
- 已停在 `merging` 的旧任务：下一个 tick 的 `merge_all` 按新分类处理，落后就进自动路径。
- 旧账本没有 `merge.auto` 事件，授权位读作假，因此 `rebase`、`merge_gate` 上的旧任务照旧停到 `await_merge`。
- 新增的事件种类与 `task.changes` 新字段对旧读者都是可忽略的增量。

## 风险与验证安排

**风险。**

- **授权位存在事件流里。** 读写顺序与延续规则见方案第 3 节。最坏情况只会多要用户按一次合并，不会出现无授权合并。M-01 的 D9、M-02 的 S3 专门守这一点。
- **槽位满时可能等很久。** 占槽任务要整轮跑完才让出槽位，这是约束 5 的直接后果。任务对外是排队中（resume = rebase），可以取消。
