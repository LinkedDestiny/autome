### D1-P01 · R1：首次进入 Merging 前未做槽位准入，越过并行上限

- 主张摘要：按合并先持久化 `Active{Merging}`（占槽），下一 tick 才发现落后并进 `Requeued{Rebase}`，其间 A、B 同时占槽，用量为 2。
- 设计位置：方案 §3「槽位」；M-02 / S5。
- 裁决：**部分采纳**（驳回「会越过并行上限」，采纳「S5 应覆盖这一段」）。
- 证据：`scheduler.rs:152` 起 `tick_locked`：第 2 步执行核心步骤，第 3 步才 `fill_slots`（`:209`、`:891`）。`Merging` 是纯 Git 步骤，不启动会话、不跑门禁；它在第 2 步里一次做完，`Behind` 转成 `Requeued{Rebase}` 后槽位已交还，`fill_slots` 数 `slots_in_use` 时 B 已不占。第 1、1b 步启动的只是已占槽位任务自己的下一轮，不新增占用。按下合并到下一 tick 之间，没有代码为别的任务启动会话。所以「并行的会话与门禁」（约束 5 守护的资源）在任何可观察的时刻都不超过上限。该短暂占用对每一次按合并都存在，是现状（约束 3）；要在按下瞬间准入，领域层必须先知道是否落后，那是 I/O，会改变默认分支没动时的行为。
- 修改落点：设计 §3「槽位」新增上述论证与不做按下瞬间准入的理由；M-02 的 S5 增加断言：对落后任务跑核心步骤阶段加 `fill_slots`，`slots_in_use` 始终等于上限、没有为它启动会话或 rebase。
- 复提计数：0。

### D1-P02 · R2：用拒绝之后的新查询推断旧拒绝原因

- 主张摘要：阶段二汇总时再调 `check_merge` 分类，反映的是新状态；实际被拒的原因是脏、之后被清理，会被误读成 `Behind` 而进自动路径，违背验收 3。
- 设计位置：方案 §1、§3 阶段二。
- 裁决：**采纳**。
- 证据：属实。设计原文在汇总时「对每个被拒的仓再调一次 `check_merge`」，`git.rs:718` 起的拒绝在当场返回不带类型的结果，两次检查之间有窗口。
- 修改落点：§1 新增 `BlockKind::MergeFailed` 与 `try_merge`（`merge_task_branch` 缩成它的薄包装，外部形状不变）；§3 阶段二改为使用 `try_merge` 当场返回的 `kind`，不重新查询，任何非 `Behind` 的当场拒绝都使汇总为 `Blocked`；M-01 新增 G3，M-02 新增 S7（脏仓与落后仓并存）。计数相应更新：M-01 lib 548、M-02 lib 554、M-03 lib 555、M-05 lib 555。
- 说明：脏文件在两次之间被清掉的竞态无法在单元测试里确定性地构造，守护靠结构（汇总不再查询）加 G3、S7。
- 复提计数：0。

### D1-P03 · R3：E3 的门禁夹具使 A 无法先合并

- 主张摘要：门禁「存在 `breaks-gate` 时失败」，而 A 引入该文件，A 自己过不了门禁，目标失败路径不可达。
- 设计位置：M-03 / E3。
- 裁决：**采纳**。
- 证据：属实。`run_gate` 对每个任务在其 worktree 的 head 上跑，同 head 才沿用；夹具条件同时作用于 A 与 B。
- 修改落点：E3 改为门禁仅在 `from-a` 与 `from-b` 同时存在时失败；A 只引入 `from-a`、B 只引入 `from-b`，各自过门禁，B 自动 rebase 到含 `from-a` 的 main 之后才失败；修复由替身删掉 `from-b`。保留其后的断言。
