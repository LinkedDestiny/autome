## 阻塞问题

### P01：已持有名额的 Active 任务失去收取路径后，仍会永久挡住健康任务

- **类别**：内部逻辑矛盾、违反任务目标。
- **追溯**：任务 §5 约束 5（名额须收回）、7（任何排队任务在有限个作业后轮到）、13（不得卡住其它任务）；设计方案 §2 第 67–108 行、§3 第 129–135 行、§4 第 161–166 行、§5 第 197–214 行；M-02 的名额释放与有限等待行为。
- **根因**：设计把持有者分成 Active 与非 Active，认为前者必然由正常业务路径 poll，后者才需要独立回收。`gate.queue_dropped` 只能移除等待者，不能释放持有者；而规则 (b) 又会保留 Active 任务已结束但未收取的作业。业务路径先报错或跳过 `ensure` 时，活作业无人超时处理，已结束作业也无人收取。

**反例 A：不需要挂死作业，已正常退出也会永久占位。**

1. N=1，A 在 Gate 启动作业，已经写了 `gate.started`；健康的 B 在另一项目排队。A 此时没有有效 `gate.queued`。
2. A 的任务 worktree 的 Git 元数据变得不可读，使读取 head 失败；主仓库的作业目录仍可读。A 的作业正常结束，留下 `.exit`。
3. `run_gate` 必须先调用 `gate_head(layout)` 才能得到当前 key 并执行旧 head 清扫。读取 head 失败后，既到不了清扫，也到不了 poll/结果记录。
4. A 仍是 Active Gate，节点上最后一条运行事件仍是匹配该日志的 `gate.started`，因此 §2(b) 使 `held=1`。错误处检查不到 A 的有效排队项，`gate.queue_dropped` 无事可做；非 Active 回收也不覆盖 A。
5. B 每次都能正常走到准入，但一直得到 `held >= limit`。它不是设计排除的「故障排队者」，仍被永久挡住。

**反例 B：没有错误返回，同样可能自锁。**

1. A 在 Gate / MergeGate / MainCheck / ReproCheck / FixGate 的门禁前准备已启动。此时从项目配置移除 `[setup]`，保留门禁命令；A 状态仍为 Active。
2. 以后 `run_gate` 因 `resolved.setup == None` 不再调用 `ensure`。准备正常结束后，`.started` 仍在，按 §2(b) 继续占唯一名额。
3. 随后的门禁没有「本次刚收完准备」的接续资格，走准入，因自己的遗留准备作业而排队。无错误、无状态迁移，退队和空闲任务回收均不生效，A 与其后的 B 都无法启动。

**源码依据与同类检查范围**：

- `crates/automed/src/scheduler.rs:3016` 先解析配置，`:3086` 先读 head，`:3107` 仅在存在 setup 配置时进入准备路径，`:3204` 才 poll 门禁；`:3375` 的 `gate_head` 将 Git 错误直接返回。设计新增清扫也必须依赖成功取得 head，因此不能补上反例 A。
- `crates/automed/src/setup.rs:75` 起的收尾路径才会 poll 准备，并在 `:105` 删除 `.started` 等文件；仅保留文件的计数规则不能使这个收尾自行发生。
- 同根因还覆盖：有效配置读取失败时的五种门禁；会话前准备在 `scheduler.rs:2217` 被冷却路由提前返回、或在 `:2228` 因配置移除跳过；Cleanup 在 `:2928` 因配置缺失跳过主检出准备。具体后果随节点是否迁移而异，但这些路径都不能用「Active 必然继续 poll」证明有限等待。非 Active 准备回收所用的“其配置的超时”在配置被移除/不可解析时也缺少确定来源。
- `gate::poll_as` 的超时杀进程只发生在被调用时（`crates/automed/src/gate.rs:148–189`）；它不是后台自动执行的定时器。

**与既有裁决的关系**：D1-P04 采纳后，新增了非 Active 超时回收和有效排队项退队；本条核对的正是修改后的机制。新反例针对已经持有名额、没有有效排队项的 Active 任务，以及不报错的准备配置移除路径，不是重复要求修复上一轮的暂停者或故障队首。D1-P01 的清扫依赖当前 head 可读，也不能处理本条反例。

**最低修订方向**：明确持有名额的作业在正常业务路径不可达时由谁收束，覆盖仍运行、已退出未收、配置移除/不可读三种情况。超时监督和遗留结果/文件处理不能仅靠 Active 分支必然走到 poll 的假设；对仍活着的作业不能只减计数，收束也不能伪造门禁通过。可将这些反例纳入 M-02 已有生命周期验收，不必增加新里程碑。

### P02：目录探测失败按零计数，会在仍有活作业时超额准入

- **类别**：违反任务目标。
- **追溯**：任务 §2 第 1 条（同一账本跨项目同一时刻最多 N 个宿主作业）、§5 约束 3（计数范围）、5（活作业占用）；设计目标 G1、方案 §2(a)、§5 第 178–180 行；M-02 准入行为。
- **根因**：设计明确规定「读不到某个项目目录时该项目的作业按 0 计，不报错」，将“无法确认”当成“没有作业”。这与 §2(a) 的活作业占名额规则冲突。

**具体反例**：

1. N=1，项目 P 的 A 已启动长期运行的宿主作业，账本仍记录该项目与任务。
2. P 的目录被临时移走或失去读取权限，原有进程仍在运行。移动目录或读取失败本身不会终止进程组。
3. 同账本另一健康项目 Q 的 B 请求准入。按 §5，无法读取 P 时 A 被按 0 个作业处理；若无其它排队者，`held=0`、`ahead=0`，B 获准启动。
4. A、B 同时消耗宿主资源，突破 N=1。P 是否能恢复、是否能写回退出文件，都不改变此次超额已经发生的事实。

**源码依据与检查范围**：`crates/automed/src/gate.rs:106–141` 启动作业后，由独立进程组后台运行；文件只是观测与收取手段，不是失去路径访问便自动撤销的名额。检查范围是 `held(ctx)` 枚举所有项目、任务及作业时的读取失败分支，尤其不能把权限错误/I/O 错误与已证实没有在途作业混为一谈。P01 处理“看得见但无人收”的名额泄漏，本条处理“看不见便当不存在”的漏计，二者需要不同处理。

**与既有裁决的关系**：第 1 轮裁决未讨论目录读取失败按零计数；这是对仍保留的显式规则的新反例，不涉及已冻结的主张。

**最低修订方向**：对可能仍有在途作业而无法探测的项目保留不确定占用或暂停新的宿主作业准入，给出可恢复的错误信息；能够证实没有相关作业时才按 0 处理。不要通过放任未知活进程并行来满足“其它任务能继续运行”；也不需要扫描整台机器或新增表。
