## 阻塞问题

### P01：head 在两次 tick 之间变化，会使旧门禁永久占位

- **类别**：关键事实错误、违反任务目标。
- **追溯**：任务 §5 约束 5（head 作废须释放名额）、7（有限等待）；设计方案 §2 第 73–86 行、§5 第 157–159 行；M-02 的「head 变化释放名额」预期。
- **根因与证据**：设计认为现有 `job.clear()` 足以处理 head 变化。实际 `crates/automed/src/scheduler.rs:3086–3091` 每次按当前 head 构造 Job，`3210–3223` 只 poll 这个 Job，末尾比较只能发现本次调用内的 head 变化。设计 §2(b) 却会枚举并保留旧 head 对应、已退出但尚未收取的作业。

具体反例（`concurrency = 1`）：

1. A 在 Gate 节点启动 SHA1 作业，写 `gate.started`。
2. 两次 tick 之间 head 变为 SHA2。下次 `run_gate` 找的是不存在的 SHA2 Job，进入新作业准入；SHA1 仍占名额，A 排队。
3. SHA1 正常退出。A 仍是同一 Active Gate 节点，最后一条运行事件仍是匹配 SHA1 日志的 `gate.started`，所以 §2(b) 继续计入 `held`。
4. 后续 tick 一直寻找 SHA2 Job，无人再 poll 或 clear SHA1。A 和队尾永久等待，即使所有进程已经结束。

**检查范围与最低修订方向**：覆盖所有按 head 建 Job 的非 MainCheck 门禁节点（Gate、MergeGate、ReproCheck、FixGate）。新 head 准入前须识别并收束同任务同节点的旧 Job，分别规定仍存活、已结束、Vanished 的处理；不能只依赖现有调用末尾的 head 比较。不要仅把旧作业从计数里删掉而放任活进程继续运行。

### P02：暂停期间释放的准备作业，恢复后仍可绕过准入

- **类别**：内部逻辑矛盾、违反任务目标。
- **追溯**：任务 §2 第 1 条（同一时刻最多 N 个宿主作业）、§5 约束 4–5；设计方案 §2 第 71–80、91–93 行与 §5 第 157–163 行；M-02 的连占名额及暂停恢复行为。
- **根因与证据**：§2 规定暂停任务的已结束准备作业不占位，§5 却把「准备作业存在且未 Vanished」当成接续豁免条件，没有证明其名额一直保留。`crates/autome-domain/src/task.rs:909–915` 暂停不杀作业，`933–950` 恢复 Paused 不清作业；`crates/automed/src/setup.rs:79–126` 可收取遗留 Done 作业，随后 `scheduler.rs:3181–3201` 直接启动门禁。

具体反例（`concurrency = 1`，项目有足够并行槽位）：

1. A 门禁前准备正在运行，用户暂停 A。
2. 准备在暂停期间结束。按 §2，A 非 Active，已结束作业释放名额。
3. B 获准启动门禁，占据唯一名额。
4. 恢复 A，并取得项目槽位。A 的准备 Job 仍存在、是 Done 而非 Vanished，按 §5 免准入接续；收完准备后直接启动 A 门禁。
5. A、B 同时运行，突破 N=1。

**检查范围与最低修订方向**：覆盖 worktree / verify 门禁前准备，以及离开 Active 后返回的接续路径。收取旧结果与启动后续作业须分开：已经释放名额的准备作业可收结果，但之后的新准备或门禁必须重新准入。只有持续持有名额的调用链才能沿用接续资格。

### P03：Fix 会话前准备排队，仍会提前消耗修复轮次

- **类别**：违反任务目标。
- **追溯**：任务卡第 2 条、任务 §5 约束 1（排队不动任何轮次与计数）；设计 G2、方案 §5 第 164–165 行、§6 第 183–184 行；M-02 会话前准备排队、M-05 预算不变要求。
- **根因与证据**：设计仅将会话前准备接入准入，并以「排队不 advance」论证 FixBudget 不变；但 `crates/automed/src/scheduler.rs:2026–2035` 在调用 `start_session` **之前**就写 `bug.fix_round_started`。准备准入才位于 `start_session` 内的 `2228–2251`。`crates/autome-domain/src/bug_loop.rs:234–236` 的 FixReview 拒绝会进入这条首次启动路径。

具体反例：A 占据唯一门禁名额；B 正在 FixReview，会话期间准备命令或 watch 输入发生变化。FixReview 打回后，内核申请新的 Fix，会先增加修复轮次，再发现需重跑准备、被准入挡住。此时没有新的 Fix `session.started`、没有 `setup.started`，却已经花掉一轮。入队之后再取快照，只能证明没有继续增加，不能证明排队未计预算。

**检查范围与最低修订方向**：覆盖所有 `Action::StartBugSession { step: Fix }` 的首次启动与准备排队交界，明确何时才记入本次修复轮次，并保证等待后真正启动只记一次。`scheduler.rs:3817–3829` 的重试直接调用 `start_session`，并不会每 tick 重走 `perform`；修订也不能让崩溃重试重复扣轮次。现有 T2 仅覆盖 ReproCheck 等门禁、T5 仅覆盖普通任务准备，不能替代这个预算路径。

### P04：设计保留两种无限阻塞，却仍宣称满足不饿死硬约束

- **类别**：违反任务目标。
- **追溯**：任务 §5 约束 7「任何排队任务在有限个作业之后一定轮到」；设计方案 §4 第 137–139 行、风险 R1/R3 第 441–447 行及 B-02。
- **根因**：有限等待证明依赖队首持续可推进、在途作业最终结束；设计自己的 R1/R3 明确允许这两个前提永久不成立，并只提供人工解除方式。

同类反例共两处：

1. **R1：不可推进的队首。** 队首在准入前持续读不到 Git head，每个 tick 只记错误，排队项仍有效。即使 `held = 0`，队尾仍被 `ahead != 0` 永久拒绝。源码 `scheduler.rs:203–216` 将内核步骤错误加入报告后继续循环，未改变该任务状态。
2. **R3：暂停的挂死作业。** N=1，A 的宿主作业挂死后被暂停，B 排队。按设计 A 不再 poll 超时且持续占名额；没有任何新作业启动，B 也可无限等待。原代码只对 Active 内核节点调用 `run_core_step`（同上），超时终止发生在 `gate.rs:148–188` 的 poll 中。

**检查范围与最低修订方向**：同时处理不可推进队首的自动退出条件，以及暂停在途作业的有界处理。保留真实活作业计数，但须给出无需用户手动解除、仍能满足约束 7 的路径。若确要接受例外，应由裁决轮明确处理与硬约束的冲突；写入风险或 Backlog 本身不能使该约束成立。本项针对通用可推进性规则，P01 则是正常退出旧作业造成的确定性自锁。

### P05：ReproCheck 超时的两条可见文案被排除在改动之外

- **类别**：关键事实错误、违反任务目标。
- **追溯**：任务 §5 约束 9（每条用户／会话可见门禁超时文案明确写「门禁超时」）；设计方案 §9 第 244–259 行、M-04 第 308–309、363–367 行。
- **根因与证据**：设计第 259 行认为 ReproCheck 的后续文案「已单独处理，不动」，但独立处理的只是原因码，不是符合要求的中文说明。

真实内核超时经过 `crates/automed/src/scheduler.rs:3254–3264` 的 `ReproDone { timed_out: true }` 后：

- `crates/autome-domain/src/bug_loop.rs:257–271` 构造 `Inject::ReproNotFailing { why: "timed_out" }`；`crates/automed/src/launcher.rs:398–406` 仍注入「复现检查没有失败……原因：timed_out……请重新定位并提交稳定的回归测试」。
- `scheduler.rs:1650–1678` 写 `bug.repro_missed`；`crates/autome-cli/src/render.rs:206–210` 仍显示「未复现……timed_out」。

首次 ReproCheck 被内核超时终止，即使按设计改完列出的七处，这两条仍没有明确写「门禁超时」，并继续把未得出结论的运行描述为没有失败／未复现。

**检查范围与最低修订方向**：把 `Inject::ReproNotFailing` 和 `bug.repro_missed` 两个展示分支补入 §9 与 M-04。真实内核超时时明确说明「门禁超时，本次不能据此断言未复现」；可保留既有 `why` 与 serde 形状，复用设计已选的 `tail` 判据。
