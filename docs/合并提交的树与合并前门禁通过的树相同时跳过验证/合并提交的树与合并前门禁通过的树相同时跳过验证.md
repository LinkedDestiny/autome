## 背景与现状

设计时核对过的事实（均来自源码，不是推测）：

1. **并行任务。** T-47（门禁排队，分支 `autome/宿主门禁按机器排队-gate`）已经设计定稿、正在实现，还没合进 main；T-61
   （`[gate] run = "before_merge"`，分支 `autome/门禁只在合并前跑一次-gate-run`）在设计轮，没合进 main。main 上
   `run_gate` 与任务文件 §6 的描述一致，本设计以它为准。T-61 的任务文件写明「MainCheck 不在范围内、行为不变」，与本任务
   没有语义冲突，只在 `config_io.rs` 读 `[gate]` 的同一段里各加一个键（见「风险」）。
2. **`run_gate` 的 MainCheck 路径**（`crates/automed/src/scheduler.rs::run_gate`，约 3127 行）：先解析配置并选门禁命令
   （没有 `[gate]` → 直接按通过结束，不写事件）；`Node::MainCheck` 分支取 `task.merge_commit`，工作区或没有合并提交 →
   `gate.skipped` 并按通过结束；否则在 `.worktree/_verify-<sha 前 12 位>` **立即建游离检出**（目录不存在时），返回
   `(检出, 合并提交)`；随后 `Job::at(.., "main_check", key)`，`!job.exists()` 时依次是 MergeGate 同 sha 复用（只对
   `Node::MergeGate`）、`[setup]` 准备（MainCheck 用 `verify_record`）、`gate::start`、写 `gate.started`；作业结束后写
   `gate.result`（`record_gate_result`），MainCheck 删除验证检出，失败时 `raise_alert("main_gate_failed")` 加
   `project.alert`，最后 `finish_gate`。
3. **合并一定是「main 是分支祖先」时的 `--no-ff`。** `git::check_merge` 在 main 不是任务分支祖先时返回 `Behind`；
   `merge_all` 遇到纯 `Behind` 就返回 `CoreStepResult::Behind`，状态机转 `Requeued { resume: Rebase }`，走自动 rebase →
   MergeGate → Merging（现有用例 `main_moving_after_the_press_takes_the_same_automatic_path` 守着这条）。所以单仓库项目里，
   合并提交的第一父提交总是分支的祖先，`--no-ff` 合并提交的树**恒等于**被合并的分支 head 的树。任务卡说的「合并时 main
   又前进、产生了真正的合并」在今天的代码里只剩两种来源：
   - `check_merge` 与 `git merge` 之间的竞争窗口（毫秒级，不可稳定构造）；
   - **分支 head 在 MergeGate 通过之后又动了**：MergeGate 通过后任务停在 AwaitMerge，按合并直接进 Merging，
     Merging 不再核对 head 是否就是 MergeGate 跑过的那个提交（用户在任务检出里手动提交即可造成）。这条是确定性的，
     验收 2 的 e2e 就用它构造（见方案 §7）。
4. **「通过的 MergeGate」在账本里的两种形状**：
   - 真跑：`gate.result { node: "merge_gate", sha, ok: true, command, … }`；
   - 沿用：`gate.reused { node: "merge_gate", sha }`，没有 `command`。它沿用的是当时**最近一条** `gate.result`
     （任意节点，通常是 `node: "gate"`），条件是 `ok == true`、`sha == head`，Bug 任务另要求 `command` 相同。
   MergeGate 失败写 `gate.result { node: "merge_gate", ok: false }`；结果出来时 head 已变则清掉作业、不写事件。
5. **Bug 任务的命令。** MergeGate（与 FixGate）跑 `( {repro} ) && ( {gate.command} )`，`repro` 取最近一条
   `bug.reproduced.command`；MainCheck 跑的是 `resolved.gate.command`（不带复现命令）。
6. **状态机。** `(Node::Merging, Ok)` 在配了 `[gate]` 时进 MainCheck；`(Node::MainCheck, _) => Cleanup`，不论结果。
   本任务不碰 `crates/autome-domain/src/task.rs`。
7. **熔断。** `gate_failure::counts` 只认 `Gate | MergeGate | FixGate`；`record_gate_result` 只在 `ok == false` 且
   `counts(node)` 时按**同一 node** 查上一条 `gate.result`/`gate.reused`。`main_check` 节点不参与，也不会被别的节点查到。
8. **读者。**
   - `autome-cli/src/render.rs::event_line`：`gate.reused` 统一打印「{任务} {节点名}：提交 {sha} 已经通过过，沿用」。
   - `dispatch.rs` 的 `task.get.gate` = `last_event(task, "gate.result")`；`autome status`（`autome-cli/src/main.rs`
     约 667 行）与桌面端 `task.js::hostTags` 都读它。现有 MergeGate 复用之后，这里显示的是被沿用的那次真跑结果。
   - `apps/desktop`、`apps/web` 只有 `main_check` 的节点文案，没有任何代码按 `gate.*` 事件种类分支（已 grep 核对）。
9. **配置。** `ProjectConfig.gate_same_failure_limit: Option<u32>` → `Resolved.gate_same_failure_limit: u32`（缺省 3）；
   `config_io.rs::parse_project` 在 `[gate]` 表里、在检查 `command` **之前**读 `same_failure_limit`，非法值报
   `[gate] same_failure_limit 必须是 1 到 10 的整数`。`save_project` 用 `toml_edit` 改写，不动 `[gate]` 表（现有用例
   `a_gate_and_a_retry_policy_are_read_from_the_project_file` 覆盖）。
10. **git 封装**（`crates/automed/src/git.rs`）没有取树 id 的函数；`head_sha` 的写法是 `run_ok(repo, &["rev-parse", "HEAD"])`。
11. **现有用例基线**（`cargo test --workspace -- --list`，设计时实测）：全工作区 1209 个；`autome-domain` 384（其中
    `config::` 31）；`automed --lib` 650（`config_io::` 40、`git::` 35、`scheduler::` 87）；`automed --test end_to_end` 112；
    `autome-cli` 的 `autome` 二进制单元测试 25（`render::` 15）。

## 目标与非目标

**目标。**

- 进入 MainCheck、还没为这个合并提交建验证检出也没有作业时，如果开关打开，且「合并提交的树」与「本任务最近一次通过的
  MergeGate 所在提交的树」相同、那次通过所用的命令覆盖了现在 MainCheck 要跑的命令，就不建检出、不跑准备、不启动作业，写
  `gate.reused { node: "main_check", sha: <合并提交>, from_sha: <MergeGate 的提交>, tree: <树 id> }`，按通过推进到
  Cleanup（卡 1、4）。
- 其它情况（树不同、没有可认定的通过记录、命令不符、取树失败、开关关闭）与今天逐事件相同（卡 2、3、6，约束 2）。
- `autome run` 对这条事件打印「T-x 验证 main 沿用合并前门禁的结果（内容相同）」（卡 5）。
- `[gate] reuse_for_main_check`，布尔，缺省 true（卡 6，约束 7）。
- README「Host gate, retries and cooldowns」与 `docs/development/technical-design.md` §8.1「宿主门禁」各补一句（验收 5）。

**非目标**（任务文件 §4「不在范围内」照录，外加本设计的决定）：

- 不改 MergeGate、Gate、FixGate、ReproCheck 的行为与事件；不改现有 `gate.reused { node: "merge_gate", sha }` 的内容。
- 不改 MainCheck 失败「只报警」的语义；不改状态机节点与转换；不新增 JSON-RPC 方法；不改 `protocol/`、`plugins/`、`.autome/`。
- 工作区项目照旧 `gate.skipped`。
- 不比较树以外的东西。不为「分支 head 在 MergeGate 之后又动了还能直接合并」这条现有缺口加核对（那是另一个问题，
  超出任务范围；本任务在这种情况下照常跑 MainCheck，正好兜住）。
- 不实现门禁排队；不改 `task.get.gate`、`autome status`、桌面端、Web 面板（理由见方案 §5）。
- 不顺手重构 `run_gate`、`gate.rs`。

## 方案

### 1. 判断放在哪：MainCheck 分支里、建验证检出之前（约束 3）

在 `run_gate` 的 `Node::MainCheck` 分支里，紧接在「工作区 / 没有合并提交 → `gate.skipped`」那段之后、
`let rel = verify_dir(&commit); if !repo.join(&rel).exists() { worktree_prune; worktree_add_detached; … }` 之前，加一段
独立的早退：

```text
let rel = verify_dir(&commit);
let job = gate::Job::at(&repo, &task.id, "main_check", &commit[..12]);
if resolved.gate_reuse_for_main_check           // 开关（§4）
    && !repo.join(&rel).exists()                // 首次进入：还没建验证检出
    && !job.exists()                            //           也没有作业
    && let Some(reused) = main_check_reuse(…)?  // 认定（§2），只读，不写任何东西
{
    append_event("gate.reused", task, reused);
    return finish_gate(…, GateOutcome::Passed);
}
// 以下是今天的代码，原样不动：建检出 → 返回 (检出, 合并提交) → job → setup → start …
```

- **为什么要「首次进入」两个条件。** 第一次 tick 判定「不复用」后已经建了验证检出、可能有在途的准备作业或门禁作业；
  这时如果后续 tick 因为开关被改等原因转去复用，检出与作业就没人收了。只在两者都不存在时考虑复用，已经开始的 MainCheck
  一律按今天的路径跑完。判定是确定性的（同样的账本、同样的树），正常情况下第二个 tick 不会改判。
- **为什么在建检出之前。** 约束 3 要求复用时不建 `.worktree/_verify-<sha>`、不跑准备命令。今天的检出建在
  `!job.exists()` 判断之前，所以判断必须再往前提，放在 MainCheck 分支内部。
- **与 T-47 的先后。** T-47 设计（其设计文档 §5「接入点」）把准入放在每一个「要起进程」的点：`setup::ensure` 里起准备
  作业之前、`run_gate` 里 `gate::start` 之前，并明确「不启动作业的路径不排队」（MergeGate 沿用、工作区 `gate.skipped`
  都在准入之前返回）；它的旧 head 清扫不作用于 MainCheck。本段早退在验证检出之前，自然在这两个准入点之前，不写
  `gate.queued`、不占名额。谁后合谁 rebase：本段是 MainCheck 分支里的一处新增，不改 T-47 会动的那几行（`!job.exists()`
  分支、`ensure`、`gate::start`），冲突面只有相邻行。
- `main_check_reuse` 是 `scheduler.rs` 里的一个私有函数，只读账本和 git，返回 `Result<Option<Value>>`（`Some` 即要写的
  事件负载）。账本读取失败按现有风格 `?` 上抛（与现有 MergeGate 复用一致，本 tick 不推进、不写事件）；git 失败一律
  当作「不复用」。

### 2. 「本任务最近一次通过的 MergeGate」怎样认定（约束 4、5、6）

`main_check_reuse` 按顺序判，任何一步不满足都返回 `None`（照常跑）：

1. **找最近一条 MergeGate 记录。** `P = store.last_event_in(task, ["gate.result", "gate.reused"], "node", "merge_gate")`
   （按 `seq` 取最大）。没有 → `None`（卡 3：门禁是任务停留期间才配上的、或 MergeGate 从没跑过）。
2. **它必须是通过。** `P` 是 `gate.result` 时要求 `ok == true`；`P` 是 `gate.reused` 时本身就是通过。最近一条是失败
   → `None`——即使更早有过一次通过，也不拿那次（失败退回实现轮之后，任务必须再过一次 MergeGate 才能走到合并）。
3. **取得那次通过的真跑记录 `R`。** `P` 是 `gate.result` → `R = P`。`P` 是 `gate.reused`（没有 `command`）→
   `R = store.last_event_in(task, ["gate.result"], "sha", P.sha)`，并要求 `R.ok == true`；找不到 → `None`。
   这就是 MergeGate 当时沿用的那次运行（它的条件正是 `ok` 且 `sha == head`）；如果之后同一 sha 又跑过一次，取到的是
   更新的那次，失败就不复用——只会更保守。
4. **命令要覆盖 MainCheck 要跑的命令。** 设 `gate.command` 为本 tick MainCheck 要跑的命令。
   - 需求任务：要求 `R.command == gate.command`。
   - Bug 任务：取最近一条 `bug.reproduced.command` 为 `repro`，要求 `R.command == format!("( {repro} ) && ( {gate.command} )")`
     （与 `run_gate` 拼 MergeGate 命令的格式逐字相同）。没有 `bug.reproduced` → `None`。
   理由（约束 6）：树相同只说明代码相同，结论还取决于跑的是什么命令。任务停在 AwaitMerge 期间用户可能改了
   `[gate] command`；Bug 任务的通过记录也可能来自只跑复现命令的运行（例如 T-61 合入后 `before_merge` 下的 FixGate）。
   `( A ) && ( B )` 退出码为 0 当且仅当 A、B 都以 0 结束，所以 Bug 的 MergeGate 通过蕴含门禁命令通过。需求任务也比较
   命令，比现有 MergeGate 复用更严一点，符合「宁可多跑，不可误跳」。`timeout_minutes` 不比较：通过就是在时限内跑完了。
5. **比较树。** `from_sha = R.sha`。`t_merge = git::tree_id(repo, merge_commit)`、`t_from = git::tree_id(repo, from_sha)`，
   任一失败（提交不存在、仓库读不了）→ `None`；`t_merge != t_from` → `None`。
6. 相同 → `Some({ "node": "main_check", "sha": merge_commit, "from_sha": from_sha, "tree": t_merge })`。

**为什么这样取到的是「合并前最后那一次」，以及取错了也不会误跳。** 任务从 MergeGate 走到 MainCheck 只有两条路：
MergeGate 通过 → AwaitMerge → 按合并 → Merging；或按合并后 `Behind` → Rebase → MergeGate 通过 → Merging。两条路上
最后一个 MergeGate 事件都是让它走到合并的那次通过；MergeGate 失败会退回实现轮，之后要再有一次通过才可能合并，所以
「账本里 node 为 `merge_gate` 的最后一条」就是合并前最后那一次。另一方面，复用的充分条件是「`R` 证明命令 C 在树 T 上
退出 0」加上「合并提交的树就是 T」加上「MainCheck 要跑的就是 C（或被 C 蕴含）」——这三条本身就保证 MainCheck 会在
同一份内容上跑同一条命令；即使 `P` 意外是更早一轮的记录，只要三条成立结论仍然成立，不成立就照常跑。

### 3. 事件（约束 1）

`gate.reused { node: "main_check", sha: <合并提交完整 sha>, from_sha: <R.sha 完整 sha>, tree: <git 给出的树 id> }`。
只新增 `from_sha`、`tree` 两个字段；MergeGate 的复用事件保持 `{ node, sha }` 不变。复用路径不写 `gate.started`、
`gate.result`、`setup.*`、`project.alert`。

`git.rs` 新增：

```text
/// The id of the tree a commit points at.
pub fn tree_id(repo: &Path, commit: &str) -> Result<String>
    // run_ok(repo, &["rev-parse", "--verify", "--quiet", &format!("{commit}^{{tree}}")])
```

### 4. 配置（约束 7）

- `autome-domain/src/config.rs`：`ProjectConfig` 加 `gate_reuse_for_main_check: Option<bool>`（serde default、
  `skip_serializing_if = "Option::is_none"`，与 `gate_same_failure_limit` 同样写法）；`Resolved` 加
  `gate_reuse_for_main_check: bool`，`resolve` 里 `unwrap_or(true)`。只在项目级，全局配置不认。
- `automed/src/config_io.rs::parse_project`：在 `[gate]` 表里、与 `same_failure_limit` 并列、在检查 `command` 之前读：
  `t.get("reuse_for_main_check")` 存在时必须 `as_bool()`，否则报 `[gate] reuse_for_main_check 必须是 true 或 false`。
  `save_project` 不改（它不碰 `[gate]`），用新单元测试守住「保存后手写的值还在、重新加载仍生效」。
- 工作区项目：开关照读，但 MainCheck 在它生效之前已经 `gate.skipped`，无影响。

### 5. 读者（卡 5）

- `render.rs::event_line`：在现有 `"gate.reused"` 分支之前加一条守卫分支：`"gate.reused" if p["node"] == "main_check"`
  → `format!("{subject} 验证 main 沿用合并前门禁的结果（内容相同）")`。MergeGate 的复用文案不变。
- `task.get.gate`（及读它的 `autome status`、桌面端门禁标签）**不改**。核对结果：它只看 `gate.result`；MainCheck 复用后，
  最近一条 `gate.result` 就是被沿用的那次真跑（MergeGate 的，或 MergeGate 当时沿用的 Gate 的），显示「合并前门禁通过 ·
  <sha>」或「门禁通过 · <sha>」，与今天 MergeGate 复用之后的显示方式完全一样，内容属实，没有显示错误——这正是
  「按现有 `gate.reused` 的处理显示」。
- 桌面端、Web 面板不按事件种类显示门禁事件，不改。

### 6. 不变的路径（约束 2、8）

- 开关关闭、找不到通过记录、命令不符、取树失败、树不同：`main_check_reuse` 返回 `None` 或根本不调用，之后的代码一字未改，
  `_verify-<sha>` 检出、`[setup]` 准备、`gate.started`/`gate.result`、`main_gate_failed` 报警全部照旧。
  `main_check_reuse` 只读不写，所以这些路径上不会多写事件。
- 没有 `[gate]`：在 MainCheck 分支之前就按通过结束，不经过本段。工作区：在本段之前 `gate.skipped`。
- 熔断：新事件的 `node` 是 `main_check`。`record_gate_result` 只为 `counts(node)` 为真的节点、按同一 node 查上一条，
  `main_check` 不在其中，别的节点也查不到它，所有节点的计数结果不变。

### 7. 测试安排与现有用例逐条处理（验收 1–4）

**e2e 构造。**

- **计数门禁脚本。** 在 `end_to_end.rs` 加一个带参数的任务夹具（例如 `run_gated_task_with(w, request, opts)`，选项：
  是否计数、`reuse_for_main_check` 写 `true`/`false`/不写）。计数时 `[gate] command` 指向一个包装脚本：先
  `echo "$AUTOME_GATE_NODE" >> {root}/gate-calls`，再 `exec sh {root}/gate.sh`。`write_gate_script` 与现有
  `run_gated_task` 的行为不变（`run_gated_task` 改为调用新夹具的缺省选项）。`[gate]` 块由夹具一次写全，不靠在文件末尾
  追加键。
- **「rebase 后过 MergeGate 再合并」**：任务停在 AwaitMerge 后，在主检出提交一个无关文件（main 前进），再 `task.merge`、
  `settle`：Merging 报 `Behind` → 自动 rebase → MergeGate 在新 head 上真跑 → Merging → MainCheck。
- **「合并提交的树与 MergeGate 的树不同」**：沿用现有用例 `main_moving_after_the_press_takes_the_same_automatic_path`
  的确定性窗口写法——`scheduler::apply_trigger(&mut w.ctx, &id, &Trigger::Merge)` 让任务停在 `merging`（`task.merge`
  会顺带 tick 一次，不能用它），然后在任务检出 `.worktree/<slug>` 里提交一个新文件 `late.txt`（`git::commit_paths`），
  再 `settle`。Merging 合并的是带 `late.txt` 的 head，合并提交的树 ≠ MergeGate 跑过的树。抽成夹具
  `merge_after_a_late_branch_commit(w, id)`，验收 2 的新用例与下面三条改写共用。
  选它而不是「main 前进」的理由见「背景与现状」第 3 条：main 前进一定走自动 rebase，MergeGate 会在新 head 上重跑，
  合并提交的树又等于它，构造不出树不同。
- **事件投影** `gate_trace(w, id) -> Vec<String>`：取该任务主体的事件，只留种类为 `gate.started`、`gate.result`、
  `gate.reused`、`gate.skipped`、`setup.started`、`setup.result`、`setup.skipped`、`merge.auto`、`merge.rebased`、
  `merge.repo` 的，按 `seq` 排序，每条记成 `"{kind}:{node}"`（无 `node` 字段的记 `"{kind}"`）。

**新增 e2e（3 个，名字都以 `main_check_reuse_` 开头）：**

- E1 `main_check_reuse_skips_the_run_when_the_merge_commit_has_the_merge_gate_tree`（验收 1）：计数、不写开关（缺省）、
  rebase 后合并。断言：任务 `done`；没有 `node == "main_check"` 的 `gate.started`/`gate.result`；恰好一条
  `gate.reused{node: "main_check"}`，其 `sha == merge_commit`、`from_sha == 最后一条 gate.result{node: merge_gate}.sha
  == merge.rebased 记录的 head == git rev-parse {merge}^2`、`tree == git rev-parse {merge}^{tree}`；结束时 `.worktree` 下没有
  `_verify-` 目录（复用不建检出；若检出建在早退之前，复用路径不会删它，这条断言就会红）；没有 `node == main_check` 的
  `setup.*` 事件；`gate-calls` 按节点计数为 `gate` 2、`merge_gate` 2、`main_check` 0，共 4 行；没有报警。
- E2 `main_check_reuse_runs_when_the_merge_commit_tree_differs`（验收 2）：计数、缺省开关，用
  `merge_after_a_late_branch_commit`。断言：任务 `done`；没有 `gate.reused{node: main_check}`；恰好一条
  `gate.started{node: main_check, sha: merge_commit}` 与一条 `gate.result{node: main_check, ok: true}`；合并提交里有
  `late.txt`；结束后 `_verify-` 检出与 `verify_record` 都已删除（接手改写前 R1 守的「验证检出用完即删」）；`gate-calls`
  里 `main_check` 恰好 1 行。
- E3 `main_check_reuse_switched_off_matches_today_event_by_event`（验收 3）：与 E1 同一构造，只是 `reuse_for_main_check
  = false`。断言：`gate_trace` **等于一份写死的字面量**；`gate-calls` 按节点为 `gate` 2、`merge_gate` 2、`main_check` 1，
  共 5 行（= E1 的 4 行 + 1，即验收 1 的「比今天少一次」）；没有 `gate.reused{node: main_check}`；`_verify-` 检出已删除。
  **字面量的来历**：M-02 的实现轮先只写夹具与 E3，在**未改 `run_gate`** 的代码上跑 E3、把得到的 `gate_trace` 冻结成
  字面量并提交，证据文件记下那次提交的 sha 与输出；之后再改 `run_gate`，E3 一字不改仍须通过。审计轮可在那个提交上复跑
  E3 确认字面量就是「今天」的行为。

   E3 的投影没有包含 `gate.queued`，T-47 合入后在单名额下这个场景是否会排队需要届时核对。
3. **与 T-61 的合并顺序。** 两边都在 `config_io.rs` 的 `[gate]` 解析段各加一个键、在 `config.rs` 各加字段，后合的一方
   rebase 时解决相邻行冲突即可。T-61 的验收要求「门禁脚本恰好被调用一次（MergeGate）」并要求说明怎样与 MainCheck 那一次
   区分——本任务先合入时，那个场景里 MainCheck 会被沿用、不调用脚本；只要 T-61 按 `AUTOME_GATE_NODE` 或按 `node` 计数
   就不受影响，若它按总数减一计数则会差一。由后合入的一方核对。
4. **与 T-47 的合并顺序。** 见方案 §1：本段早退在 T-47 所有准入点之前，冲突只在相邻行。T-47 先合入时，本任务 rebase
   后在 `run_gate` 里重新确认早退仍在 `worktree_add_detached`、`setup::ensure`、`gate::start` 与准入判定之前。
5. **崩溃窗口。** 写 `gate.reused` 之后、`finish_gate` 推进之前进程退出，下一次 tick 会再判一次并再写一条
   `gate.reused`。现有 MergeGate 复用有同样的窗口，后果只是多一条事件，不会误跳或漏跑，不另做处理。
6. **e2e 时长。** E1–E3 各是一条完整任务（含两次 Gate 与两次 MergeGate），与现有门禁 e2e 同量级，`end_to_end` 增加
   约三条用例的时间，可以接受。
