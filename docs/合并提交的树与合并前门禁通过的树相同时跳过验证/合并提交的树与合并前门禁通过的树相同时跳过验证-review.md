## 问题

### R1-P01：结果事件中的命令不一定是实际执行的命令，可能错误跳过新的门禁

- 类别：**关键事实错误**；严重度：P1。
- 违反条款：任务 §5 约束 4“认不准就照常跑——宁可多跑，不可误跳”；设计“目标”第 1 条及方案 §2 第 3–4 步，要求那次通过所用的命令覆盖当前 MainCheck 命令。
- 设计位置：方案 §2 以 `R.command` 认定执行过的命令，以及该节末尾“R 证明命令 C 在树 T 上退出 0”的论证。
- 根因与证据：`crates/automed/src/scheduler.rs:3134` 每次调用 `run_gate` 都重新解析配置；`:3780` 的 `resolve_config` 每次重读项目文件。`:3301` 启动作业，`:3310` 的 `gate.started` 记录启动时命令；但完成时 `:3339–3346` 的 `gate.result.command` 使用当前 tick 的 `gate.command`，没有从启动记录恢复。因此结果中的命令并非可靠的执行凭据。

具体反例：

1. 提交 H 上的 MergeGate 启动命令 A，A 最终返回 0。
2. 作业运行期间把项目门禁命令改成 B；令 B 在相同内容上必定返回非零。
3. 下一次收集结果时，现有代码记录 `gate.result { node: merge_gate, sha: H, ok: true, command: B }`，实际跑完的是 A。
4. 合并提交的树等于 H，当前配置仍为 B。方案 §2 所有条件成立，写 `gate.reused{node: main_check}` 并直接 Cleanup。
5. B 从未执行；原有 MainCheck 会执行 B 并报警，新路径却省略了它。

检查范围：真跑的 MergeGate，以及 MergeGate 复用的 Gate/FixGate 真跑结果，都由同一 `run_gate` 产生，存在相同的证据问题；Bug 的组合命令也应按实际启动内容认定。

建议修改：只在 MainCheck 的只读认定中核对 R 所属运行的 `gate.started`，以对应的 node、sha、事件顺序及启动命令建立执行依据；无法对应或命令不一致时照常跑。不要为修本问题改变 Gate/MergeGate 的既有行为。增加“运行中 A 改为 B”的反例，保留命令未变时可复用的正向对照；仅手工写一条 `command: B` 的成功结果不能验证这一问题。

### R1-P02：配置移除会留下无结果事件的最后一轮，历史最新 MergeGate 不等于合并前最后一轮

- 类别：**违反任务目标**；严重度：P2。
- 违反条款：任务 §5 约束 4，明确要求保证取到“合并前最后那一次而不是更早一轮的记录”，无法认定时照常跑。
- 设计位置：方案 §2 第 1–2 步，以及末尾“只有两条路”“即使 P 意外是更早一轮的记录……仍然成立”的论证。
- 根因与证据：只对 `gate.result` / `gate.reused` 取最大 seq 没有约束所属轮次。`crates/autome-domain/src/task.rs:1262–1276` 在 Rebase 完成且没有 gate 时直接绕过 MergeGate；`crates/automed/src/scheduler.rs:3174–3178` 在已进入 MergeGate 后移除配置，也按 Passed 推进且不写成功结果事件。两条路径都会保留旧 P。

具体反例：旧轮在 H 上通过 MergeGate 并停在 AwaitMerge；main 增加一个空提交，按合并触发自动 Rebase；在本轮 Rebase 完成时临时移除 gate，任务绕过 MergeGate 进入 Merging；下一 tick 前恢复原门禁命令；合并后按恢复的配置进入 MainCheck。空提交不改变树，旧 H 与合并提交的树可以相同，于是方案沿用旧轮 P，尽管最后一轮没有可认定的 MergeGate 通过记录。

该调度窗口真实存在：`scheduler.rs:2160–2164` 明确将 `Action::RunCoreStep` 留到下一 tick 执行，不会在 Rebase 的转换中同步完成 Merging。本问题是时序契约违例，不主张同树旧结果必然导致测试失败。

检查范围：Rebase 时已移除 gate、进入 MergeGate 后才移除 gate，这两种无事件通过路径均需处理。建议将 P 绑定到最后一轮合并前检查的事件范围，核对已有转换/Rebase 证据；不能确认本轮成功时返回 None。不能以“更早记录同树同命令也有效”替代任务规定的轮次约束。

### R1-P03：E2 替换了验收 2 指定的 main 前进场景，无法识别拿分支树代替合并树的错误实现

- 类别：**违反任务目标**；严重度：P2。
- 违反条款：任务卡“验收标准”第 2 条、任务 §3 验收 2，要求“按下合并后 main 再前进一步（走自动 rebase 之外、让合并提交的树与 MergeGate 的树不同的构造）”。
- 设计位置：方案 §7 的 `merge_after_a_late_branch_commit`、E2，以及“测试与验收对照”中声明 E2 覆盖验收 2 的一行。
- 根因：设计改为在任务分支提交 `late.txt`，main 没有前进。该场景能验证一种树不等，但没有覆盖任务明确指定的另一侧变化。

可区分的错误实现：若误用“合并提交第二父提交的树”代替“合并提交自身的树”进行比较，当前 E1 仍能复用，当前 E2 的第二父提交已含 `late.txt`、与通过门禁时的树不同，也会按预期真跑。两个用例都可能通过。但在 main 于检查后前进、任务分支未变的真实合并中，第二父提交仍等于门禁通过的树，合并树却包含 main 的新改动，错误实现会误跳 MainCheck。

源码依据：`crates/automed/src/git.rs:824` 检查 main 是否为分支祖先；`:840–853` 在 `check_merge` 返回后另行调用 `git merge --no-ff`，检查与合并之间存在窗口。设计“背景与现状”第 3 条也承认此窗口，却以难以稳定构造为由换了场景。

检查范围：E2、共用 late-branch 夹具、验收对照表。建议保留 late-branch 夹具用于 R2–R4，同时为验收 2 明确确定性的 main 前进构造，使实际合并树不同于第二父树且不同于门禁通过的树；用上述错误比较作为负向对照。若决定放弃任务卡原场景，应由裁决明确处理该偏离，不能直接声明已覆盖。此项是指定验收对象被替换，不是要求笼统增加测试。
