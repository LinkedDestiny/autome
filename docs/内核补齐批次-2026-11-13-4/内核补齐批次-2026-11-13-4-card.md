# 内核补齐批次（2026-11-13）：十一项需求与缺陷一次设计、一次评审，按项分组里程碑依次实现

## 背景

2026-11-13 用户确认的做法：一个大的工作只跑一次完整循环，不要每个细分需求各跑一遍「任务整理 → 设计 → 评审 → 裁决 → 批准」，也不要每个小缺陷各开一个 Bug 循环——太消耗资源。这张卡把当时排队中、尚未开始的全部内核工作合成一个任务：六项需求（原 T-79、T-85、T-80、T-88、T-91，以及已做完实现、卡在合并前的原 T-69）与五项缺陷（原 T-78、T-89、T-90、T-83，以及 T-68 合并后新发现的一项），原任务均已取消。十一项的完整任务卡原文在下面「要做什么」里，一字未删，只是标题降了级。

它们都落在内核同一批文件上（`scheduler.rs`、`dispatch.rs`、`task.rs`、`bug_loop.rs`、`brief.rs`、`protocol/mod.rs`），分开做会互相 rebase 冲突，「补一个能改代码的轮次」「会话结束事件」「保护集基线」这类机制还会被各自设计一遍。

## 要做什么

十一项。实现顺序：**K 最先**（代码已存在，见 K 小节），然后 A → B → C → D → J → E → F → G → H → I（J 与 A–D、K 同属「里程碑关闭后的轮次与守卫」）：

- **A（需求）**：Bug Loop 补一条路：回归测试本身有缺陷时，修复轮 / 复核轮可以把任务退回定位轮修测试
- **B（缺陷）**：失败 / 已停止的 Bug 任务无法补充信息：`autome reply` 报「Bug 节点不使用需求转换表」（重提，原 T-75）
- **C（缺陷）**：Bug 任务第二次定位（reply 之后、或 rerun locate）被判「回归测试保护集为空」：保护集只看本次会话的改动
- **D（需求）**：给进行中的任务捎一句话：`autome note <任务> "…"`，下一个实现 / 修复轮的简报原样带上
- **E（需求）**：快检和复现检查不该排在别人的完整门禁后面：给轻量的宿主检查单独一条车道
- **F（需求）**：任务详情页缺的内核数据：Bug 文档与复盘教训进文档清单、已完成任务仍能读文档、改动带类型、按任务读事件、会话结束事件
- **G（需求）**：项目管理页缺的内核数据：probe 提前给出拒绝原因、Onboarding 会话进账本、config.get 给全字段、dashboard.get 不被一个坏配置拖垮
- **H（缺陷）**：工作区项目的 Onboarding 完成或跳过时必报内部错误：在不是仓库的工作区根目录做 init commit
- **I（缺陷）**：每个任务每次开会话都记一条「协议副本被改过」的完整性警告：记录的哈希含 evals/，任务副本不含
- **J（缺陷）**：新守卫 `impl_closed_milestone` 把旧协议版本的在跑任务判协议失败：旧 prompt 让实现轮更新「最新证据」指针
- **K（需求，已有实现）**：审计 / 复盘 / 复核轮越界改动时内核自己还原并转交实现轮，不再让任务失败等人

A、B、C 是同一组（Bug Loop 的健壮性），G、H 是同一组（项目与 Onboarding）。

对设计轮与评审轮的总要求：

1. **一份设计文档覆盖十一项。** 里程碑按项分组、同一项的里程碑连续排列，标题以「A·」「B·」… 开头；需求每项 1–3 个里程碑，缺陷每项 1 个（同一组里改同一段代码的缺陷可以并进相邻需求的里程碑，但验收条目要分开列）；总数不超过 16 个（本任务不适用「超过 6 个里程碑就拆分」的惯例，这是有意的）。每个里程碑仍然要能独立验收。
2. **按项推进。** 前一项的里程碑全部审计通过后再开始下一项；后面的项不得成为前面验收的前提。某一项在设计阶段被判定做不了或应当缩小范围，写进争议项或 Backlog，不拖住其余各项。
3. **缺陷项的做法。** 缺陷小节是按 Bug 任务卡写的，里面「定位轮 / 修复轮 / 复核」是 Bug Loop 的说法，在本任务里对应：设计轮确认根因并写明回归测试放在哪；实现轮**先提交一个修复前失败的回归测试、再修**，证据里要有同一条命令修复前失败、修复后通过的两次输出；审计轮核对根因、回归测试是否有意义、改动是否最小。小节里「复现命令写成仓库根目录可直接执行」「回归测试提交前跑 `cargo fmt --all -- --check`」照做。
4. **共用机制只设计一次。** 至少核对这几处并在设计文档里写明归属：
   - 「里程碑都关闭之后还需要一个能改代码的轮次」——A（退回定位轮修测试）、D（审计通过后补一个实现轮处理备注）、K（越界补丁交给实现轮）与已合并的 T-68（里程碑之外的实现轮要被审）是同一类机制，用同一套，不另造；以 main 上 T-68 的实现为准，K 的原实现按它对齐。
   - Bug 任务在失败 / 已停止 / 等补充信息之间的补充信息通道——A、B、D 都涉及「把人的话或上一轮的结论送进下一轮」，`Inject` 的扩展点只加一处。
   - 回归测试保护集——A（测试有缺陷时谁能改）与 C（保护集的基线）改的是同一段 `guard_bug_regression`，一起设计。
   - 会话结束事件 `session.ended`——F 定义，G 的 Onboarding 会话直接用。
   - `task.get` / `events.since` / `config.get` / `dashboard.get` 的键基线测试——F、G 各自加字段，基线只在各自的里程碑里更新一次。
   - Onboarding 结束的提交与状态顺序——G（会话进账本）与 H（工作区 init commit）改同一个 `onboarding_step`，一起设计。
5. **协议版本。** 整个任务如果需要改协议正文 / prompt，合成**一个**新版本，带独立的 `## protocol/vN` 标题；旧协议版本的在跑任务不得因此协议失败。I 项只改内核的哈希口径，不改协议正文。
6. **账本迁移。** 需要改表结构时整个任务只加一个 `SCHEMA_VERSION`；rebase 时如果 main 上的版本号已被占用就顺延。
7. **不接触真实账本。** 实现轮与审计轮不在 worktree 里不带临时 `AUTOME_HOME` 地跑 `autome` / `automed` / 面板，不跑 `sh scripts/ci-local.sh --package`（2026-11-13 有任务这样把真实账本迁到了新版本）。
8. 评审轮按项逐一评审，评审意见标明属于哪一项；裁决同理。

### A（需求）：Bug Loop 补一条路：回归测试本身有缺陷时，修复轮 / 复核轮可以把任务退回定位轮修测试

#### 背景

Bug Loop 规定定位轮写出一条「现在是红的」回归测试，之后修复轮不得修改它。这条保护是对的，但它假设定位轮写的测试没有毛病。2026-11-13 一天里三个 Bug 任务因为这个假设不成立而卡死，每次都把三轮修复预算耗在「如实报告自己被约束挡住」上：

- **T-72**：定位轮把一条时序性测试固定成必现的红测，但断言本身与产品契约不符；修复轮三轮都写「需要调度方明确允许修正测试」，任务被取消后换提法重开（T-74）。
- **T-64**：产品修复第 2 轮就通过了复核，但定位轮的测试过不了 `cargo fmt --check`；修复轮不敢格式化，轮次耗尽。操作者手工 `cargo fmt` 才继续（T-76 处理格式化这一种）。
- **T-75**：产品修复第 1 轮就写对了；定位轮的测试夹具对假 CLI 的会话编号假设错了，产品修好之后用例才走到那一步并失败——定位时它「因为正确的原因是红的」，但永远变不绿。三轮耗尽后取消重提（T-78）。

共同点：**测试的缺陷只有在产品被修好之后才暴露**，而唯一被允许改测试的定位轮已经过去了。现在唯一的出路是取消重提，产品修复白做一遍。

#### 要做什么

1. **新的会话结论：回归测试缺陷。** 修复轮与复核轮可以在 Bug 文档状态块里声明「回归测试需要修正」（字段与取值由设计轮定，例如 `复核: 测试缺陷` 或单独一个字段），并在文档固定小节里写明：哪条用例、缺陷是什么、证据（产品修复之后它卡在哪一步）、建议怎么改。声明这个结论的那一轮**不得**自己改回归测试（保护不变）。
2. **内核据此把任务送回定位轮（「修测试」模式）**，而不是送去修复门禁 / 判为未通过：
   - 定位轮的 prompt 说明这次是回来修测试的，带上修复轮 / 复核轮写的缺陷说明；它可以修改回归测试，**不得**修改产品代码（已有的产品修复留在分支上）。
   - 这一轮不计修复轮次；但要有自己的上限（例如每个任务最多 2 次，设计轮定），防止修复轮与定位轮来回推。超过上限按现有方式失败并给出可读原因。
3. **重新确认「红 → 绿」**，因为此时产品修复已经在分支上，直接跑复现命令是绿的：
   - 内核要验证修正后的测试「在产品修复之前是红的、之后是绿的」。口径由设计轮定准并可测试，建议：在一个临时检出里把分支上非测试、非任务文档的改动还原到任务基线（或直接用任务基线提交 + 修正后的测试文件），跑复现命令必须失败（且不是 126/127 / 编译错误之外的无关失败——沿用现有复现检查的判定）；再在当前 HEAD 上跑必须通过。两头都满足才接受。
   - 只满足「基线上红」而 HEAD 上不绿 → 进入修复轮继续修产品；基线上就不红 → 按现有「未复现」流程处理。
   - 回归测试保护集按修正后的测试重新快照（`bug.regression_snapshot`）。
4. **之后的流程不变**：修复门禁 → 独立复核 → rebase → 合并前门禁。复核轮要复核「修测试」这一轮的改动没有弱化断言（缺陷说明与实际改动对得上）。
5. **可见**：`autome run` / `status` / `task.get` 能看出任务正在「修正回归测试」以及已经用了几次；事件名与文案由设计轮定。README 的 Bug Loop 一节与 `docs/development/technical-design.md` §5.6 补上这条路径与上限。
6. **协议与 prompt**：`protocol/bug-protocol.md`、`protocol/prompts/{locate,fix,fix-review}.md` 同步（什么时候该声明测试缺陷、声明时写什么、定位轮回来修测试时的边界）。按 `protocol/CHANGELOG.md` 的规矩发新版本（独立的 `## protocol/vN` 标题，`behavioral` 条目带 eval）。固定在旧协议上的在跑任务不迁移、行为不变。

#### 不做什么

- 不放宽「修复轮不得修改回归测试」。
- 不处理纯格式化（T-76）与「失败后补充信息」（T-78）；三者互补，不要重复实现。
- 不让定位轮在「修测试」模式下改产品代码。
- 不改需求 Loop。

#### 验收标准

1. e2e：定位轮写出一条夹具有缺陷的回归测试（产品修好后仍然红）→ 修复轮修好产品并声明测试缺陷 → 任务回到定位轮（prompt 含缺陷说明与边界）→ 定位轮修正测试 → 内核确认基线红、HEAD 绿 → 复核 → 合并卡点。全程修复轮次计数没有因为「修测试」那一轮增加。
2. e2e：定位轮在「修测试」模式下改了产品代码 → 被拒绝（守卫文案可读）。
3. e2e：修正后的测试在基线上不红 → 走「未复现」流程，不接受。
4. e2e：修正后的测试基线红、HEAD 不绿 → 进入修复轮。
5. e2e 或单测：修测试次数超过上限 → 任务失败，原因写明。
6. 单测：状态块新结论的解析；旧协议版本的 Bug 文档不出现新结论时行为与今天逐事件相同。
7. prompt / 简报金样更新；协议 eval「改前红、改后绿」。
8. `cargo fmt --check`、`clippy -D warnings`、`sh scripts/ci-local.sh` 全绿。

### B（缺陷）：失败 / 已停止的 Bug 任务无法补充信息：`autome reply` 报「Bug 节点不使用需求转换表」（重提，原 T-75）

#### 现象

Bug 任务进入 `Failed`（例如修复门禁连续失败、修复轮次用完）或被 `autome stop` 停下之后，操作者想把补充信息 / 决定告诉下一轮会话：

```
$ autome reply T-72 "产品决定：……"
autome：Bug 节点不使用需求转换表
```

报错是内核内部措辞，也没说该怎么办。`autome rerun <任务> locate|fix` 不能带文字，`autome extend` 只加轮次。结果：Bug 任务一旦失败或被停止，就没有任何办法把补充信息交给下一轮，只能取消重提（2026-11-13 的 T-72 就是这样被取消的）。

#### 复现步骤

1. 让一个 Bug 任务进入 `Failed`，或 `autome stop` 停在某个 Bug 节点；
2. `autome reply <任务> "补充信息"`。

#### 期望行为

- 对 `Failed` / `Stopped` 的 Bug 任务，`autome reply <任务> "文字"`（RPC `task.reply`）被接受：文字原样追加到 `docs/<slug>/<slug>-replies.md`（与等待补充信息时的 reply 同一个文件、同一种格式），任务回到定位轮重新判断（与 `AwaitInfo` 下 reply 的去向一致）；满槽时按现有准入排队。
- 修复轮次预算：回到定位后不能因为「轮次已用完」立刻再失败；口径定为「已用轮次保留，上限至少抬到 已用 + 配置的 fix_rounds」，写进技术设计。
- 其它不接受 reply 的状态（已完成、已取消、运行中的会话节点等）给出用户能看懂的中文原因和下一步该用哪个命令，不出现「需求转换表」这类内部措辞。
- 需求任务的 reply（等同 reject）行为不变；Bug 任务在 `AwaitInfo` / `NotABug` 下的 reply 行为不变。
- CLI 帮助里 `reply` 那一行补上「失败或已停止的 Bug 任务也可以用」。

#### 实际行为

`task.reply` 对 Bug 任务的 `Failed` / `Stopped` 状态走到了需求 Loop 的转换表入口，被 `Bug 节点不使用需求转换表` 拒绝。

main `c0038c9`；`crates/automed/src/dispatch.rs`（`task.reply`）、`crates/autome-domain/src/bug_loop.rs`（`apply_for` 对 reply 的处理）、`crates/automed/src/scheduler.rs`、`crates/autome-cli/src/main.rs`（帮助文本）。

- 上一次的产品修复保留在本仓库的引用 `refs/keep/t75-fix`（提交 `b4b118f fix(bug): 允许失败和停止任务补充信息并恢复修复预算`），上一次的回归测试在 `refs/keep/t75-test`（提交 `dcf4763`）。可以 `git show refs/keep/t75-fix` 参考；修复轮可以直接 cherry-pick 这个修复提交。
- 上一次回归测试的缺陷：`crates/autome-cli/tests/cli.rs` 的假 CLI（`FAKE_CLI`）**在检查步骤脚本是否存在之前就递增会话编号**。「停止后 reply」的用例里，`rerun locate` 已经启动并消耗了第 2 次会话（随后被 stop 杀掉），`reply` 启动的是第 3 次会话；但测试只在 stop 之后准备了 `2.sh`、并固定检查 `2.prompt`，于是第 3 次会话因为没有 `3.sh` 以 92 退出，断言 `await_info` 实际得到 `locate`。产品修复无论怎么写这条用例都红。
- 所以定位轮写用例时：为**每一次会启动的会话**（包括 `rerun` 启动后又被停掉的那次、以及 `reply` 启动的那次）都准备好对应编号的步骤脚本，检查 prompt 时检查 reply 实际启动的那次会话的编号；写完后在脑中（或用 `git stash` 掉产品代码之外的改动）核对「如果产品修好了，这条用例从头到尾每一步都能走通」，而不只是确认它现在是红的。可以把 `refs/keep/t75-fix` 临时 cherry-pick 上来跑一遍确认用例能变绿，再撤掉，然后才提交定位结果——提交里不能带产品修复。
- 回归测试提交前跑 `cargo fmt --all -- --check`。复现命令用仓库根目录可直接执行的形式：`cargo test --offline -p autome-cli --test cli bug_loop_reply_`。

### C（缺陷）：Bug 任务第二次定位（reply 之后、或 rerun locate）被判「回归测试保护集为空」：保护集只看本次会话的改动

#### 现象

T-86（2026-11-13）：定位轮 #1 新增了回归测试 `apps/web/test/logtail-live-cleanup.test.ts` 并提交，但会话沙箱里跑不了复现命令，状态写「无法复现」，任务进入「等你补充信息」。操作者在宿主上跑通复现后 `autome reply T-86 "…"`，任务回到定位轮 #2；定位轮 #2 把状态改成「已定位」（测试已经在分支上，不需要再改），宿主复现检查通过（「已复现，退出码 1」），紧接着任务被判：

```
失败（定位）：协议失败：定位轮回归测试保护集为空：必须新增或修改 test/spec 测试文件，或在复现命令中引用回归脚本路径
```

回归测试明明在分支上，复现命令也引用了它。

#### 复现步骤

1. 建一个 Bug 任务；定位轮第一次会话新增一个测试文件并提交，Bug 文档状态写「无法复现」（或「需要补充信息」）。
2. `autome reply <任务> "补充信息"`，任务回到定位轮。
3. 第二次定位会话不改测试文件，只把 Bug 文档状态改成「已定位」，复现命令引用第一步的测试且在宿主上失败（符合预期）。
4. 观察任务状态。

同样的路径：定位轮判「已定位」→ 复现检查没复现 → 退回定位轮，第二次只修正复现命令、不动测试文件；以及对失败 / 已停止的 Bug 任务 `autome rerun <任务> locate`。

#### 期望行为

保护集覆盖「这个任务的定位阶段」写下的全部回归测试，而不是「最后一次定位会话」的改动：第二次（及以后）定位会话即使一行测试都没改，之前定位会话新增 / 修改的测试仍在保护集里，任务进入修复轮，修复轮照常不得修改它们。

#### 实际行为

`crates/automed/src/scheduler.rs` 的 `guard_bug_regression` 用本次会话 `session.started` 事件里的 `locate_heads`（会话开始时的 HEAD）到当前 HEAD 的 diff 找测试文件。第二次定位会话开始时测试已经在 HEAD 里，diff 里没有它，`files` 为空 → 记 `bug.regression_empty` → 复现成功后任务被判协议失败。

另一个后果：如果第二次定位会话恰好改了别的测试文件，`bug.regression_snapshot` 会被新快照整体替换（修复轮只读最后一条），第一次会话写的回归测试就失去保护了。

#### 环境

main @ 5851c7e9（2026-11-13），macOS。

#### 线索

- 修法方向（定位轮定准）：diff 的基线改用任务第一个定位会话的 `locate_heads`（即任务分支上定位阶段开始前的提交；`store` 里按任务取最早一条 `session.started` 且 kind 为 locate 的事件），或把历次定位会话的快照并起来。注意工作区项目 `locate_heads` 是按仓库的数组。
- 中途 rebase 过的任务：基线提交可能已不在分支历史上，这时退回到与默认分支的 merge-base（设计上保护集宁可多不可少），不要报错。
- 修复轮侧 `bug.regression_snapshot` 取「最后一条」的逻辑要与上面一致：最后一条快照必须已经包含之前定位会话的文件。
- 操作者当时的绕法是 `autome rerun T-86 fix`（任务没有任何快照，修复轮的保护检查被跳过）——这说明「没有快照就不检查」本身也是个口子：`rerun <任务> fix` 时如果任务从未记过快照，应当按上面的基线现算一份，而不是放行。是否一并修由定位轮判断范围，至少写进 Bug 文档。
- 回归测试放在 `crates/automed/tests/end_to_end.rs`（Bug Loop 的 e2e 都在这里，搜 `bug_`）：按「复现步骤」造两次定位会话，断言任务进入修复轮且 `bug.regression_snapshot` 的 `files` 含第一次会话新增的测试；再断言修复轮改了这个测试会被拦下。
- 回归测试提交前跑 `cargo fmt --all -- --check`；复现命令写成仓库根目录可直接执行的形式（`cargo test -p automed --test end_to_end <测试名>`）。
- 会话沙箱里如果跑不了 e2e（需要起子进程），如实写明；静态根因成立就写「已定位」，复现由宿主的复现检查完成，不要因此写「无法复现」。

### D（需求）：给进行中的任务捎一句话：`autome note <任务> "…"`，下一个实现 / 修复轮的简报原样带上

#### 背景

Loop 里人能说话的地方只有两个卡点：设计定稿时的驳回意见、Bug 任务「等你补充信息」时的 `reply`。任务一旦进入实现 / 审计 / 门禁这一段，操作者看到了问题也没有办法告诉它，只能等它自己撞上，或者取消重提。2026-11-13 一天里的现场：

- T-59（W8）的 `apps/web/test/logtail-live.test.ts` 每跑一次就留下一组不会退出的假会话进程（收尾时目录先被删，假 CLI 永远等不到 `stop` 文件），机器上攒了 7 组。任务当时正在实现轮，没有通道告诉它，只能等合并后另提 Bug。
- T-72、T-64、T-75：修复轮被回归测试的缺陷卡住，操作者早就知道该怎么办，但 `rerun` 不能带文字，`reply` 被拒绝，只能取消重提（T-78、T-79 各补了一条专门的路）。
- T-61 在门禁关闭期间的证据全写「由宿主门禁负责」，操作者知道门禁没跑，也没法提醒。

T-78（失败的 Bug 可以 reply）、T-79（测试缺陷退回定位轮）、T-69（越界补丁交给实现轮）都是在给某一种情况单独开口子。缺的是一条通用的：操作者随时可以留一句话，下一个能改代码的轮次一定看到。

#### 要做什么

1. **命令与 RPC。** `autome note <任务> "内容"`（内容也可用 `--file <路径|->`）；RPC `task.note`。任务处于任何未结束状态（排队、进行中、卡点、已停止、失败）都可以留；已完成 / 已取消的拒绝。长度上限与 `task.reply` 一致。可以留多条，按时间排。
2. **送达。** 下一个**实现轮**（需求）或**修复轮 / 定位轮**（Bug，谁先开始给谁）的简报里加一节「操作者备注」，逐条原样列出（时间 + 内容），并写明：「这是操作者在任务进行中留下的话。逐条处理：照做，或者写一句不照做的理由；处理结果写进本轮证据的『操作者备注』小节。」送达后标记为已送达，不重复送。
3. **不抢跑、不打断。** 留备注不改变任务状态、不终止正在跑的会话；正在跑的那个会话看不到，下一轮才看到。如果任务后面已经没有实现 / 修复轮了（例如正在审计最后一个里程碑、或已经停在合并卡点）：
   - 还没到合并卡点：审计通过后内核补一个实现轮来处理备注，再回审计（与 T-68「里程碑之外的实现轮要被审」、T-69「补一个实现轮处理补丁」用同一套机制，设计轮确认三者共用，不另造）；
   - 已经停在合并卡点：`autome note` 提示「任务已在等你合并；加 `--reopen` 会把它送回实现轮处理这条备注，之后重新审计与过门禁」，带 `--reopen` 才执行。
4. **失败 / 已停止的任务。** 留备注后任务状态不变；之后 `autome rerun <任务> <节点>` 重跑到实现 / 修复 / 定位轮时带上未送达的备注。这样「rerun 不能带文字」的缺口也补上了。
5. **看得见。** `autome status <任务>` / `task.get` 列出备注：内容、时间、未送达 / 已送达（哪一轮）。事件 `task.note_added`、`task.note_delivered`。`autome run` 各打一行。
6. **审计要核对。** 审计轮的简报里列出本里程碑期间送达的备注，审计核对实现轮是否逐条处理（照做或给了理由）；没处理按未通过退回。这一条如果需要改审计 prompt / 协议正文，按 `protocol/CHANGELOG.md` 的规矩发新版本并带独立的 `## protocol/vN` 标题；旧协议版本的在跑任务照旧送达备注，只是审计不强制核对。
7. **网页网关。** `apps/web/server/gates/write-gate.ts` 放行 `task.note`（字段与长度校验照 `task.reply`），W7 任务详情页之后可以直接用；本任务不做页面。
8. 文档：README 命令表与「卡点与控制」一节；`docs/development/technical-design.md` 写明送达时机与补轮规则。

#### 不做什么

- 不做给正在运行的会话实时插话（不往会话 stdin 里写）。
- 不把备注当成设计变更：要改需求范围仍然走驳回设计或新任务；简报里的措辞要让实现轮在备注与已冻结需求冲突时停下来写明冲突，而不是悄悄改范围。
- 不替代 `reply`（Bug 卡点的问答）与设计驳回意见；它们照旧。
- 不做网页上的输入框（W7 之后另提）。

#### 验收标准

1. e2e（需求）：任务在实现轮运行中时留一条备注 → 当前会话不受影响；下一个实现轮的简报含该备注原文；`task.get` 显示已送达及轮次；再下一轮不重复出现。
2. e2e（需求，最后一个里程碑审计中留备注）：审计通过后内核补一个实现轮，简报含备注，之后回审计，再到合并卡点。
3. e2e（合并卡点）：不带 `--reopen` 被拒绝并给提示；带 `--reopen` 回到实现轮，处理后重新审计、过门禁、回到合并卡点；之前的预先授权合并（如果 T-70 已合并）保留。
4. e2e（Bug）：修复轮运行中留备注 → 下一个修复轮简报带上；任务失败后留备注再 `rerun <任务> fix` → 修复轮简报带上；`rerun <任务> locate` → 定位轮带上。

### E（需求）：快检和复现检查不该排在别人的完整门禁后面：给轻量的宿主检查单独一条车道

#### 背景

T-47 让宿主任务共用一条队列（`[gate] concurrency`，本仓库是 1），避免几个完整门禁同时跑互相拖慢。T-67 加了每轮快检（`[gate] quick`，本仓库实测 6–12 秒），T-61 让 Bug 的修复门禁在 `before_merge` 下只跑复现命令（通常几秒到一两分钟）。这些轻量检查和完整门禁（`sh scripts/ci-local.sh`，空闲 3 分钟、有会话并行时 10–17 分钟）排在同一条队列里。

2026-11-13 10:24 的现场：

```
10:24  T-76 合并前门禁开始：( … ) && ( sh scripts/ci-local.sh )
10:24  T-58 → 运行中 · 门禁
10:24  T-58 排队等门禁（门禁，入队时前面还有 0 个）      ← 12 秒的快检
10:25  T-77 → 运行中 · 修复门禁
10:25  T-77 排队等门禁（修复门禁，入队时前面还有 1 个）  ← 几秒的复现命令 + 快检
```

T-58（W6 的实现轮刚结束）等一个 12 秒的快检等了 10 分钟以上，T-77 排在它后面。每个实现轮、每个修复轮、每次复现检查都可能这样等一整个完整门禁；同时它们占着会话槽位不干活。完整门禁越慢，轻量检查被卡得越久。

#### 要做什么

1. **把宿主任务分成两条车道**：
   - 重车道：会跑完整门禁命令的任务——需求的 `Gate`（`each_round` 下）、`MergeGate`、真正要跑的 `MainCheck`、Bug 的 `MergeGate`、`each_round` 下的 `FixGate`、准备命令（`[setup]`）。继续受 `[gate] concurrency` 约束，行为与今天相同。
   - 轻车道：不含完整门禁命令的任务——`before_merge` 下跑快检的 `Gate`、`before_merge` 下的 `FixGate`（复现命令，或复现 + 快检）、`ReproCheck`。有自己的并发上限，不与重车道互相等待。
2. **轻车道的并发**：新增全局 / 项目配置键（名字由设计轮定，例如 `[gate] quick_concurrency`），缺省 1，范围校验与 `concurrency` 同一风格；轻车道内仍是 FIFO。缺省值下「同一时间最多 1 个完整门禁 + 1 个轻量检查」。
3. **判定按实际要跑的命令**：一个任务进哪条车道，取决于这次运行拼出来的命令是否包含完整门禁命令（T-67 的 `kind`：`full` 进重车道，`quick` / `repro` 进轻车道），不是按节点名硬编码；运行中改配置（`each_round` ↔ `before_merge`、加减 `quick`）时按 T-61 / T-67 已有的「启动时记下种类」口径，不让一次运行中途换车道。
4. **可见**：`gate.queued` 事件带车道；`autome run` / `status` / `task.get.gate_queue_position` 的「排队等门禁（前面还有 n 个）」只数同一车道里排在前面的；文案能看出等的是快检队列还是完整门禁队列。驱动重启后两条车道的顺序都从账本恢复。
5. README Host gate 一节与 `docs/development/technical-design.md` 对应小节更新：两条车道、各自的并发键、推荐值。
6. 本仓库 `.autome/config.toml` 不在任务里改。

#### 不做什么

- 不改完整门禁之间的排队规则与 `[gate] concurrency` 的语义。
- 不做合并队列（T-70）、不改会话槽位准入（T-51 / T-73 / T-77）。
- 不给轻车道任务设「优先插队到正在跑的完整门禁之前」这类抢占。
- 协议正文与 prompt 不需要改；如果设计认为要改，按 `protocol/CHANGELOG.md` 的规矩发新版本。

#### 验收标准

1. e2e：任务 A 的合并前门禁（完整门禁脚本里 sleep 住）在跑时，任务 B 的实现轮结束、配置了 `quick` → B 的快检立即开始并完成，B 进入审计；A 不受影响。事件里两者车道不同。
2. e2e：两个任务同时需要快检、轻车道并发为 1 → 先后执行，FIFO；并发设为 2 → 同时执行。
3. e2e：Bug 任务在 `before_merge` 下的复现检查与修复门禁走轻车道；`each_round` 下的修复门禁（含完整门禁命令）走重车道。
4. e2e：两个合并前门禁仍然互相排队（重车道行为与今天逐事件相同，现有 T-47 用例不改就通过）。
5. 单测：车道判定、新配置键的解析 / 缺省 / 越界、`save_project` 不改写用户的 `[gate]`；排队位置只数同车道。
6. 驱动重启后两条车道的队列从账本恢复，有测试。
7. `cargo fmt --check`、`clippy -D warnings`、`sh scripts/ci-local.sh` 全绿。

### F（需求）：任务详情页缺的内核数据：Bug 文档与复盘教训进文档清单、已完成任务仍能读文档、改动带类型、按任务读事件、会话结束事件

#### 背景

W7（T-87，任务详情页）的设计轮对照真实内核实测后，列出六处「页面想展示、内核现在给不出」的数据，都记成了 Backlog（B-01 – B-06）。W7 按「不改内核」先收窄了页面，下面这些缺口不补，详情页上会长期看到：

1. **Bug 任务没有文档。** `task.get` 的 `documents` 由 `dispatch.rs` 的 `documents()` 生成，固定清单里只有设计文档、任务文件、评审、裁决、审计、运行记录与证据文件——没有 Bug 文档 `<slug>-bug.md`。Bug 任务的 `documents` 实测为空，详情页的文档标签页只剩任务卡正文，看不到根因分析与修复说明。
2. **复盘教训与任务卡文件不在清单里。** `lessons.md`、`<slug>-card.md` 不列。
3. **任务合并完成后什么文档都看不到。** worktree 清理后 `documents` 为空、`status_block` 为 `null`；而这些文档明明已经随合并进了默认分支的 `docs/<slug>/`。已完成的任务恰恰是最常被回头翻的。
4. **`task.changes` 的 `files[]` 没有改动类型**（新增 / 删除 / 修改 / 改名）。详情页要在合并前醒目提示「删除文件数异常多」（T-13 出过分支被清空只剩 4 个文件的事故），现在只能按「只删不增」近似。
5. **没有按任务读事件的办法。** `events.since` 只能按 seq 拉全账本；面板服务端为了画一个任务的时间线（门禁、rebase、合并等内核步骤）要在内存里维护全账本的索引。
6. **会话没有结束事件。** 有 `session.started`，结束时间只在 `task.get.sessions[].ended_at`；时间线上会话条目的结束时刻、被截断的老会话都定不了位。

#### 要做什么

1. `documents()` 的清单补上：Bug 文档（`<slug>-bug.md`，标签「Bug 文档」）、`lessons.md`（「复盘教训」）、`<slug>-card.md`（「任务卡」）。存在才列，顺序：任务卡、设计文档 / Bug 文档、任务文件、评审、裁决、审计、运行记录、复盘教训、证据文件。

### I（缺陷）：每个任务每次开会话都记一条「协议副本被改过」的完整性警告：记录的哈希含 evals/，任务副本不含

#### 现象

账本里 `integrity_warning`（`what = protocol_copy_edited`）从 2026-09-17 起累计 800 条，覆盖 70 个任务——几乎每个任务、每次开会话都记一条，而这些任务的协议副本没有任何人改过。例：T-59 共 20 个会话，20 条警告，第一条出现在固定协议提交之后 5 分钟。

#### 复现步骤

1. 在临时 `AUTOME_HOME` 与临时仓库里建一个需求任务，跑到第二个会话开始（例如任务整理 → 设计），期间不碰 `docs/<slug>/protocol/`。
2. 查事件：`select count(*) from events where kind='integrity_warning'`。

仓库根目录可直接执行的现场核对（只读，查本机账本）：

```sh
sqlite3 ~/.autome/state/automed.sqlite3 "select count(*), count(distinct subject_id) from events where kind='integrity_warning'"
```

#### 期望行为

- 协议副本没被改过时，不记 `integrity_warning`；会话上挂的 `protocol_ref` 与 `tasks.protocol_ref` 一致。
- 副本里任何一个文件真被改了（内容变、增删文件），照旧记一条，且同一任务同一份改动只记一次（现在每个会话重复记）。
- 已经在跑的任务（按旧口径记了含 evals 的哈希）升级后不再误报，也不丢「真改了要报」的能力。

#### 背景

T-48 的会话范围守卫（`scheduler.rs` 的 `guard_session_scope`）规定审计轮、复盘轮、Bug 复核轮只能改任务文档目录。越界一次，任务就以「协议失败」停下，提示用户「先保存需要交回实现 / 修复轮的改动，将越界文件恢复到对应基线并提交，再 rerun」。

实际发生的越界几乎都是同一种：审计发现项目测试 / lint 因本里程碑的实现而失败，顺手修了一两行。

- T-47 审计改了 `config_io.rs` 的一处 clippy；
- T-44 审计 #4 给 `end_to_end.rs` 的 `task.get` 键基线补了 `cost_usd`、`cost_sessions_without_cost` 两行（2026-11-13 03:10）。

每次都要人来做三件纯机械的事：存补丁、把越界文件还原到会话基线并提交、`autome rerun <任务> audit`。夜里没人时任务就一直停着；还原之后那一两行有用的改动也没有通道交给实现轮，只能等合并前门禁失败时再被重新发现一遍。固定在旧协议（v2 prompt 仍写「当场加强验收或补检查」）上的在跑任务会反复触发。

#### 要做什么

1. 守卫发现越界时，内核不再直接判协议失败，而是自己完成机械的那部分：
   - 把基线到 HEAD 之间**越界路径**的差异存成补丁：主检出 `.autome/output/scope/<任务>/<会话 id>.patch`（与门禁日志同级的位置约定，路径由设计轮定准）；
   - 在任务 worktree 里把这些路径还原到会话开始基线（新增的越界文件删除，被删的恢复），做一个内核提交，提交信息写明会话、路径清单与补丁位置；文档目录内的改动原样保留；
   - 记一条事件（例如 `session.scope_restored`：角色、路径清单、补丁路径），`autome run` 打一行可读的话，`autome status <任务>` 能看到最近一次。
2. 还原之后按会话本来的结果继续走 Loop（状态块照常解析、照常过其它守卫）。
3. 把补丁交给能改代码的一方：
   - 需求 Loop：下一个实现轮的简报里加一段「上一轮审计 / 复盘越界改动已被还原」：路径清单、补丁路径、`git apply --stat` 的摘要，并说明「由你判断是否采纳；采纳就自己应用并跑相关测试，不采纳就写一句理由」。如果审计把里程碑判了通过、此后没有实现轮了（最后一个里程碑），内核要补一个实现轮来处理这份补丁，再回审计——不能让补丁无人处理就走到合并（与 T-68「里程碑之外的实现轮要被审」衔接，设计轮确认两者的交界，不重复造机制）。
   - Bug Loop：复核轮越界 → 还原后按「复核不通过」退回修复轮，修复轮简报带同样的一段。
4. 熔断：同一任务同一角色**连续第二次**越界仍然按今天的协议失败停下（文案保留，并补一句「上一次已自动还原」），防止会话与内核来回拉锯。次数口径由设计轮定准并写进技术设计。
5. 还原失败（worktree 有未提交改动挡住、路径冲突等）时退回今天的行为：协议失败 + 现有提示。
6. 文档：README 与 `docs/development/technical-design.md` 写明这条自愈路径与熔断；`autome status` 的失败提示在熔断时仍然给出手工步骤。prompt / 协议正文不需要改（v3 已写明边界）；如果设计认为要改，按 `protocol/CHANGELOG.md` 的规矩发新版本并带独立的 `## protocol/vN` 标题。

#### 不做什么

- 不放宽边界：审计 / 复盘 / 复核轮仍然不能让越界改动留在分支上。
- 不自动采纳补丁，不由内核判断补丁对不对。
- 不处理实现轮 / 修复轮自己的范围问题。
