### T-68 在 main 上的「里程碑之外的实现轮」机制（X-4a 的基准）

- 进入实现轮而没有开放里程碑的现有入口（`task.rs`）：rebase / 合并前门禁冲突 → `Inject::RebaseConflict`；合并前门禁失败 →
  `back_to_impl(Inject::GateFailed)`；`press_merge` 有已决表态 → `start_impl(Inject::Decisions)`；`RerunFrom{Implement}` / `ExtendBudget`。
- 判定与复验不依赖入口：`scheduler::apply_guards` 调 `integration::range`，实现轮前后状态表都是全部完成且有目录外提交时记
  `integration.range`；审计启动时 `integration::integration_for_audit` 只在任务冻结的 `audit` prompt 含 `<!-- integration-audit -->`
  （v8 起）时把这一轮变成集成复验——v8 之前冻结模板的任务到这里直接返回 `None`（J 项的兼容路径见「J」一节，裁决 D1-P06）。触发标签映射在 `integration.rs` 约 112 / 231 行：`rebase_conflict | gate_failed | decisions | none`。
- 结论：任何「里程碑都关闭之后补出来的实现轮」只要有产品提交，都自动被 T-68 集成复验覆盖；新入口只需要一条域转换边和一个触发标签。

### A / B / C Bug Loop

- Bug 节点是 `Node` 的 `Locate, ReproCheck, Fix, FixGate, FixReview, AwaitInfo, NotABug`；`BugProgress { fix_round, repro_misses }`；
  `start_fix` 在 `fix_round >= limit`（`limit = budget_n.unwrap_or(config.bug.fix_rounds)`）时 `Failed{FixBudget}`。
- `bug_doc.rs` 只读头部键 `status, fix-round, 复现命令, 根因, 复核, repos`，`复核` 只能是 `待复核 / 通过 / 打回`；
  `protocol/bug-protocol.md` 第 10–24 行的 `kernel-contract: bug-status-block` 区写死了「`复核` 只能是 `待复核`、`通过`、`打回`」。
- 复现判定：`!timed_out && exit_code != 0 && exit_code ∉ {126,127}`，**没有**编译错误识别。未复现第一次 → `Locate` +
  `Inject::ReproNotFailing`；连续第二次 → `AwaitInfo`。
- `guard_bug_regression`：定位轮（已定位）用**本次会话**的 `locate_heads..HEAD` 求保护集，空则记 `bug.regression_empty`，复现成功后若
  `regression_empty` 属于最后一个会话即 `Failed{Locate, Protocol}`；修复轮读**最后一条** `bug.regression_snapshot`；没有快照时修复轮
  不检查（`rerun <任务> fix` 由此绕过保护）。
- B：`task.reply` 对 Bug 任务发 `Trigger::Reply`；`bug_loop::apply_for` 没有 `Failed` / `Stopped` 的 Reply 分支，落到
  `apply_with_merge_request`，在 `task.rs` 约 978–986 行被「Bug 节点不使用需求转换表」拒绝。`refs/keep/t75-fix` 的 `bug_loop.rs`
  改动可干净合并；`main.rs`（帮助行旁新增了 `merge` 行）与 `scheduler.rs`（测试插入点）冲突；它没有改 `main.rs` 里断言旧帮助文案的
  `bug_loop_usage_no_longer_says_reply_equals_reject`，搬过来会红。`refs/keep/t75-test` 的「停止后」用例按 B-T2 所述编号错位，不能原样用。
- 补充信息只走 `task.replied` 事件，每次定位会话开始时渲染成 `<slug>-replies.md` 并提交。Bug 会话没有简报（只有 prompt）。

### D 操作者备注

- `Inject` 只活在 `session.started` 载荷、`session_retries.inject` 与 `task.resume_input` 里，通过 prompt（`launcher::render_inject`）
  送达；「表态下一轮生效」靠 `decisions` 表的租约（`carried_by` / `consumed_by`，会话 Ok 才结算）。
- `events` 是通用表（`seq, event_id, kind, subject_id, payload, at`，索引 `(subject_id, seq)`），`task.replied` 就是先例；备注不需要表。
- `task.reply` 内核侧没有长度上限；网页写网关 `PROSE_FIELDS['task.reply'] = ['info']`，上限 `MAX_PROSE_LENGTH = 8000` 字符。
- CLI 没有 `--file`；最近的先例是 `--brief <文件|->`。合并预先授权只存成 `merge.auto` 事件，任何回到实现轮的路径都不清除它。

### J 守卫

### E 门禁队列

### F 任务详情数据

### I 协议副本完整性警告

- 根因：版本身份哈希含 `evals/`，任务副本不含。
- 修法（§9 哈希口径）：版本身份只算「会写进任务副本的文件」——`ProtocolFiles` 加 `task_copy()`（去掉 `evals/` 前缀，`contract.toml` 保留），
  `current()` 用它的 `hash()`；`copy_into_task` 改为直接写 `task_copy()`，两边由同一个函数定义。`protocol.versions` / `protocol.get` / 用量
  与指标都读 `current()` 或 `tasks.protocol_ref`，口径随之一致。
- 存量任务（§9 迁移方式；D1-P09 区分三类）。新事件 `protocol.hash_scheme {ref, scheme: "task_copy", reason: "frozen" | "migrated", verified?: bool, previous?}`，每个任务至多一条。
  1. **新冻结的任务**：固定协议时记 `frozen`，`tasks.protocol_ref` 用 `task_copy()` 的哈希。
  2. **可验证的旧任务**：比较时该任务还没有这条事件（旧口径冻结），且 `tasks.protocol_ref` 的 tag 等于本二进制 seed 的当前版本 tag、哈希等于 `seed().hash()`
     （旧口径哈希）——说明副本冻结时的原始内容就是本二进制里的这份 seed。可信预期哈希 = `seed().task_copy().hash()`。把 `tasks.protocol_ref` 改写为
     「tag + 可信预期哈希」（**不是**副本现算哈希），记 `migrated {verified: true, previous}`；随后照常比较副本现算哈希与新 ref：相同则无告警，**不同则按 I-E2 告警**
     （升级前就存在的真实修改不会被当成口径迁移吞掉）。
  3. **无法验证的旧任务**（ref 的 tag 或哈希与本二进制 seed 对不上：更早或更新的版本，原始内容不可得）：把 `tasks.protocol_ref` 改写为「记录的 tag + 副本现算哈希」，
     记 `migrated {verified: false, previous}`，本次不告警，并在事件里写明证据限制（升级前的副本改动无法核实）——这是 I-E3 允许的退路，仅限这一类。
- 只记一次（§9 记法）：不一致时，若该任务最后一条 `integrity_warning` 的 `actual_hash` 等于现算值就不再记；副本又变了（哈希不同）再记一条（I-E2）。
  会话上挂的 `protocol_ref` 在一致时与 `tasks.protocol_ref` 相同（I-E1）。
- 不改 `protocol/` 正文，不发版本（X-5）。既有用例 `the_version_in_force_is_the_newest_changelog_heading_over_the_seed` 断言
  `r.hash == seed().hash()`，改为与 `seed().task_copy().hash()` 比（约束 13 列出的既有测试改动）。

## 风险与验证安排

- **R1 并行任务改同一批文件（约束 14）。** 新逻辑尽量放新文件（`handoff.rs`、`scope.rs`）与新函数，对 `scheduler.rs` 只做插入调用。

- **R8 v9 eval 的行为验证要花钱。** 会话只跑静态门；`--behaviour` 的「改前红、改后绿」放进人工验收清单（H-01）。

  （任务 §7.4）；快检与合并前全量门禁由宿主跑。e2e 一律用现有夹具的临时 `AUTOME_HOME` 与临时仓库（X-7）；新测试里起的子进程收尾时等它退出（V-5）。
