## 2. 目标与背景

2026-11-13 用户确认的做法：一个大的工作只跑一次完整循环，不为每个细分需求各跑一遍「任务整理 → 设计 → 评审 →
裁决 → 批准」，也不为每个小缺陷各开一个 Bug 循环。这张卡把当时排队中、尚未开始的全部内核工作合成一个任务：
六项需求与五项缺陷，原任务均已取消。

它们都落在内核同一批文件上（`scheduler.rs`、`dispatch.rs`、`task.rs`、`bug_loop.rs`、`brief.rs`、
`protocol/mod.rs`），分开做会互相 rebase 冲突，「补一个能改代码的轮次」「会话结束事件」「保护集基线」这类机制
还会被各自设计一遍。

**目标：** 用一份设计文档、一次评审覆盖下表十一项，按项分组的里程碑依次实现并逐项审计通过，最后一次合并。

## 3. 对设计轮、评审轮、实现轮与审计轮的总要求（任务卡原文整理，编号 X-1 – X-8）

- **X-1 一份设计文档覆盖十一项。** 里程碑按项分组、同一项的里程碑连续排列，标题以「A·」「B·」… 开头；需求每项
  1–3 个里程碑，缺陷每项 1 个（同一组里改同一段代码的缺陷可以并进相邻需求的里程碑，但验收条目要分开列）；
  **总数不超过 16 个**（本任务不适用「超过 6 个里程碑就拆分」的惯例，这是有意的）。每个里程碑仍然要能独立验收。
- **X-2 按项推进。** 前一项的里程碑全部审计通过后再开始下一项；后面的项不得成为前面验收的前提。某一项在设计阶段
  被判定做不了或应当缩小范围，写进争议项或 Backlog，不拖住其余各项。
- **X-3 缺陷项的做法。** 缺陷小节是按 Bug 任务卡写的，里面「定位轮 / 修复轮 / 复核」是 Bug Loop 的说法，在本任务里
  对应：**设计轮**确认根因并写明回归测试放在哪；**实现轮先提交一个修复前失败的回归测试、再修**，证据里要有同一条
  命令修复前失败、修复后通过的两次输出；**审计轮**核对根因、回归测试是否有意义、改动是否最小。小节里「复现命令
  写成仓库根目录可直接执行」「回归测试提交前跑 `cargo fmt --all -- --check`」照做。
- **X-4 共用机制只设计一次。** 至少核对这几处并在设计文档里写明归属：
  - **X-4a「里程碑都关闭之后还需要一个能改代码的轮次」**——A（退回定位轮修测试）、D（审计通过后补一个实现轮处理
    备注）、K（越界补丁交给实现轮）与已合并的 T-68（里程碑之外的实现轮要被审）是同一类机制，用同一套，不另造；
    以 main 上 T-68 的实现为准，K 的原实现按它对齐。
  - **X-4b 补充信息通道**——Bug 任务在失败 / 已停止 / 等补充信息之间，A、B、D 都涉及「把人的话或上一轮的结论送进
    下一轮」，`Inject` 的扩展点只加一处。
  - **X-4c 回归测试保护集**——A（测试有缺陷时谁能改）与 C（保护集的基线）改的是同一段 `guard_bug_regression`，
    一起设计。
  - **X-4d 会话结束事件 `session.ended`**——F 定义，G 的 Onboarding 会话直接用。
  - **X-4e 键基线测试**——`task.get` / `events.since` / `config.get` / `dashboard.get` 的键基线，F、G 各自加字段，
    基线只在各自的里程碑里更新一次。
  - **X-4f Onboarding 结束的提交与状态顺序**——G（会话进账本）与 H（工作区 init commit）改同一个
    `onboarding_step`，一起设计。
- **X-5 协议版本。** 整个任务如果需要改协议正文 / prompt，合成**一个**新版本，带独立的 `## protocol/vN` 标题；
  旧协议版本的在跑任务不得因此协议失败。I 项只改内核的哈希口径，不改协议正文。
- **X-6 账本迁移。** 需要改表结构时整个任务只加一个 `SCHEMA_VERSION`；rebase 时如果 main 上的版本号已被占用就顺延。
- **X-7 不接触真实账本。** 实现轮与审计轮不在 worktree 里不带临时 `AUTOME_HOME` 地跑 `autome` / `automed` / 面板，
  不跑 `sh scripts/ci-local.sh --package`（2026-11-13 有任务这样把真实账本迁到了新版本）。
- **X-8 按项评审。** 评审轮按项逐一评审，评审意见标明属于哪一项；裁决同理。

### 6.K（需求，已有实现，最先做）审计 / 复盘 / 复核轮越界改动时内核自己还原并转交实现轮

**背景。** T-48 的会话范围守卫 `guard_session_scope` 规定审计轮、复盘轮、Bug 复核轮只能改任务文档目录；越界一次

实际越界几乎都是「审计发现测试 / lint 因本里程碑的实现而失败，顺手修了一两行」（T-47、T-44）。

**这一项已经做过一遍（原 T-69），不要从零写：**

- 原分支保留在本仓库引用 **`refs/keep/t69-scope-self-heal`**（提交 `91e6c2ed`）；6 个里程碑全部实现并审计通过，
  只是卡在合并前的集成修复上（它固定旧协议 v6，被 J 项那条新守卫反复判协议失败）。设计文档、评审、审计记录与证据
  在该提交的 `docs/审计-复盘/` 下：`git show refs/keep/t69-scope-self-heal:docs/审计-复盘/审计-复盘.md`。
- **设计轮：** 先读它的设计文档与产品改动（`git diff main...refs/keep/t69-scope-self-heal -- crates apps`），本任务的
  设计直接采用它的方案，只写与本任务其它项（A、D、J 的「里程碑关闭后的轮次」机制、T-68 合并后的集成复验）需要
  对齐的差异。
- **实现轮：** 把它的产品改动与测试 cherry-pick 或按提交搬进本任务分支（**不要搬 `docs/审计-复盘/` 这个旧任务文档

要做什么（原任务卡）：

- **K-R1** 守卫发现越界时，内核不再直接判协议失败，而是自己完成机械的那部分：

  日志同级的位置约定，路径由设计轮定准）；

  写明会话、路径清单与补丁位置；文档目录内的改动原样保留；

  `autome status <任务>` 能看到最近一次。
- **K-R2** 还原之后按会话本来的结果继续走 Loop（状态块照常解析、照常过其它守卫）。
- **K-R3** 把补丁交给能改代码的一方：
  - 需求 Loop：下一个实现轮的简报里加一段「上一轮审计 / 复盘越界改动已被还原」：路径清单、补丁路径、
    `git apply --stat` 的摘要，并说明「由你判断是否采纳；采纳就自己应用并跑相关测试，不采纳就写一句理由」。如果审计
    把里程碑判了通过、此后没有实现轮了（最后一个里程碑），内核要补一个实现轮来处理这份补丁，再回审计——不能让补丁
    无人处理就走到合并（与 T-68 衔接，见 X-4a）。
  - Bug Loop：复核轮越界 → 还原后按「复核不通过」退回修复轮，修复轮简报带同样的一段。
- **K-R4** 熔断：同一任务同一角色**连续第二次**越界仍然按今天的协议失败停下（文案保留，并补一句「上一次已自动
  还原」）。次数口径由设计轮定准并写进技术设计。
- **K-R5** 还原失败（worktree 有未提交改动挡住、路径冲突等）时退回今天的行为：协议失败 + 现有提示。
- **K-R6** 文档：README 与 `docs/development/technical-design.md` 写明这条自愈路径与熔断；`autome status` 的失败提示
  在熔断时仍然给出手工步骤。prompt / 协议正文不需要改（v3 已写明边界）；设计认为要改就并进 X-5 的那一个新版本。

不做什么：

- **K-N1** 不放宽边界：审计 / 复盘 / 复核轮仍然不能让越界改动留在分支上。
- **K-N2** 不自动采纳补丁，不由内核判断补丁对不对。
- **K-N3** 不处理实现轮 / 修复轮自己的范围问题。

验收标准：

- **K-V6** 还原失败的回退路径有测试。
- **K-V7** `cargo fmt --check`、`clippy -D warnings`、`sh scripts/ci-local.sh` 全绿，前两条由实现轮在会话里跑并记录

### 6.A（需求）Bug Loop 补一条路：回归测试本身有缺陷时退回定位轮修测试

**背景。** Bug Loop 规定定位轮写出一条「现在是红的」回归测试，之后修复轮不得修改它。这条保护假设定位轮写的测试
没有毛病。2026-11-13 一天里 T-72（断言与产品契约不符）、T-64（测试过不了 `cargo fmt --check`）、T-75（夹具对假
CLI 的会话编号假设错了）三个 Bug 任务因此卡死。共同点：**测试的缺陷只有在产品被修好之后才暴露**，而唯一被允许改
测试的定位轮已经过去了，唯一出路是取消重提。

要做什么：

- **A-R1 新的会话结论：回归测试缺陷。** 修复轮与复核轮可以在 Bug 文档状态块里声明「回归测试需要修正」（字段与取值
  由设计轮定，例如 `复核: 测试缺陷` 或单独一个字段），并在文档固定小节里写明：哪条用例、缺陷是什么、证据（产品修复
  之后它卡在哪一步）、建议怎么改。声明这个结论的那一轮**不得**自己改回归测试（保护不变）。
- **A-R2 内核据此把任务送回定位轮（「修测试」模式）**，而不是送去修复门禁 / 判为未通过：
  - 定位轮的 prompt 说明这次是回来修测试的，带上修复轮 / 复核轮写的缺陷说明；它可以修改回归测试，**不得**修改产品
    代码（已有的产品修复留在分支上）。
  - 这一轮不计修复轮次；但要有自己的上限（例如每个任务最多 2 次，设计轮定），防止修复轮与定位轮来回推。超过上限按
    现有方式失败并给出可读原因。
- **A-R3 重新确认「红 → 绿」**（此时产品修复已在分支上，直接跑复现命令是绿的）：
  - 内核要验证修正后的测试「在产品修复之前是红的、之后是绿的」。口径由设计轮定准并可测试，任务卡的建议：在一个临时
    检出里把分支上非测试、非任务文档的改动还原到任务基线（或直接用任务基线提交 + 修正后的测试文件），跑复现命令
    必须失败（判定沿用现有复现检查：126/127、编译错误之外的无关失败不算复现）；再在当前 HEAD 上跑必须通过。两头都
    满足才接受。
  - 只满足「基线上红」而 HEAD 上不绿 → 进入修复轮继续修产品；基线上就不红 → 按现有「未复现」流程处理。
  - 回归测试保护集按修正后的测试重新快照（`bug.regression_snapshot`）。
- **A-R4 之后的流程不变：** 修复门禁 → 独立复核 → rebase → 合并前门禁。复核轮要复核「修测试」这一轮的改动没有弱化
  断言（缺陷说明与实际改动对得上）。
- **A-R5 可见：** `autome run` / `status` / `task.get` 能看出任务正在「修正回归测试」以及已经用了几次；事件名与文案
  由设计轮定。README 的 Bug Loop 一节与 `docs/development/technical-design.md` §5.6 补上这条路径与上限。
- **A-R6 协议与 prompt：** `protocol/bug-protocol.md`、`protocol/prompts/{locate,fix,fix-review}.md` 同步（什么时候该
  声明测试缺陷、声明时写什么、定位轮回来修测试时的边界）。按 `protocol/CHANGELOG.md` 的规矩发新版本（`behavioral`
  条目带 eval；并进 X-5 的那一个新版本）。固定在旧协议上的在跑任务不迁移、行为不变。

不做什么：

- **A-N1** 不放宽「修复轮不得修改回归测试」。
- **A-N2** 不处理纯格式化（T-76，已在 main）与「失败后补充信息」（本任务 B 项）；三者互补，不要重复实现。
- **A-N3** 不让定位轮在「修测试」模式下改产品代码。
- **A-N4** 不改需求 Loop。

验收标准：

- **A-V1** e2e：定位轮写出一条夹具有缺陷的回归测试（产品修好后仍然红）→ 修复轮修好产品并声明测试缺陷 → 任务回到
  定位轮（prompt 含缺陷说明与边界）→ 定位轮修正测试 → 内核确认基线红、HEAD 绿 → 复核 → 合并卡点。全程修复轮次计数
  没有因为「修测试」那一轮增加。
- **A-V2** e2e：定位轮在「修测试」模式下改了产品代码 → 被拒绝（守卫文案可读）。
- **A-V3** e2e：修正后的测试在基线上不红 → 走「未复现」流程，不接受。
- **A-V4** e2e：修正后的测试基线红、HEAD 不绿 → 进入修复轮。
- **A-V5** e2e 或单测：修测试次数超过上限 → 任务失败，原因写明。
- **A-V6** 单测：状态块新结论的解析；旧协议版本的 Bug 文档不出现新结论时行为与今天逐事件相同。
- **A-V7** prompt / 简报金样更新；协议 eval「改前红、改后绿」。
- **A-V8** `cargo fmt --check`、`clippy -D warnings`、`sh scripts/ci-local.sh` 全绿。

参考：`crates/autome-domain/src/bug_loop.rs`（节点与转换）、`crates/autome-domain/src/bug_doc.rs`（状态块）、
`crates/automed/src/scheduler.rs`（`guard_bug_regression`、`regression_protection`、复现检查与修复门禁）；
`protocol/bug-protocol.md`、`protocol/prompts/{locate,fix,fix-review}.md`。现场：T-72、T-75 的 Bug 文档不在分支上；
T-75 那条有缺陷的夹具可用 `git show refs/keep/t75-test` 看；T-64 的记录在
`docs/驳回设计时不带上已做的-backlog-表态/` 下 Bug 文档的「复核意见」。

### 6.B（缺陷）失败 / 已停止的 Bug 任务无法补充信息

重提。**复现：** 让一个 Bug 任务进入 `Failed`，或 `autome stop` 停在某个 Bug 节点，再 `autome reply <任务> "补充信息"`。
**实际行为：** `task.reply` 对 Bug 任务的 `Failed` / `Stopped` 状态走到了需求 Loop 的转换表入口并被拒绝。

### 6.C（缺陷）Bug 任务第二次定位被判「回归测试保护集为空」

**现象（T-86）。** 定位轮 #1 新增了回归测试并提交，但会话沙箱里跑不了复现命令，状态写「无法复现」→「等你补充信息」；
操作者 `autome reply` 后定位轮 #2 把状态改成「已定位」（测试已在分支上，不需要再改），宿主复现检查通过，紧接着任务
被判 `协议失败：定位轮回归测试保护集为空：必须新增或修改 test/spec 测试文件，或在复现命令中引用回归脚本路径`。

**复现：** (1) 建一个 Bug 任务；定位轮第一次会话新增一个测试文件并提交，Bug 文档状态写「无法复现」（或「需要补充
信息」）；(2) `autome reply <任务> "补充信息"`；(3) 第二次定位会话不改测试文件，只把状态改成「已定位」，复现命令
引用第一步的测试且在宿主上失败；(4) 观察任务状态。同样的路径：「已定位」→ 复现检查没复现 → 退回定位轮，第二次只
修正复现命令；以及对失败 / 已停止的 Bug 任务 `autome rerun <任务> locate`。

**实际行为：** `guard_bug_regression` 用本次会话 `session.started` 事件里的 `locate_heads`（会话开始时的 HEAD）到
当前 HEAD 的 diff 找测试文件；第二次定位会话开始时测试已在 HEAD 里，`files` 为空 → 记 `bug.regression_empty` →
复现成功后任务被判协议失败。另一个后果：第二次定位会话恰好改了别的测试文件时，`bug.regression_snapshot` 被新快照
整体替换（修复轮只读最后一条），第一次会话写的回归测试失去保护。

期望行为：

- **C-E1** 保护集覆盖「这个任务的定位阶段」写下的全部回归测试，而不是「最后一次定位会话」的改动：第二次（及以后）
  定位会话即使一行测试都没改，之前定位会话新增 / 修改的测试仍在保护集里，任务进入修复轮，修复轮照常不得修改它们。

回归测试与线索：

- **C-T1** 回归测试放在 `crates/automed/tests/end_to_end.rs`（Bug Loop 的 e2e 都在这里，搜 `bug_`）：按「复现步骤」
  造两次定位会话，断言任务进入修复轮且 `bug.regression_snapshot` 的 `files` 含第一次会话新增的测试；再断言修复轮改了
  这个测试会被拦下。复现命令形如 `cargo test -p automed --test end_to_end <测试名>`；提交前跑
  `cargo fmt --all -- --check`。
- 修法方向（设计轮定准）：diff 的基线改用任务第一个定位会话的 `locate_heads`（`store` 里按任务取最早一条
  `session.started` 且 kind 为 locate 的事件），或把历次定位会话的快照并起来。工作区项目 `locate_heads` 是按仓库的
  数组。
- 中途 rebase 过的任务：基线提交可能已不在分支历史上，这时退回到与默认分支的 merge-base（保护集宁可多不可少），
  不要报错。
- 修复轮侧 `bug.regression_snapshot` 取「最后一条」的逻辑要与上面一致：最后一条快照必须已经包含之前定位会话的文件。
- 「没有快照就不检查」本身是个口子：操作者当时用 `autome rerun T-86 fix` 绕过（任务没有任何快照，修复轮的保护检查
  被跳过）。`rerun <任务> fix` 时如果任务从未记过快照，应当按上面的基线现算一份，而不是放行。是否一并修由设计轮判断
  范围，至少写进设计文档。
- 与 A 共用 `guard_bug_regression`（X-4c）。

### 6.D（需求）给进行中的任务捎一句话：`autome note`

**背景。** Loop 里人能说话的地方只有两个卡点：设计定稿时的驳回意见、Bug 任务「等你补充信息」时的 `reply`。任务一旦
进入实现 / 审计 / 门禁这一段，操作者看到了问题也没有办法告诉它（T-59 测试泄漏进程、T-72 / T-64 / T-75、T-61 的现场）。
缺的是一条通用的：操作者随时可以留一句话，下一个能改代码的轮次一定看到。

要做什么：

- **D-R1 命令与 RPC。** `autome note <任务> "内容"`（内容也可用 `--file <路径|->`）；RPC `task.note`。任务处于任何
  未结束状态（排队、进行中、卡点、已停止、失败）都可以留；已完成 / 已取消的拒绝。长度上限与 `task.reply` 一致。
  可以留多条，按时间排。
- **D-R2 送达。** 下一个**实现轮**（需求）或**修复轮 / 定位轮**（Bug，谁先开始给谁）的简报里加一节「操作者备注」，
  逐条原样列出（时间 + 内容），并写明：「这是操作者在任务进行中留下的话。逐条处理：照做，或者写一句不照做的理由；
  处理结果写进本轮证据的『操作者备注』小节。」送达后标记为已送达，不重复送。
- **D-R3 不抢跑、不打断。** 留备注不改变任务状态、不终止正在跑的会话；正在跑的那个会话看不到，下一轮才看到。任务

  - 已经停在合并卡点：`autome note` 提示「任务已在等你合并；加 `--reopen` 会把它送回实现轮处理这条备注，之后重新
    审计与过门禁」，带 `--reopen` 才执行。
- **D-R4 失败 / 已停止的任务。** 留备注后任务状态不变；之后 `autome rerun <任务> <节点>` 重跑到实现 / 修复 / 定位轮时

- **D-R5 看得见。** `autome status <任务>` / `task.get` 列出备注：内容、时间、未送达 / 已送达（哪一轮）。事件

- **D-R6 审计要核对。** 审计轮的简报里列出本里程碑期间送达的备注，审计核对实现轮是否逐条处理（照做或给了理由）；

  只是审计不强制核对。

### 6.J（缺陷）新守卫 `impl_closed_milestone` 把旧协议版本的在跑任务判协议失败

**现象。** T-68 合并并重装后（2026-11-13 21:30），T-69 在 rebase 冲突修复的实现轮 #8 结束时被判「协议失败：实现轮
把已完成里程碑验收契约的『最新证据』改指向了实现证据：M-06：… Autome 不会替你改回去。」T-69 固定的协议是 v6，它的
`prompts/impl.md` 让实现轮更新「最新证据」指针，没有「里程碑已完成时不要动这行」这条（那是 v8 才加的）。实现轮照旧
prompt 做了，却被新内核的守卫判失败，操作者只能手工改回、提交、`autome rerun <任务> audit`。

**复现：** (1) 用 v8 之前的协议副本建一个需求任务（e2e 里把任务的 `docs/<slug>/protocol/` 换成旧版本的
`prompts/impl.md`，`protocol_ref` 记旧 tag），所有里程碑审计通过；(2) 让它进入里程碑关闭后的实现轮（rebase 冲突或
合并前门禁失败）；(3) 实现轮把某个已完成里程碑的「最新证据」行改成指向本轮的 `M-xx-r<k>-impl.md`；(4) 观察任务状态。

**实际行为：** `crates/automed/src/guards.rs` 的 `no_retargeting_closed_evidence` 不看任务的协议版本，一律返回
`Finding::error("impl_closed_milestone", …)`。

期望行为：

- **J-E1** 协议版本早于引入这条规则的版本（v8）的任务：不判协议失败。内核自己把被改的「最新证据」行还原成会话开始前
  的内容（只动这一行，做一个内核提交并记事件），照常进入集成复验审计；`autome run` 打一行提醒。
- **J-E2** v8 及以后的任务：维持现在的行为（判协议失败），或同样自动还原后继续——由设计定，但两种协议版本下都不应该
  需要人手工改文档。
- **J-E3** 一般原则写进技术设计：新增的「error 级」守卫如果依赖某个协议版本才写进 prompt 的规则，对更早版本的任务
  只能是提醒或自动修正。

### 6.E（需求）快检和复现检查单独一条车道

**背景。** T-47 让宿主任务共用一条队列（`[gate] concurrency`，本仓库是 1）；T-67 加了每轮快检（`[gate] quick`，本仓库
实测 6–12 秒），T-61 让 Bug 的修复门禁在 `before_merge` 下只跑复现命令。这些轻量检查和完整门禁
（`sh scripts/ci-local.sh`，空闲 3 分钟、有会话并行时 10–17 分钟）排在同一条队列里：2026-11-13 10:24，T-58 一个 12 秒
的快检等了 10 分钟以上，T-77 排在它后面，同时它们占着会话槽位不干活。

要做什么：

- **E-R1 把宿主任务分成两条车道：**
  - 重车道：会跑完整门禁命令的任务——需求的 `Gate`（`each_round` 下）、`MergeGate`、真正要跑的 `MainCheck`、Bug 的
    `MergeGate`、`each_round` 下的 `FixGate`、准备命令（`[setup]`）。继续受 `[gate] concurrency` 约束，行为与今天相同。
  - 轻车道：不含完整门禁命令的任务——`before_merge` 下跑快检的 `Gate`、`before_merge` 下的 `FixGate`（复现命令，或
    复现 + 快检）、`ReproCheck`。有自己的并发上限，不与重车道互相等待。
- **E-R2 轻车道的并发：** 新增全局 / 项目配置键（名字由设计轮定，例如 `[gate] quick_concurrency`），缺省 1，范围校验
  与 `concurrency` 同一风格；轻车道内仍是 FIFO。缺省值下「同一时间最多 1 个完整门禁 + 1 个轻量检查」。
- **E-R3 判定按实际要跑的命令：** 一个任务进哪条车道，取决于这次运行拼出来的命令是否包含完整门禁命令（T-67 的
  `kind`：`full` 进重车道，`quick` / `repro` 进轻车道），不是按节点名硬编码；运行中改配置（`each_round` ↔
  `before_merge`、加减 `quick`）时按 T-61 / T-67 已有的「启动时记下种类」口径，不让一次运行中途换车道。
- **E-R4 可见：** `gate.queued` 事件带车道；`autome run` / `status` / `task.get.gate_queue_position` 的「排队等门禁
  （前面还有 n 个）」只数同一车道里排在前面的；文案能看出等的是快检队列还是完整门禁队列。驱动重启后两条车道的顺序都
  从账本恢复。
- **E-R5** README Host gate 一节与 `docs/development/technical-design.md` 对应小节更新：两条车道、各自的并发键、
  推荐值。
- **E-R6** 本仓库 `.autome/config.toml` 不在任务里改。

不做什么：

- **E-N1** 不改完整门禁之间的排队规则与 `[gate] concurrency` 的语义。
- **E-N2** 不做合并队列（T-70）、不改会话槽位准入（T-51 / T-73 / T-77）。
- **E-N3** 不给轻车道任务设「优先插队到正在跑的完整门禁之前」这类抢占。
- **E-N4** 协议正文与 prompt 不需要改；如果设计认为要改，并进 X-5 的那一个新版本。

验收标准：

- **E-V1** e2e：任务 A 的合并前门禁（完整门禁脚本里 sleep 住）在跑时，任务 B 的实现轮结束、配置了 `quick` → B 的快检

- **E-V5** 单测：车道判定、新配置键的解析 / 缺省 / 越界、`save_project` 不改写用户的 `[gate]`；排队位置只数同车道。

### 6.H（缺陷）工作区项目的 Onboarding 完成或跳过时必报内部错误

**现象。** 工作区项目（`project add --workspace`）走 Onboarding，点「完成」（最后一步的 advance）或「跳过」时内核返回
内部错误 `git add -- .autome AGENTS.md: fatal: not a git repository (or any of the parent directories): .git`；但项目的
Onboarding 状态已经被写成 `skipped` / 已完成，`project.onboarding` 事件没有记，重新读取后项目显示为已结束，实际上没有
任何 init commit。

**复现：** (1) 建一个工作区目录，下面两个 Git 仓库 `docs`、`backend`（各有一个提交）；
(2) `autome project add <工作区目录> --workspace --docs-repo docs`（不带 `--skip-onboarding`）；
(3) `autome rpc project.onboarding.skip '{"project_id":"<id>"}'`（或 `autome project onboard <项目> --finish`）；
(4) 看返回与 `autome project ls`、事件表。（按约束 4，这些命令只能带临时 `AUTOME_HOME` 跑，或在测试夹具里复现。）

**实际行为：** `crates/automed/src/dispatch.rs` 的 `onboarding_step` 先写状态，再调 `init_commit` 在项目路径（工作区
根目录）执行 `git add`；工作区根不是仓库，命令失败，错误以 `internal` 返回，状态已改、事件未记。

期望行为：

- **H-E1** 工作区项目的 Onboarding 结束（完成或跳过）成功返回；该有的初始化提交落在**文档仓库**里（`.autome/` 与
  `AGENTS.md` 所在的那个成员仓库——以 `project add --workspace` 时实际写入这些文件的位置为准），工作区根目录不是仓库
  就不在那里提交；没有可提交内容时不提交也不报错。
- **H-E2** 状态与事件一致：成功才把 Onboarding 状态写成结束并记 `project.onboarding` 事件；提交失败时状态不变、返回
  可读的原因，可以重试。

回归测试与线索：

- **H-T1** 回归测试放 `crates/automed/src/dispatch.rs` 的单测区（已有 `workspace_at` 夹具与工作区添加的测试，搜
  `workspace_at(`）或 `tests/end_to_end.rs`：工作区项目 skip 与 advance 到结束各一条，断言返回成功、文档仓库里有 init
  commit、工作区根目录没有 `.git`、事件已记；再加一条「提交失败时状态不变」。复现命令形如
  `cargo test -p automed <测试名>`；提交前跑 `cargo fmt --all -- --check`。
- `dispatch.rs`：`onboarding_step`、`init_commit`、`project_add` 里工作区分支（`init::init_kind(&canonical, workspace)`、
  `disposition`）——看工作区添加时 `.autome/`、`AGENTS.md` 实际写在哪，Onboarding 结束就在同一处提交。
- 顺序问题单独成立：单仓库项目里如果 `git commit` 因为别的原因失败（例如钩子），同样会留下「状态已结束但没有提交」。
  先提交、成功后再写状态与事件。
- 与 G-R2 共用 `onboarding_step`（X-4f）。

### 6.I（缺陷）每个任务每次开会话都记一条「协议副本被改过」的完整性警告

**现象。** 账本里 `integrity_warning`（`what = protocol_copy_edited`）从 2026-09-17 起累计 800 条，覆盖 70 个任务——
几乎每个任务、每次开会话都记一条，而这些任务的协议副本没有任何人改过。后果：这条警告全是误报，真改了也分辨不出来；
`freeze_protocol` 在不一致时返回的是「记录的 tag + 现算的哈希」，于是会话与用量数据上挂的 `protocol_ref` 哈希和
`tasks.protocol_ref` 里记的不是同一个值，按版本归因的口径也对不上。

**复现：** 在临时 `AUTOME_HOME` 与临时仓库里建一个需求任务，跑到第二个会话开始（例如任务整理 → 设计），期间不碰
`docs/<slug>/protocol/`；查事件 `select count(*) from events where kind='integrity_warning'`。

**实际行为：** `crates/automed/src/protocol/mod.rs` 的 `current()` 用 `seed().hash()` 作为版本哈希，seed 含 `evals/`
下的用例文件；`copy_into_task` 写任务副本时跳过 `evals/`；之后每次开会话 `scheduler.rs` 的 `freeze_protocol` 用
`read_task_protocol(dir).hash()`（只含副本里的文件）与记录值比较——两边文件集合不同，永远不相等。与协议版本无关，
v1 起就有。

期望行为：

- **I-E1** 协议副本没被改过时，不记 `integrity_warning`；会话上挂的 `protocol_ref` 与 `tasks.protocol_ref` 一致。
- **I-E2** 副本里任何一个文件真被改了（内容变、增删文件），照旧记一条，且同一任务同一份改动只记一次（现在每个会话
  重复记）。
- **I-E3** 已经在跑的任务（按旧口径记了含 evals 的哈希）升级后不再误报，也不丢「真改了要报」的能力。

回归测试与线索：

- **I-T1** 回归测试写在 `crates/automed/tests/end_to_end.rs` 或 `scheduler.rs` 的单测里：固定协议后再开一个会话，断言
  没有 `integrity_warning`；改副本里一个文件后再开两个会话，断言恰好一条。复现命令形如
  `cargo test -p automed <测试名>`；提交前跑 `cargo fmt --all -- --check`。
- 修法方向（设计轮定准）：让「记录的哈希」与「副本的哈希」算在同一个文件集合上——例如版本身份只算会进任务副本的
  文件（去掉 `evals/`），或固定时记录「写进副本的那批文件」的哈希。`protocol.versions` / `protocol.get`、用量与指标里
  按 `tag@hash` 归因的地方要保持同一口径。
- 存量任务：`tasks.protocol_ref` 里已经记了旧口径（含 evals）的哈希，副本没法反推出它。可行做法之一：比较时若记录值
  等于「本二进制 seed 的旧口径哈希」或无法验证，就按新口径重算并把 `protocol_ref` 更新成新值（记一条一次性的迁移
  事件），之后按新口径比较；不要让存量任务继续每个会话报一次。
- 「只记一次」：不一致时把现算的哈希写回任务（或记住已报过的哈希），同一个哈希不重复报。
- **不要改 `protocol/` 正文；这只是内核里哈希口径的问题，不需要发新协议版本**（X-5）。

## 9. 任务卡明确交给设计轮定准的事项（清单，不是结论）

设计文档须逐条给出确定、可测试的口径；这里只列出任务卡点名的那些，便于评审对照有没有漏答。

- **共用机制（X-4a – X-4f）** 各自的归属与唯一实现点；K 的原实现怎样对齐 main 上 T-68 的实现。
- **K：** 补丁路径；熔断的次数口径；与 A、D、J 的交界。
- **A：** 状态块新结论的字段与取值；「修测试」次数上限；「基线红、HEAD 绿」的验证口径；事件名与文案。
