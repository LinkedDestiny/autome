## 阻塞问题

### R1-P01：出队 rebase 后重跑准备命令时尚未持锁，后来的任务可以先合并

- 类别：违反任务目标。
- 追溯：任务 §3.2（出队 rebase → 门禁 → 合并属于同一临界区）、§3.6（FIFO）、§8.1（rebase 到开跑之间不得被本项目合并推进）；设计 G2/G6、D1 第 5–6 步（第 81–88 行）、D3 起点（第 162 行）。涉及 M-01。
- 根因：D1 在 rebase 后回到第 2 步，允许先异步重跑 setup，直到第 6 步才写 `merge.locked`。所谓“第 5 步与第 7 步在同一次调用里”的证明不覆盖这个明确存在的返回分支。
- 源码证据：`crates/automed/src/setup.rs:161` 准入后启动准备作业，第 172 行写 `setup.started`，第 180 行返回 `Ready::Pending`；`scheduler.rs:3424` 附近的 Pending 分支直接返回。`gate_queue.rs:13` 的队列事件集合包含 `setup.started`，第 36 行只保留最后一个相关事件为 `gate.queued` 的任务，所以 setup 开始后原队首条目已经失效。
- 具体反例：
  1. 同项目 B、C 都已授权，宿主并发为 2，B 的排队 seq 早于 C；之前的任务合并使 main 前进并改变 B 的 watch 文件。
  2. B 出队、rebase 到新 main，第二遍 setup 启动作业并返回 Pending；此时 B 没拿合并锁，原队列条目也已被 `setup.started` 消耗。
  3. C 使用另一个宿主名额，准备先完成（也可以已有有效准备记录），通过 D1 第 6 步拿锁并跑完门禁、合并。B 的准备作业此时仍未完成。
  4. B 必须等待 C，再对齐一次。C 在更早出队的 B 之前合并，而且 B 的出队对齐到门禁之间被同项目合并推进了 main；无需外部提交即可发生。
- 检查范围：D1 正常准入、rebase 后再次准备、D3 锁范围、D4 等锁排除、R2/B-03。R2/B-03 仅将“外部推进”列为可接受边角，不能涵盖上述内部插队。
- 建议修正：已授权任务获得出队资格后，在可能异步返回的准备重跑之前建立并持久化项目占用，保持到合并结束；同步调整冲突、准备失败、暂停等退出的释放规则。沿用宿主 setup→gate 连占规则，避免持锁者第二次准入时被本项目等锁者反向阻塞。用 B 的准备作业受控阻塞、C 已就绪的顺序验证 C 不能先合并。

### R1-P02：沿用门禁结果直接拿锁，能越过更早的合并队列条目

- 类别：违反任务目标。
- 追溯：任务 §3.6、设计 G6 和 D4“锁释放后带着原来的 seq 回到队列，按进队先后轮到它”（第 201–206 行）；与 D1 第 2 步（第 76–77 行）冲突。涉及 M-01。
- 根因：D1 第 2 步在 `gate_queue::admit` 之前执行；满足沿用条件的已授权任务可以直接拿锁、`finish_gate`，没有核对更早的合并队列条目。D4 只保证保存 seq，不能约束绕过准入的路径。
- 源码证据：`scheduler.rs:3384` 附近的 MergeGate 沿用分支直接 `finish_gate`；宿主准入位于第 3469 行附近。`gate_queue.rs:47` 按 seq 排序，但只有调用准入逻辑时该排序才约束执行。设计保留这一顺序并在沿用分支加拿锁。
- 具体反例：
  1. A 持锁，B、C 都已授权并停在 MergeGate；B 先进入队列，C 后进入队列。C 创建得比 B 早，但因为实现耗时更长而晚入队，这是合法顺序。
  2. C 的上一轮 Gate 已在当前 HEAD 通过，当前分支不落后；B 需要实际跑门禁。A 的锁使二者都先经过 D4 记下 `gate.queued`。
  3. A 门禁失败并释放锁，main 没有前进，C 的沿用条件仍成立。
  4. 后续 tick 按创建时间先处理 C，C 在 D1 第 2 步直接拿锁并转 Merging。B 虽有更早 seq，却在第 1 步被 C 的锁挡住，最终 C 先合并。
- 检查范围：普通沿用、已排队任务的沿用、rebase 后返回第 2 步的沿用；这与 R1-P01 的异步准备间隙不同，即使没有 setup 也成立。
- 建议修正：明确已授权沿用路径也必须取得项目合并顺序资格后才能持锁和转换；沿用本身可以不消耗宿主执行名额，但不能越过同项目更早的合并队列条目。验证时使用“创建顺序与入队顺序相反、锁持有者失败、后入队者可沿用”的安排。

### R1-P03：撤销接口在 Merging 状态返回成功，却不阻止随后的自动合并

- 类别：内部逻辑矛盾。
- 追溯：任务 §3.3（提供撤销）、§5.3（撤销授权后停在卡点）；设计 D2 撤销分支（第 142–145 行）、D4 Merging 分支（第 207–210 行）、M-02 的结果与撤销用例。
- 根因：D2 对普通 merge 明确拒绝 `Merging | MainCheck | Cleanup`，但对 `cancel: true` 另行规定“有效授权为真”即写撤销，不限定状态、不改节点，并立即 tick。D4 只在 Merging 检查别人的锁，不检查本任务授权；因此已进入 Merging 的任务不会因撤销退回合并卡点。
- 源码证据：`scheduler.rs:3153` 的 Merging 分支执行 `merge_all`；`dispatch.rs:1901` 附近的派发路径应用操作后立即 tick。设计只为前者加等锁检查，明确保留后者 tick，未增加撤销转换。
- 具体反例：已授权的 A 门禁通过，tick N 将它转到 Merging，但还没执行合并。下一次自动 tick 前收到 `task.merge {cancel: true}`；D2 写 `active: false, by: user` 并准备返回 `merge_request: revoked`。RPC 内的 tick 随即执行 A 的 `merge_all`，main 已推进，用户却收到“已撤销预先同意合并”。如果 A 此时在等别人的锁，撤销也只延迟合并，锁一释放仍会合并。
- 检查范围：门禁通过后的 tick 间隙、Merging 等锁、无门禁 Rebase 完成后的 Merging，以及 MainCheck/Cleanup/终结状态下仍残留的有效授权记录。
- 建议修正：为撤销定义状态边界。至少在已开始合并及合并后的状态拒绝撤销并说明已无法撤销，不返回 `revoked`；若承诺 Merging 尚未执行 git 时仍可撤销，则应经 domain 转换和 `advance` 返回 AwaitMerge、释放占用，并处理工作区部分仓库已经合并的情况。保留 MergeGate 通过前撤销后停在卡点的行为。
