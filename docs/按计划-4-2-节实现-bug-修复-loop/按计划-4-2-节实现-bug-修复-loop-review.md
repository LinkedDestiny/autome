## 阻塞问题

### R1-P01：需求表入口的全面拒绝与 Bug 控制操作的委托互相冲突

- **类别 / 级别：** 内部逻辑矛盾 / P1。
- **追溯：** 任务 A4（不是 Bug 后可以取消）；设计方案 §1 第 101–103 行的入口防御、第 90–92 行的等待节点操作、第 143 行的通用控制委托；M-01 第 12、29 号用例，以及 M-04 第 2 个 e2e。
- **根因与证据：** 设计要求在 `task::apply_with_merge_request` 第一行对“状态里的节点属于 `Node::BUG`”直接返回 `Err`，同时又要求 Bug 的取消、暂停、停止、恢复和 `Requeued` 出队委托需求表。当前入口先调用 `apply_inner`（`crates/autome-domain/src/task.rs:695`），控制触发器在后者内部处理（`:748–807`），出队在 `:817–832` 处理。因此入口拒绝会发生在这些可复用处理之前。
- **具体反例：** 新 Bug 定位得到 `不是 Bug`，进入 `Active{not_a_bug}`；用户取消。Bug 表按设计委托需求表，需求表入口看到 `not_a_bug ∈ Node::BUG` 返回 `Err`，无法得到 `Cancelled + RunCancel`，直接违反 M-04 的取消验收。类似地，`Active{fix} + Pause`、`Paused{fix} + Resume`、`Requeued{fix} + SlotAvailable` 都被同一防御挡住。
- **同类检查范围：** 已检查 §1 整张转换表和 `task.rs` 的全部通用控制分支；受影响的是新节点上的取消、暂停、停止、恢复、出队，包括两个等待节点的取消。`Stopped{repro_check/fix_gate}` 虽有专门的恢复分支，其后的 `Requeued` 出队仍受影响。
- **建议裁决落点：** 在 §1 明确允许通用控制处理先于 Bug 节点的拒绝，或由 Bug 表自行处理这些控制操作；把拒绝限制在确实可能进入需求会话转换的路径。同步 M-01 的范围说明和 R7，不能同时保留“入口一律拒绝”和“通用控制委托”两项规定。

### R1-P02：共享门禁增加命令匹配条件会改变需求任务行为

- **类别 / 级别：** 违反任务目标 / P2。
- **追溯：** 任务 C2（需求任务零行为变化，含转换与事件）；设计“目标”、风险 R2；方案 §4 第 227 行与 M-03 第 544 行。
- **根因与证据：** 设计对 F7 的共享复用条件增加“命令相同”，并以“需求任务的命令永远是 `[gate].command`”推导需求行为不变。这忽略了配置可在两次门禁之间变化。当前 `run_gate` 每次重新读取配置（`crates/automed/src/scheduler.rs:2075`），但在没有当前作业时，合并前门禁仅按上次结果通过且 SHA 相同复用（`:2110–2124`），没有命令匹配条件。
- **具体反例：** Feature 任务在 SHA H 上用命令 A 通过实现门禁；用户把项目门禁改成会失败的命令 B；之后 rebase 没改变 H，且尚无该 H 的合并前门禁作业。现有实现复用 A 的通过结果，发出 `gate.reused`；按设计新增共享条件后，则执行 B，失败后退回实现。事件、是否执行命令及后续转换均改变，不能称为 C2 下的零变化。
- **同类检查范围：** 检查了 `run_gate` 的配置读取、跨节点结果复用和结果记录，以及设计所有“命令相同”的改动落点。问题涉及共享 `merge_gate` 路径上的 Feature 任务，也涉及设计承诺继续走需求 Loop 的旧 Bug 任务。
- **建议裁决落点：** 将新增匹配条件明确限定于 `uses_bug_loop` 为真的新 Bug Loop；Feature 和旧 Bug 继续使用原条件。若要同时修正旧路径，应另行授权范围，不能在本任务中以“行为不变”为由纳入。同步 §4 与 M-03。

### R1-P03：直接拒绝工作区 Bug 是任务未授权的功能范围缩减

- **类别 / 级别：** 违反任务目标 / P1。
- **追溯：** 任务 §2 的目标“`kind = bug` 的任务从创建起走 Bug Loop”、同节“需求、Bug 共用的部分不变：worktree、分支、rebase……”；A1；任务 §4 的范围排除没有排除工作区项目。参考文档 §4.2 第 128 行同样规定共用部分不变。
- **设计位置：** “非目标”第 62 行、方案 §7 第 276–277 行、M-04 第 592、610 行的工作区拒绝与验收，以及 Backlog B-02。
- **根因与证据：** 设计因为新 Bug 文档没有 `repos:` 行，就把所有工作区 Bug 在定位前变成 `Failed{Config}`。仓库现有工作区路径从文档确定成员仓并建立检出（`crates/automed/src/scheduler.rs:1392–1432`、`:1600–1612`）；这说明省去任务整理后确实需要解决仓库选择问题，不能证明用户已经同意停用这类项目。任务 Q9 正要求回答无任务整理时如何准备工作，未授权直接删除工作区适用性。
- **具体反例：** 在已经正常配置、能够运行需求任务的工作区项目创建一个信息充分、可以复现的 Bug。按设计，它不会进入定位、复现检查或修复，而是在任何检出建立前失败；补充信息也无法使其进入 Bug Loop。这不是无法复现等规格异常，而是对整类合法项目新增禁用条件。
- **同类检查范围：** 检查了任务范围、参考文档 §4.2，以及设计中全部工作区相关规定。新增“拒绝工作区”的 e2e 只能证明缩减被落实，不能证明它满足任务目标。
- **建议裁决落点：** 在 Q9/§7 给出沿用现有工作区能力的仓库选择和输入准备方案，并调整相应里程碑。若确需延期，应先记录为待用户裁定的范围变更，不能仅放入 B-02 就视为完成原目标。

## 非阻塞建议

- **N1：手动重跑时的复现计数语义。** §3/§4 以“复现成功后不会再回定位”解释 `repro_misses` 只按最近一次 `task.replied` 清零，但 §1 同时允许 `Failed/Stopped + RerunFrom{locate}`。例如先未复现一次，随后复现成功并在修复阶段停止，再手动重跑定位，此时旧的 miss 仍在计数范围内。任务没有规定手动重跑是否开启新的复现周期，故不据此阻塞；由裁决轮决定是否明确其语义或放入 Backlog。
