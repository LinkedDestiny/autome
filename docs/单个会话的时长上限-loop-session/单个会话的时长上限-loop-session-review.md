## D2-P01：恢复查询限定为有退出标记，与超时恢复及轮号复用规则冲突

- **类别：内部逻辑矛盾。**
- **追溯：R-3、C-5（超时不消耗轮数预算）、R-5（会话可识别为超时）；设计方案 §3 第 1 步、§4「账本里的轮号」、§6 的 `timed_out` 派生规则；影响 M-02、M-03、M-04。**
- **矛盾位置：** 设计第 141～145 行先规定 `Exited / Vanished` 照旧收割、已有 `session.timeout` 事件则例外地再次终止并确认，但又明确写「这次查询只发生在会话已有退出标记的那一次 tick」。这两条规则在「有超时事件、无退出标记、已满足 Vanished 条件」时不能同时执行。按后一条实现，就没有机会识别前一条规定的例外。
- **源码依据：** `crates/autome-domain/src/session.rs:258` 的 `classify` 在无标记、组长 pid 不活、日志静默至少 600 秒时返回 `Vanished`。退出标记不是终止的必然产物：wrapper 依赖 shell 的信号处理函数写文件（`.autome/skill/run_session.sh:47`、`:59`），写文件和移动标记都可能失败；升级 SIGKILL 也不能保证信号处理函数完成。设计 §3 自己就允许升级 SIGKILL，因此不能把「终止过」等同于「一定有 130 标记」。当前 `reap_session` 对非 Running 生命周期直接 `finish_session`（`crates/automed/src/scheduler.rs:264`），`read_outcome` 把 `Vanished` 转成「会话消失且长时间没有输出」（同文件 `:1661`）。
- **具体反例：**
  1. 实现轮第 1 轮超过上限；内核持久化 `session.timeout`，终止进程组。退出标记未成功落盘，内核在 `finish_session` 之前退出，账本仍为 Running。
  2. 内核十分钟以上后恢复；进程已不存在、日志不再变化、没有退出标记，`classify` 返回 `Vanished`。
  3. 遵循「只有退出标记才查询超时事件」的规则，恢复路径直接把生命周期写成 `Vanished`。§4 的 `schedule_retry` 虽然能再次查到超时事件并计次重派，却不负责纠正已经写入的生命周期。
  4. §4 的 `next_round` 只排除 `timed_out` 行，这条 `Vanished` 行仍占第 1 轮，重派被登记为第 2 轮，违反 C-5；§6 从生命周期派生的 `timed_out` 同时为 false，违反 R-5。若此时重试已用尽，按既定 `reason = detail` 规则，失败理由也只剩「会话消失」，没有超时说明。
- **与上一轮的区别：** D1-P01 的「已有 130 标记，但组内仍有残留进程」已由新设计修复，本轮不重复要求修复它。本项针对修订后新增的查询条件，补充的是「无标记、恢复时已经 Vanished」这一不同输入；不是以增加测试数量为理由要求复审。
- **检查范围与最小修订要求：** 一并核对正常退出、普通 Vanished、已有超时事件的有标记/无标记恢复、仍为 Running 的终止重试。对已有超时事件的恢复，不能以退出标记存在为识别前提；确认进程组停止后统一按 `TimedOut` 收割，继而执行既定的轮号、失败理由与展示规则。没有超时事件的普通心跳兜底继续保持 N-3。可在 M-02 现有恢复用例中补入上述输入，复核同一链路的生命周期与轮号结果，无需新增里程碑。
