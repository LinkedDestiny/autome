## D1-P01：未完成进程组终止就结束会话并重派

- **类别：违反任务目标。**
- **追溯：R-2、C-4、A-3；设计方案 §3 的收割顺序、§4「进程组已经没了，没有并发写者」；影响 M-02。**
- **根因：** 方案把超时事件或 wrapper 的退出当成整个进程组已经终止，缺少终止完成这一前置条件。§3 第 3 步还明确规定 `pid=None` 跳过终止、出错只记 warn，随后仍进入 `finish_session → sweep_commit → retry`。
- **反例一（正常可见终端启动延迟）：** `read_pid` 只等 `40×50ms`，超时就把 `None` 登记到会话中（`crates/automed/src/scheduler.rs:2977`、`:3022`）。终端在两秒之后才启动 wrapper，CLI 此后持续输出；没有后续补读 pid 的路径。到上限时按设计跳过 kill，却提交改动并重派，旧 CLI 继续写同一工作树。
- **反例二（终止中内核退出）：** 写 `session.timeout` → 向组发 TERM → wrapper 写 130 标记退出，但同组某子进程忽略 TERM → 内核在三秒宽限内退出、尚未补 KILL。恢复后，§3 第 1 步凭超时事件把退出标记转换成 `TimedOut`，直接收割，不再完成终止；旧子进程和新会话并发运行。wrapper 的信号处理只写标记并退出（`.autome/skill/run_session.sh:60`）；`classify` 优先采用退出标记（`crates/autome-domain/src/session.rs:263`），当前终止函数的 TERM/KILL 之间确有宽限期（`crates/automed/src/launcher.rs:1260`）。
- **检查范围与修订要求：** 一并处理新超时、缺失 pid、终止错误、已有超时事件恢复这几条入口。区分「超时已决定」与「进程组已停止」，恢复时继续完成终止；无法确认停止时不能假定不存在并发写者并继续提交、重派。进程组归属与 pid 补取方式由裁决轮明确，不要求改动心跳判定。

## D1-P02：沿用现有重派路径实际会消耗实现轮数预算

- **类别：关键事实错误。**
- **追溯：R-3、C-5；设计方案 §4「不动轮数」、§5 续做文案及风险节把问题归为模型是否遵循；影响 M-03。**
- **证据：** `crates/automed/src/store.rs:1571` 的 `next_round` 对同角色所有会话取 `MAX(round)+1`，不排除超时重派。`start_due_retries → redispatch_with → start_session → launch_session` 仍调用它（`scheduler.rs:649`、`:4396`、`:2833`），并将结果作为实现预算轮号（`:2844`）。`launcher.rs:744` 明确要求模型把 `implementation-round` 写成这个新轮号。
- **确定性反例：** 预算为 3，第 1 轮实现超时后重派被登记为第 2 轮，成功后进入 rebase。若 rebase 冲突，再开的修复会话被登记为第 3 轮；再次发生冲突时 `next_round=4 > 3`，`scheduler.rs:1843` 的预算判断直接产生 `FailureReason::ImplBudget`。没有那次超时重派时，同一路径的下一修复轮仍是第 3 轮，不会在此耗尽。即使模型服从超时说明、保持文档轮数，账本这一硬判断也不会改变。
- **同类指令冲突：** §5 先写「已经加过则不要再加」，随后逐字渲染原注入；现有 `GateFailed`、`QuickGateFailed` 文案又要求 `implementation-round` 照常加一（`launcher.rs:547`、`:587`、`:594`），加上前述预算行，重派 prompt 同时给出相反要求。
- **检查范围与修订要求：** 明确物理会话次数与逻辑实现轮次的区别，统一重派登记、预算行、rebase 预算判断、原门禁注入和状态块的续做语义。已核对 Bug 的 `bug.fix_round_started` 有 requested/started 条件保护，不能因此推断普通实现轮也不会增加。不得仅把 C-5 留给人工 H-01 或模型遵循程度兜底。

## D1-P03：包装 carried 注入后，只递归渲染会丢失其调度语义

- **类别：内部逻辑矛盾。**
- **追溯：设计目标第 4 条、方案 §5「原来携带的注入一起带上」及「原注入不能丢」的承诺；C-5；影响 M-03。**
- **根因：** 方案只修改注入构造、持久化和文本渲染，假定把原变体放进 `SessionTimedOut.carried` 就保持原行为；当前生产代码还有按顶层变体判定的语义消费者。
- **反例一（用户决定丢失）：** 带 `Decisions` 或 `DesignFeedback` 的会话超时后，其未处理决定被释放；重派的顶层变体变成 `SessionTimedOut`。`scheduler.rs:2599` 仅对顶层 `Decisions / DesignFeedback` 调用 `carry_decisions`，因此重派得到 `decisions=[]`。即使递归渲染原变体，`launcher.rs:516`、`:573` 读取的也是这份空列表，`:840` 将其渲染为空。保留了变体名称，却没有带回用户表态正文。
- **反例二（合法修复变协议失败）：** 原本带 `GateFailed` 的修复轮超时，重派保留门禁文案，按要求让待审里程碑保持待审并正常结束。`scheduler.rs:717` 只把顶层 `GateFailed` 认作 `repairing=true`；包装后变成 false。若快照没有开放里程碑、至少一项待审，其余已完成，`guards.rs:276` 会产生 `impl_had_no_target` 错误，进入 GuardFailed/协议失败路径。现有 `guards.rs:833` 的 `a_round_repairing_a_red_gate_needs_no_open_milestone` 正好证明这个修复豁免不可省略。
- **检查范围与修订要求：** 一次核对所有 `Inject` 判别消费者，至少覆盖决定领取/释放/结算、门禁修复守卫、提示渲染；对包装后的有效原注入保留原语义。轮数指令冲突统一归 D1-P02，不重复计项。

## D1-P04：Onboarding 不在方案依赖的会话登记与检查链中

- **类别：关键事实错误。**
- **追溯：R-2「每个在跑的会话」；设计背景「所有会话都从这里进来」、方案 §2 唯一登记点、§3 覆盖表；M-02 对开放问题 7 的覆盖承诺。**
- **证据：** `scheduler.rs:4467` 的 `start_onboarding` 独立调用 `launcher::launch`，随后只追加 `session.started` 事件，没有调用 `insert_session`。`store.rs:1554` 的 `all_running_sessions` 只读取会话表。并且 `reap_session` 一开始就要求真实 task（`scheduler.rs:250`），而 Onboarding 的合成键明确不是真实任务（`:4523`）。其中现存的 `SessionKind::Onboarding` 提前返回分支不能证明实际启动路径可达。
- **反例：** 向导 CLI 一直输出超过配置上限；按方案只修改现有任务会话登记点和 `reap_session`，tick 永远取不到这次会话，既不终止，也不记录超时。
- **检查范围与修订要求：** 已交叉检查唯一任务会话登记点、独立 Onboarding 启动入口、运行会话查询及收割入口。给 Onboarding 明确可执行的跟踪、项目归属、上限快照和终止路径；若裁决决定把它排除，应明确处理与 R-2 的范围冲突，不能继续声称当前路径已经覆盖。此问题不要求凭空给向导增加任务节点。

## D1-P05：Intake 的提前返回绕过超时注入渲染

- **类别：违反任务目标。**
- **追溯：R-4；设计方案 §3 将任务整理纳入重试、§5 的注入实现；影响 M-03。**
- **证据：** `launcher.rs:473` 对 `SessionKind::Intake` 直接 `return intake_prompt(spec)`，早于 `:489` 的 `match spec.inject`；`intake_prompt`（`:896`）没有读取或渲染 `spec.inject`。§5 只要求把后面的 match 抽成 `render_inject`，不会改变该提前返回。
- **反例：** Intake 超时，重试行正确持久化了 `SessionTimedOut`，`redispatch_with` 也传递了它；第二个会话实际 prompt 仍完全没有超时说明、日志尾或缩小目标要求。
- **检查范围与修订要求：** 核对 `build_prompt` 的所有类型分支：Bug 和 Role 会到达注入段，Intake、Onboarding 提前返回。让任务整理重派实际执行公共注入渲染，并保留原任务卡和附件内容；Onboarding 是否需要重派注入随 D1-P04 的范围裁决处理，不重复计项。
