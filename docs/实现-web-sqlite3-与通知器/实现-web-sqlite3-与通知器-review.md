## 阻塞问题

### D1-P01：铃铛另建 WebSocket，放宽了 R-05 的连接约束

- **类别：违反任务目标。**
- **违反依据：**任务 R-05（任务文件第 63 行）要求经 W3 `/ws` 推送，“不另开 WebSocket 或轮询”。
- **设计位置：**方案 §6 第 206–209 行、风险第 247 行、Backlog B-01 第 351 行。
- **事实与反例：**设计要求铃铛自己连接同一 `/ws`，并明确每标签页有两条连接、到 W5 再合并。当前 `app/root.tsx:7` 已调用 `useLiveEvents()`，后者在 `app/lib/live.tsx:16–18` 经 `createLiveClient` 创建 WebSocket；按设计再挂铃铛后，一个页面就会创建第二条连接。地址相同不等于复用现有连接。
- **根因及同类检查范围：**为绕过 `app/lib/` 不在可改范围的限制，把任务的“不另开 WebSocket”替换成“不另开服务端通道”；已检查 §6、风险说明及 B-01，三处采用同一替代解释。现有 live-client 缺少扩展消息回调是实际限制，但不能单方豁免 R-05。
- **建议裁决落点：**明确在本任务内复用连接的接入办法；如确需放宽文件范围或连接约束，按协议写成争议项交用户裁定，不以 W5 Backlog 视为当前要求已满足。对应 M-04 接线方案与验收应保持一致。

### D1-P02：正常点击通知进入 404，与目标不存在时不报错冲突

- **类别：违反任务目标。**
- **违反依据：**任务 R-06（任务文件第 65–66 行）明确目标路由不存在时不报错。
- **设计位置：**方案 §7 第 222–225 行；M-04 链接检查；M-05 系统通知点击行为与 H-02。
- **事实与反例：**设计明确用 `<Link>` 跳转，并让 React Router 显示自带 404，只承诺“铃铛本身不抛错”。现有 `app/routes.ts:2` 仅注册首页，`app/root.tsx` 没有通知目标的降级展示。W4 完成而 W7 尚未实施时，点击正常任务通知 `/tasks/T-3` 会从面板进入错误页，这正是 R-06 要求处理的场景。
- **根因及同类检查范围：**把用户“不报错”缩小为组件“不抛错”；同类位置包括铃铛任务链接、无任务告警的项目链接，以及系统通知点击后的 `href` 跳转。任务链接直接违反 R-06，其余入口应一起核对，避免同一路由在不同入口行为不一致。
- **建议裁决落点：**在保留目标链接、且不实现 W6/W7 页面这一范围内，明确目标尚不可用时的正常中文反馈或留在面板的行为；让铃铛与系统通知入口共同遵守，不能以默认 404 作为验收预期。

### D1-P03：有限认领记录与固定等待不能保证多标签页通知约定

- **类别：违反任务目标、内部逻辑矛盾。**
- **违反依据：**任务 R-07 要求避免多个后台标签页重复弹同一通知；设计 §7 第 227–231 行承诺“多个后台标签页同一通知只弹一次，有一个标签页在前台时不弹”；M-05 的预期及 H-03 也要求这些结果。
- **设计位置：**方案 §7 的 400 ms 等待、最近 100 个 id 的认领数组；M-05 第 331–337 行；H-03 第 344 行。
- **反例 A（有锁仍重复）：**A、B 都在后台且已授权。A 先收到并处理 n1…n101，n1 已 `show`，随后被最近 100 条记录淘汰；B 延迟处理自己的 n1 消息，在同一把锁内检查发现 n1 不存在，于是再次认领并 `show`。两次认领完全串行，锁不会修复被淘汰的历史。通知消息没有参与 W3 的事件续传去重，独立标签页的接收或处理延迟也未被设计限定在 100 条以内。
- **反例 B（存在前台仍弹）：**B 始终可见，A 在后台。A 于 t=0 收到 n；B 对同一消息的回调延迟至 t=500 ms。A 在 t=400 ms 的认领成功并弹出，B 随后认领失败。400 ms 只能给前台页一次机会，不能证明它已经参与认领；这违反设计自身 §7 与 H-03 的前台抑制承诺。
- **根因及同类检查范围：**跨标签页的正确性依赖未规定的消息处理时差与积压上限。已检查认领、记录淘汰、前后台分支及 M-05/H-03；两个反例均在 `navigator.locks` 可用的主路径成立，不依赖降级路径或浏览器 API 缺失。
- **验证：**本轮以 Node 对设计中的锁内串行读写及时间顺序作最小模拟，反例 A 的 n1 `show` 次数为 2，反例 B 在 B 可见时发生 `show`，断言均通过。原始结果在 `.autome/output/review-notification-counterexamples.txt`。这是设计反例验证，不是浏览器或系统通知实测。
- **建议裁决落点：**给出不依赖上述固定窗口的跨页协调与记录淘汰条件；用这两种顺序核对修订后的方案。此项针对已经承诺的行为会失败，不是要求“测试更多”，也不以验收不明确要求复审。

## 非阻塞建议

- **N-01：重启边界的“进入”语义。**设计第 144–146、245 行允许重启后的首条相同状态再次通知。例如 seq 100、101 状态相同，中间重启会比不中断多一条。R-02 明确把“进入”的含义交给设计决定，而 R-03 的正文重点是已处理事件不重复、未处理事件补齐；此例的 `event_seq` 不同，不能直接证明同一事件重复处理。本轮不将其作为阻塞。建议裁决轮决定是否将跨重启语义一致性纳入 Backlog。
- **N-02：状态记忆应随处理成功提交。**设计没有规定最近状态的更新时间；实现时若先更新记忆、再补齐信息，补齐超时后重试同一事件可能被当作相同状态跳过。现有 §4.5 与 M-02 已要求“下次补上”，实现可以通过成功提交后才更新记忆满足它，所以不把尚未选定的错误实现当成设计缺陷，也不据此增加轮次。
