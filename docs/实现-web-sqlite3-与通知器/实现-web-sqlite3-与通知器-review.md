## 阻塞问题

### D2-P01：列表请求失败会永久吞掉已收到的系统通知

- **类别：违反任务目标。**
- **违反依据：**任务 **R-07** 要求后台标签页对「需要你」级通知发系统通知；设计 §7 第 265–269 行规定级别、权限、本标签页是否隐藏三个条件，并允许找不到列表条目时仅凭消息标题和任务信息显示。
- **设计位置：**§6 第 241–245 行，特别是「拉取失败则不交」；§7 第 265–269 行；M-04 验收契约第 370 行的「拉取失败不交」。
- **具体反例：**后台标签页已授权，成功收到 `notification`（带 `id`、`kind: await_merge`、`task_id`、`title`）。随后用于刷新铃铛的 GET 因一次网络错误失败，按设计不调用 `onNotification`，因此不显示系统通知。WebSocket 可以继续正常，也可以稍后重连；网络恢复后的 `hello` 只刷新列表，不会重放这条 `notification`。服务端已提交游标且重复事件不再推送，这条提醒永久遗漏，即使列表随后已能显示它。
- **根因及同类检查范围：**把正文、项目等可选信息的补齐成功变成系统通知的额外必要条件。已核对控制器首次拉取、三类刷新消息、失败分支、系统通知参数降级与 M-04/M-05 契约；没有失败后重交原通知的路径。这是明定的失败行为损害 R-07，不是要求增加泛化重试或“测试更多”。
- **验证：**用 Node 按上述明确分支作最小控制流模拟：收到通知 → GET 失败 → `hello` 后 GET 成功，`show` 次数仍为 0。结果存于 `.autome/output/review-2-checks.txt`。这是设计逻辑反例，不是尚未实现的产品实跑。
- **建议裁决落点：**列表请求失败时也把原消息交给系统通知判定，沿用 §7 已有的无正文、仅任务信息降级；铃铛继续显示加载失败文案。同步修订 §6 与 M-04 的“失败不交”预期，并在 M-05 验证这个失败分支。无需恢复跨标签页协调。
- **与既有裁决关系：**新问题；不复提 D1-P03 的认领机制，也不否定用户选定的 `hidden + permission + tag` 方案。

### D2-P02：H-03 的自动退回指令与固定协议冲突

- **类别：内部逻辑矛盾。**
- **违反依据：**任务指定的 `protocol/loop-protocol.md:188–202`「验收必须是会话自己能跑的」，其中第 196–198 行明确：人工验收清单任何一条都不阻塞里程碑关闭、不触发轮次，由用户在合并前确认。
- **设计位置：**人工验收 H-03，第 405 行：「这是 `tag` 合并在真实浏览器里的唯一验证，失败即退回 M-05」。
- **具体反例：**M-05 自动验收通过并关闭后，人工观察某浏览器通知中心未按预期合并。H-03 命令退回 M-05，固定协议却禁止这个人工清单项触发轮次，两条规则无法同时执行。没有拿到人工证据也不能据此保持里程碑待审或宣告协议失败。
- **根因及同类检查范围：**将合并前的人工确认附加成 Loop 的自动退回条件。已检查 H-01..H-07、风险说明和 M-05 契约，只有 H-03 明写该退回指令；M-05 本身三项契约完整，不属于“验收不够明确”。
- **建议裁决落点：**保留 H-03 的真实浏览器检查内容，去掉“失败即退回 M-05”的自动调度指令；人工结果由用户合并前确认并决定后续处理，Loop 按会话可执行的验收项运行。
- **与既有裁决关系：**本条针对当前 H-03 的退回规则，与 D1-P03 的跨标签页技术反例不同，不要求修改用户已选定的简化方案。

## 非阻塞建议

### N2-01：检测到换账本后，一并清空通知器的内存状态与补齐缓存

- **关联位置：**设计 §2 第 142 行、§3 第 166–180 行、§4.4 第 192–193 行；R-03 与 M-02「换账本……之后正常」。
- **反例：**旧账本的 T-1 最近状态为 `await_design_approval`、缓存项目 A。Web 进程保留而内核接入新账本，新账本的 T-1 属于项目 B；通知器检测到序号回退并重置到 20。若仍保留旧内存，新账本 seq 21 的 T-1 首次进入同一批准状态会被旧状态抑制；换成另一命中状态也可能复用项目 A 的补齐信息。
- **可达依据：**`crates/automed/src/store.rs:1256–1271` 按本库任务编号分配新 ID，新账本可以复用 T-1；`apps/web/server/core/supervisor.ts:42–50` 支持保留 Web 进程并重启内核。这不是设计已经接受的“新账本序号已超过旧游标”检测盲区。
- **非阻塞理由：**设计没有禁止重置时清缓存，且 M-02 已要求换账本之后正常；实现可在现有方案内清理并满足契约。沿用前轮 N-02 的标准，不把尚未选定的错误实现当成设计缺陷。建议裁决轮决定是否写成实现注意事项或纳入 Backlog，不据此增加轮次。
