# Loop V1 协议审计与优化建议

日期：2026-09-16
对象：五角色 Loop 协议 v1（1.x `template.md` 与 2.0 `loop-protocol.md` / `role_prompt` 同源），以及它在三次真实运行里的表现。
目标：提高研发准确度、保证评估准确性、减少 Token 消耗，且不增加机制复杂度。

## 0. 结论

协议骨架是对的：五角色、生成/评测双模型、审计独立复验、里程碑三态。三次真实运行都在预算内推进，审计每一次退回都被修复轮先红后绿地复现，没有一次误报。

浪费不在机制，而在三个落点：

1. **设计文档被当成日志。** 三次运行的设计文档分别长到 335KB、323KB、230KB，其中七成是逐轮追加的证据块。每个会话开场先读它，Claude 会话再把它带进后面 50–104 个 turn 里。
2. **实现轮的出口只有「验收命令通过」。** 于是可以从设计里枚举出来的缺陷类别（状态迁移、设计点名的失败分支、输入域边界）一律留给审计去抓。每抓一次就多花一对会话。
3. **审计造出来的判别检查落在 gitignore 目录里。** 既没进项目测试体系，后续审计还要每轮重跑，合并后也没有回归保护。

下面 7 条建议全是条文和落点的改动，不新增状态、不新增文件类型。

## 2. 发现

### 2.1 研发准确度

**F1 返工率高，根因是实现轮的出口条件。** voice-schedule 七个里程碑里六个被退回过，15 个实现轮里 6 个是修复轮；dashboard-mvp 13 次 reopen。协议对实现轮的要求是「取得验收命令的通过证据」，验收命令天然是正路径；对高风险行为的负向对照写在设计阶段要求里，判别性检查写在审计要求里，唯独实现者没有这一步。每次漏掉都要付一对会话（实现约 10 USD + 审计约 110k tokens + 30–60 分钟）。

**F2 审计的判别检查不入库。** 审计把检查程序写在 `.autome/output/audit-m0x/`，该目录在 `.gitignore` 第 3 行。后果有三：修复轮靠它复现但不把它搬进测试体系（`Tests/` 里只有零星几份被搬进来）；后续审计要手工重跑前几轮的矩阵（审计 #8 重跑了 #6 的 76 项与 #7 的 346 项、72 项）；合并到主分支后这些检查全部消失。dashboard-mvp 那次做对了（「审计轮的 repro 逐字节搬进 tests/e2e」），但协议没要求。

**F3 实现预算的分母有两处真相。** 2.0 的 `loop-protocol.md` 把「N = 5 × M」改成了「按初始里程碑数计算」却没写系数，会话自己填了 `N = 2 × 7 = 14`；全局配置 `budget_factor = 5`，内核 `compute_budget` 算的是 35。会话在 #14 写下「预算已到上限、M-07 未开工」，内核照常调度 #15，会话又把这解释成「用户放行到第 16 轮」。会话从头到尾看不到内核的 k 与 N。

**F4（已解决）** 前两轮因权限被拒而空耗，并误判「协议失败」。2.0 的 `role_prompt` 已加了「提交不上不是协议失败」的段落，无需再动。

### 2.2 评估准确性

**F5 审计有效、无误报，保留。** 12 次审计 7 次发现缺陷，每一次都由修复轮先原样复现红、再修绿。双模型分工（Claude 生成、Codex 评测）实测成立。

**F6 三份复盘的协议建议一条都没落地，2.0 还丢了「验证缺口」。** 1.x 两次运行的 retro 各给了 3 条建议：报用例总数与基线之差而不是 pass/fail/skip；验证缺口要有领域记账；「无法复现」不等于「不存在」；审计要盘点只有人工能看见的结果；升级口径按同成因而非同领域。2.0 的 `loop-protocol.md` 把审计结论改成了二选一（通过 / 实现缺陷），「验证缺口由审计就地加强并复验」这一条不见了，实际运行里审计仍在做这件事，只是无条文可依。

**F7 人工才能看见的结果被当成了里程碑。** M-07「端到端真机验收」要真实鼠标、麦克风、通知横幅；会话从 M-01（菜单栏图标可见）起就把这些记为「待人工复验」，累积到 M-07 后审计 #12 只能写「真机未取证」再退回。这种里程碑会话永远关不上。island-workbench 的复盘建议 1 是同一件事。

**F8 审计结论写三遍。** `-audit.md`（覆盖）、设计文档「M-0x 独立审计结论」（追加）、retro 一段（追加）。覆盖式的审计文件反而丢历史，追加式的设计文档反而成了日志。另外 Codex 会话会自动加载用户全局技能（`git-commit`、`finishing-task-loops`、`correctness-reviewer`），审计行为有一部分不受 Loop 配置控制，需知悉。

### 2.3 Token 消耗

**F9 设计文档是日志。** voice-schedule 设计文档 230KB，「里程碑」一节 158KB（69%），每个里程碑下挂着「验收证据 / 修复证据 / 独立审计结论」子节，每轮约 +14KB；「背景与现状」30KB 里还有「实现轮 #1–#15 记录」。1.x 两次运行同样是 335KB、323KB。估算 64k tokens，每个会话开场读一遍，Claude 会话再在每个 turn 里带着它。按 cache 读 ÷ turns 算，文档约占每 turn 上下文的四成。

**F10 retro 不是一行。** 29 条记录 68KB，平均 2.3KB 一条；1.x 是 225KB。协议原文是「每轮追加一行简要记录」。

**F11 会话 turn 数 50–104。** 其中读写文档的 turn 不少：Codex 审计会 `cat` 230KB 的设计文档，任务文件与审计文件各 `cat` 两次。

## 3. 建议（按性价比排序）

每条给出：改什么、落在哪、预期、复杂度。2.0 的落点是 `crates/automed/src/init.rs` 里的脚手架文本（改后 bump `SCAFFOLD_VERSION`）与 `launcher.rs` 的 `role_prompt`。1.x 已冻结，不动 `template.md`。

### S1 证据出仓（Token，收益最大）

- 设计文档每个里程碑只保留一行 `最新证据：<路径> · 结论 · 轮次`。证据正文、修复证据、审计结论写到 `docs/<slug>/evidence/M-xx-r<k>.md`（受跟踪，但会话默认不读，只在退回时读当轮那一份）。
- 「背景与现状」不得追加轮次记录；审计结论只写 `-audit.md`，不再抄进设计文档。
- 可选：内核在设计文档超过 80KB 时打一条警告事件。
- 预期：设计文档回到定稿时的 60–70KB；每 turn 上下文减三到四成，Claude 实现轮费用大致同比下降。
- 复杂度：条文 + 两条 prompt 句子。

### S2 retro 一行制（Token，小）

- 固定字段、不超过 200 字：`轮次 | 里程碑 | 结果（待审 / 通过 / 退回+领域） | 证据路径 | 阻塞`。只有终止总结允许成段。
- 预期：retro 从几十 KB 降到几 KB。
- 复杂度：一句条文。

### S3 实现轮出口加自审清单（准确度，收益最大）

标「待审」之前，实现轮必须在当轮证据文件里写一份自审清单并逐项执行：

1. 对照设计里本里程碑的情形表 / 落法表，逐行列出检查与结果。
2. 设计点名的每条失败分支各跑一个检查（拒绝授权、读盘失败、超时等）。
3. 有状态机或多通道的，列出全部迁移（状态 × 事件、通道 × 方向）并各跑一次。
4. 有输入域声明的，跑域边界（前导零、闰日、跨年、空串）。

- 依据：1.3 的九条缺陷全部落在这四类里。
- 预期：不替代审计，但把「拿着设计就能列出来」的那类漏洞挡在退回之前；每少一次 reopen 省一对会话。
- 复杂度：`role_prompt` 的 Impl 段加一段，协议「实现循环」加四行。

### S4 审计判别检查入库，审计不重跑历史矩阵（准确度 + Token）

- 审计发现缺陷用的检查，由修复轮逐字搬进项目测试体系（作为该缺陷的回归用例），修复轮的通过证据必须包含它。
- 审计通过时新造的检查可以丢弃，只在 `-audit.md` 记一行「构造了什么、结果」。
- 审计不得重跑前几轮的临时矩阵；复验范围是项目测试体系 + 验收命令 + 本轮新造检查。
- 预期：合并后有回归保护；审计每轮少跑几百到几千项历史检查。
- 复杂度：协议两行 + Impl / Audit prompt 各一句。

### S5 内核把 k / N 注入 prompt（状态准确，很小）

- 实现轮与审计轮的 prompt 首行加 `本轮是实现轮第 k+1 轮，预算 N=<compute_budget>`；协议写明「分母由 Autome 提供，会话只增分子」。
- 预期：消除 F3 的两处真相。
- 复杂度：`role_prompt` 一个参数。

### S6 人工可见结果进「人工验收清单」，不做里程碑（准确度，小）

- 设计模板规定：里程碑的验收命令必须是会话能执行的；需要真实鼠标、麦克风、系统弹窗、肉眼看横幅的结果，写进设计文档固定小节「人工验收清单」，在合并卡点由用户勾选。
- 预期：不再出现 M-07 那种会话永远关不上的里程碑；用户在按合并前有一份明确的清单。
- 复杂度：协议「里程碑」一节加三行；UI 若愿意可在合并面板展示该清单，但不是必需。

### S7 采纳复盘里的三条一句话条款（准确度，很小）

1. 验收证据报「用例总数与上一轮基线之差」，不报 pass/fail/skip 三个数。
2. 审计遇到不可复现的失败不得直接结案，须给出机制性解释或时序 / 因果证据。
3. 恢复「验证缺口」条款：现有验收放得过错误实现但产品未被证明错误时，审计就地加强、立即复验，不计 reopen。

「验证缺口领域记账」和「按同成因升级」两条会加计数器，暂不采纳，等下一次运行再看。

## 4. 不建议改的

五角色、SAME-MODEL 闸门、里程碑三态、设计 15 / 实现 5×M 的预算、裁决记录 append-only、Backlog 只进不出。证据：三次运行设计轮只用了 1–5 / 15，实现轮 13–22 / 45；卡点与预算都不是瓶颈。

## 5. 预期合计

- Token：S1 + S2 让每 turn 上下文减三到四成；S3 + S4 若把 reopen 减半（voice-schedule 6 → 3），少 6 个会话（约五分之一）。同类任务合计约减四到五成，属估算。
- 准确度：S3 覆盖已观察到的全部九条缺陷类别；S4 让每一个被发现的缺陷成为永久回归用例；S6 让人工验收有明确出口。
- 评估准确性：审计机制不变，只减重复劳动（S4）与三写（S1）。

## 6. 落地情况（2026-09-16 当天执行）

S1–S7 七条全部实施，改动在 autome-v2，未提交。1.x 未动。
