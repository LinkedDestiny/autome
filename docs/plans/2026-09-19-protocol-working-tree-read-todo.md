# TODO：协议页的重复工作——量过之后，目标换了

日期：2026-09-19
状态：**已量化。原定的改法试过，实测更慢，已撤回。** 真正的瓶颈是另一个。

## 起点

原以为的问题：打开协议页会发出 `protocol.get`、`protocol.triggers`、
`protocol.eval`、`protocol.versions` 四个读，其中 `get` 和 `eval` 各自把协议仓库
的工作区完整读一遍（91 个文件），内容几乎必然相同。

## 量出来的实情

`protocol.get` 内部分解（debug 构建，10 次取中位数）：

| 部分 | 耗时 |
|---|---|
| `git tag --list` | **10.05 ms** |
| `working_files()`（那处重复） | 5.41 ms |
| `resolve`（`files_at` 缓存命中 + 哈希） | 3.40 ms |
| `verify_contract` | 0.52 ms |

**一次 git 进程约 10 ms，比读 91 个文件还贵。** 这推翻了两个先前的判断：

- 「读 91 个文件很贵」——它 5.4 ms，占整页约 11%，不是大头。
- 「改用 `git status --porcelain` 回答」——那要多一次 git 进程，只会更慢。

## 试过并撤回的改法

把 `working_tree_differs` 从 `get` 移到 `eval`（`eval` 本来就把工作区读进来了），
渲染层改读 `gate`。测试全过，**但整页 49.4 → 60.6 ms，更慢**：

- `get` 22.4 → 17.7 ms（如预期省下约 5 ms）
- `eval` 4.4 → **22.9 ms**

因为 `eval` 要拿当前标签的哈希来比，就得调 `resolve(None)`，而那里面又是一次
`tags()`。等于用一次 10 ms 的 git 调用换掉一次 5 ms 的文件读。已撤回，不要再试。

## 真正的目标

一次页面加载里 `tags()` 至少跑两次：`get` 一次，`triggers` 经 `resolve(None)`
一次。每次约 10 ms，而它们问的是同一个问题——「当前是哪个版本」。

可行的改法是把标签列表在进程内缓存，并在本模块自己创建标签的三处
（`release`、`revert_to`、`offer_upstream_of`）失效。

**代价要说清楚**：`files_at` 的缓存成立是因为「标签内容不可变」，这是构造性的；
而标签**列表**会变，只是通常只经由本应用变。用户手工在 `~/.autome/protocol` 里
`git tag` 就会看到过期列表，直到重启。这是拿一点正确性换速度，**属于产品决定，
不该由实现者单方面做**。

## 现状

协议页整页到达约 49 ms（debug）/ 约 35 ms（发行包）。本轮性能工作开始前是约
5000 ms。所以这已经不是一个在伤人的问题，下面这条只在有人愿意接受上述取舍时才做。
