# 降低 Loop 的 Token 消耗

日期：2026-11-22。状态：待执行。来源：friday（youjie）协调会话对两个项目全部会话的实测分析，交给另一会话按本文修改 Autome。

## 1. 结论

快不是单次请求贵，而是**每个会话都从头读一遍大量上下文，又被「实现 → 审计 → 退回」的循环成倍放大**。

- 两个项目（friday、MustAI）合计约 60 个会话/小时，1.5 亿～2.3 亿 token/小时。
- 累计输入 64.4 亿 token，输出 4500 万，输入:输出 ≈ 140:1；输入里 96% 是缓存读。
- Claude 部分按标价约 1760 美元；Codex 会话的 `cost_usd` 为空，金额未知（见 §4 的 P7）。

## 2. 数据（2026-11-20 ～ 11-22，共 2611 个会话）

数据来源：账本 `~/.autome/state/automed.sqlite3` 的 `session.started`、`session.ended`、`task.metrics`，以及两个项目 `.autome/output/sessions/*/*.jsonl` 里的用量。Claude 的用量取 `result` 事件，Codex 的用量是各 `turn.completed` 的合计。复算脚本见附录。

### 2.1 按角色

| 角色 | 运行时 | 会话数 | 输入（亿 token） | 占比 | 每会话输入 | 平均峰值上下文 |
|---|---|---|---|---|---|---|
| 审计 | Codex | 883 | 25.0 | 39% | 230 万～350 万 | —（平均 45 条命令） |
| 实现 | Claude Sonnet | 1028 | 18.0 | 28% | 160 万～190 万 | 8.5 万 |
| 设计 | Claude Opus | 87 | 6.8 | 11% | friday 1360 万 / MustAI 380 万 | 19.3 万（平均 53 轮） |
| 裁决 | Claude Sonnet | 174 | 6.0 | 9% | 350 万 | 15.2 万 |
| 评审 | Codex | 172 | 4.4 | 7% | 250 万 | —（平均 54 条命令） |
| 需求整理、复盘等 | Claude Opus 为主 | 约 240 | 4.2 | 6% | 110 万～490 万 | 约 10 万 |

### 2.2 循环

- 183 个里程碑，用了 836 轮实现，**平均每个里程碑 4.6 轮**。
- 其中 **529 次重开（reopen），占 63%**。审计判出缺陷 512 个，验证缺口 155 个，关闭后又被推翻 28 次。
- 审计会话与实现会话约 1:1（941 : 1028）。
- 最极端：MustAI T-15，10 个里程碑跑了 160 轮，4.9 亿 token。

### 2.3 设计文档体积

friday 的设计文档 116～207KB，裁决记录另有 40～90KB。每轮裁决都把改动追加进设计文档（例如「裁决 #8 的改动」这样的小节），不删旧内容。`impl.md`、`audit.md` 两个提示模板都写着「先读 `{slug}-task.md` 和 `{slug}.md`」，于是每个实现和审计会话开头都要把整份文档读进来。

### 2.4 复盘次数

复盘每回到「完成」一次就跑一次。同一任务最多跑了 14 次（friday T-34，主要因为反复的冲突修复轮），8 个任务跑了 5 次以上。复盘用 Opus。

### 2.5 设计不收敛

评审几乎每轮都还能找出 5～10 条六类问题，裁决又常常改完就定稿，不经复审。协调者按「评审要求复审却直接定稿就退回」处理，又多出若干轮，每轮约 600 万 token（评审约 250 万 + 裁决约 350 万）。

### 2.6 次要项

崩溃会话共 97 个有用量记录，合计约 2500 万 token，不到 0.5%，不是主因。

## 3. 原因，按影响从大到小

1. **返工循环**：每一轮实现都配一轮审计，63% 的轮次是被退回后重做。
2. **审计每次都重新摸一遍仓库**：平均 45 条命令，读 230 万～350 万 token。
3. **设计文档越来越大，每个会话都整份读**：提示模板要求先读整份。简报虽然写了「多数轮次不必整份拉进来」，但被前一句覆盖了。
4. **设计阶段用 Opus、上下文大、轮数不封顶**。
5. **复盘随每次回到「完成」重跑，而且用 Opus**。
6. **并行度**：只影响每小时的速度，不影响总量（friday 的并行数是用户配置的 5）。

## 4. 改进方案

按「省得多、改得少」排序。每项都写了改哪里、怎么验证。

### P1 实现轮提交前必须自检（预计影响最大）

- **做什么**：实现会话把里程碑标为 `待审` 之前，必须先在本轮跑完该里程碑验收契约里的命令和负向对照，把原样输出写进证据文件。
  - 证据缺失、或命令失败的，Autome 在启动审计之前就判本轮不合格，直接开下一轮实现，不开审计会话。
- **改哪里**：
  - `protocol/prompts/impl.md` 补这条硬要求；
  - `protocol/loop-protocol.md` 的实现节；
  - 内核在 `Impl → Audit` 的转移上加证据存在性与退出码的检查（`crates/autome-domain/src/task.rs` 的状态机、`crates/automed` 里读证据文件的地方）。
- **先测再改**：抽样 friday 与 MustAI 的 `*-audit.md`，把退回理由分成「证据或格式不全」「验收命令本身没过」「真缺陷」三类。前两类正是 P1 能在实现轮内挡掉的。
- **验收**：用 `task.metrics` 对比改动前后的 `reopen_total / impl_rounds_used` 和每个里程碑的轮数，目标是重开率从 63% 降到 35% 以下。

### P2 收窄审计的输入

- **做什么**：
  - 审计只看三样东西：本里程碑的 diff（上一次审计通过的 head 到当前 head）、验收契约、实现轮的证据文件；
  - 不要求整份读设计文档，只读该里程碑那一节，加上简报里摘出的相关约束；
  - 命令数设软上限，比如 20 条，超过要在审计记录里说明理由。
- **改哪里**：
  - `protocol/prompts/audit.md` 第 7 行「先读 `{doc_dir}/{slug}-task.md` 和 `{doc_dir}/{slug}.md`」改为只读简报，以及简报指向的里程碑小节；
  - 简报生成（`protocol/brief-map.toml` 与生成简报的代码）把本里程碑的设计小节和 diff 的范围直接写进简报。
- **配置**：给 `[roles.audit]` 提供推理强度参数。Codex 的 `model_reasoning_effort` 通过 `[runtimes.codex]` 或角色级参数传入，审计用 medium。
- **验收**：审计会话的平均输入从约 300 万降到 120 万以下，同时审计判出的真缺陷数不明显下降。用 P1 的分类做对照。

### P3 设计文档设体积上限，裁决改正文而不是追加

- **做什么**：
  - 裁决把修改直接落进正文对应小节，「第 n 轮改了什么」只写进 `-adjudication.md`；
  - 设计正文设上限（建议 60KB），超过时 `doclint` 或内核在设计定稿前报警，要求裁决轮先压缩；
  - `impl.md` 与 `audit.md` 不再要求整份读设计。
- **改哪里**：`protocol/loop-protocol.md` 的裁决节、`protocol/prompts/adjudicate.md`、`protocol/prompts/impl.md` 第 7 行，以及设计定稿检查。
- **验收**：新任务的设计正文不超过 60KB；实现会话的平均峰值上下文从 8.5 万降到 6 万以下。

### P4 设计轮数封顶与收敛规则

- **做什么**：
  - 第 3 轮起，评审只能针对上一轮裁决引入的改动提六类问题，不得重新扫描全文；
  - 设计轮数设软上限（建议 5 轮）。到上限后，未解决的主张自动冻结为争议项，设计进入「等待批准」，由用户或协调者裁定；
  - 裁决在「评审建议再评审」的情况下仍定稿时，必须在状态块里标 `unreviewed: <改动小节>`，让批准方一眼看到，而不是靠协调者翻会话日志。
- **改哪里**：`protocol/loop-protocol.md` 的设计循环节、`protocol/prompts/review.md`、`protocol/prompts/adjudicate.md`，以及内核的设计轮计数（现在上限 15）。
- **验收**：新任务的设计轮数中位数 ≤ 3；设计阶段的 token 下降一半。

### P5 复盘只在合并时跑一次，用 Sonnet

- **做什么**：复盘不在每次回到「完成」时跑，只在合并成功后跑一次，拿合并时的最终指标。冲突修复轮、追加轮次之后不再重复复盘。
- **改哪里**：`crates/autome-domain/src/task.rs` 里进入 `retro` 节点的转移（目前在 `session_ended` 后重新进入）；全局配置的 `[roles.retro] model` 缺省值改为 Sonnet（`crates/autome-domain/src/config.rs` 的缺省值和文档）。
- **验收**：每个任务恰好一次复盘；复盘的 token 降到现在的约 1/4。

### P6 设计与需求整理少读原始代码

- **做什么**：
  - 设计会话的峰值上下文 19 万、平均 53 轮，主要花在逐文件读源码；
  - 需求整理轮把「要读的文件清单和每个文件的要点」写进 `-task.md`，设计轮只按清单读；
  - 对「搬迁类」任务（比如 friday M7 的原版页面搬迁），允许任务卡附带预先生成的对照表，设计轮引用它，不重读原版仓库。
- **改哪里**：`protocol/prompts/intake.md`、`protocol/prompts/plan.md`。
- **配置**：设计轮仍用 Opus，但给出峰值上下文的告警线（比如 15 万），超过就写进指标，供复盘对照。
- **验收**：friday 类任务的设计会话平均输入从 1360 万降到 600 万以下。

### P7 Codex 会话也记账

- **做什么**：Codex 会话的 `session.ended.cost_usd` 现在是 `null`，`task.metrics.total_cost_usd` 只算了 Claude。
  - 账本记录 Codex 的输入、缓存、输出 token；
  - 按配置里的单价折算成金额（单价可配，缺省留空，只显示 token）；
  - 面板与 `autome status` 显示「Claude 金额 + Codex token」。
- **改哪里**：会话结束时解析 Codex 的 `turn.completed` 用量（`crates/automed` 的会话收尾逻辑），`TaskMetrics` 加字段。
- **验收**：`autome status T` 的费用一栏包含 Codex 的用量，与本文附录脚本的统计一致。

### P8 并行度与速度看板（可选）

- **做什么**：面板显示最近一小时的 token 速度和同时在跑的会话数；项目级配置可以设「每小时 token 上限」，超过就暂停发起新会话。
- **说明**：这一项不减少总量，只让速度可见、可控。

## 5. 建议顺序

1. **先测**：做 P1 的退回理由分类和 P7 的 Codex 记账。不改行为，先把数据补全。
2. **最省的三项一起做**：P2、P3、P5。主要改提示和协议，内核改动很少。
3. **P1 的内核检查**：在实现轮到审计的转移上加证据检查。
4. **P4**：会改变设计循环的规则，要和用户确认后再做。
5. **P6、P8**：作为后续。

每一步合并后，用附录的脚本在同一类任务上重新统计，和 §2 的基线对比。

## 附录：复算脚本

脚本在 `scripts/token-usage/`，只读账本和会话记录，不改任何东西：

```sh
python3 -I scripts/token-usage/agg.py friday=~/workspace/youjie/friday MustAI=~/workspace/youjie_ai/MustAI   # 按项目、运行时、角色汇总，并写出逐会话明细
python3 -I scripts/token-usage/turns.py ~/workspace/youjie/friday ~/workspace/youjie_ai/MustAI             # 平均轮数、峰值上下文、模型、会话结束方式
python3 -I scripts/token-usage/rate.py                                                                     # 每小时速度（读 agg.py 写出的明细）
```

逐会话明细默认写到 `/tmp/autome-tokens-rows.json`，可以用环境变量 `AUTOME_TOKENS_ROWS` 改位置。
