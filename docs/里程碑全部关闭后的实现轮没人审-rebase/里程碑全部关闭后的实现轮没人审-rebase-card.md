# 里程碑全部关闭后的实现轮没人审：rebase 冲突修复、合并前门禁失败修复之后，审计轮以「无待审里程碑」空转

## 背景

需求 Loop 里，实现轮除了推进里程碑，还会在三种情况下被叫回来，而此时里程碑表往往已经全部 `已完成`：

- rebase 冲突（`Inject::RebaseConflict`）；
- 合并前门禁失败（`Inject::GateFailed`，`run = "before_merge"` 下这是门禁问题暴露的**唯一**时机，会成为常态）；
- 用户在合并卡点纳入 Backlog 条目之外的手动重跑。

这些实现轮改的是产品代码和测试，但审计轮的简报与 prompt 都按里程碑表决定「审什么」：表里没有 `待审`，审计就写一句「无待审里程碑」结束。T-61 的实际记录：

- 实现 #9（rebase 集成）改了 `launcher.rs`、`scheduler.rs`、两份 prompt 金样，并改了两个测试的前提（给 e2e 加 `reuse_for_main_check = false`、旧模板兼容测试改成先选模板），还把 M-08 验收契约的「最新证据」指向自己的实现证据；审计 #9：「无待审里程碑，未改表」，一项也没复验。同一轮 rebase 丢了 `## protocol/v4` 标题（T-66），也没人发现。
- 实现 #10（修合并前门禁的 Clippy 失败）之后的审计 #10 同样没有对象。

现在兜底的只有合并前门禁的退出码。门禁拦得住编译与现有测试，拦不住「为了让旧断言继续成立而改测试前提」「冲突两侧都保留」「版本标题丢失」这类改动。来源：T-61 复盘 L-05、L-06。

## 要做什么

1. 内核识别「里程碑之外的实现轮」：实现轮开始时里程碑表没有 `开放` / `待审` 的行（即由 rebase 冲突、门禁失败或手动重跑触发），且该轮在任务文档目录之外产生了提交。记下这一轮的提交范围（轮前 HEAD..轮后 HEAD；rebase 轮用 rebase 之后的等价范围，见第 4 条）。
2. 紧随其后的审计轮改为「集成复验」：
   - 简报新增一段「本轮要审的集成改动」：触发原因（rebase 冲突的文件清单 / 门禁失败的命令与尾部）、提交范围、`git diff --stat`、改到的测试文件清单（单独列出，提醒审计关注测试前提的改动）。
   - prompt 增加对应分支：没有 `待审` 里程碑但简报有这一段时，审计必须逐项复验这些提交——改动是否只为解决触发原因、有没有削弱既有断言或改测试前提、有没有残留冲突标记（对范围内每个提交查 `^(<<<<<<<|>>>>>>>) `）、受影响里程碑的验收命令是否仍然通过——并写出审计证据文件；结论二选一：通过，或把受影响的里程碑退回 `开放`（计 reopen）。
   - 守卫：这种审计轮以「无待审里程碑」结束且没有新增审计证据时，判为未推进（沿用 `audit_made_no_progress` 一类的现有守卫，不新造失败类型更好），不让它静默放行。
3. 实现轮不得把已关闭里程碑验收契约的「最新证据」改指向自己的实现证据（现有 `impl_closed_milestone` 守卫的同一精神）：检测到就按现有守卫失败，文案说明原因。
4. rebase 冲突轮的提交范围要对得上：以 rebase 前分支与 rebase 后分支的 `git range-diff` 或「冲突文件清单 + 冲突解决提交」为准，设计轮定一个确定的、可测试的口径，不要求审计重审整条分支。
5. 协议文字（`loop-protocol.md` 的实现与审计循环、`prompts/audit.md`、需要的话 `prompts/impl.md`）同步；协议有改动就在 `protocol/CHANGELOG.md` 发新版本（独立的 `## protocol/vN` 标题），`behavioral` 条目带 eval。
6. `technical-design.md` 相关小节补一段。

## 不做什么

- 不改有 `待审` 里程碑时的审计流程。
- 不让审计轮修改产品代码或测试（T-48 / T-62 的范围守卫不变）；发现问题只能退回。
- 不处理 Bug Loop（修复轮之后本来就有独立复核）。
- 不做 T-66（版本标题）与 T-67（每轮快检）的内容。

## 验收标准

1. e2e：任务所有里程碑关闭后制造一次 rebase 冲突 → 实现轮解决冲突并提交 → 审计轮的 prompt / 简报含「本轮要审的集成改动」段与冲突文件；审计通过后流程继续到合并卡点。
2. e2e：合并前门禁失败 → 实现轮修复 → 审计轮拿到集成复验简报；审计把里程碑退回 `开放` 时，Loop 回到实现轮并计 reopen。
3. e2e 或单测：集成复验的审计轮不写证据、只写「无待审里程碑」→ 被守卫判为未推进（任务停下并给出可读原因）。
4. 单测：实现轮改已关闭里程碑的「最新证据」指向 → 守卫失败。
5. 里程碑之外的实现轮没有产生文档目录以外的提交时（例如只是 rebase 无冲突后的空轮），审计行为与今天相同。
6. 简报、prompt 金样更新；现有金样与 e2e 在不触发新路径时不改就通过。
7. `cargo fmt --check`、`clippy -D warnings`、`sh scripts/ci-local.sh` 全绿，前两条由实现轮在会话里跑并记录退出码。
