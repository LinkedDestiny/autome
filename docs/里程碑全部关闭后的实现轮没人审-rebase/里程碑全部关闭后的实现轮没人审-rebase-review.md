## 阻塞问题

### R1-P01：rebase 范围算法会把实际冲突解决改动判为空

- **类别：关键事实错误。**
- **违反要求：**任务 §2 第 4 条、§5 约束 3（rebase 后的等价范围必须对得上）；§3 验收 1（关闭里程碑后的冲突解决须进入独立集成复验）。涉及 M-01 的范围算法和 M-04 的 rebase 端到端路径。
- **设计位置：**方案 §1 条件 (c)(d)，§2 第 120–133 行，§3 第 166–168 行，风险 R1 第 412–413 行。
- **根因与检查范围：**设计把 `rev-list --cherry-pick` 右侧的非等价补丁集合，当作全部冲突解决改动；只用右侧目录外提交触发事件。核查了“补丁消失”和“补丁被判等价”两类过滤结果，均有漏审反例，不能支持 R1 的“多列不少列”。

两个反例均在 `.autome/output/` 下的独立临时 Git 仓库实跑，未改任务仓库源码：

1. **冲突解决丢掉产品补丁。** 基线产品内容为 `base`；任务分支提交 F 将其改为 `feature`，再提交任务简报；main 将产品改为 `upstream`。rebase 实际发生冲突，实现轮选择 `upstream` 后继续，F 被判为空而丢弃。设计公式的右侧为空，左侧只有旧 F；最终产品为 `upstream`。虽然设计收集 `dropped`，但没有右侧目录外提交就不写事件，原已验收的产品改动丢失后仍无人复验。
2. **补丁判等价掩盖语义变化。** `product.rs` 基线为 `let msg = "base";`，分支 F 改为 `let msg = "hello world";`，main 改为 `let msg = "ba se";`。rebase 实际发生冲突，实现轮解决成 `let msg = "helloworld";` 并产生重写提交。两条设计公式的输出都为空；patch-id 的空白归一化消除了字符串中的差别，但产品字符串已经改变。这不是单纯的文档轮，也不符合“没有目录外提交”的豁免。

复现实际执行的范围命令是设计原式：

```sh
git rev-list --reverse --cherry-pick --right-only "$H0...$H1" "^$B1"
git rev-list --reverse --cherry-pick --left-only "$H0...$H1" "^$B1"
```

原始记录：`.autome/output/feasibility-review-1/dropped-only.log`、`.autome/output/feasibility-review-1/patch-id-whitespace.log`。第二例 H0 为 `bb47ce6df05ac4e18f1ec55d0a855d45b567bbe5`，H1 为 `5325be9c40e4210d18793c46062cd366f9f5a0e9`，B1 为 `719793d6f998ba3b2957964afcfe510ac99a0914`。

**建议裁决落点：**修订 §1–§3 的触发与范围口径。冲突文件对应的实际解决改动必须保守纳入；目录外补丁被丢弃也须保留其路径和差异供审计。不能只凭 patch-id 一致断定无需复验。将上述两类反例纳入 M-01，继续保留真正无产品改动时的零变化路径。

### R1-P02：文件名存在不能证明本轮审计新增了独立证据

- **类别：违反任务目标。**
- **违反要求：**任务 §5 约束 5（通过和退回均须新增审计证据）、约束 6（表未动且无本轮新增证据必须拦截）；§3 验收 3。涉及 M-02 守卫与 M-04 未推进端到端路径。
- **设计位置：**方案 §7 第 262–272 行；B-03、风险 R2 第 408、414–416 行。
- **根因与检查范围：**检查了证据来源、轮次和文件名的判定。设计只要求 `evidence_files` 中存在任意 `M-*-r<impl_round>-audit.md`，既没有确认是简报指定文件，也没有确认由本次审计新增。R2 把风险限定为实现轮忘记递增 k，遗漏了正常递增 k 时的同类绕过。

**具体反例：**实现轮正常将 k 增为 9，修产品代码，同时提前提交 `M-08-r9-audit.md`；后续集成审计只写“无待审里程碑”，按要求追加一行 retro，但不写审计证据、不改表。按 §7，“有证据 → 通过”，未推进被放行。现有替身就具备这个前提：`crates/automed/tests/end_to_end.rs:257–264` 的 `World::EVIDENCE` 在每步同时写入同 k 的 `-impl.md` 和 `-audit.md`。`scheduler.rs:822–834` 的 `evidence_filenames` 仅枚举文件名，不能识别写入者或新增时间；`guards.rs:149–157` 的旧认法也没有这些能力。

**建议裁决落点：**修改 §7 和 R2/B-03，使集成守卫核验简报指定路径及本次独立审计产生的证据，依据审计启动时的基线区分已有文件；明确重试与文件已存在时的处理，不能用文件名的 k 替代新增性。将“实现轮预写同 k 审计文件，审计实际不写证据”作为应拒绝的对照。不能为了让旧替身通过而把任务要求降为文件存在性检查。

### R1-P03：已确认有集成改动后，读取统计失败仍会取消审计对象

- **类别：违反任务目标。**
- **违反要求：**任务 §2 第 1、2 条、§5 约束 2（满足条件的实现轮须被识别并交给审计）；§5 约束 6（不能无新增审计证据而放行）。
- **设计位置：**方案 §3 第 169–170 行，§4 第 178–181 行，§7 的 `integration: None` 分支第 259 行，风险 R6 第 424 行。
- **根因与检查范围：**检查了 Git 事实收集失败到审计选择、守卫的整条分支。设计把“统计读取失败”与“没有集成改动”都归为不写事件；告警不参与后续守卫判定，因而仍可继续到合并流程。

**具体反例：**已确认轮前和轮后全部完成，已经取得非空提交范围及目录外路径；随后仅 `git show --stat` 读取失败。依设计无条件错误分支，不写 `integration.range`，只写 warning。审计启动看不到 E，走普通审计；全完成表不动且不新增证据仍被旧免查分支放行。此时触发条件已经证实，展示统计失败不能撤销独立复验要求。该反例由设计明确规定的分支直接推导，未声称实跑尚未实现的新守卫。

**建议裁决落点：**已确认集成条件后，统计等后续信息读取失败不得取消集成身份；可保留范围并在简报明确缺失项，或沿用现有错误路径停下并允许重试。范围本身未知时也不得当作已证实的空轮。无需新增 `FailureReason`，环境故障也不应标为「协议失败」。同步修改 §3 和 R6。

### R1-P04：内联测试只改准备条件时，测试文件清单会漏列

- **类别：违反任务目标。**
- **违反要求：**任务 §2 第 2 条（单列测试文件，提醒审计测试前提改动）、§5 约束 9（覆盖含 `#[cfg(test)]` 的源文件，宁可多列）。涉及 M-01 `integration_range_test_files_by_path_and_by_content` 和 M-03 简报。
- **设计位置：**方案 §2 的测试文件规则，第 135–140 行。
- **根因与检查范围：**逐条核对了目录、文件名和内容三条判定。第三条只扫描增删行里的测试/断言关键词，未识别文件中已有的内联测试模块，因而所有“只改准备条件或 helper，保留测试标记与断言”的同类修改都可漏列。

**具体反例：**`crates/automed/src/scheduler.rs` 在第 4534 行起有 `#[cfg(test)]` 模块；其 `reuse_config` 在第 9401 行构造测试配置。若把该行的 `reuse_for_main_check = {enabled}` 改为 `reuse_for_main_check = false`，修改的正是测试前提，但路径无测试目录、文件名不匹配、增删行也不含四个关键词。按设计该文件不进入测试清单。

已读取真实源码，在内存中构造这一行差异并逐条代入设计规则，结果为 `sourceHasInlineTests: true`，三条判定均为 false，`listedByDesign: false`；未修改源码。记录在 `.autome/output/review-1-inline-test-counterexample.log`。仓库已有 `scheduler.rs:1197–1210` 的 `test_section_start` 会从全文找内联测试标记，可供实现时参考。

**建议裁决落点：**修改内容判定，至少保守列出前后版本包含内联测试标记的被改源文件；不要要求本次恰好增删了标记或断言。用只改变测试准备条件的差异验证这一规则。

## 非阻塞建议

### R1-N01：将审计选择的尝试组边界相对于最近实现会话定位

方案 §1 第 105–106 行用“最近 task.head 后第一次实现 session.started”取 H0；§4 第 179 行选择 S 时说沿用同一口径。`scheduler.rs:738–750` 会在实现收尾写新的 `task.head`，审计收尾也一样。若在审计启动时直接按当前最新 `task.head` 查询，其后没有实现会话，会得到空 S。

但 §4 也可合理解释为先定位最新实现会话，再向前定位该实现尝试组的基线，因此不据此认定关键路径必然不可达。建议明确：取最新实现开始事件 I，再取严格早于 I 的最近 task.head B，于 B 到 I 之间选择首次实现开始事件；后续审计的 task.head 不改变组身份。由裁决轮决定是否作为实现注意事项收入 Backlog，不据此要求复审。

### R1-N02：守卫失败后仅修文档的重跑可能使旧集成事件失效

实现第一次已修产品但被指针守卫拦下，收尾仍写 task.head；重跑只修文档，新实现会话 S 会使旧 E 失效，而新轮没有目录外提交，不记新 E。此前产品改动可能仍未独立审计。

任务同时要求“文档目录内的空轮保持旧行为”，未明确守卫失败尝试是否与重跑累计为同一审计单元；不能自行扩大触发范围。建议裁决轮确认这项边界是否进入 Backlog，本轮不列阻塞。
