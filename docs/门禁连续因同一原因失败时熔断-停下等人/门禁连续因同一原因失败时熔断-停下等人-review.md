## R-01：结果落账与状态推进之间重启，会重复计数，甚至绕过已经达到阈值的熔断

- **类别 / 严重性**：违反任务目标 / P1。
- **违反要求**：任务 §5 约束 6「计数的来源必须重启后仍正确」；任务 §3 验收 2「第 3 次之后没有再起实现会话」；设计 §2「用户介入后从零开始」与 §4「计数完全来自账本，重启后照常」。
- **设计位置**：第 66、74、134–142、162 行。根因是把“最近结果 `tripped: true`”当作“任务已经失败且用户已经恢复”的充分证据，并把每次结果重读当成一次新运行。
- **源码证据**：`crates/automed/src/scheduler.rs:2847` 先追加 `gate.result`，之后才经 `finish_gate`（第 2911 行）调用 `advance`；任务状态到第 1525 行才写入。`crates/automed/src/store.rs:531` 的 `append_event` 是独立的 INSERT。现有代码确实存在设计风险段提到的两次写之间的窗口。

默认阈值 3、预算充足时的反例：

1. 同一任务同一节点已经实际失败两次，最近事件为 `same_failures: 2, tripped: false`。
2. 第三个作业失败，按设计 §4 写入 `same_failures: 3, tripped: true`。
3. 进程在调用 `advance` / 写入失败状态前退出。持久任务状态仍是 `Active{Gate}`；没有任何用户 `rerun` 或 `extend`。
4. 重启后再次读取第三个作业的退出文件。§2 因上一条 `tripped: true` 把本次计数置为 1，§4 改发普通 `GateDone{Failed}`。
5. 任务退回实现并启动第 4 个实现会话，违反验收 2。这里的最坏结果并非风险段声称的“提前一轮熔断”，还包括漏掉本应发生的熔断。

同一根因还有提前熔断：在第二个作业的 `count=2` 事件落账后重启，会把同一个作业再计成第 3 次。因而仅补“重开数据库接着数”的 M-03 测试不能证明约束 6 成立。

**检查范围及同类位置**：共用 `run_gate` 的特性 `gate`、特性 / Bug `merge_gate`、Bug `fix_gate` 均受影响；不计数的 `repro_check`、`main_check` 不在此问题内。

**需要裁决的修改**：设计必须区分同一次作业结果的重放与用户明确发起的新运行，保证已落账的熔断决定在重启后继续生效，重复消费不能增次或清零。可采用原子落账 / 状态推进或可重放的结果处理方案，由裁决选择最小改动；仅按 `node + sha` 去重不足以支持设计明确要求的同一 head 人工重跑。验收应覆盖上述两个落账窗口，并保留人工重跑从零计数的行为。这是在落实已有约束 6，不是新增可靠性目标。

## R-02：`merge_gate` 沿用成功结果不写 `gate.result`，按设计读取历史会跨过这次通过继续累计

- **类别 / 严重性**：内部逻辑矛盾 / P2。
- **违反要求**：任务 §2「中间只要有一次门禁通过或指纹不同，计数清零」；任务 §5 约束 1 要求保留 `merge_gate` 同 SHA 沿用和 `gate.reused` 行为；设计 §2 又明确将清零解释为“该节点通过”。
- **设计位置**：§2 的上一条结果表与按节点清零规则；§4 第 134–140 行仅查询同节点的 `gate.result`，且只在实际作业 `Done` 后接入计数。
- **源码证据**：`crates/automed/src/scheduler.rs:2789` 起的沿用分支只写 `gate.reused`（第 2800 行），随后直接 `finish_gate(..., GateOutcome::Passed)`，不会到达第 2847 行的 `gate.result` 写入。这个通过结果属于 `MergeGate`，不能用“其它节点通过不清零”排除。

默认阈值 3 时的可达反例：

1. `merge_gate` 曾两次失败，指纹 F，最近同节点结果的计数是 2；每次均按原逻辑退回实现 / 修复。
2. 新一轮 `gate`（Bug 为相同组合命令的 `fix_gate`）通过，随后 rebase 没有改变 head，`merge_gate` 沿用该结果，写 `gate.reused` 并进入 `await_merge`。此时同节点已经通过，应清零。
3. 等待合并期间 main 前进，用户点合并；现有 `Merging + Behind → Requeued{Rebase}`，rebase 后重新进入 `merge_gate`（`task.rs:1181–1187,1205–1210`），这次 head 已变，实际运行再次以 F 失败。
4. §4 的查询忽略第 2 步的 `gate.reused`，仍读到旧的 `count=2`，于是直接熔断。正确结果应是通过之后的第一次失败、计数 1。

**检查范围及同类位置**：特性与 Bug 的 `merge_gate` 共用沿用分支，均有此问题；实际作业成功会写 `ok: true`，这条路径可以清零。另核对了配置移除时直接 `finish_gate(Passed)` 的分支（`scheduler.rs:2757`），它同样没有 `gate.result`，修改时应明确这种免运行通过是否也构成计数边界。

**需要裁决的修改**：连续失败历史必须识别同节点最近一次有效通过，至少包含现有 `gate.reused`；不得为了计数改动沿用条件、通过后的节点或原事件含义。可在读取历史时纳入现有成功事件。以 `失败 F、失败 F、沿用通过、失败 F` 为判据，最后一次必须得到计数 1 且不熔断。这是在修正清零路径，不是要求更多泛化测试。
