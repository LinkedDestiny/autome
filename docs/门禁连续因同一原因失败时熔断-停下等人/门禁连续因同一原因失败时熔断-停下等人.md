下文「验收 n」指任务文件 §3 的第 n 条验收标准，「约束 n」指 §5 的第 n 条硬性约束。

## 背景与现状

T-14 的门禁因缺依赖 `ws` 连续失败 21 次（日志为准），每次都退回实现轮，会话确认修不了就结束，门禁再跑，直到实现预算耗尽。现状代码里没有任何「同一原因」的概念：

- `task.rs` 的 `after_gate`：`(Gate, Failed)` 只查实现预算，没耗尽就 `back_to_impl` 注入 `GateFailed{head, command, tail}`；`(MergeGate, Failed)` 不查预算直接退回；`(MainCheck, _)` 一律去 Cleanup。
- `bug_loop.rs`：`fix_gate` / `merge_gate` 失败走 `start_fix`，只受 `fix_rounds` 限制；`repro_check` 用的是 `Trigger::ReproDone`，不走 `GateDone`。
- `scheduler.rs` 的 `run_gate`：作业结束后取 `gate::tail(log, 60)`（再截到 6000 字节），写一条 `gate.result`（`node/sha/ok/exit_code/command/log/tail`），再发 `Trigger::GateDone`。`Vanished` 与 head 已变两种情况直接 `job.clear()` 返回，不写事件。
- `Context { config, budget_n, decisions }` 不带历史；`store.last_event(subject, kind)` 只取同 kind 的最后一条，不分节点。
- 失败面板：`ExtendBudget` 只认 `ImplBudget` / `DesignBudget`（Bug 另认 `FixBudget`）；`RerunFrom` 不认门禁节点。桌面端失败面板固定有「追加 5 轮继续」（文案：预算上限加 5，从停下的节点继续）与「从实现重跑」两个按钮。

T-14 日志的实测形状（只读核对过 `/Users/dannie/project/autome-v2/.autome/output/gates/T-14/`）：第 1–18 次失败只在耗时、`Start at` 时间、构建哈希上不同；关键错误行（`error TS2307: Cannot find module 'ws'`、`Error: Cannot find package 'ws' imported from /Users/…`）在倒数约 100 行处，不在最后 60 行里；第 19 次汇总只剩 `FAILED  Web test`，并多出 `AssertionError` 与带随机端口的 `http://127.0.0.1:49403`；第 20、21 次只剩一条带随机端口的超时错误。

## 目标与非目标

目标：同一任务、同一门禁节点连续 N 次（`[gate] same_failure_limit`，1–10，缺省 3）因同一失败指纹失败时，任务进入失败 `门禁连续 N 次因同一原因失败：<指纹摘要>`，附最近一次日志路径；用户处理环境后可用 `rerun` 或 `extend` 继续。

非目标：自动修复环境；改变门禁通过时的任何行为；改 `main_check`；改 `ci-local.sh` 输出；新增或改动 JSON-RPC 方法；动 `apps/web/`、`protocol/`、`plugins/`、`.autome/`；改账本 schema；重构 `gate.rs` / `scheduler.rs`。

## 方案

### 1. 失败指纹（`crates/autome-domain/src/gate_failure.rs`，纯函数）

`pub fn fingerprint(log: &str, exit_code: i32, timed_out: bool) -> Fingerprint { id: String, summary: String }`。入参是日志文本，函数自己只看最后 **400 行**（调用方多给不影响结果）。

1. **预处理**：按 `\n` 切行，去 `\r`，去 ANSI 控制序列（`ESC [ … 终止字节`），两端去空白。
2. **超时**：`timed_out` 为真时不看日志内容（被杀时打印到哪里是随机的），`id` 取常量材料 `timeout` 的哈希，摘要 `门禁运行超时，被内核终止`。`timed_out` 由调度器按现有 `exit_code == gate::TIMED_OUT` 的判定传入（与 `ReproDone` 同一口径）。
3. **失败步骤**：形如 `FAILED <名字>`（行首 `FAILED` + 空白 + 名字，名字不以 `(` 开头，排除 `    FAILED (4s)`）的行，名字归一化后按出现顺序去重。这是 `ci-local.sh` 汇总行的形状，但规则本身不依赖它：别的命令没有这种行，步骤集为空，靠关键行区分。
4. **关键错误行**：除步骤行以外，满足任一条件的行——按 ASCII `[A-Za-z0-9_]` 切出的词里有 `error` / `Error` / `ERROR` / `fatal` / `FATAL` / `panicked`，或有长度 > 5 且以 `Error` / `Exception` 结尾的词（`TypeError`、`AssertionError`），或含 `Cannot find` / `cannot find` / `not found` / `No such file`。按词判断，所以 `an_error_not_a_panic` 这类测试名不算。
5. **归一化**（步骤名与关键行都做）：
   - 以 `/`、`~/`、`X:\` 开头的词（行首或前一个字符是空白、引号、`(`、`[`、`<`、`=`、`,`）→ `<path>`，一直吃到空白、引号、`` ` ``、`)`、`]`、`>`、`,` 为止，非 ASCII 字符也吃（另一任务的中文 worktree 名不泄漏）；
   - `http://`、`https://`、`ws://`、`wss://` 开头 → `<url>`，同样吃法（端口在其中）；
   - 长度 ≥ 7、全是 `[0-9a-f]` 且同时有数字和字母的词 → `<hash>`；
   - 以数字开头的数字串（数字之间可夹 `.`）→ `#`：耗时 `14.02s`、时间 `23:22:08`、行列号、端口、计数一并消掉；**标识符中间的数字保留**（`TS2307` 与 `TS7006` 不同）；
   - 连续空白压成一个空格。
6. **兜底**：步骤集与关键行都为空时，取最后 5 个非空行归一化后作关键行（例如只打印一句 `gate says no` 的脚本）。
7. **id**：材料 `exit:<退出码>\nsteps:<步骤名排序后逐行>\nlines:\n<关键行去重排序后逐行>` 的 sha256 取前 16 个十六进制字符（`sha2` 已是 domain 的依赖）。关键行排序去重，所以同一错误打印次数、并行步骤的交错顺序不影响结果。
8. **摘要**（给人看，不参与 id）：`<步骤名用「、」连接>：<最后一条以错误词开头的关键行原文>`（无步骤则只有后半；没有以错误词开头的就取最后一条关键行；再没有就取最后一个非空行），摘要最多 160 个字符；超长时取前 159 个字符再加 `…`。T-14 第 1 次的摘要是 `Web typecheck、Web test：Error: Cannot find package 'ws' imported from /Users/dannie/…`。

**已用 T-14 真实日志验证（只读）。** 设计轮用一个一次性原型（`.autome/output/fp/proto.py`，不入库）按上述规则跑了全部 25 次运行：第 1–18 次失败指纹全部相同，第 19 次不同（步骤集与关键行都变了），第 20、21 次彼此相同（端口被归一化）；摘要分别为 `Web typecheck、Web test：Error: Cannot find package 'ws' …`、`Web test：AssertionError: expected 400 to be 404 …`、`Web test：Error: 等待超时：autome-web 已启动：http://127.0.0.1:…`。若只看最后 60 行，关键行一条都没有（约束 11 所说），指纹只剩步骤集，摘要也说不出 `ws`——这就是窗口取 400 行的理由；再大则会卷入更多通过步骤的噪声。M-01 把这一验证固化为测试。

### 2. 连续计数（同一模块，纯函数）

`pub fn counts(node: Node) -> bool`：只有 `Gate`、`MergeGate`、`FixGate` 计数。

`pub fn streak(prev: Option<&PreviousResult>, fingerprint: &str, limit: u32) -> Streak { count: u32, tripped: bool }`，`prev` 是**同一任务、同一节点**最近一条「门禁结论」事件——`gate.result`，或合并前门禁沿用上次通过结果时写的 `gate.reused`（由 automed 从账本读出后解析，见 §4）：

| 上一条同节点结果 | 本次 count |
|---|---|
| 没有 | 1 |
| 通过（`ok: true`），或沿用通过（`gate.reused`，automed 把它映射成 `ok: true`） | 1 |
| 没有 `fingerprint` 字段（升级前的旧事件，或未计数的结果） | 1 |
| `tripped: true`（上次已熔断，之后是用户介入） | 1 |
| 指纹不同 | 1 |
| 指纹相同 | 上一条的 `same_failures` + 1 |

`tripped = count >= limit`。

- **「同一门禁节点」按节点各自计数**：其它节点的结果既不累加也不清零。理由：特性 Loop 里 `merge_gate` 失败后必经实现轮和 `gate`；若任何节点的结果都打断计数，`merge_gate` 永远到不了 2，按节点计数的规定就落空。「中间有一次门禁通过就清零」因此解释为**该节点**通过——包括 `merge_gate` 同 sha 沿用上次通过结果这种不跑作业、只写 `gate.reused` 的通过：判据 `失败 F、失败 F、沿用通过、失败 F`，最后一次必须得到 1 且不熔断（Bug Loop 的 `merge_gate` 同理）。配置里门禁被移除后免运行直接放行的分支（`scheduler.rs` 里 `selected_gate` 为空）不写任何事件，也**不是**计数边界：没有跑门禁，既没有新的结果也没有通过，按「不算结果的运行」处理。
- **不算结果的运行**（`Vanished`、head 已变、停止后被丢弃的运行）现有代码不写 `gate.result`，所以天然既不计数也不清零（约束 4）。
- **用户介入后从零开始**（约束 10）：熔断后任务停在失败，只有用户的 `rerun` / `extend` 能让它继续，所以「上一条已熔断」等价于「其后有用户介入」，下一次失败从 1 数起，不需要额外的标记事件。这条规则只对**新的一次运行**成立；对同一次运行结果的重复消费（崩溃重放）另有规则，见 §4「重放」——否则落账后、推进状态前崩溃，重启会把已落账的熔断读成「用户已介入」而漏掉它。其它中途介入（停止后恢复、会话崩溃后重跑）不清零：它们与门禁无关。
- **配置改动**：`limit` 每次取当时的配置，计数存在事件里，调小后下一次失败按新上限判断。

### 3. 状态机（`task.rs`、`bug_loop.rs`）

新增失败原因（`FailureReason` 只加种类，不改旧种类）：

```rust
/// The gate failed `count` times in a row on the same node for the same reason.
GateSameFailure { count: u32, summary: String, log: String },
```

JSON 形状 `{"kind":"gate_same_failure","count":3,"summary":"…","log":"/…/gate-<sha12>.log"}`，节点在 `TaskState::Failed.at`。

新增触发器（不改 `GateDone`、`GateOutcome`、`Context`：它们在现有测试里以字面量构造，加字段就得改旧测试）：

```rust
/// The gate failed at `node` for the same reason as the run(s) before it,
/// enough times in a row to stop.
GateSameFailure { node: Node, count: u32, summary: String, log: String },
```

调度器只在 `tripped` 时发它，其余失败照旧发 `GateDone{Failed}`——未达上限时转换表、注入、预算判断一字不变（约束 2）。

转换：

| 状态 × 触发 | 结果 |
|---|---|
| 特性 `Active{Gate\|MergeGate}` × `GateSameFailure{node 相同}` | `Failed{at: node, GateSameFailure{…}}`，`Action::None` |
| Bug `Active{FixGate\|MergeGate}` × `GateSameFailure{node 相同}` | 同上（在 `bug_loop::apply_for` 里显式处理） |
| 其它节点 / 节点不符 | 拒绝「门禁结果与当前节点不符」 |
| `Failed{at: n, GateSameFailure}` × `RerunFrom{node: n}`（n 为 Gate / MergeGate / FixGate） | `Active{n}` + `Action::DiscardGateRuns{n}` |
| 上一行之外 `RerunFrom` 指向门禁节点 | 照旧拒绝 |
| `Failed{…, GateSameFailure}` × `RerunFrom{implement / fix / …}` | 照旧（现有分支已接受） |
| 特性 `Failed{at: n, GateSameFailure}` × `ExtendBudget{k>0}` | `Active{n}` + `DiscardGateRuns{n}`，`with_budget(budget_n + k)`；`budget_n` 缺失时拒绝「读不到实现预算」 |
| Bug `Failed{at: n, GateSameFailure}` × `ExtendBudget{k>0}` | 同上，基数 `budget_n` 缺省取 `bug.fix_rounds` |
| `ExtendBudget{0}` | 照旧拒绝「追加轮次必须大于 0」 |

- **为什么重跑要带 `DiscardGateRuns`**：作业文件按 `<node>-<head 前 12 位>` 命名，熔断时 head 没变，不丢弃旧作业的话 `run_gate` 会直接读回那次失败的结果。`DiscardGateRuns` 正是停止后恢复门禁时用的动作，调度器已实现。
- **`extend` 的语义**：与桌面端按钮的现有文案一致——「预算上限加 k，从停下的节点继续」。环境修好后先在同一 head 上重跑门禁，通过就按原路走；追加的轮次让之后若有失败仍能退回实现，而不是立刻撞上预算。
- **熔断与预算耗尽同时成立时以熔断为准**：熔断分支不读 `status`、不查预算。理由：①熔断原因指出了真正的问题（环境），`ImplBudget` 会诱导用户直接追加轮次，再白跑一遍；②熔断后的 `extend` 本身就加预算，用户不会因此卡住；③两者只有在第 N 次相同失败恰好落在最后一轮时才同时成立。未达上限时预算耗尽照旧报 `ImplBudget`。

各门禁节点的作用范围（约束 3）：

| 节点 | 计数 | 熔断 | 理由 |
|---|---|---|---|
| `gate` | 是 | 是 | T-14 的浪费就在这里 |
| `merge_gate`（特性与 Bug） | 是 | 是 | 失败同样退回实现 / 修复轮，浪费方式相同；按节点计数才数得到 |
| `fix_gate` | 是 | 是 | 失败退回修复轮，与 `gate` 同构 |
| `repro_check` | 否 | 否 | 期望复现命令失败，失败是正常结果；它走 `ReproDone`，不经过本机制 |
| `main_check` | 否 | 否 | 失败不退回任何轮次，只写项目报警，没有可省的轮次 |

### 4. 内核接线（`automed`）

**配置**（约束 8）。`[gate] same_failure_limit` 放在 `ProjectConfig.gate_same_failure_limit: Option<u32>`（`serde(default, skip_serializing_if = "Option::is_none")`）与 `ResolvedConfig.gate_same_failure_limit: u32`（`resolve` 里缺省 `DEFAULT_GATE_SAME_FAILURE_LIMIT = 3`），**不放进 `GateConfig`**：`GateConfig` 在 `task.rs`、`bug_loop.rs` 的现有测试里以字面量构造，加字段就得改旧测试（验收 5）；`ProjectConfig` 的测试构造都用 `..Default::default()`，`ResolvedConfig` 只在 `resolve` 里构造。Bug Loop 现场拼的 `GateConfig` 因此不需要带这个值——调度器对三个计数节点统一读 `resolved.gate_same_failure_limit`，约束 8 要的「Bug Loop 也用同一上限」照样成立。

`config_io.rs` 解析 `[gate]` 表时，只要出现 `same_failure_limit` 就校验：`as_integer()` 且在 `1..=10`，否则报 `[gate] same_failure_limit 必须是 1 到 10 的整数`（0、11、负数、小数、字符串都落在这里；文案沿用 `[retry] attempts` 的写法）。`save_project` 不重写 `[gate]` 表（现有测试已说明它只改自己管的表），新键自然保留，M-03 用测试固定下来。

**读日志**。`gate.rs` 新增 `pub fn log_window(log: &Path) -> String`：读文件末尾最多 256 KiB，丢掉第一行残片，返回最后 400 行；读不到返回空串。现有 `tail(log, 60)` 不动，注入内容不变。

**读上一条**。`store.rs` 新增两个只读查询（SQLite `json_extract`，现有 `session_event`、`resume_input` 已这样查；不改 schema，`SCHEMA_VERSION` 仍是 5）：
- `last_event_in(subject_id, kinds, field, value) -> Option<(seq, kind, payload)>`：按 `seq` 倒序取该任务 `kinds` 里任一 kind 中 `payload.$.<field> = value` 的最近一条。`run_gate` 用它取同节点最近的 `gate.result` 或 `gate.reused`（`kinds = ["gate.result","gate.reused"]`，`field = "node"`）。`gate.reused` 映射为「通过」。
- `any_event_after(subject_id, kinds, seq) -> bool`：该任务在 `seq` 之后是否有 `kinds` 里任一 kind 的事件。

**`run_gate`**（只在 `Done` 且 head 未变之后、写 `gate.result` 之前插入）：

1. `!ok && gate_failure::counts(node)` 时：读上一条同节点门禁结论 `prev`，先判**重放**（见下）。不是重放才算：`fingerprint(log_window(&job.log), exit_code, exit_code == TIMED_OUT)`，`streak(prev, id, resolved.gate_same_failure_limit)`。
2. 不是重放时，照旧写 `gate.result`，已有字段名与含义不变（约束 6），仅在这类结果上**追加**四个字段：`fingerprint`、`fingerprint_summary`、`same_failures`、`tripped`。通过的结果、`repro_check`、`main_check` 的结果不带这些字段。
3. `tripped`（新算出的，或重放时沿用的）时发 `Trigger::GateSameFailure{node, count, summary, log: job.log}`；否则照旧 `finish_gate`。

**重放**（约束 6 的落实）。`run_gate` 写完 `gate.result` 与 `advance` 写入任务状态是两次独立的写；其间重启，作业文件还在，下一个 tick 会再读到同一份结果。判据：`prev` 是一条带 `fingerprint` 的失败 `gate.result`，且该任务在 `prev.seq` 之后**没有**任何 `gate.started` 或 `session.started` 事件。成立时这是同一次运行结果的重复消费：**不写新事件**，直接沿用 `prev` 的 `same_failures` / `tripped` / `fingerprint_summary` 当作本次决定。这两类事件就是「新的一次尝试」的边界：用户 `rerun` 门禁节点会丢弃作业并重新启动（写 `gate.started`），实现 / 修复轮的会话启动写 `session.started`——所以同一 head 上的人工重跑、以及会话没有产出新提交时读回旧作业结果的情形，都不是重放，照 §2 的表计数。两个落账窗口的结果：
- 第 N 次失败写了 `tripped: true`、状态仍是 `Active{Gate}` 时重启：重放，再次发 `GateSameFailure`，熔断不丢（不会因「上一条已熔断」被读成 1）。
- 第 2 次失败写了 `same_failures: 2`、状态未推进时重启：重放，仍是 2、不熔断、不多写事件，下一次失败是 3（不会提前一次熔断）。
作业启动与 `gate.started` 落账之间的极窄窗口（两次写之间崩溃）无法靠账本识别，最坏是那一次运行的结果沿用上一次的决定；不为它加作业侧标记。

计数完全来自账本，重启后照常（约束 6）；旧账本里没有指纹字段的事件按上表视为「从 1 数起」，升级不会让正在跑的任务立刻熔断（约束 7）。`trigger_name` 等对 `Trigger` / `FailureReason` 的穷举匹配同步加分支。

### 5. 读者与文档

- `autome-cli/src/render.rs` 的 `failure()`：`gate_same_failure` → `门禁连续 {count} 次因同一原因失败：{summary}（日志：{log}）`；`next_step()` 对它给 `autome rerun {id} {at}    或    autome extend {id} 1`。
- `apps/desktop/renderer/lib/labels.js` 的 `failureReason()`：`门禁连续 ${count} 次因同一原因失败：${summary} · 日志 ${log}`。失败面板的按钮不用改：「追加 5 轮继续」走上面的 `extend`，「从实现重跑」走现有分支。
- `README.md` 的 `[gate]` 示例加 `same_failure_limit = 3   # the default, 1–10: …`，并在 The gate 一段补一句；`docs/development/technical-design.md` §8.1「宿主门禁」补一句熔断规则。
- 不新增 JSON-RPC 方法、不改参数（约束 12）：`task.rerun_from` 的 `node` 本来就能解析出 `gate` / `merge_gate` / `fix_gate`。

### 6. 否决的做法

- **在 `Context` 或 `GateDone` 上加历史字段，由 `after_gate` 判断**：两者在现有测试里有十几处字面量构造，违反验收 5。
- **只在内存里计数**：重启即丢，违反约束 6。
- **改 schema 加一张计数表**：事件上加字段已经够用，约束 7 倾向不改 schema。
- **任何节点的结果都打断计数**：`merge_gate` 永远数不到 2，见 §2。

## 风险与验证安排

- **指纹过粗，不同原因被判成相同而误熔断。** 代价是停下等人，用户一次 `rerun` / `extend` 即可继续，远小于白跑轮次；上限可调到 10。M-01 的「不同错误不相等」「步骤集不同不相等」「标识符数字保留」三类用例看守。
- **指纹过细，同一原因判成不同而不熔断。** 退化为现状，不会更坏。T-14 全量日志已验证；M-01 的忽略测试可在本机对全部 21 次失败复核。
- **写事件与推进状态之间崩溃。** `append_event` 与 `advance` 是两次写，崩溃后重新 tick 会再读到同一作业的结果。已由 §4「重放」处理：不重复计数，也不会把已落账的熔断读成「用户已介入」而漏掉；M-03 用两个落账窗口的用例固定下来。
- **`ResolvedConfig` 序列化多一个键。** 若有测试对整份配置 JSON 做全等比较，会在 M-02 / M-03 暴露；按「旧断言不变、只加新键」处理，若真要改旧测试，在证据文件里逐条列理由。
- **并行任务冲突**（约束 14）。`task.rs` / `bug_loop.rs` 只加新分支，`scheduler.rs` 只在 `run_gate` 写事件处插入一段；主体逻辑放新模块 `gate_failure.rs`。
- **本任务自己的门禁被环境卡住**（约束 13）。如实记录，不改 `ci-local.sh`、不跳步骤。

验收 5「现有门禁相关测试不改」的核对方式见 M-05：`end_to_end.rs` 与 `apps/desktop/test/` 相对基线零删除行；其余文件里删除的行逐条确认都在非测试代码里。本设计不计划修改任何已有测试。
