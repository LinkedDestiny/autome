## 六类范围内的问题

### D1-P01 · 违反任务目标：把角色覆盖误判为技能列表覆盖，向用户错误说明全局绑定不生效

- **追溯**：F-2、验-7；设计 F-Q2（L511–517）、E-Q2（L436–439）；M-09 的「有覆盖项目的提示名单」。
- **问题与根因**：F-Q2 用角色级 `provenance = project` 直接认定该项目有自己的技能列表。但 E-Q2 明确允许只改模型或 Effort；这类覆盖不影响技能继承。角色级来源不能回答某一个字段是否覆盖。
- **证据与反例**：`crates/autome-domain/src/config.rs:519` 起用整个角色的 `over.is_empty()` 决定 provenance，而 `:528` 的技能仍单独走 `over.skills.unwrap_or_else(|| base.skills.clone())`。本轮真实内核探针先仅覆盖项目 A 的设计模型，再给全局设计角色绑定 alpha：A 的 provenance 始终为 project，A 的技能列表却正确新增 alpha。按设计会对 A 展示「这条全局绑定不生效」，与读回值相反。
- **影响与修改落点**：错误说明直接影响用户选择绑定范围。修改 F-Q2 与 M-09 的名单逻辑：不能用角色 provenance 断言技能覆盖。现有回包也不能区分「技能列表碰巧相同」与「正在继承」；需要精确信息时按任务允许的条件增加最小只读字段，或明确显示无法判定，不能断言不生效。检查全局绑定预览、保存后的提示及恢复说明中的全部同类判断。判别场景应同时有「仅模型覆盖」与「显式技能列表覆盖」。

### D1-P02 · 违反任务目标：同名技能的混合来源会错误禁用合法全局绑定

- **追溯**：F-1…F-3、验-7；设计 F-Q3（L521–524）；M-09 的「项目技能禁用全局」。
- **问题与根因**：设计把 `project_scoped` 当成「仅存在于项目」使用。该字段实际表示任一来源在项目内，并不排除同名全局来源。
- **证据与反例**：`crates/autome-domain/src/skill.rs:62` 使用 `sources.any(scope == Project)`；`crates/automed/src/dispatch.rs:3271` 起按名字合并来源。本轮在全局与项目都创建 alpha，项目查询返回 `project_scoped=true`，同时 sources 含 global、project；不带 project_id 为全局角色绑定 alpha，真实内核成功。按设计，抽屉会禁用这条合法的全局绑定。
- **影响与修改落点**：修改 F-Q3、M-09 的来源与可见性规则。全局绑定应以全局清单/全局 sources 判断是否存在及哪些工具可见；项目绑定以对应项目清单判断。检查纯全局、纯项目、同名混合三类，尤其不能把项目独有的 runtime 可见性并入全局判断。这里只绑定全局同名技能，不要求把项目文件迁移为全局。

### D1-P03 · 内部逻辑矛盾：「今天」的候选任务过滤会丢掉今天已经发生的花费、门禁和等待

- **追溯**：B-4；设计 B-Q1 的候选任务（L241–242）与花费、门禁、等待定义（L244–248）；M-03 的今天汇总。
- **问题与根因**：设计只读取「completed_at 在今天」或「未终结」任务的事件，却又定义统计今天发生的事件。终结状态和完成时间不是事件发生日期的充分索引。
- **证据与反例**：`crates/autome-domain/src/task.rs:377` 将 cancelled 视为终结；`crates/automed/src/store.rs:1539` 的状态写入不写 completed_at，`:1555` 单独维护该字段；`scheduler.rs:2875` 只有转为 Done 才调用 complete_task。任务今天先运行、花费 $2、等待用户 30 分钟，随后取消，completed_at 仍为空，整条任务被候选集排除。页面会在取消后把已发生的花费、门禁、等待一并抹掉。旧终结任务今天运行手动复盘也是同类：`scheduler.rs:458` 起明确支持终结任务的独立复盘会话。
- **影响与修改落点**：修改 B-Q1 的事件收集范围和 M-03 汇总场景，使今天已发生的活动不因当前终结状态被排除；合并数仍只统计今天 Done。可以由服务端增量消费现有事件并关联任务，不能靠改写 completed_at 或放开浏览器 `events.since` 解决。至少覆盖「今天有活动后取消」「旧终结任务今天有新会话」。

### D1-P04 · 内部逻辑矛盾：总览与详情宣称采用相同门禁口径，却对相同事件计出不同总数

- **追溯**：B-4、D-2、验-4；设计 B-Q1（L246）与 D-2（L375–376）；M-05 的真实门禁断言（L760–761）。
- **问题与根因**：B-Q1 数所有 gate.result，并声明「与 TaskMetrics 同口径」；D-2 只数 gate/fix_gate/merge_gate。M-05 又把真实断言写为「等于事件中 gate.result 个数」，未采用 D-2 的节点范围。
- **证据与反例**：`crates/automed/src/task_metrics.rs:120–141` 仅把 gate/fix_gate 计为每轮门禁、merge_gate 计为合并前门禁，忽略 repro_check 等其它节点。相同的一天有 gate 通过、repro_check 非零结果、merge_gate 通过时，总览按当前定义是 2/3，详情与 TaskMetrics 是 2/2。Bug 的预期非零复现检查还会被总览当成一次未通过的门禁。
- **影响与修改落点**：统一 B-Q1、D-2、M-03 与 M-05 的节点过滤及通过口径；若有意展示不同范围，必须明确修改「同口径」声明和界面名称，不能让同名总数互相矛盾。检查 repro_check、main_check、gate、fix_gate、merge_gate，以及 reused/skipped；不是只补一个测试数量。

### D1-P05 · 违反任务目标：等待区间漏掉「确认不是 Bug」，相应用户操作也未纳入新时间线

- **追溯**：B-2、B-4、D-2、D-3、验-4；设计等待区间（L247–248）、等待卡片（L262–263）、用户行（L393–394）；M-03、M-05。
- **问题与根因**：等待区间仅识别 await_* 或 failed，设计却同时把 not_a_bug 列为「等你处理」。新用户行只列 approve/reject/merge 与 task.decided，也漏掉等待补充信息后常用的 reply。
- **证据与反例**：`crates/autome-domain/src/task.rs:132–135` 的 awaits_user 明确包含 NotABug；`apps/web/app/components/task-columns.ts:2` 同样包含 not_a_bug。Bug 在 10:00 进入 not_a_bug，10:30 用户补充信息，真实等待 30 分钟，按设计的区间条件为 0。现有 `task-timeline-model.ts` 的 operations 已有 reply，且 `:57` 会展示对应 task.updated；新枚举不能把这个用户操作丢掉。
- **影响与修改落点**：统一 B 与 D 共用的等待状态/结束事件规则，纳入 not_a_bug 及其合法退出，保留已有用户操作的展示并为结束等待的操作关联时长。逐项核对 await_design_approval、await_merge、await_info、not_a_bug、failed；暂停/停止是否计时另行明确，不能用 await_ 前缀代替状态枚举。该问题是漏算现有业务状态，并非要求增加新状态。

### D1-P06 · 内部逻辑矛盾：仅按事件序号缓存汇总，会冻结仍在增长的等待时长

- **追溯**：B-4；设计 B-Q1 的「还在等的区间算到现在」（L248）与「序号不变就不重算」（L249）；M-03 的持续等待与缓存用例（L713、L716）。
- **问题与根因**：缓存的是最终结果，但最终结果既依赖事件序号，也依赖 now 和服务端的当天边界。客户端 ClockProvider 刷新相对时间，不会自动重新计算服务端已汇总的数字。
- **反例**：10:00 进入等待，10:10 首次汇总为 10 分钟；10:40 没有新事件，即使重新调用 loader，也会按相同序号取回 10 分钟，而非 40 分钟。跨午夜时，事件序号同样不必变化，「今天」的切片却已经改变。
- **影响与修改落点**：修改 B-Q1 的缓存对象和刷新路径。事件/已闭合区间可以按序号缓存，开放区间与日期切片要按当前时钟更新；明确页面如何在无新账本事件时更新数字。检查 M-03 两条相冲突的要求，保留「不重复读历史事件」，取消「不更新时间相关结果」。D 的未结束总用时如复用此缓存，也须采用同一处理。
