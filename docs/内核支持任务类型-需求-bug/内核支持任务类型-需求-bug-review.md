## 阻塞问题

### R1-01：从正文提取的标题仍进入占位符渲染，合法 brief 会被改写或拒绝启动

- **类别：违反任务目标（第 4 类）。优先级：P1。**
- **违反要求：C7** 明确要求正文不做模板替换，正文出现 `{request}` 等文本不得触发 `check_no_placeholders_left` 拒绝启动；同时影响 A2、A4、A6 的 brief-only 创建与启动路径。
- **设计位置：**方案 §5 第 173–174 行以「正文不进 prompt」推出占位符安全；但 §7 Q1 第 207–211 行又要求从正文一级标题（或第一条非空行）提取 request，且 §5 保留现有模板渲染与全结果占位符检查。这两条路径相接后，正文的一部分实际进入了模板。
- **源码依据：**`crates/automed/src/launcher.rs:616–622` 先替换 `{request}`，再替换 `{inputs}`、`{slug}`、`{design_rounds}`，最后调用 `check_no_placeholders_left`；该检查在同文件第 534–555 行拒绝形如 `{lower_snake}` 的剩余文本。
- **具体反例：**调用 `task.create`，只传 `brief = "# 修复 {request} 展示\n\n应原样保留。\n"`，不传 request。按 Q1 得到 `request = "修复 {request} 展示"`。它被填进模板后仍含 `{request}`，首个任务整理会话在 prompt 构建时被拒绝。加 `draft: true` 只是把失败延后到 `task.start`。
- **同类范围：**同时检查了一级标题提取与无一级标题时的首行回退路径；二者最终使用同一 renderer。标题含 `{request}`、`{doc_dir}`、`{unknown}` 会触发检查；含 `{inputs}` 会被删掉，含 `{slug}` 或 `{design_rounds}` 会被替换成内核值。显式给普通 request、只在正文其余位置放占位符的已有拟定用例不能覆盖这条派生路径。
- **验证证据：**按现有 renderer 的替换顺序和检查条件做了 6 个确定性文本反例，全部出现上述拒绝或改写。输出：`.autome/output/review-1-placeholder-repro.log`。这是源码等价的文本实验，**不是尚未实现的 K1 集成测试**。
- **建议裁决落点：**修改方案 §5 / §7 Q1，明确从 brief 派生的 request 也作为字面数据处理，不能再次参与占位符替换或剩余占位符判定；保留 C1 要求的旧路径输出兼容。将上述 brief-only 标题反例纳入对应 M-02/M-03 验证。需要修的是已规定的数据流，不是单独增加测试数量。

### R1-02：同秒开始旧草稿会插队，排序公式不满足设计的队尾承诺

- **类别：内部逻辑矛盾（第 2 类）。优先级：P2。**
- **违反设计条款：**方案 §7 Q3 第 215–218 行明确承诺「排在此前已经排队的任务之后」；M-03 的 `task_card_a_started_draft_waits_behind_the_parallel_limit` 要求先排队任务先启动、草稿 `queue_position = 2`。C5 要求设计决定并落实开始后的排队规则。
- **冲突位置：**方案 §2 第 115–117 行规定按 `COALESCE(queued_at, created_at)` 升序、同值按 `created_at` 排序。旧草稿的创建时间通常更早，同值时恰好会被放到先排队任务前面。
- **源码依据：**`crates/automed/src/store.rs:1898–1906` 明确将 `now_iso()` 定义为全库统一的 RFC 3339 **秒级**时间格式；`crates/automed/src/dispatch.rs:1390` 起的任务初始化使用它记录 `created_at`。因此，同一秒内先创建排队任务、再开始草稿是正常可达路径，不需要并发或系统故障。
- **具体反例：**并行槽位已满。草稿 D 于 `01:00:00Z` 创建；任务 Q 于 `02:00:00.100` 实际入队，持久化 `created_at = 02:00:00Z`；随后于 `02:00:00.900` 开始 D，按现有时间工具记 `queued_at = 02:00:00Z`。两者第一排序键相同，第二键令 D 在 Q 前，D 的队列位置为 1，而不是设计承诺的 2。
- **同类范围：**检查了普通排队任务与已开始草稿混排、两张草稿同秒开始两种情况；同秒按与创建顺序相反的顺序开始两张草稿，也会被第二排序键恢复为创建顺序。未发现需要改变既有非草稿任务排序的理由，修正须继续满足 C1。
- **验证证据：**在 SQLite `:memory:` 中按设计的原始排序表达式执行两行反例，实际顺序为 `old-draft, already-queued`，与 Q3 相反。输出：`.autome/output/review-1-queue-repro.log`。未打开任何真实账本。
- **建议裁决落点：**修改方案 §2 / §7 Q3，定义在现有秒级时间戳碰撞时仍保留入队先后的规则，并保留旧任务之间的顺序；M-01/M-03 使用确定的相同时间戳检验该规则。不能仅通过给测试加等待来回避正常运行中可出现的同秒入队。

## 非阻塞建议

### N1-01：补写时区分「文件存在」与「已提交」

- **位置：**方案 §4 第 153–155 行、风险 R2；关联 A2 的「第一个会话之前提交」。
- **观察：**现有 `git::commit_paths` 在写文件之后才 `git add`（`crates/automed/src/git.rs:459–465`）；若写卡成功、add 失败，重试时文件存在但不在提交里。`freeze_protocol` 只把协议路径加入暂存区（`crates/automed/src/scheduler.rs:1822–1831`），不会自动补交未跟踪的卡片。
- **实验：**在 `.autome/output/` 内的独立临时 Git 仓库中，用该仓库自己的 `index.lock` 让 add 失败，再解除锁、按「存在就跳过 inputs」的解释重试，协议提交成功后卡片仍为 `??`，且不在 HEAD 中。输出：`.autome/output/review-1-card-commit-repro.log`。没有操作任务 worktree 的 Git 锁或创建额外 worktree。
- **为何不阻塞：**设计只限定了卡片的**写入**条件，没有明确要求文件存在时跳过**提交**；实现完全可以不重写已有文件、仍把卡片路径交给 `commit_paths`。目前不能据此认定设计必然违反 A2，也不将可在实现期验证的故障路径升级为第 6 类重大风险。
- **供裁决考虑：**实现 §4 时保留已有文件的补提交路径；明确成功提交之后无需再次「补写」。是否补充说明或进入 Backlog，由裁决轮决定。
