## 六类问题

### D4-P01：设计将任务规定的 Node 下限从 22 提高到 22.18.0

- **类别：违反任务目标。**
- **违反的任务要求：** R-02 明确启动时检查 Node ≥22；任务 §4 硬性约束第 5 条再次明确“下限 22”。R-01 要求两条启动路径都能运行。上游计划 §5 架构与 §6 W1 同样写 Node ≥22。
- **设计位置：** §2 第 80 行 `engines.node >=22.18.0`；§3 第 86–88 行直接执行 TypeScript；§4 第 106–115 行最低版本、理由与拒绝提示；风险安排第 182–183 行允许实现轮继续上调下限；M-02 第 217–218 行将拒绝 22.9.0、22.17.1 列为正确结果及负向对照。
- **具体反例：** 用户使用 Node 22.17.1，满足任务规定的 Node ≥22，但按设计执行 `npm run dev` 或 `npm start`，入口必须打印中文提示并退出 1。M-02 又会把这种拒绝行为计为通过，因此按设计实现并通过验收，仍会缩窄任务要求的兼容范围。
- **根因与检查范围：** 设计先选定原生类型剥离与依赖版本，再用这些选择的运行条件重新解释任务下限。检查了全部依赖、engines、启动入口、版本检查、风险处理与 M-02 契约；上列位置属于同一根因，应一并处理。
- **事实核对：** Node 22.18.0 默认开启类型剥离这一技术前提正确，见 [Node 官方 22.18.0 发布说明](https://nodejs.org/en/blog/release/v22.18.0)。但它只能说明当前执行方案有额外版本要求，不能授权设计变更任务硬性下限；中文错误提示也不能补偿兼容范围的缩小。
- **修正方向：** 保留任务 Node ≥22 下限，调整服务端执行方式及依赖选择，并统一修订 engines、版本检查、提示、风险安排和 M-02 预期。若要提高任务下限，须先有明确的任务约束变更，不能仅凭设计对 R-02“用意”的解释。
- **判据：** 不再把 22.x 中满足原任务下限的版本预设为拒绝对象；启动方案、声明与验收共同遵守任务下限。这不是要求增加测试数量，也不是环境未取证问题。

## 非阻塞建议

以下仅供裁决轮决定是否进入 Backlog，不作为额外轮次的依据。

- **N4-01｜M-01 的静态资源负向对照。** 设计 §3 第 94–95 行同时安排 assets 专用与 client 通用静态处理中间件；第 212 行却预期只删除 client 中间件就使 `/assets/*.js` 返回 404。若 assets 中间件按通常方式挂在 `/assets`，该请求仍会返回 200。建议对照时删除实际服务该资源的全部处理器，或选仅由通用中间件提供的资源。这是验收鉴别力调整，四个契约三行均齐全，不据此判“里程碑不可执行”；本轮未运行 mutation。
- **N4-02｜生产 build 参数的实现写法。** 设计 §3 第 95 行的 `build: import(...)` 若逐字实现，会把 Promise 直接作为 build；应先 `await import(...)` 或提供返回构建模块的函数。见 [React Router 官方 Quick Start](https://reactrouter.com/tutorials/quickstart)。本处同段还使用了静态中间件参数简写，按设计伪代码看待；这是实现时可局部纠正、可由既定生产首页与类型检查发现的细节，不构成整体方案不可行的依据。
