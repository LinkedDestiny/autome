### 内核 `session.log` 的真实回包（探针实测）

探针用 `CoreSupervisor` 起真实 `target/debug/automed`，用临时 `HOME`/`AUTOME_HOME` 和假 CLI（`AUTOMED_CLAUDE_BINARY`）
跑一个 Bug 草稿任务的会话。假 CLI 先输出一行，等触发文件出现后再输出第二行，等第二个触发文件出现后退出。
探针脚本放在 `.autome/output/w8-probe/probe.ts`，这个目录被 git 忽略，只作临时验证。实测结果：

- 回包键是 `log`、`path`、`session`、`truncated`。`session` 的键是 `effort, ended_at, id, kind, label, lifecycle, log_path, metrics, model,
  protocol_ref, round, running, runtime, skills, started_at`，**没有 `task_id`**。
- `path` 等于 `session.log_path`，是**绝对、规范化**的路径，以 `.log` 结尾。例如
  `/private/var/folders/…/repo/.autome/output/sessions/T-1/ses-<32 位十六进制>.log`。原因是项目路径登记时经过了 `canonicalize`
  （`dispatch.rs` 约 631 行），`launcher.rs` `launch` 用的是 `repo.join(SessionPaths::log(..))`，其中 `repo` 是项目主检出目录，不是任务 worktree。
- 会话 id 的形如 `ses-` 加 32 位十六进制。
- 运行中时 `running: true`、`lifecycle: {"state":"running"}`。假 CLI 退出、`scheduler.tick` 收割之后变成
  `running: false`、`lifecycle: {"state":"exited","exit_code":0}`，同时 `ended_at` 有值。
- 假 CLI 写下一行以后，约 **191 ms** 就能在 `.log` 里读到这一行。延迟来自假 CLI 自己 0.1 秒的轮询，加上 `render-stream` 逐行 flush。
- 会话结束后，日志最后一行是包装脚本写的 `=== autome session <id> finished, exit 0 ===`。包装脚本先写这一行和退出标记，
  内核才会把会话收割成非 running（`.autome/skill/run_session.sh` 末尾；`scheduler.rs` `reap_session` 读的是退出标记）。
  所以**看到 `running: false` 时，日志已经写完**。
- 找不到会话时，`CoreSupervisor.call` 抛出 `code: 'not_found'`、`message: '找不到会话 <id>'`。传 `../x` 也走这条路：内核只按 id 查表，不拿它当路径。

源码事实：

- `session_log`（`dispatch.rs` 2260 行）每次调用都用 `read_to_string` 把整个文件读进来，回包里的 `log` 只取末尾至多 256KB（先对齐字符边界，再对齐行边界）。
  文件不是合法 UTF-8 时，`log` 返回空串。这个方法在 `READ_METHODS` 里，不占驱动锁。
- `.log` 由包装脚本生成：先 `: > "$log"` 截成空文件，写一行 `=== autome session … started … ===`，再把 CLI 的输出经
  `automed render-stream` 逐行渲染后 `tee -a` 追加。`render_stream` 读不懂的行原样透传（`stream_render.rs` 56 行），
  所以假 CLI 输出的纯文本会原样进 `.log`。
- 命令行 `autome logs -f`（`autome-cli/src/main.rs` 989 行）的读法：每 500ms 整读一次文件，输出 `shown` 之后的字节；
  如果会话已经不是 `is_running()`，并且文件长度不超过 `shown`，就结束。
- 本机真实会话日志的大小：`/Users/dannie/project/autome-v2/.autome/output/sessions` 下大于 1KB 的 `.log` 共 642 个，
  中位数 6,082 字节，P90 12,298 字节，最大 34,832 字节。

## 方案

### 总体数据流

```
浏览器 SessionLog（展开）
  └─ session-log-controller ──sendLiveMessage──▶ live-client（同一条 /ws）
                                                  │ {type:"log.subscribe", session_id, offset}
服务端 eventbus.receive ─onClientMessage──▶ logtail
  logtail ─ call('session.log',{session_id}) ─▶ CoreSupervisor ─▶ automed   （只从这里拿 path 与 running）
  logtail ─ 每 500ms：open(path) → fstat → read(pos..) → close ─▶ logtail-chunk 切块
  logtail ─ connection.send(log.chunk / log.end / log.rejected) ─▶ 浏览器
浏览器 live-client ─publishLiveMessage──▶ controller ─▶ session-log-model（追加、限量、滚动决定）─▶ 视图
```

### 协议（R-04；写进 `server/eventbus-protocol.ts`）

浏览器 → 服务端：

```jsonc
{ "type": "log.subscribe", "session_id": "ses-…", "offset": 0 }   // offset 可省略
{ "type": "log.unsubscribe", "session_id": "ses-…" }
```

服务端 → 浏览器：

```jsonc
{ "type": "log.chunk", "session_id": "ses-…", "offset": 8192, "next": 9000, "text": "…" }
{ "type": "log.end", "session_id": "ses-…", "offset": 9000, "reason": "ended", "message": "会话已结束" }
{ "type": "log.rejected", "session_id": "ses-…", "code": "limit", "message": "每个连接最多同时订阅 4 个日志，请先收起其它日志" }
```

字段语义：

- `offset`、`next`、`log.end.offset` 都按**文件字节**计。`log.chunk.offset` 是 `text` 第一个字节在文件里的位置，
  `next` 是这段之后的下一个字节位置，也就是续传时要带的值。同一订阅内，相邻两条 chunk 满足 `next(i) = offset(i+1)`。
  `log.end.offset` 是结束时已经推到的位置。
- 为什么多一个 `next`：文件里有非法 UTF-8 字节时，`text` 里替换成 U+FFFD（3 字节），`text` 的字节长度就不等于它对应的文件字节数，
  客户端算不出下一个偏移。任务卡列出的 `type/session_id/offset/text` 四个字段都在，语义不变，`next` 是附加字段。
- `log.end.reason` 的取值集合是 `ended | rotated | deleted | error`，`message` 是给人看的中文说明：
  - `ended`：会话已结束，最后一段已推完。文案「会话已结束」。
  - `rotated`：文件被替换（inode 变了）、被截短（长度小于已推位置），或者订阅时带的 offset 超过文件长度。文案「日志文件被替换或截短，已停止跟随」。
  - `deleted`：文件不存在或已被删除。文案「日志文件不存在或已被删除」。
  - `error`：其它读文件错误。文案「读取日志失败：<错误码>」。
- `log.rejected.code` 的取值集合是 `invalid | limit | not_found | offline | kernel`。被拒绝的订阅不占名额，也不会打开任何文件：
  - `invalid`：消息不合法。`message` 写明原因：「log.subscribe 只接受 session_id 与 offset；日志路径只能来自内核」（出现了任何额外字段）、
    「session_id 不合法」、「offset 必须是非负整数」。`session_id` 本身不合法时，回包里的 `session_id` 是 `null`。
  - `limit`：「每个连接最多同时订阅 4 个日志，请先收起其它日志」。
  - `not_found`：原样转发内核的「找不到会话 <id>」。
  - `offline`：「内核离线，暂时拿不到日志：<原因>」，原因来自 `CoreSupervisor` 的「内核未连接：…」。
  - `kernel`：内核回包里的路径不合法时，文案是「内核返回的日志路径不合法」；其它内核错误的文案是「查询日志失败：<内核错误>」。

校验函数（M-01，供 logtail 与前端测试共用）：

- `parseLogSubscribe(message)` / `parseLogUnsubscribe(message)` 返回 `{ ok: true, value }` 或 `{ ok: false, code: 'invalid', message, session_id }`。
  - 键集合必须是 `{type, session_id}` 或 `{type, session_id, offset}` 的子集。出现任何别的键（`path`、`log_path`、`file`、`dir`、随便一个 `foo` 都算），
    一律拒绝。这样做的依据是硬性约束 1「客户端消息里出现路径（任何字段名）即拒绝」：只放行白名单键，比猜哪个字段名像路径更可靠。
  - `session_id` 必须匹配 `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$`。这个规则比 `read-gate.ts` 的「不像路径」更严：
    `/`、`\`、`.`、`~`、NUL、空白一律不允许，真实 id `ses-<hex>` 能通过。`read-gate.ts` 不在本任务可改范围内，所以这里另写一份，不导出复用。
  - `offset` 可以省略；如果给了，必须是非负安全整数。
- `parseClientMessage` 不变。`log.*` 照旧原样放行给 logtail，由 logtail 回 `log.rejected`，这样拒绝是看得见的。
  如果在 `parseClientMessage` 里直接丢掉，浏览器收不到任何回音。
- `isKernelLogPath(path)`：必须是字符串、绝对路径，`path.normalize(p) === p`，不含 NUL，以 `.log` 结尾。这是对内核回包的纵深校验，
  不通过就回 `kernel` 拒绝。
- 类型 `LogClientMessage`、`LogServerMessage`（`log.chunk | log.end | log.rejected`）并入 `ServerMessage` 旁边导出，`encodeMessage` 照用。

与计划 §5.2 的差异：

| 计划 §5.2 | 本任务（以任务卡为准） |
|---|---|
| `{ type: "log", session_id, offset, chunk }` | `{ type: "log.chunk", session_id, offset, next, text }` |
| `subscribe-log` / `unsubscribe-log` | `log.subscribe` / `log.unsubscribe` |
| 无结束消息 | `log.end { offset, reason, message }` |
| 无拒绝消息 | `log.rejected { session_id, code, message }` |

只实现右边这一组。`subscribe-log` 不做别名，`parseClientMessage` 对它的已有行为不变。

### 切块（R-02；`server/logtail-chunk.ts`，纯函数）

`splitChunks({ sessionId, start, bytes, final })` 返回 `{ messages: LogChunk[], consumed }`。

- **64KB 的单位**：整条下行消息 `encodeMessage(message)` 的 UTF-8 字节数 ≤ **65536**。限制的是编码后的整条消息，不是原文。
  JSON 转义会让内容变长：日志里常见 ANSI 转义 `\u001b`，一个字节要编码成 6 个字节；`"`、`\`、换行要编码成 2 个字节。
  按原文字节切，会超限。
- 切法：逐个扫描 UTF-8 标量或最大非法前缀，累计 JSON 转义后的文本字节数，加上当前 offset/next 对应的空 text 信封字节数；加入下一单元会超限时先输出当前块。
  不会切在多字节字符中间，偏移按原始字节推进。
- 末尾残缺：如果读到的末尾是一个合法多字节序列的前缀（≤ 3 字节），`final: false` 时先不发这几个字节，`consumed` 停在这个字符的起点，等下一次读；
  `final: true` 时（会话已结束、文件读完）用 U+FFFD 发出去，推进到末尾。
- 中间的非法字节解码成 U+FFFD，偏移仍然按原始字节推进（这就是 `next` 字段存在的原因）。
- 内核截尾时还会对齐行边界，logtail 不需要：它推的是首尾相接的连续字节流。按行对齐只发生在前端 DOM 裁剪的时候。

### 服务端 logtail（R-01、R-02；`server/logtail.ts`）

```ts
createLogtail({ bus, call, log, intervalMs = 500, statusEveryMs = 1000, readBudget = 256 * 1024,
                maxSubscriptions = 4, now = Date.now, open = fs.promises.open })
  → { flush(): Promise<void>; stats(): { connections, subscriptions, openHandles, timer }; close(): Promise<void> }
```

- **挂接**：`bus.onClientMessage('log.subscribe', …)`、`bus.onClientMessage('log.unsubscribe', …)`、`bus.onDisconnect(…)`。
  订阅表是 `Map<Connection, Map<session_id, Subscription>>`。
- **订阅流程**：
  1. 用 `parseLogSubscribe` 校验，不过就回 `invalid`。此时**不调内核、不碰文件**。
  2. 同一连接、同一 `session_id` 已经有订阅时，**替换**旧订阅：旧订阅作废，不改变计数。否则，如果这个连接的订阅数（包括还在等内核回包的）已经 ≥ 4，回 `limit`。
  3. 调 `call('session.log', { session_id })`。错误映射：`code === 'not_found'` 回 `not_found`；消息以「内核未连接」开头回 `offline`；其它回 `kernel`。
     回包里的 `path` 不过 `isKernelLogPath` 也回 `kernel`。路径只取自回包，客户端给的任何字符串都不进 `fs` 调用。
  4. 起点：给了 `offset` 就用它；没给就用当前文件长度（「从文件末尾」，文件还不存在时取 0）。起点超过文件长度时，推 `log.end { reason: 'rotated' }`。
  5. 记下 `path`、`running`、`pos`；inode/dev 基线在第一次成功打开文件时记下。
- **跟随**：只有一个共享的 `setInterval(intervalMs)`。有活跃订阅时才创建，订阅清空后立即清除。每一轮对每个订阅做下面的事，同一个订阅同时最多一轮在跑：
  1. **先查生命周期**：距上次检查已经 ≥ `statusEveryMs` 时，调 `session.log`，拿回 `running`。回包 `path` 与订阅时不同，就按 `rotated` 结束。
     内核离线或调用失败时，记一行服务端日志，继续跟随文件，下次再查。
     一旦看到 `running: false`，订阅上的 `ended` 标记置位并保持，之后的轮次不再查询状态。
  2. **再读文件**：`open(path, 'r')` → `fstat` → 比对 inode/dev 基线（不同就是 `rotated`）→ 长度小于 `pos` 也是 `rotated` → 从 `pos` 读至多 `readBudget` 字节
     → 在 `finally` 里 `close`。读取终点 `readEnd = pos + 实际读到的字节数`；`atEof = readEnd >= 本次 fstat 的长度`（读满预算但没到文件尾时为 `false`）。`ENOENT` 时：已有基线记 `deleted`；还没有基线且会话仍在运行，说明文件还没创建，就等下一轮；
     还没有基线且会话已结束，记 `deleted`。其它错误记 `error`。
  3. 切块后逐条 `connection.send`。发送前核对订阅仍然有效（同一个对象、没有被替换或退订），已经作废的结果直接丢弃。
  4. **最后一段与结束**：`final = ended && atEof`，**由读取终点决定，不由消费终点决定**。切块前就算出 `final`，传给 `splitChunks`；发出去以后 `pos += consumed`。
     `final` 为 `true` 时，`splitChunks` 会把末尾残缺的多字节序列用 U+FFFD 发出，`consumed` 等于读到的全部字节，随后推
     `log.end { reason: 'ended', offset: pos }`，删除订阅。`final` 为 `false` 而 `ended` 为 `true`（读满预算没到文件尾）时，下一轮立即接着读。
     不能用「`pos` 到了 `fstat` 的长度」当条件：文件尾是残缺字符时 `consumed` 会停在字符起点，`pos` 永远追不上长度，既不发 U+FFFD 也不结束
     （评审 #1 的反例：长度 2、内容 `E4 B8`，`running: false`，`offset: 0`）。
     顺序是「先查生命周期，再读到文件尾」：探针已经证实，看到 `running: false` 时，包装脚本的最后一行已经落盘，所以 `ended` 置位之后的任何一次读到文件尾，
     都包含了全部内容，最后一段不会丢。这和 `autome logs -f` 先读再比长度的判法等价。
  5. 读满 `readBudget` 时，本订阅下一轮立即接着读（不等 500ms），单条仍然 ≤ 64KB，单轮内存有上界。
- **历史会话**走同一条路径：订阅时内核回 `running: false`，第一轮就从 `offset` 读到文件尾（超过预算就连续几轮），然后 `log.end ended`。订阅马上释放，不长期占名额。
- **释放**：`log.unsubscribe`、连接断开（`onDisconnect`）、`log.end`、`close()` 都会把订阅删掉；订阅清空后定时器跟着清除。
  文件句柄只在单次读的 `try/finally` 里存在，轮与轮之间不持有任何句柄。`stats().openHandles` 在 `open` 成功时加 1，在 `close` 后减 1。
  `close()` 停掉定时器，作废全部订阅，等进行中的读取全部结束后才 resolve；之后再来订阅一律忽略。
- **为什么轮询不用 `fs.watch`**：命令行 `logs -f` 本来就是 500ms 轮询，已经证明可用。`fs.watch` 在 macOS 上每个被监视的文件要长期占一个句柄，
  这和「不再持有文件句柄」的验收正好相反。前几次 Web 任务在实现轮环境里还撞上过 watcher EMFILE（任务文件 §5「前车之鉴」）。
  延迟估算：假 CLI 写入到落盘约 191ms（实测），加上至多 500ms 的轮询，再加 WebSocket 传输，远小于 3 秒的 tick。
- **生命周期为什么用 `session.log` 而不用账本事件**：内核收割会话时只更新 `sessions` 表（`store.rs` `finish_session`），没有专门的「会话结束」事件；
  引导会话（Onboarding）收割后连任务事件都没有。`session.log` 是唯一能逐会话拿到 `running` 的只读方法。代价是内核每次都要整读文件，
  并回传至多 256KB 的末尾。按真实日志大小（最大约 35KB），每个订阅每秒一次，可以接受；轻量方法记进 Backlog B-02。
- 服务端日志用中文前缀 `[日志]`，例如 `[日志] 查询会话状态失败：…`。

### 前端发送通道（R-03、R-04；`app/lib/live-client.ts`、`app/lib/live.tsx`）

### 前端日志组件（R-03；`app/components/session-log*`）

三个文件，逻辑都放在不依赖 DOM 的模块里：

- `session-log-model.ts`（纯函数）：把**内容保留**和**DOM 渲染**分开。已收到的日志文本全部保留在内存里（`parts`，每个 `log.chunk` 的 `text` 一项，
  单项 ≤ 64KB），DOM 里只渲染其中一个**窗口**，窗口的 UTF-8 字节数 ≤ N。保留的内存是流式日志文本，不是业务数据，符合硬性约束 8。
  状态是 `{ sessionId, phase: 'idle'|'subscribing'|'live'|'ended'|'rejected', parts, total, from, to, next, follow, unseen, notice }`：
  `parts` 是 `{ text, bytes }[]`（`bytes` 是该项 `text` 的 UTF-8 字节数），`total` 是全部保留的字节数，`[from, to)` 是窗口覆盖的 `parts` 下标范围。
  派生函数 `viewOf(state)` 返回 `{ text, hiddenBefore, hiddenAfter }`：`text` 是窗口内各项首尾相接，`hiddenBefore` / `hiddenAfter` 是窗口前、后未渲染的字节数。
  动作是 `open | chunk | end | rejected | hello | scrolled(atBottom) | pause | jump | earlier | later | top | retry | close`，返回 `{ state, send?, scroll? }`，
  `scroll` 取 `'bottom'`（滚到底）或 `'top'`（滚到顶）。
  - `chunk` 只接受 `offset === next` 的段，追加到 `parts` 后 `next = msg.next`。`offset < next` 是重复或过期的段，丢弃。`offset > next` 是缺口，
    丢弃并返回从 `next` 重新订阅的 `send`。
  - **DOM 限量 N = 256 KiB（262,144 个 UTF-8 字节）**：窗口取整项，字节数之和 ≤ N，至少含一项。跟随（`follow: true`）时窗口是「字节数 ≤ N 的最长后缀」，
    每次追加后重算，`to` 恒等于 `parts.length`；顶部显示「前面还有约 X KB 未显示」。取 256 KiB 的理由：和内核 `session.log` 截尾的量级一致；
    本机 642 个真实日志最大 34,832 字节，全部落在一个窗口里；256 KiB 的纯文本放进一个 `<pre>`，DOM 开销可以接受。
  - **窗口翻页**（让超过 N 的历史日志也能看到全部内容，A-04）：`earlier` 把窗口移到紧挨 `from` 之前的一段（新的 `to` 等于旧的 `from`，`from` 向前取到字节数 ≤ N 的最长前缀），
    进入暂停，返回 `scroll: 'bottom'`（让用户停在这一页的末尾，接着往上读）。`later` 把窗口移到紧挨 `to` 之后的一段（`from` 等于旧的 `to`，`to` 向后取到字节数 ≤ N），
    `to` 到达 `parts.length` 时恢复跟随，返回 `scroll: 'top'`。`top` 把窗口移到最前面（`from = 0`，`to` 向后取到字节数 ≤ N），暂停，返回 `scroll: 'top'`。
    `jump` 把窗口移回最后面，恢复跟随，清掉 `unseen`，返回 `scroll: 'bottom'`。`hiddenBefore` > 0 时界面提供「查看更早内容」「跳到开头」，
    `hiddenAfter` > 0 时提供「查看后面内容」。从 `top` 起反复 `later`，各窗口首尾相接，拼起来逐字节等于全部保留的文本。
  - 窗口不在末尾（`to < parts.length`）时 `follow` 一定是 `false`：新到的段只追加进 `parts`，窗口不动，`unseen` 置 `true`，不返回 `scroll`。
  - 跟随时追加返回 `scroll: 'bottom'`；暂停时不返回滚动，置 `unseen: true`；暂停时窗口仍停在原来的位置（`from`、`to` 不变），所以屏幕上的内容不会因为新段而变化。
  - `scrolled(false)` 进入暂停，`scrolled(true)` 在窗口位于末尾时恢复跟随并清掉 `unseen`（窗口不在末尾时不恢复）。`pause` 进入暂停。
  - `end` 进入 `ended`，状态文字取 `message`；`rejected` 进入 `rejected`，原样显示服务端给的中文原因，并提供「重新加载日志」（`retry`，从 `next` 重新订阅，已保留的 `parts` 不清）。
  - `hello`：处于 `subscribing` 或 `live` 时，返回 `log.subscribe { offset: next }`。这就是 R-04 的「重连带 offset」。处于 `ended` 时不重新订阅。
- `session-log-controller.ts`：`createSessionLogController({ sessionId, send = sendLiveMessage, subscribe = subscribeLiveMessages, onChange })`。
  `open()` 发 `log.subscribe { offset: 0 }`。发送失败（还没连上）就停在 `subscribing`，等下一个 `hello` 再发。
  控制器只处理本 `session_id` 的 `log.*` 和全局的 `hello`。`close()` 时，如果订阅还活着就发 `log.unsubscribe`，然后解除监听。
  发出去的消息只会有 `type/session_id/offset` 三个键。
- `session-log.tsx`：`<SessionLog session={{ id, label, round, running, started_at }} />`。用 `<details>` 展开或收起：展开时 `open()`，收起或卸载时 `close()`。
  摘要行显示「第 N 轮 · <label> · 正在运行/已结束」，`running` 来自 loader。展开后有工具条，放「暂停滚动」和「跳到最新」两个按钮，
  有新内容未看时「跳到最新」带提示；还有窗口前后的提示与翻页按钮、空态「还没有日志输出」、状态行，以及 `<pre className="session-log-text">`。
  - 导出两个滚动适配器：`applyScroll(element, scroll)` 只在 `scroll === 'bottom'` 时设置 `element.scrollTop = element.scrollHeight`；
    `isAtBottom(element)` 的容差是 4px。组件在 `onScroll` 里用 `isAtBottom` 产生 `scrolled` 动作。
  - 滚动适配器按 `scroll` 取值：`'bottom'` 设 `scrollTop = scrollHeight`，`'top'` 设 `scrollTop = 0`；没有 `scroll` 时什么也不做。
  - **不抢焦点**：组件只改日志容器自己的 `scrollTop`，不调用 `focus()`、`scrollIntoView()`，不设 `autoFocus`，日志区不设 `aria-live`。
    暂停时追加内容只进 `parts`、不改窗口，也不动 `scrollTop` 和页面滚动。
  - 窗口翻页按钮（「查看更早内容」「跳到开头」「查看后面内容」）只在 `hiddenBefore` / `hiddenAfter` > 0 时出现，点击后产生对应动作。
- 「历史会话一次加载」与「完整内容」：历史会话展开时同样 `offset: 0` 订阅，服务端一次从头读到尾，再发 `log.end`；所有段都保留在 `parts` 里。
  DOM 里同一时刻只渲染一个 ≤ N 的窗口；日志不超过 N 时窗口就是全部，逐字节完整。超过 N 时默认显示最后一个窗口，用户可以用「查看更早内容」「跳到开头」
  一页页读到最前面，再用「查看后面内容」「跳到最新」回来，不存在读不到的内容。三句话因此同时成立：历史一次加载（一条订阅读到尾）；
  DOM 只留最近 N（窗口 ≤ N，默认是末尾一页）；完整内容（保留全部、可翻页读取，没有日志大小豁免）。
  保留全部文本的内存与日志大小成正比，本机真实日志最大约 35KB；极端大日志的内存上限记进 Backlog B-01。

### 逐条回答任务文件 §2 末尾的待定问题

1. **单位与多字节**：`offset`/`next` 按文件字节计；64KB 指整条编码后消息 ≤ 65536 字节。切块不会切在字符中间；读到末尾的残缺字符先留着，
   等下一次读，会话结束时才用 U+FFFD 补出；中间的非法字节替换成 U+FFFD，偏移照原始字节推进，并用 `next` 告诉客户端。见「切块」。
2. **起点**：`log.subscribe` 带可选的 `offset`，省略时从当前文件末尾开始（文件还不存在时从 0 开始）。前端第一次展开带 `0`，重连带最后一条 chunk 的 `next`。
   `offset` 超过文件长度，按「被截短」处理，推 `log.end { reason: 'rotated' }`。
3. **历史会话**：同一条订阅从 0 读到尾，然后 `log.end ended`，不用内核回包里的 `log` 字段（那只是末尾 256KB）。N = 256 KiB 是 DOM 窗口的上限；全部文本保留在内存里，
   超过 N 的部分用窗口翻页读取。三句话怎么同时成立见「前端日志组件」末条。
4. **结束判定**：用内核 `session.log` 的 `session.running`，每个订阅每秒查一次，订阅时也查一次。每轮先查生命周期，再读到文件尾，最后一段因此不丢（探针证实了写入先于收割）。
5. **`reason` 与拒绝**：`log.end.reason ∈ {ended, rotated, deleted, error}`；拒绝用 `log.rejected { code ∈ {invalid, limit, not_found, offline, kernel}, message }`。见「协议」。
6. **tick 与轮询**：一个 tick 按 `ticker.ts` 的 3000ms 算。跟随用 500ms 轮询，不用文件监听；生命周期 1000ms 查一次。A-03 断言「触发写入 → 收到 chunk」≤ 3000ms，并把实测耗时写进证据。
7. **句柄断言**：logtail 自己记 `openHandles`，每次读完都在 `finally` 里关闭；集成测试在会话结束后断言 `running.logtail.stats()` 全为 0，
   再用 `lsof -nP -p <测试进程 pid> -Fn` 断言输出里没有这个日志路径。为了证明这条断言真能看到被打开的文件，测试先自己 `openSync` 这个日志，
   确认 `lsof` 列得出来，关掉以后再做断言。CI 的 web job 跑在 `macos-14` 上，本机 `/usr/sbin/lsof` 也有。
8. **组件怎么发消息**：`createLiveClient` 返回 `send`，经 `setLiveSender`/`sendLiveMessage` 暴露给组件；重连后的重新订阅挂在 `hello` 的分发上。见「前端发送通道」。
9. **任务页占位**：`/tasks/:id` → `routes/tasks.$id.tsx`，内容见「任务页占位」。

- 新测试 `test/logtail.test.ts`，17 条：
  1. 不带 `offset` 订阅时，从当前文件末尾开始，之后追加的内容作为 `log.chunk` 推送；带 `offset: 0` 时，推送全部内容。
  2. A-01：带 `path: '/etc/passwd'` 的订阅回 `log.rejected invalid`，假 `call` 一次也没被调用，`open` 一次也没被调用；`session_id: '../x'` 同样如此。

  4. A-02：同一连接第 5 个订阅回 `log.rejected limit`，文案含「最多同时订阅 4 个日志」；另一个连接不受影响；退订一个以后，第 5 个可以订上；同一会话重复订阅是替换，不增加计数；还在等内核回包的订阅也计入名额。

  6. 最后一段：假内核在回 `running: false` 的那次 `session.log` 调用里，先往文件追加「尾行」再返回。断言收到的最后一条 chunk 含「尾行」，紧接着是 `log.end { reason: 'ended', offset: 文件长度 }`；之后 `stats()` 的 `subscriptions`、`openHandles` 都是 0，`timer` 是 `false`。
  7. 历史会话：内核回 `running: false`，`offset: 0` 订阅，收到全部内容和 `log.end ended`；之后同一连接仍能再订 4 个。
  8. 轮转：文件被 rename 替换成新文件（inode 不同），推 `rotated`；文件被截短，推 `rotated`；订阅时 `offset` 大于文件长度，推 `rotated`。每种情形结束后 `stats().openHandles` 都是 0。
  9. 删除：跟随中文件被删，推 `deleted`；历史会话的文件不存在，推 `deleted`；运行中的会话文件还没创建时不结束，文件出现后照常推送。每种情形结束后 `stats().openHandles` 都是 0。
  10. 拒绝映射：内核抛 `not_found`，回 `not_found`，文案含「找不到会话」；抛「内核未连接：…」，回 `offline`，文案以「内核离线」开头；其它错误回 `kernel`。
  11. 断开：传输断开以后，该连接的订阅全部释放；断开前已经发出的 `session.log` 调用晚到时，不打开文件，也不发送任何消息。
  12. 退订：`log.unsubscribe` 之后不再推送，计数减 1；退订一个不存在的订阅没有副作用；非法退订回 `invalid`。
  13. `close()`：有读取在进行时，`close` 等它结束；之后 `stats()` 全为 0，新订阅被忽略（不发送、不调内核）。
  14. 状态查询失败（假 `call` 抛「内核未连接」）时继续跟随文件，不结束；恢复以后看到 `running: false`，照常结束。
  15. 续传：第一个连接收到一部分后断开，第二个连接带最后的 `next` 订阅；两个连接拿到的内容拼起来等于文件全文，不重复，也不遗漏。
  16. 读取预算：一次追加 1 MiB，在多轮 `flush` 里送达，每轮读的字节数 ≤ 256 KiB，没有一条消息超过 65536 字节。
  17. 残缺 UTF-8 尾部（评审 #1 D1-P02）：(a) 内核回 `running: false`，文件内容恰好是「中」的前两个字节 `E4 B8`，`offset: 0` 订阅：一轮 `flush` 内收到
      `text` 为 `\uFFFD`、`offset: 0`、`next: 2` 的 chunk，紧接着 `log.end { reason: 'ended', offset: 2 }`，`stats()` 全为 0；(b) 文件是 `ab` 加 `E4 B8`（共 4 字节），同样 `running: false`、`offset: 0`：
      收到 `text` 为 `ab\uFFFD`、`offset: 0`、`next: 4` 的 chunk（替换字符 3 字节，偏移照原始字节推进）后 `log.end { offset: 4 }`；(c) 会话仍在运行、文件同为 `ab` 加 `E4 B8`：
      先只发出 `ab`（`next: 2`），残缺的 2 字节不发，订阅不结束；追加第 3 个字节 `AD` 之后发出「中」（`offset: 2`、`next: 5`），订阅仍不结束。

## Backlog

- B-01 前端保留全部已收到的日志文本（超过 256 KiB 的部分靠窗口翻页读取），内存与日志大小成正比，没有上限。本机真实日志最大 34,832 字节，没有问题；极端大日志（几十 MiB 以上）需要「按 offset 向前按需取」的服务端能力（订阅带长度上限），那要扩协议，留给后续任务。
- B-02 内核缺一个只返回会话生命周期的轻量只读方法。现在为了判断会话是否结束，logtail 每个订阅每秒调一次 `session.log`，内核每次都要整读日志文件，并回传至多 256KB 的末尾。改法在 `crates/automed`，本任务不能改。
- B-03 `gateway-task-lifecycle.test.ts`、`gateway-http.test.ts`、`gateway-task-card.test.ts` 在 production 模式下进程内启动服务，没有 `apps/web/build/` 时会失败。设计轮实测：worktree 刚 `npm ci`、还没 build 时，`gateway-task-lifecycle` 的 2 个用例报 `Cannot find module …/build/server/index.js`。全量里能过，只是因为别的文件先做了 build。可以照 `notifier-live.test.ts` 那样在 `beforeAll` 里显式 build。不属于 W8 的范围。
- B-04 下行没有按 `ws.bufferedAmount` 做背压，靠每个订阅每轮 256 KiB 的读取预算限制内存。浏览器消费得很慢时，消息会在服务端的发送缓冲里堆积。
