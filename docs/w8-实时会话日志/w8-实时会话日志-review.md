## 问题

### D1-P01 历史日志完整性被缩减为「不超过 256 KiB 时完整」

- **类别：违反任务目标。**
- **违反要求：**任务 R-03、A-04；任务文件 §2 待定问题 3 明确要求同时解决「历史一次加载」「DOM 限量」「完整内容」。A-04 没有日志大小豁免。
- **设计位置：**「前端日志组件」第 254–257、270–273 行；M-04 模型测试第 6 条（第 461 行）；Backlog B-01（第 511 行）。
- **根因：**把 DOM 渲染上限同时当成日志内容永久丢弃上限，再用本机历史样本最大 34,832 字节替代任务的输入范围。当前样本较小不能给 A-04 增加上限。
- **具体反例：**已结束会话的日志为 `HEADER\n` 加 262,144 字节按行组成的正文。展开时服务端从 0 推完，模型最终从头裁掉 `HEADER\n`，只剩最后 N 字节。用户没有读取早期内容的入口；再次展开从 0 加载仍执行同样裁剪。提示「前面还有约 X KB 未显示」不能让被丢弃内容可查看。该例完全满足任务输入条件，却不满足 A-04；100 KiB 的既定测试避开了这个分支。
- **检查范围与同类位置：**同时核对了目标映射、前端模型、历史加载说明、M-04 验收情形、人工 H-03 和 B-01；对完整性的缩限集中在上述模型、说明、测试及 B-01，属于同一根因。
- **建议裁决落点：**保留有限 DOM，设计在本轮范围内可查看全部历史内容的机制，例如对已加载内容作窗口化呈现；明确内容保留与 DOM 渲染的区别。不把满足 A-04 所必需的能力放进 Backlog，也不靠扩大 N 回避。同步替换 M-04 的完整性情形，使超过 N 的历史日志仍能查看首尾。具体实现由裁决轮决定。

### D1-P02 残缺 UTF-8 尾部使结束条件与消费条件互相等待

- **类别：内部逻辑矛盾。**
- **违反要求：**R-01「会话结束后推最后一段并 log.end，自动停止跟随」及硬性约束 4 的资源释放；设计自身「切块」末尾残缺规则（第 183–184 行）和 M-01 切块测试第 5 条（第 383 行）。
- **设计位置：**「服务端 logtail」跟随第 2–4 步，尤其第 212–214 行：先切块发送，再以已推进的 `pos` 到达 `fstat` 长度为条件调用 `final: true`。
- **根因：**把「已消费到文件尾」作为刷新未消费尾字节的前置条件。设计的 `pos` 用于下一次读取并表示已推位置；切块返回的 `consumed` 在残缺字符前停住。
- **具体反例：**文件长度 2，内容为「中」的前两个字节 `E4 B8`，内核已返回 `running: false`，订阅 `offset: 0`。按当前顺序先以非 final 切块，`consumed = 0`，`pos = 0`。因此 `pos === fstat.size`（0 === 2）不成立，永远进入不了 `final: true`；下一轮重新读取相同两个字节，状态不变。结果是既不发送替换字符，也不发送 `log.end`，订阅和定时器不能自动释放。有效前缀后带残缺尾部时同理。这是设计明确支持的输入，并非额外健壮性要求。
- **检查范围与同类位置：**核对协议 offset/next、切块 consumed、跟随结束顺序和历史会话路径；运行中会话结束与直接展开历史会话共享此条件，均受影响。
- **建议裁决落点：**在切块前，以「已确认非 running，且本次实际读取覆盖到本次 fstat 的 EOF」确定 final；再按 consumed 推进已发送位置并判断发送 log.end。区分读取终点与消费终点，避免用后者决定是否刷新尾部。将同一反例纳入 M-02 的结束情形，使从切块到释放的完整路径可核验。
- **证据性质：**上述为按设计条款逐步推导的确定性反例；当前尚未实现 logtail，未声称已经运行产品实现并复现。
