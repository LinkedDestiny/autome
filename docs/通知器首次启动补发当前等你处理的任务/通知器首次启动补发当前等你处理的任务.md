## 背景与现状

W4（T-16）的通知器有两条有意的设计，本任务要改掉它们：

- **首次启动不补发。** `apps/web/server/notifier.ts:22-27`：库里没有 `notifier` 游标时只调一次
  `events.since {after_seq: MAX_SAFE_INTEGER}`，把 `latest_seq` 写成游标后返回，一条通知也不生成。装好面板的第一天，
  已经停在 `await_merge` 等节点上的任务不会出现在铃铛里。
- **「进入」的记忆只在进程内。** `notifier.ts:15` 的 `states: Map<任务 id, 最近一条 task.updated 的 state>`。重启后这个
  Map 是空的，每个任务的第一条 `task.updated` 都算「进入」，所以重启后同一状态、序号更大的一条事件会再通知一次。

本轮核实过、设计依赖的事实（均为只读核对，内核一行不改）：

1. `dashboard.get`（`crates/automed/src/dispatch.rs:2190`）一次返回所有项目里 `awaits_user()` 的未终结任务，放在 `waiting` 里。
   每项是 `{project_id, project_name, task, pending_decisions, session, retry}`，其中 `task` 是 `task_json`。
   `task_json` 的 `"state": t.state`（`dispatch.rs:566`）和事件 `json!({"state": transition.next, …})`（`scheduler.rs:1749`）
   用的是同一个 `TaskState` 序列化，所以快照里的 `task.state` 与事件里的 `payload.state` 深相等。
2. `events.since` 的 `latest_seq` 是 `SELECT COALESCE(MAX(seq),0) FROM events`（`crates/automed/src/store.rs:666`），
   事件按 SQL 现读，内核没有缓存。
3. 内核写状态和记事件是两条语句，不在一个事务里（`scheduler.rs` 里 `set_task_state` 之后才 `append_event`）。另外，
   `autome run` 和面板托管的 `automed` 可以是两个进程，同时写同一个账本（w4 夹具就是这样跑的）。所以 `dashboard.get` 可能
   先看到新状态，后看到对应事件。
4. **真实内核产生不出「状态不变的 `task.updated`」。** 证据有三条：
   - 暂停、停止在等你处理的节点上被拒绝：`autome-domain/src/task.rs:909-931` 返回「任务正在等待你，没有会话可暂停」。
   - 驳回只在 `await_design_approval` 上有效，并且会转到 `design`（`task.rs:1225`）。
   - `dispatch.rs:1880/1974/2024` 那几条 `payload {}` 的 `task.updated` 只作为推送消息返回，没有写进账本。

   W4 设计 §3 也记过「实测账本没有连续相同状态」。所以验收 2 用等价手段完成，见「验证安排」。
5. 驳回（`autome reject <slug> <意见>` → `task.reject`）只能从 `await_design_approval` 发起。验收 3 因此要用另一个任务，
   不能用验收 1 里那个停在 `await_merge` 上的任务。
6. 账本文件是 `<AUTOME_HOME>/state/automed.sqlite3`（`config_io.rs:77`），事件表是
   `events(seq INTEGER PRIMARY KEY AUTOINCREMENT, event_id, kind, subject_id, payload, at)`，开了 WAL 和 `busy_timeout`。
7. 面板的 `/api/notifications` 把 `store.list()` 的 `SELECT *` 去掉 `event_seq` 后原样返回（`notifier-api.ts:29`）。
   如果给 `notifications` 加一列又不处理，新列会被带进接口。

## 目标与非目标

目标（对应任务卡「要做什么」与验收 1–4）：

- G1 首次启动（库里没有 `notifier` 游标）时，对**那一刻**处于「等你处理」的每个任务各补发一条通知，不补历史事件。
- G2 「最近一次观测到的任务状态」写进 `web.sqlite3`，重启后仍按它判断是不是「进入」：同状态、新序号不重复通知；
  离开后再进入一定重新通知，停服期间离开也一样。
- G3 已有 `web.sqlite3` 升级到第 2 版后，不重发历史，也不重发升级前已经通知过的等待。
- G4 账本更换时清掉持久化状态，并对新账本补发。
- G5 既有测试按新契约改写（不删除），新增用例覆盖上面各条；`npm test --prefix apps/web` 全绿，用例数只增不减。

非目标（任务卡「不做什么」）：

- 不改内核（`crates/` 一行不动），不扩读白名单。
- 不改铃铛界面（`apps/web/app/`、`bell-*.test.ts`），不改 `notifier-api.ts`，也不改系统通知的触发条件。
- 不补 `done`（`fyi`）通知；不补项目告警（`project_alert`）；不补历史事件。
- 不改 `notifier-rules.ts`：补发复用 `matchEvent` / `renderTitle`，见方案 D2。
- 不动 `apps/desktop/`、`protocol/`、`plugins/`、`.autome/`、`scripts/`，不改 W4 归档设计文档。

## 设计

### D1 面板库第 2 级迁移

在 `MIGRATIONS` 末尾追加一级，第 1 级的 SQL 一字不改：

```sql
ALTER TABLE notifications ADD COLUMN source TEXT NOT NULL DEFAULT 'event';
CREATE TABLE notifier_task_state (task_id TEXT PRIMARY KEY, state TEXT NOT NULL, seq INTEGER NOT NULL);
INSERT INTO event_cursor (name, seq) SELECT 'notifier_seed', seq FROM event_cursor WHERE name = 'notifier';
```

- `notifications.source`：通知来源，取 `event`（事件路径，也是旧行的默认值）或 `backfill`（补发），满足约束 2 的「来源标
  `backfill`」。`store.list()` 改成显式列出原来的九列，不再用 `SELECT *`。这样 `Notification` 类型、`/api/notifications`
  的返回和 WebSocket 消息的形状都不变，铃铛界面和它的测试都不用改。测试要读 `source` 时直接用 `DatabaseSync` 查。
- `notifier_task_state`：每个任务一行，记通知器最近一次**观测到**的状态（`state` 是 `payload.state` 的 JSON 文本），
  以及**进入**这个状态时的序号 `seq`。
  - 这就是任务卡说的「state_key」：一次等待由 `(task_id, state, seq)` 标识，`seq` 是进入的序号。
  - 补发路径上不知道任务真实的进入序号，所以 `seq` 取补发时的 `latest_seq`（L0），意思是「不晚于 L0 已经在这个状态」。
  - 播种路径上 `seq` 取历史里最后一次状态变化的序号。
  - 比较时把 `state` 解析回对象再用 `isDeepStrictEqual` 比，不按字符串比，不受键顺序影响。
- `notifier_seed`：在 `event_cursor` 里借用的一行播种游标，只在升级时**已经存在 `notifier` 游标**的库里出现，值等于
  当时的 `notifier` 游标。新建库执行这一级时 `event_cursor` 是空的，所以不会出现这一行。用法见 D4。
- `migrate()` 的逐级事务、整级回滚，以及「库比代码新」的中文报错都不变。

### D2 「进入」判定改为读持久化状态（事件路径）

对每条 `task.updated` 事件 e：

1. `prev = store.getTaskState(e.subject)`。`same = prev && isDeepStrictEqual(prev.state, payload.state)`。
2. `same` 时这条事件不算进入，不匹配规则，也不写状态；游标照常在页末推进。
3. 不是 `same` 时：
   - `rule = matchEvent(e)`。命中规则就按现有流程补齐信息、生成通知。
   - 不论是否命中，都用 `store.commit({ cursor: e.seq, notification?, taskState: {task_id, state, seq: e.seq} })`
     在**一个事务**里写通知、状态和游标。
   - 「离开」事件（非等待状态）也要落库，再次进入才能被认出来。
4. 补齐遇到没有 `code` 的错误时，`save(cursor)` 后返回，不写状态，下次重试仍按进入处理。带 `code` 的拒绝照旧生成
   空字段的通知，并随通知写状态。
5. `project.alert` 不碰 `notifier_task_state`，去重仍靠唯一索引 `(kind, ifnull(task_id,''), event_seq)`。
6. 进程内的 `states` Map 删掉；`cache`（补齐缓存）保留。

每条改变状态的 `task.updated` 都多一个小事务。账本事件稀疏，一页最多 200 条，代价可以接受，换来的是「状态与游标同时落库」，
不需要另做批量回写。

### D3 首次启动补发（G1，约束 1–5）

条件：`store.getCursor('notifier') === undefined`。

1. `page0 = events.since {after_seq: MAX_SAFE_INTEGER}`，`L0 = page0.latest_seq`。**先取序号，后取快照。**
2. `snap = dashboard.get {}`。
3. 对 `snap.waiting` 的每一项 w：
   - 构造合成事件 `{seq: L0, kind: 'task.updated', subject: w.task.id, payload: {state: w.task.state}}`。
   - 用现有的 `matchEvent` 匹配；匹配不到，或规则的 `level !== 'need_you'`，就跳过（防御用，`awaits_user()` 恰好对应五条
     `need_you` 规则）。
   - 生成通知：`kind = rule.kind`，`title = renderTitle(rule, 合成事件)`，`body = w.task.title`，
     `project_id = w.project_id`，`task_id = w.task.id`，`event_seq = L0`，`source = 'backfill'`。
     这些字段和事件路径完全同源：事件路径的 `body` 取 `task.get` 的 `task.title`，`project_id` 取 `project.id`，
     标题用同一个 `renderTitle`。
   - 补发**不调用** `task.get`。
   - 同时记一条状态 `{task_id: w.task.id, state: w.task.state, seq: L0}`。
4. `rows = store.backfill({ cursor: {name:'notifier', seq: L0}, notifications, taskStates })`。所有通知、状态和游标在
   **一个** `BEGIN IMMEDIATE` 事务里写，要么全成，要么全不成（约束 3）。
5. 事务提交后，对 `rows` 逐条 `publish` 五键消息（约束 5，见 D6）。
6. `cursor = L0`，进入正常拉取循环，补齐 `(L0, latest]` 之间的事件。
7. 第 1、2 步之间或之后如果 `closed`，直接返回，什么都不写。任一调用失败时，由 `pull()` 现有的 catch 记一行
   「拉取失败」，什么都不写，下次 `pull()` 重新走首次启动。中途崩溃时，事务要么已经提交（游标已存在，不会再补），
   要么没有提交（库里没有补发行，下次重来）。不论哪种，结果都是每个等待任务恰好一条。

`dashboard.get` 一次就拿到全部项目的等待任务（包含 `failed`），所以选它，不选逐个项目调 `project.get`
（`project.get` 还会读配置、扫技能目录，开销更大）。

#### 快照与序号的竞态（约束 4）

「当前等待中」定义为**快照那一刻**处于等待的任务。通知范围由两部分组成：

- 快照里的等待，由补发覆盖；
- 序号大于 L0 的每次进入，由事件路径覆盖。

任意交错下，同一次等待最多一条，并且两部分不会漏掉中间的进入：

| 交错情形 | 补发 | 回放 L0 之后的事件 | 结果 |
|---|---|---|---|
| L0 前进入 W，快照时仍在 W | 1 条，状态记 W | 没有这个任务的变化 | 1 条 |
| L0 后、快照前进入 W | 快照含 W：1 条，状态记 W | 回放进入 W 的事件：与状态深相等，跳过 | 1 条 |
| L0 后进入 W，但快照取在内核写入新状态之前，看到的仍是旧状态 X（非等待） | 不补 | 回放进入 W 的事件：X≠W，通知 | 1 条 |
| L0 后在 W 与 X 间往返，快照看到 W | 1 条 | 回放：W 跳过、X 记下、再次 W 通知 | 2 次等待各 1 条 |
| L0 时在 W，快照前已经离开 | 不补 | 回放离开事件，不通知 | 0 条：这次等待在快照前已经结束，属于「历史」，按约束 1 不补 |
| L0 后从等待 W1 转到等待 W2 | 快照看到哪个就补哪个 | 回放：与快照相同的跳过，不同的通知 | 每个不同的等待各 1 条 |

顺序反过来（先快照、后取 L0）会漏发：落在快照和 L0 之间的进入既不在快照里，又在游标之前，回放时看不到。
M-02 的负向对照就是这种实现。

### D4 已有面板库升级（G3，约束 10）

- 升级后游标已经存在，不走首次启动，不补发。
- 「最近状态」的初值**从账本历史播种**：`drain()` 开头如果发现 `notifier_seed` 游标 S，就用
  `events.since {after_seq, limit: pageSize}` 从 0 分页读到 S，对每个任务取 `seq ≤ S` 的最后一条 `task.updated`
  的 `payload.state` 和它的 `seq`。然后用 `store.seedTaskStates(taskStates)` 在一个事务里写入全部状态，并删掉
  `notifier_seed`。
  - 播种不生成任何通知。
  - 中途关闭或出错时什么都不写，下次重扫。
  - 扫描中如果 `latest_seq < S`，说明账本已经换了，就放弃播种，交给正常循环的换账本分支处理（那里会清掉播种游标）。
- 为什么不用另外两种播种来源：
  - **由已有通知行播种**会漏发。任务在升级前进入 W 并被通知，在游标前离开，升级后再进入 W。按通知行播种会以为它
    还在 W，于是把这次真实的再进入吞掉。
  - **由当前快照播种**也会漏发。任务在游标处于非等待状态，停服期间进入 W（事件在游标之后）。按快照播种会把这次进入
    当成「同状态」跳过。
  - 只有「游标时刻的真实状态」不会出错，而它只能从账本历史得到。这里读历史只用来播种，不生成通知，不违反「不补历史」。
- 一次性代价：读一遍账本。几千条事件就是几次到十几次 `events.since` 调用。

### D5 账本更换（约束 9）

`page.latest_seq < cursor` 时：

1. 先调 `dashboard.get` 取新账本的快照（这一页的 `latest_seq` 就是新账本的 L0，先取序号、后取快照的顺序与 D3 一致）。
2. 调用 `store.resetLedger('notifier', latest_seq, { notifications, taskStates })`，在一个事务里完成：
   - 把旧通知的 `event_seq` 置空；
   - 清空 `notifier_task_state`；
   - 删掉 `notifier_seed`；
   - 写入新账本的补发通知与状态；
   - 写游标。
3. 清空补齐缓存，记现有那一行日志，提交后推送补发行。

**换账本后补发**，理由是：新账本对通知器来说等同于一次全新安装。旧通知的 `event_seq` 已经置空，指向的是旧账本里的
任务编号；不补发的话，新账本里正在等待的任务永远不会出现在铃铛里，等于把本任务要修的问题原样带回来。快照失败时什么都
不写、游标不动，下次 `pull()` 仍会检测到换账本并重试。

`resetLedger` 的第三个参数可以省略（现有 store 用例就是这样调的），省略时只清理、不补发。

### D6 推送

补发行在事务提交后照常 `publish`，消息与事件路径的完全一样，恰好五键 `type/id/kind/task_id/title`。理由：

- 铃铛只在收到 `hello` 或 `notification` 时刷新（`app/components/bell-client.ts:66`）。面板首次连上内核之前就已经打开的
  页面，如果不推送，要等下一次连接才能看到补发的通知。
- 补发通知本来就是 `need_you`，语义与事件路径相同。系统通知仍由浏览器端现有的 `levelOf === 'need_you'`、已授权、
  页面隐藏三个条件决定，一行不改。

### D7 存储原语（`store.ts`）

- `getTaskState(task_id): { state: unknown; seq: number } | undefined`
- `commit({ cursor, notification?, taskState? })`：在原事务里追加 `taskState` 的 upsert。
  返回值的语义不变：被唯一索引挡下时返回 `undefined`。
- `backfill({ cursor, notifications, taskStates }): Notification[]`：一个事务；通知按 `INSERT OR IGNORE` 写入，
  `source='backfill'`；返回实际插入的行。
- `resetLedger(name, latest, backfill?)`：见 D5，返回实际插入的行。
- `seedTaskStates(taskStates)`：一个事务里写状态，并删掉 `notifier_seed`。
- `list()`：显式列出九列。

`NotificationInput` / `Notification` 两个类型不变。

## 风险

- **真实用例耗时。** 两个任务，每个都要跑完整个设计循环，驳回后还要再跑一轮。预计比 w4 账本（七个任务，上限 300 秒）短，

  能处理写冲突。注入只发生在测试用的临时账本上。

  不会变成一个假的绿。
- **并行任务也在改 `apps/web/`。** 改动只限 `store.ts`、`notifier.ts` 和上面列出的测试文件与夹具，不做无关的移动或重排。
