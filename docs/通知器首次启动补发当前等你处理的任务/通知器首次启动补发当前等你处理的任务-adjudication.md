### R1-P01 快照状态被回放中的较早状态覆盖，同一次等待重复补发

- 主张摘要：D3 把「快照看到的较新状态」记成 `(state, seq=L0)`，再从 L0 回放；L0 与快照之间发生的连续转换（`merge_gate`→`await_merge`）
  会先把状态覆盖成 `merge_gate`，再把 `await_merge` 当新进入，同一次等待得到 `backfill` 与 `event` 两条。W1→X→W2 变体得 3 条而非表里写的 2 条。
- 设计位置：D1 `seq` 说明、D2 第 1–3 步、D3 第 1–6 步与竞态表、D5。
- 裁决：**采纳**。
- 证据：复核成立。`crates/autome-domain/src/task.rs:1433` 允许 `MergeGate + Passed → AwaitMerge`；唯一索引按 `event_seq` 去重，
  序号 100 与 102 不同，挡不住。设计里「快照 = L0 时刻状态」的假设在两次读取之间账本前进时不成立。
- 修改落点（均在设计文档）：
  - D3 改为 `takeSnapshot()`：取 L0 → `dashboard.get` → 再取 L1，`L1 === L0` 才接受，否则丢弃重取，最多 3 次，仍不齐则抛无 `code` 错误、
    什么都不写、下次 `pull()` 重来。接受时快照就是 L0 位置上的状态，不再有「快照比游标新」的情形。「状态先写、事件后写」的窗口
    由 D2 的同状态跳过吸收，不需要额外处理。
  - D3 竞态表重写，并补一段最小模型核对：3–5 步转换、X/W/V 三态、三次读取在内核「写状态」「记事件」之间的全部插入位置，共 12464 种交错，
    新规则与真值（快照时刻的等待一条，加快照之后每次进入等待各一条）全部一致，旧稿在 5776 种下不一致。脚本 `.autome/output/adjudicate-1-model.mjs`。
  - D5 换账本补发改用同一个 `takeSnapshot()`，补发和游标用它返回的 L0。
  - D1 `seq` 说明补上「快照与 L0 对齐」的前提。
  - D8 首次启动用例的调用顺序改为 `events.since MAX`、`dashboard.get`、`events.since MAX`。
  - D9 N3 重写，覆盖评审反例、W1→X→W2 变体、快照后离开再进入、状态先写事件后写、3 次对不齐不写半截、调用顺序；N4 的 `close()` 覆盖三次调用中任意一次；
    N6 带一次对齐重试。
  - M-02 负向对照增加「不做 `L1 === L0` 确认」一条（评审反例得 2 条、变体得 3 条）。
- 没有靠「跳过所有非等待事件」或「禁止再次通知」来消重：离开再进入仍重新通知（约束 7），N2 与 N3 的快照后 X、W 用例守着。
- 同类检查：D2 的事件路径本身不变；D4 用游标前历史播种、不用未来快照，无同根因；D5 已随 D3 改。
- 复提计数：0（首次提出）。
