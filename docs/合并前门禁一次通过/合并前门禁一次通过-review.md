## 阻塞问题

### R1 · P1 · globalSetup 失败时，仅靠 reporter 事件无法列全未执行用例

- **类别与追溯：**关键事实错误；任务 **B-1**，设计「B-1 / B-Q1 三类清单的来源与体量」（168–173 行）及 M-03。
- **问题与证据：**设计让报告器仅从 reporter 事件取得用例及未执行清单。但 Playwright 1.64.1 普通 CLI 的任务顺序是 globalSetup、加载测试、运行测试；setup 抛错会终止后续任务，没有正常 onBegin 时只补发一个空 Suite。这是源码确定的控制流，不是「测试还可以更多」。参见 [CLI 顺序](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright/src/runner/testRunner.ts#L401-L411)、[错误中断后续任务](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright/src/runner/taskRunner.ts#L55-L76)、[onEnd 补发空 Suite](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright/src/reporters/internalReporter.ts#L80-L89)。
- **具体反例：**复现任务背景中的 `prepare()` ETIMEDOUT：29 条用例都没运行，报告器却没有这 29 条的身份，只能得到非用例错误和空套件，无法交付 B-1 要求的完整未执行清单。M-04 的清单目前只在快检运行、交给内核做 B-3 匹配；它没有成为合并前门禁报告器的输入，不能补足此路径。
- **根因、同类范围与修订方向：**用例库存依赖已经成功完成 setup。应让每次整套/子集运行在 setup 前取得与本次选择范围一致的清单，并把它接到报告生成路径；同时处理 setup 抛错和 setup 期间总超时。修订 M-01/M-03 的数据来源与对应夹具，避免把后续 M-04 的功能当作前置保障。

### R2 · P1 · 预算截断正常结束时，没有必达的进程清理路径

- **类别与追溯：**违反任务目标；任务 **§6 约束 7「测试不留存活进程」**、A-2；设计 A-2 的截断/上一层超时处理（128–136 行）。
- **问题与证据：**设计主动缩短 Playwright `globalTimeout`，截断后记 `not_run` 并结束，同时只依靠「万一被内核杀」时的 `kill_group`。Playwright 到达 deadline 后，cleanup 仍使用同一已过期 deadline，不能保证执行 globalTeardown；源码对此有明确说明，且测试任务清理先等待 dispatcher 停止。[超时清理实现](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright/src/runner/taskRunner.ts#L91-L106)、[测试任务清理](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright/src/runner/tasks.ts#L437-L440)。本仓库 `apps/web/e2e/harness/setup.ts:34` 启动长期服务，实际清理与残留断言在 `teardown.ts:13–33`；`crates/automed/src/gate.rs:309–310` 发现退出标记直接返回，只有作业仍运行且达到内核超时才在 323–324 行杀进程组。
- **具体反例：**两套 fixture 已启动，测试阶段耗尽缩短后的 globalTimeout，globalTeardown 未执行；脚本把截断记为 `not_run` 后在内核 deadline 前退出。内核看到退出标记，不会执行超时杀组，fixture 服务/内核可能留下。预留 60 秒并不会使 Playwright 已过期的清理 deadline 延长。
- **根因、同类范围与修订方向：**把运行器总超时当作既能截断又能完成收尾的机制。为浏览器阶段设计独立且必达的清理路径、单独的清理时间和残留检查，覆盖整套/子集、正常完成、setup 失败及预算截断；不能只验证替身命令返回 `not_run`。此结论为源码推导，本轮未启动进程复现。

### R3 · P1 · 错误原文已在日志生成端裁切，给日志路径无法恢复完整材料

- **类别与追溯：**违反任务目标；任务 **B-1**，设计 B-1（170–183 行）、M-03。
- **问题与证据：**设计先承诺非用例错误原文，随后把单条原文限至 2 KB、整段过大时缩到 300 B；内核再把 digest 限至 16 KiB，提示去日志标记段看完整内容。但该日志段已经裁切。未截原文仅保存在固定 `.autome/output/playwright-gate/report.json`，没有规定把本次报告作为稳定材料交付给修复轮，简报只提供日志路径。
- **具体反例：**globalSetup 抛出一条超过 2 KB、关键错误原因在尾部的错误。修复轮读提示词和所指日志，仍看不到尾部；如果后续再跑一次，固定 report.json 还会被替换。
- **根因、同类范围与修订方向：**摘要与完整材料共用已截断的交付路径。检查失败断言详情、非用例错误和整段清单三层裁切，按本次作业保留完整报告，并把可读取路径与摘要一起交付。任务 §7 B-Q1 已允许「完整文件＋路径＋摘要」，无需取消摘要预算，也无需把全文塞进提示词。

### R4 · P2 · 表达式预算被主动略过，现有专设 timeout 不满足 A-4

- **类别与追溯：**违反任务目标；任务 **A-4**，设计「A-4 / A-Q6 专设预算过半」（157–158 行）、M-01。
- **问题与证据：**设计明确规定表达式预算不比较、只计「N 处预算不是字面量」。当前 `apps/web/e2e/controls.spec.ts:154–155` 和 `apps/web/e2e/live.spec.ts:20` 已使用 `Math.max(1, 5000 - …)` 专设超时。这些也是 A-4 要求覆盖的预算，任务未授权只支持字面量。
- **具体反例：**某次表达式求值得到 4 秒预算，断言耗时 3 秒成功，已超过一半；按设计只增加一个不支持计数，不会列出对应条目、预算与耗时。
- **根因、同类范围与修订方向：**用源码字面量替代运行时实际预算。检查全部 `e2e/*.spec.ts` 的专设断言预算，采集实际求值与实际耗时，或为现有动态预算提供显式计时封装，保持原断言语义。未把多行调用单独列为缺陷：尚无证据证明现有调用的 reporter location 一定漏掉其 timeout。

### R5 · P2 · B-3 把完整失败记录缩成同行匹配与前 60 条

- **类别与追溯：**违反任务目标；任务 **B-3**，设计 B-3 的匹配/交付规则（201–206 行）、M-04（320 行）。
- **问题与证据：**只有同一行同时包含名字与失败词才提取；交付最多 60 条/12 KB、每条原文最多 300 字节，剩余只给计数和 `rg` 命令。任务要求机械提取并附上所有相关记录；允许识别不了进入 Backlog 的明确豁免属于 D-1，不能自动用于 B-3。
- **具体反例：**一个合法 Markdown 条目首行写 `controls.spec.ts B-3`，缩进续行写「4 次复验 2 次失败，环境限制」，记录完全不命中。另构造 61 条都含 `B-3 失败` 的记录，第 61 条有不同失败原因，只能收到「另有 1 条」，而不是该记录；单条原因写在 300 字节后也会丢失。
- **根因、同类范围与修订方向：**把物理文本行当作完整记录，并把展示限额作用到材料本身。Backlog 条目和审计证据应按可确定的记录单元提取；摘要可限长，但应生成并交付完整提取产物，不能只让下一轮重新检索。同步修改 M-04 对「要求同行」的验收，不能把遗漏固化为通过条件。

### R6 · P2 · C-1 / 验-4 的简报契约被换成提示词契约

- **类别与追溯：**违反任务目标；任务 **C-1、验-4**，设计 C-1/C-Q2（210–219 行）、M-05（288、326 行）。
- **问题与证据：**设计明确把起点和快检命令放进 `round_gate_line` 提示词，不放进简报；M-05 也只断言提示词中的 SHA。即使用户应用 `quick_session`，简报仍不包含任务要求的 `sh scripts/ci-quick.sh --since <提交>`。现有 `scheduler.rs:4210` 提交简报、3927–3940 行随后取起点，确实支持设计所说的自引用难题，但它只说明需要调整生成/提交顺序，不等于已满足简报验收。
- **具体反例：**实现与宿主都拿到同一 SHA、M-05 的提示词断言全部通过；按验-4 打开 `brief/impl-<轮次>.md` 查找 `--since <提交>`，仍然没有。
- **根因、同类范围与修订方向：**为绕开当前生命周期，把指定交付载体从验收中删除。应给出无需提交 SHA 自引用的起点/简报生成方案并实际检查简报；若裁决认为提示词已足够，需要明确记录这是对任务载体要求的调整，不能把提示词断言直接称为验-4 原样通过。检查需求实现轮及修复轮的同类入口。

## 非阻塞建议
