# 合并前门禁一次通过：浏览器测试提前到每轮由宿主跑，门禁失败一次报全

## 背景

T-98（13 个里程碑，11-15 至 11-16）全部里程碑审计通过之后，合并前门禁连续失败 6 次、第 7 次才过。数据取自账本 `gate.result` 事件与 `docs/面板收尾批次-用上新的内核数据-补齐备注/lessons.md`（L-01…L-11）：

- 合并前门禁 7 次共 7412 秒（约 2 小时 4 分），6 次失败全部在 `Web e2e` 这一步；每次失败各多花一个修复实现轮、一个审计、一个复盘（实现 #24–#29、审计 #16–#21、复盘第 2–7 轮）。
- 每轮快检 29 次共 4906 秒，其中 8 次失败、13 次超过 120 秒预算，中位数 116 秒，最长 603 秒。
- 6 次失败依次是：360 秒 `globalTimeout`、B-3 读到 0 个会话、夹具 `prepare()` 60 秒超时、D-1「运行中」列不可见、360 秒 `globalTimeout`（同第一次）、C-2 准备阶段 75 秒只凑到 17 个会话。

根因有四条，都是机制问题，不是 T-98 特有的：

1. **浏览器用例在合并前门禁才第一次完整运行。** Codex 实现会话在 `--sandbox workspace-write` 下运行（`crates/automed/src/launcher.rs`），不能 `ps`、不能监听 127.0.0.1，29 份实现证据里 24 份记了 EPERM，Playwright 在 globalSetup 就停下。审计只跑本里程碑点名的 spec 子集。整套 29 条用例第一次一起跑就是合并前门禁。
2. **门禁一次只暴露一个问题。** Playwright 配置 `workers: 1`、`retries: 0`、没有 `maxFailures`，被 `globalTimeout` 截断时报告是「N 通过、M 未执行、2 个非用例错误」，修复轮拿到的日志尾部没有这些错误的详情，于是一次修一个、往返六次。
3. **实现轮拿到的快检命令没有起点。** 简报里是不带参数的 `sh scripts/ci-quick.sh`，脚本支持 `--since <rev>`，7 份证据写了「未提供本轮起点，未跑改动相关的测试」。会话内只跑了静态检查，相关测试等宿主快检才第一次运行，8 个实现轮只用来修宿主快检抓到的失败。
4. **审计见过的失败被放行。** 第二、三次门禁失败的位置，审计 #4（BL-13，B-3 四次里两次读到 0 个会话）与审计 #14（`prepare()` 60 秒 ETIMEDOUT）都已经看到，分别按「测试竞态」「环境限制」通过。

## 要做什么

一次设计、一次评审，按下面分组里程碑实现。只做机械保证，不靠提示词要求会话自觉。

### A 浏览器用例每轮由宿主跑

- A-1 实现轮 / 修复轮结束后，宿主在每轮快检之后按本轮改动跑相关的浏览器用例：改了 `apps/web/e2e/<x>.spec.ts` 就跑该文件；改了 `apps/web/e2e/harness/` 或 `playwright.config.ts` 就跑整套；改了 `apps/web/app`、`apps/web/server` 时怎样选用例由设计轮定（可以是里程碑验收命令里点名的 spec）。失败当轮退回给实现方，日志进简报。
- A-2 这一步有自己的预算，不计入快检的 120 秒；设计轮按 T-98 的实测耗时（审计 #21：单跑 C-2 共 3.9 分钟，其中用例外 2.4 分钟）给出预算与超预算时的行为。通过记录进入现有的步骤沿用机制（T-97），合并前门禁在输入没变时沿用。
- A-3 整套浏览器用例的总耗时每次运行都写进门禁报告，并与 `globalTimeout` 比较；余量低于设计轮定的比例时该步骤判失败并写明「总耗时 X 秒，上限 Y 秒」。
- A-4 用例里专设的超时 / 轮询预算（`expect.poll` 的 timeout、`test.setTimeout`、`prepare()` 的超时）：报告里列出实测耗时超过预算一半的条目。

### B 门禁失败一次报全

- B-1 `Web e2e` 步骤失败时，交给修复轮的材料包含三类完整清单：失败用例（含断言与位置）、未执行用例、非用例错误（原文）。不再只给日志尾部。
- B-2 报告是「有未执行用例」且配置没有 `maxFailures` 时，直接标明「整套被总超时截断」，并给出各用例耗时与 setup / teardown 耗时。
- B-3 合并前门禁失败后的第一个修复轮，简报里附上本任务 Backlog 与既往审计证据中所有提到门禁会运行的用例或 setup 步骤失败、超时的记录（按文件名与用例名匹配，机械提取）。

### C 实现轮快检带起点

- C-1 简报与 `AUTOME_ROUND_START`（T-97 已导出给宿主）一致地把本轮起点交给会话，简报里的快检命令是 `sh scripts/ci-quick.sh --since <本轮起点>`。
- C-2 宿主每轮快检的 120 秒预算：T-98 有 13 次超出、一次跑到 603 秒。设计轮查清超出的原因（冷缓存、相关测试选得太多、还是与其它门禁抢资源），给出修法或把预算改成实测值。

### D 审计放行的口径（机械部分）

- D-1 审计证据里把门禁会运行的用例 / setup 步骤的失败或超时记为「环境限制」「测试竞态」时，内核在里程碑关闭前核对：只有权限拒绝（EPERM）一类可以放行，其余按退回处理。怎样机械识别由设计轮定；识别不了的部分如实写进 Backlog，不为此改协议文本。

### E T-98 留下的两条测试补强

- E-1（T-98 BL-13）`controls.spec.ts` B-3 已改为有界轮询会话数，在宿主上真实浏览器复验一次并把结论写进证据。
- E-2（T-98 BL-14）`controls.spec.ts`「BL-01」用例在「相关表恒不匹配」变异下仍通过：让用例排除整页重验路径（或断言详情数据请求只带本路由），并补一条挂载 / 卸载 `TaskPage` 的组件测试，守住 effect 的清理函数。

## 不做什么

- 不放宽 Codex 会话的沙箱（不改 `--sandbox workspace-write`）。会话跑不了的验收由宿主跑。
- 不改协议文本、不新增协议版本；复盘教训里 level 为 `protocol` / `rule` 的条目只取其中能机械保证的部分。
- 不改调度、合并队列、门禁时机（合并前门禁仍只在合并前跑一次）。
- 不动 `.autome/`；需要改 `.autome/config.toml` 的地方写进设计文档的「合并后由用户应用」一节。

## 验收标准

- 验-1 夹具任务：实现轮改坏一条浏览器用例，宿主在该轮结束后报出失败并退回，不等到合并前门禁。
- 验-2 夹具任务：整套浏览器用例总耗时超过上限的设定比例时，步骤失败且报告写出总耗时与上限。
- 验-3 构造一次被 `globalTimeout` 截断的运行：修复轮简报含失败、未执行、非用例错误三类清单，并标明「被总超时截断」。
- 验-4 实现轮简报里的快检命令带 `--since <提交>`，该提交等于宿主记录的本轮起点。
- 验-5 E-1、E-2 各有测试或结论。
- 验-6 `sh scripts/ci-local.sh` 全部通过；浏览器用例输入没变时合并前门禁沿用每轮的通过记录。
