## 可要求再评审的问题

### R1-P01：启动记录缺失时回退当前命令，仍会把复现通过当成完整门禁通过

- 类别：违反任务目标。优先级：P1。
- 违反要求：约束 6（仅复现的 FixGate 通过不能让同一 head 的 MergeGate 沿用）、约束 10（运行中切换不能漏跑合并前完整门禁）。
- 设计位置：方案 §5，第 203 行「找不到才用当前配置」；M-03 的命令来源修正。
- 根因与证据：设计把 `gate.started` 当作作业命令的可靠来源，却在来源缺失时用新配置补造事实。`scheduler.rs:3298–3320` 先调用 `gate::start`，随后才独立写 `gate.started`；`gate.rs:106–140` 已写 `.started` 文件并启动独立进程组，文件只保存开始时间，没有命令。两步不原子。`scheduler.rs:3896–3900` 的恢复逻辑保留 core 节点，随后 tick 继续读取作业，并不清掉这类未记账的运行。
- 具体反例：① head H 上以 `before_merge` 启动 FixGate，仅跑复现命令；② 包装进程已启动，daemon 在写 `gate.started` 前退出，包装进程正常结束为 0；③ 用户改为 `each_round` 后恢复 daemon，H 不变；④ 现存作业被读取，但找不到其启动事件，按设计回退为当前的 `( repro ) && ( gate )`，写出 `ok = true`；⑤ 到同一 H 的 MergeGate 时，`scheduler.rs:3211–3223` 的 sha、ok、command 判断全部满足，写 `gate.reused`，完整门禁实际一次未跑。这正是约束 6 和 M-03 ④要求防止的同 head 情形，不依赖更改门禁命令。
- 检查范围：FixGate 命令来源、作业文件存在判定、启动与记账顺序、恢复路径、MergeGate 沿用判断。另一同根情形是同 node/head 的旧作业被丢弃后重新启动，在新启动事件写入前退出；仅匹配 node/sha 还可能拿到上一次运行的命令，不能证明是“本作业那条”。
- 建议裁决落点：§5 明确实际运行与命令来源的关联及缺失处置，无法证明执行过完整命令时不得把结果升级为完整门禁通过；可采用可靠运行元数据或安全重跑。M-03 加入上述中断窗口的判别场景，保证不会出现错误 `gate.reused`。不要求新增事件种类或账本 schema。
- 证据性质：源码顺序与设计算法的因果反例；本轮未执行 daemon 崩溃注入，也未声称未来实现已复现该缺陷。

### R1-P02：明确排除 Bug 复核提示，遗漏任务卡要求的一个交付对象

- 类别：违反任务目标。优先级：P2。
- 违反要求：任务卡「要做什么」第 4 条、目标 4、约束 8，以及验收 5 对该文案的金样要求。
- 设计位置：非目标「不给 Bug 复核轮新增简报」；方案 §6.3，第 236 行「本任务不给复核轮新增简报或 prompt 段落」；M-04 只交付审计简报和审计金样。
- 根因与证据：把“现状没有复核简报”当作可以免除新任务要求的理由。`scheduler.rs:2639–2660` 确实过滤全部 Bug 会话；`protocol/prompts/fix-review.md:5–7` 只要求读取 Bug 文档并自行复验，没有宿主门禁结果提示。这证明现状缺口存在，不能证明任务卡允许不补。任务卡明确写“审计 / 复核简报……写明……不留空”，不是仅禁止把复现结果误报成完整门禁结果。
- 具体反例：配置项目门禁并设置 `before_merge`，FixGate 的复现通过后启动第一次 Bug 复核；完整宿主门禁尚未执行。按设计，该会话仍收不到「本项目门禁只在合并前运行，本轮没有宿主门禁结果」。即使 M-04 所列所有测试通过，复核对象的交付仍然缺失。
- 检查范围：需求 Audit 和 Bug FixReview 两类接收者、启动时的 brief 过滤、复核 prompt、M-04 金样。需求 Audit 已有落实方案；缺失集中于 Bug FixReview，不要求给定位轮、修复轮增加简报。
- 建议裁决落点：修改 §6.3 和 M-04，为 `before_merge` 下 Bug 复核提供可读取的宿主证据提示，并纳入金样；FixGate 仅复现通过不得被显示为完整门禁通过。保留 `each_round` 的原提示与会话自行复验规则。具体使用专门简报还是宿主注入由裁决轮确定，无须先扩大到修改协议源。

### R1-P03：命令来源修正无条件作用于 FixGate，改变未启用新模式的行为

- 类别：违反任务目标。优先级：P2。
- 违反要求：约束 1（缺省与显式 `each_round` 的事件、注入等行为与今天完全一致）；任务 §4「不改 each_round 下的任何行为」。
- 设计位置：方案 §5，第 202–204 行：所有 FixGate 的 `gate.result` 和 `GateOutcome::Failed.command` 都取启动事件；只用“配置没变时……逐字节不变”论证兼容。
- 根因与证据：方案按节点限定改动，没有按新模式涉及的运行限定改动。“配置没变”比任务规定的“没有启用新模式”窄。现有 `scheduler.rs:3134` 每次重新解析配置，`3340–3344` 和 `3416–3420` 分别用当前命令记录结果与失败注入；`3216` 的 Bug 沿用判断也比较该命令。
- 具体反例：用户始终不写 `run`，FixGate 用项目门禁 A 启动，完成前只把项目门禁命令改成 B。今天结果记录/失败注入使用 `( repro ) && ( B )`；按设计则使用启动时的 `( repro ) && ( A )`。若作业通过且随后同 head 到 MergeGate，今天可能沿用，设计则因命令不等重新执行。整个过程从未出现 `before_merge`，事件、注入和沿用行为却发生变化。
- 检查范围：FixGate 的成功记录、失败注入以及后续 MergeGate 沿用；不把修正需求扩展到其它节点。该项与 R1-P01 同处 §5，但触发条件和违反要求不同：前者是命令来源缺失会漏验，本项是有可靠来源时改动仍超出兼容边界。
- 建议裁决落点：§5 明确修正仅覆盖新模式涉及的运行/切换，并说明如何保留从未涉及新模式的旧行为；如认为应顺带修复旧行为，须正面裁决它与任务硬约束的冲突，不能仍宣称零行为变化。不能只按结束 tick 的 `gate_run` 限定，否则会再次漏掉设计已识别的 `before_merge → each_round` 场景。
