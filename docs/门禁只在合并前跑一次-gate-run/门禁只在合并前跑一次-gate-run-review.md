### R2-P01：启动函数会删除刚写入的复现标记，仍可能错误沿用完整门禁

- 类别：关键事实错误。优先级：P1。
- 违反要求：约束 6（仅复现的 FixGate 通过不能让同 head 的 MergeGate 沿用）、约束 10（切换模式不得漏跑合并前完整门禁）；设计方案 §5、M-03 ③④⑤。
- 设计位置：§5 第 252–259 行要求把 `.repro-only` 加进 `Job::clear`，在 `gate::start` 之前写标记，并据此认定作业必定带标记；第 274 行明确不动 `start / poll` 的行为。
- 根因与证据：方案遗漏了启动函数内部的清理。`crates/automed/src/gate.rs:106–111` 的 `start()` 先建目录，再在第 110 行调用 `job.clear()`，随后才写 `.started`。按设计把标记加入 `clear` 后，每次正常启动都会删掉刚写的标记；“标记先于作业出现”不能推出“作业存在时标记仍在”。
- 具体反例：① head H 上以 `before_merge` 启动 Bug FixGate，调度器写标记；② `gate::start()` 清掉标记，只执行复现命令；③ 作业结束被读取前切换为 `each_round`；④ 因标记不存在，按 §5 的兜底分支把通过结果记成当前完整命令 `( repro ) && ( gate )`；⑤ 随后在同一 H 上进入 MergeGate，`scheduler.rs:3212–3223` 的 ok、sha、command 检查全部满足，写 `gate.reused`，完整门禁未执行即被放行。这也是 M-03 已要求验证的同 head 场景。
- 检查范围：`Job::clear`、`gate::start`、`discard_node`、`run_gate` 启动与结果记账、MergeGate 沿用。正常启动即触发，不需要额外假设 daemon 崩溃；D1-P01 所关注的恢复路径也不能依赖一个已被删除的标记。
- 与既有裁决的关系：D1-P01 采纳后改用了旁路标记。本条的新证据是该修法与现有 `start → clear` 调用关系冲突，不是无新证据复提事件回溯主张。D1-P03 要求的默认行为边界仍须保留。
- 建议裁决落点：修订 §5 的初始化顺序，使清理旧作业发生在写本次标记之前，并保证标记在发布 `.started`、启动进程之前就绪；正常丢弃仍清理标记。不能简单改为 `start` 返回后再写，否则重新引入 D1-P01 的中断窗口。M-03 按真实启动路径验证标记存续和切换后的 MergeGate。
- 证据性质：源码顺序与设计算法的确定性反例；未修改生产代码，未声称未来实现已被实跑复现。

### R2-P02：门禁命令原文进入模板占位符校验，合法配置会阻断会话启动

- 类别：内部逻辑矛盾。优先级：P1。
- 违反要求：设计方案 §6.3 的“门禁命令原文照抄”、§6.4 的渲染顺序及设计目标 6；任务约束 10 的切换后不卡死要求。涉及 M-05 的渲染机制与 M-06 的五份新模板。
- 设计位置：§6.3 第 308–318 行把用户命令拼进 `gate_line`；§6.4 第 343–346 行先替换 `{gate_line}`，再沿用现有 `check_no_placeholders_left`。
- 根因与证据：把配置数据重新当作模板源码检查。`config_io.rs:322–327` 接受非空命令字符串，不限制 shell 的花括号语法；`launcher.rs:624–644` 会把任意 `{lower_snake}` 判为未识别占位符并返回错误。现有 `bug_prompt` 在 `launcher.rs:520–533` 专门先检查模板片段、最后拼入用户 `request`，正是为了隔离数据里的花括号；新命令通道没有这层隔离。
- 具体反例：合法项目门禁命令为 `ci_script=scripts/ci-local.sh; sh "${ci_script}"`，启用 `before_merge` 后启动使用 v3 模板的设计轮。将命令放入 `{gate_line}` 后，检查器读到 `{ci_script}`，报“Autome 不认识的占位符”，prompt 构造失败。相同问题影响实现、审计、修复与复核。该命令在 shell 中合法，不需要改变现有门禁执行规则。
- 同根情形：若在替换 `{slug}` 等普通占位符之前插入命令，命令中本应原样显示的 `{slug}` 还会被替换成任务名。未知占位符误拒绝与已知占位符误改写都源于模板与用户数据未分离。
- 检查范围：`gate_line` 的命令插入、`role_prompt`、`bug_prompt`、`eval_run::render_prompt` 的替换顺序；失败注入中直接追加的命令也应保持原文，但不能因此放宽真正的未知模板占位符校验。
- 建议裁决落点：§6.4 明确先解析、替换并验证模板，再把门禁命令作为数据插入，参照现有 `{request}` 的处理原则，避免二次解释。用 `${ci_script}` 与 `{slug}` 两种原文验证角色和 Bug 渲染路径，固定 `make check` 的金样继续保留。
- 证据性质：配置解析与模板检查源码形成的逻辑反例；本轮未启动会话或执行该门禁命令。

### R2-P03：把复核说明完全迁入新版模板，遗漏固定旧协议的 Bug 任务

- 类别：违反任务目标。优先级：P2。
- 违反要求：目标 4、约束 8（审计 / 复核没有本轮门禁结果时必须写明，不留空）；设计目标 5。涉及 §6.5、§6.8 与 M-06。
- 设计位置：§6.5 第 399–402 行取消 D1-P02 采纳的宿主追加说明，删除 `PromptSpec.gate_note` / `brief::bug_review_gate_note`，只靠 v3 `fix-review` 模板；§6.8 第 443–446 行保留旧 v2 模板，同时让宿主 FixGate 只跑复现的行为对旧任务生效。
- 根因与证据：宿主行为覆盖已有任务，而证据说明只覆盖新版模板。`scheduler.rs:2639–2656` 排除全部 Bug 简报；`launcher.rs:492–501` 从任务固定模板读取 `fix-review`；旧 `protocol/prompts/fix-review.md:6` 要求独立复验复现与项目门禁，没有缺证说明。`bug_loop.rs:300–301` 在 FixGate 通过后以 `None` 注入启动 FixReview，§6.7 的失败注入无法补救成功路径。
- 具体反例：升级前创建且固定在 v2 的 Bug 任务，升级后中途启用 `before_merge`；修复后 FixGate 仅复现通过，进入 FixReview。按设计旧模板原样渲染，没有简报、没有宿主追加说明，也没有失败注入，该复核轮完全收不到“本项目门禁只在合并前运行，本轮没有宿主门禁结果”。
- 检查范围：固定 v2 及更早、不含新说明的 Bug 复核模板；新版 v3 模板已覆盖，无须重复追加。需求审计简报由宿主生成，已有方案不受此项影响。
- 与既有裁决的关系：D1-P02 已采纳复核说明交付；本版删除宿主通道并改为仅新版模板承载，锚定设计发生了实质变化，因此属于新证据。协议固定可以解释不修改旧模板，不能免除随宿主新行为提供事实说明；现有任务要求没有豁免旧任务的该项交付。
- 建议裁决落点：保留旧模板与协议副本不变，在有门禁且 `before_merge`、旧模板尚未提供说明的 Bug 复核轮补宿主事实提示；新版模板继续按设计渲染。验证旧模板的 FixGate 成功 → FixReview 路径确实收到缺证文案，且 `each_round` 输出保持不变。不要求改变旧协议的测试范围规则。
