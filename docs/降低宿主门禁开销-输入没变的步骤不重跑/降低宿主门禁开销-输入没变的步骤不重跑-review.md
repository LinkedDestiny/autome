## 阻塞问题

### R1-01：任务合并会把未获最终验收的历史报告一并提升为跨任务可信记录

- **类别：内部逻辑矛盾。** 追溯：B-S3、X-3；设计 B.3 第 1 条、信任边界第 4–5 条；M-03 `gate_report` 用例③。
- **位置：** 设计第 259–277 行。快照采集本任务及 `merge_commit` 有值任务最近 7 天的报告，`passes` 直接取报告中的 `ran` 行；同时断言「被改过的脚本最多给本任务报告假通过」「合并意味着那份脚本过了评审、审计和合并前门禁」。
- **具体反例：** 任务 A 的早期脚本向宿主报告一个未执行过的键 K，内核按设计把它存成 `gate.result.passes`。随后恢复正确脚本，最终门禁实际通过的是另一组输入 K0，任务正常合并。此时 A 的 `merge_commit` 有值，早期假 K 也满足快照查询条件；任务 B 恰好使用 K 对应的输入就会沿用它。K 可以是预先计算好的另一棵源码树的键，不必等于 A 最终门禁的输入。整个过程不需要会话直接写 SQLite，也不需要在最终合并内容中留下假报告逻辑。
- **根因与检查范围：** 以“任务最终合并”担保该任务所有历史报告；最终脚本获准不等于早期脚本及其声明的键获准。检查范围包括本任务记录、跨任务快照、失败/超时留下的部分报告及最终合并后的提升规则。`unverified` 只检查 `reused` 是否在快照中，不能识别已经以 `ran` 入库的假 K。
- **应修改：** 明确跨任务发布的是哪次获验收输入及其可信通过记录，防止仅因任务已合并就发布全部历史自报键；给出“早期伪报 → 恢复脚本 → 最终真实通过 → 合并 → 其它任务查询”的判别对照。无需禁止正常的本任务失败后复用，但不能继续以当前提升规则证明 B-S3。
- **证据性质：** 按设计数据流构造的反例；尚无新实现可实跑，未操作真实账本。

### R1-02：缓存键与准备步骤没有约束实际被测试的内核二进制

- **类别：违反任务目标。** 追溯：X-3、B-R1、B-S4；设计 B.2「工具链指纹」、B.4「当前源码构建」承诺。
- **位置：** 设计第 240–243、287–291 行。指纹只列出 `RUSTFLAGS CARGO_BUILD_TARGET CARGO_TARGET_DIR NODE_OPTIONS`，`Build core` 只构建默认命令的产物。
- **源码证据：** `apps/web/test/fixtures/w9-replies.ts:18–19` 优先使用 `AUTOMED_BIN`；`apps/web/test/eventbus-live.test.ts:14–15` 同时读取 `AUTOME_BIN` 与 `AUTOMED_BIN`；`apps/web/test/task-live-real.test.ts:53` 优先使用 `AUTOME_BIN`。这些值既未进入键，也未在门禁环境中清除或固定到本次构建产物。
- **具体反例：** 仓库树、命令和已列出的工具链指纹不变，先用默认新内核通过 Web test，再把 `AUTOMED_BIN` 指向旧内核或不存在的文件。设计仍得到相同键并沿用，但实际运行会测试另一份二进制或启动失败。即使因其它输入变化而执行 Web test，`cargo build` 也不会更新这个覆盖路径，因此 B.4 的保证仍不成立。仅把覆盖路径字符串加入键也不能处理同一路径被替换为旧二进制。
- **根因与检查范围：** 把构建目录当作实际测试进程的唯一来源。已检索 `apps/web/test`、`apps/desktop/test`、`apps/web/server/core` 的两项覆盖变量：除上述位置，还涉及 `gateway-http`、`gateway-task-card`、`gateway-task-lifecycle`、`server`、`core-supervisor`、`core-sidecar`、`task-log-live`、`ticker`、`gateway`。Desktop 的同名环境变量测试会自行删除并恢复，不能拿它证明 Web 已隔离。
- **应修改：** 门禁固定实际测试所用的两个二进制到本次源码构建的产物，或将覆盖产物的身份和新鲜度纳入验证；同时处理 `CARGO_TARGET_DIR` / `CARGO_BUILD_TARGET` 使构建输出位置变化的情形。保留“输入相同可沿用”，但必须先证明实际执行输入等价。
- **证据：** `.autome/output/review-1/binary-override-scope.txt`；本项为现有源码和键定义的直接对照，未启动真实内核。

### R1-03：Rust 快检把二进制 crate 当作有库目标的 crate

- **类别：关键事实错误。** 追溯：C-R1、C-R4；设计 C.2 候选表优先级 2、3，M-04。
- **位置：** 设计第 345、348 行统一使用 `cargo test -p <c> --lib`，并明确把 `autome-cli` 列入依赖 `autome-domain` 后要跑 `--lib` 的 crate。
- **实测：** `cargo test -p autome-cli --lib --no-fail-fast --no-run` 退出 **101**，报 `no library targets found in package autome-cli`。`crates/autome-cli/Cargo.toml:10–12` 只声明 `[[bin]] autome`，`src/` 没有 `lib.rs`；`src/main.rs:1480` 起确实有应执行的单元测试。
- **影响：** 正常修改 CLI 源码，或修改 domain 后执行到这个候选，都会因为不存在的目标退回快检；这些单元测试也没有被执行。这不是测试本身失败。
- **根因与检查范围：** 候选生成未区分库/二进制测试目标。已核对三个 workspace crate；同类落点有“改动所在 crate”及“domain 的依赖者”两条规则，应一起修正。
- **应修改：** 按实际 target 选择单元测试，CLI 至少使用其二进制测试目标（如 `--bin autome`），保留 automed/domain 的库目标；用真实 CLI crate 命令验证，不只断言候选字符串。
- **证据：** `.autome/output/review-1/quick-command-probes.txt`。只做目标解析检查，未运行测试或访问账本。

### R1-04：Web 快检命令不会加载 Web 的 Vitest 配置

- **类别：关键事实错误。** 追溯：C-R1、C-R4、D-R1；设计 C.2 第 343 行与 D.1 分组，M-04 用例③。
- **设计命令：** 从仓库根执行 `npm exec --prefix apps/web -- vitest related --run <这些路径>`。
- **实测：** 同一调用方式的 `npm exec --offline --prefix apps/web -c 'node -p process.cwd\(\)'` 输出仍为仓库根。用本地安装的 Vitest `resolveConfig` 核对：默认调用没有读取配置文件，`testTimeout=5000`、`hookTimeout=10000`；显式 `root: 'apps/web'` 才加载 `apps/web/vitest.config.ts`，得到两个 60000 ms 超时和 `fileParallelism: false`。
- **影响：** 当前快检会丢失串行及超时配置，多个读写共享 `build/` / `.react-router/types` 的 related 套件可能同时跑，并让正常长用例因默认超时报错；D 落地后，同样不会加载三个 project 的分组和 `globalSetup`。这是快检与设计的运行语义冲突，不是要求增加测试数量。
- **根因与检查范围：** 把 npm 的依赖查找前缀当作命令工作目录。已检查 C.2 的 Web 候选、M-04 用例③和 M-06 命令；后者使用 `cd` 或 `npm run`，不具有同一问题。
- **应修改：** 明确 Web cwd / root / config，并把仓库相对的改动路径转换到该 root 或使用绝对路径；在真实候选调用上核对有效配置，确保它与完整 Web test 使用同一份分组和 setup。
- **证据：** `.autome/output/review-1/quick-root-and-protocol.txt`、`verified-counterexamples.txt`。只解析配置、列举测试，未运行 Web 测试套件。

### R1-05：按字符截断不能保证失败用例块完整进入按字节截断的摘要

- **类别：内部逻辑矛盾。** 追溯：A-R3、C-R4；设计 A.3 第 183–184 行；M-01 验收契约用例③。
- **矛盾：** 设计以“最多 20 行、每行 160 字符”推导用例块和结论必在 6000 字节 tail 中。`crates/automed/src/gate.rs:412–426` 实际按 UTF-8 字节保留末尾内容。
- **具体反例：** 18 行用例，每行 4 个 ASCII 前缀字符加 156 个汉字，单行恰好 160 字符；仅这些行就有 **8513 字节**，尚未计标题、省略计数与结论。它仍满足设计行数/字符数限制，但 tail 必然裁掉前面的失败用例，不能满足契约③要求的完整用例块。20 行同样格式实测为 9459 字节。
- **根因与检查范围：** 汇总输出使用字符预算，接收方使用字节预算；Rust 和 Vitest 解析后的共享汇总、以及复用该汇总的快检都受影响。
- **应修改：** 以整个摘要的 UTF-8 字节预算分配标题、用例、剩余数量及结论空间，截断保持字符边界；用多字节名称验证契约③，不必扩大 tail 或无上限输出所有用例。
- **证据：** `.autome/output/review-1/verified-counterexamples.txt`；现有 `gate::tail` 源码。

### R1-06：设计把空闲性能验收替换成了带负载交替基准

- **类别：违反任务目标。** 追溯：X-2、V-5 / D-R2 / D-V1、V-6；任务卡「先量再改」「空闲机器墙钟时间不超过改动前的 50%」。
- **位置：** 设计「改动前基线」第 93–99 行、D.2 第 401–405 行、M-06 验收契约。基线表只有历史负载数据及 load average 5–7 的实测；D.2 以“主机常年有 Loop，没有真正空闲时段”为由，仅要求在同一时段交替测量并比较中位数，M-06 也没有保留空闲条件。
- **影响：** 带负载的交替样本可以用于补充分析，却不能证明空闲机器满足 50% 硬指标。并发负载对串行/并行方案的影响不同，记录 load average 也不能把样本转换为空闲数据。照现有契约可能在没有满足用户性能目标时关闭 M-06。
- **根因与检查范围：** 将当前取证条件不足改写成降低验收条件。已核对基线、D.2、M-06 三处，需同步恢复口径。
- **应修改：** 保留空闲与负载两种口径及空闲前后各 3 次、50% 的原条件；已有负载数据照实保留。暂时拿不到空闲证据就记录待宿主复测，不能据此声明原目标已通过。**本意见针对替换验收条件，不针对本轮拿不到实测证据；这不是协议失败，也不要求本轮停止其它工作。**
- **证据性质：** 任务卡、任务要求与设计条款的直接对照；本轮未做性能实测。
