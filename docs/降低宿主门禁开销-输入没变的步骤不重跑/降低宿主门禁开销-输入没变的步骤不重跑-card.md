# 降低宿主门禁开销：输入没变的步骤不重跑、每轮在宿主上跑改动相关的测试、Web 测试并行、Rust 测试一次报出全部失败——一次设计、一次评审

## 背景

本仓库的宿主门禁（`.autome/config.toml` 的 `[gate]`）现在是：合并前跑一次完整门禁 `sh scripts/ci-local.sh`（`run = "before_merge"`），每个实现轮 / 修复轮结束后跑一次快检（格式、Clippy、Web lint、Web typecheck）。合并后在 main 上的检查复用合并前门禁的结果，不再重跑。这三点不改。

2026-11-13 一天的实测（31 个任务合并）：

| 项 | 次数 | 总用时 | 说明 |
|---|---|---|---|
| 完整门禁 | 54 | 509 分钟 | 其中 23 次失败，占 204 分钟 |
| 快检 | 81 | 23 分钟 | 平均 17 秒 |
| 合并后 main 检查 | 28 | 0 | 全部复用 |

单次完整门禁在三个任务并行的负载下要 9–15 分钟：Rust 测试 5–7 分钟，Web 测试 3.5–8 分钟，其余步骤合计不到 2 分钟。开销集中在四处：

1. **改什么都跑全部步骤。** 只改 `apps/web/` 的任务照样跑 5–7 分钟 Rust 测试；只改 `crates/` 的照样跑 Web lint / typecheck / build；只改 `docs/` 的也跑全套。失败修复后再跑一次，上次已经通过、输入也没变的步骤全部重跑。
2. **会话沙箱里跑不了的测试，第一次真跑是在合并前门禁。** Codex 沙箱不能监听 127.0.0.1、不能执行 `ps`，Claude 会话里实现轮也常只跑一个子集。HTTP、真实内核、进程清理这类用例第一次真正执行是在合并前门禁，23 次失败大部分属于这一类。一次失败的代价是 9–15 分钟门禁，再加一个实现轮、一个审计轮、一次复盘。
3. **Web 测试完全串行。** `apps/web/vitest.config.ts` 是 `fileParallelism: false`，112 个测试文件（其中 17 个 `*live*` 用真实内核与端口）逐个跑。
4. **Rust 测试遇到第一个失败的目标就停。** `scripts/ci-local.sh` 第 83 行的 `cargo test --workspace --all-targets` 没带 `--no-fail-fast`。T-95 的合并前门禁失败了 4 次（后两次 914 秒、739 秒），其中 3 次是「前一个测试目标失败，后面的目标没跑，修完再跑才看到下一个」；它的复盘连续四轮记下这一点（`docs/内核补齐批次-2026-11-13-4/lessons.md`），但不在任务范围内。

## 要做什么

四项，按 A → B → C → D 的顺序实现。一份设计文档覆盖四项，里程碑按项分组、标题以「A·」「B·」… 开头，总数不超过 6 个。

### A Rust 测试一次报出全部失败

- `cargo test` 带 `--no-fail-fast`，一次门禁报出所有失败的测试目标；`.github/workflows/ci.yml` 对应步骤同样处理。
- 门禁日志末尾的汇总除了步骤级的 ok / FAILED，再列出失败的测试目标与用例名（Rust 与 Web 都列），让实现轮简报里的失败摘要一眼看全，不用翻几千行日志。

### B 输入没变的步骤不重跑

目标：一次完整门禁只执行「输入相对上一次通过发生了变化」的步骤；其余步骤标为「沿用」，并写明沿用的是哪一次通过。

- 每个步骤声明自己的输入（路径集合，加上命令本身与工具链版本）。例：Rust 测试的输入包含 `crates/`、`Cargo.toml`、`Cargo.lock`、`protocol/`（seed 是 `include_str!` 进去的）；Web 测试的输入包含 `apps/web/`，以及内核源码（`*live*` 用例起真实内核）；Desktop 步骤的输入包含 `apps/desktop/` 和它解析的 `crates/automed/src/dispatch.rs`。具体划分由设计轮按代码事实定。
- 通过记录按内容寻址（输入路径的 git tree 哈希 + 命令 + 工具链版本），不按时间、分支名或提交号。这样三种情形共用一套机制：只改一侧的任务跳过另一侧；失败修复后重跑只跑受影响的步骤；rebase 到新的 main 之后，main 上已经通过的输入不重跑。
- **安全边界（必须满足）**：
  1. 不属于任何步骤输入、也不在「明确不需要门禁」名单里的路径发生改动时，整套门禁全跑。加一条守卫测试：仓库顶层新增目录或文件而没有归属时测试失败。
  2. `scripts/`、`.github/`、各 `package.json` / lockfile、门禁脚本自身的改动让全部步骤失效。
  3. 通过记录只由宿主门禁进程写入，放在任务会话不会写到的位置（不在 worktree 里）；设计文档写明信任边界：会话伪造一条通过记录应当做不到，或者做了能被发现。
  4. 沿用的步骤依赖的构建产物（例如 Web `*live*` 用例需要的内核二进制）在该步骤确实要跑时保证是当前源码构建的，不能用到旧产物。T-95 复盘里记过一次「`target/debug` 里 `autome` 比 `automed` 旧，3 个用例假失败」。
  5. 提供强制全跑的开关（参数或环境变量）；GitHub CI 始终全跑。
- 门禁日志与汇总里逐步骤写明：执行 / 沿用（沿用自哪次、输入哈希）/ 失败。任务详情时间线上的门禁条目能看出这次跑了几步、沿用了几步（内核若需要给事件加字段，只增不减）。
- 实现位置（`ci-local.sh` 内部、内核、或两者配合，例如内核给门禁命令导出基线提交的环境变量）由设计轮定。Autome 是通用工具，门禁命令是项目配置的一条 shell 命令：内核侧只做对任何项目都成立的事（导出环境变量、保存与展示结果），本仓库特有的步骤划分留在 `scripts/` 里。

### C 每轮在宿主上跑改动相关的测试

目标：把「合并前门禁第一次真跑才发现」的失败提前到当轮发现。

- 实现轮 / 修复轮结束后的宿主快检，在现有的格式、Clippy、lint、typecheck 之外，再跑本轮改动相关的测试：改到或新增的测试文件本身，以及能便宜地确定受影响的测试（Web 侧可用 vitest 的 related / changed 能力；Rust 侧至少是改动所在 crate 的单元测试与被改动的集成测试文件，`end_to_end` 是否整套跑由设计轮按实测耗时定）。
- 快检要保持「快」：给一个时间预算（设计轮实测后定，建议热缓存下中位数不超过 90 秒、上限 5 分钟）；超预算的部分留给合并前门禁，并在快检结果里写明哪些没跑。
- 内核需要让快检命令知道「本轮改了什么」：给门禁 / 快检命令导出本轮起点提交与任务基线提交的环境变量（名字设计轮定；`crates/automed/src/gate.rs` 的 `start` 已经导出 `AUTOME_GATE_*`）。没有配置快检的项目行为不变。
- 快检失败退回当轮的现有流程不变；失败摘要里带上失败的用例名。
- B 项的通过记录在这里同样适用：快检里已经通过、输入没再变的测试步骤，合并前门禁可以沿用——前提是快检跑的是该步骤的全集而不是子集；子集的结果不能当作步骤通过。

### D Web 测试并行

- 实测 112 个测试文件里哪些必须串行（占端口、起真实内核、检查进程残留、改全局状态），其余并行。分成两组（例如两个 vitest project）：纯逻辑与组件测试并行，`*live*` 一类保持串行或按可隔离程度有限并行。
- 目标：空闲机器上 Web 测试步骤的墙钟时间降到现在的一半以下；连续跑 5 次全绿；跑完没有残留进程（`apps/web/test/logtail-live-cleanup.test.ts` 的检查方式）。
- T-95 第四次门禁的失败是 `test/eventbus-live.test.ts` 的 afterAll `rmSync` 报 ENOTEMPTY，根因没有定位，当时只加了有界重试。本项实测并行时把它查清楚：是谁在 afterAll 之后还往临时目录写；能定位就修根因并去掉重试，定位不了如实写明。
- 不允许用条件跳过来换时间（面板有不允许条件跳过的守卫）。

## 对设计轮的要求

1. **先量再改。** 设计文档给出改动前的基线表（各步骤空闲与负载下的耗时，取自 `.autome/output/gates/` 下的真实日志与设计轮自己的实测），每项给出预期收益；实现完成后在证据里给出同口径的改动后数据。
2. **不降低检查强度。** 判定标准：合并到 main 的每个提交，`ci-local.sh` 的每个步骤都在「与该提交等价的输入」上通过过。设计文档逐步骤论证输入声明没有漏项，并说明漏项时的兜底（B 的安全边界 1、2、5）。
3. **与并行任务的衔接。** T-96（面板交付批次）正在实现，它会给 `scripts/ci-local.sh` 增加一个浏览器步骤并改 `.github/workflows/ci.yml`。本任务的步骤声明方式要让「新增一步」只需要写出它的命令和输入；谁后合并谁在 rebase 时对齐。
4. **`.autome/` 不由会话修改。** 需要调整 `.autome/config.toml`（`[gate]` 的 `command` / `quick`）时，设计文档与最终证据里给出建议的配置原文，由操作者在合并后手工应用；在那之前，旧配置配新脚本、新配置配旧脚本都不能出错（`sh scripts/ci-local.sh` 不带参数的行为保持「全部步骤都被覆盖」）。
5. 不接触真实账本：测试与实测一律用临时 `AUTOME_HOME`。会话沙箱里跑不了的验收命令如实写明，由宿主门禁复验。

## 不做什么

- 不改门禁的时机：仍然是每轮快检 + 合并前一次完整门禁；合并后的 main 检查继续复用结果。
- 不删减任何测试，不加条件跳过，不放宽 Clippy / lint 规则。
- 不改门禁并发数与合并队列（T-70）、轻量检查车道（T-95 的 E 项）的调度。
- 不做跨机器或远程缓存；通过记录只在本机。
- 不改 `.autome/`。

## 验收标准

1. A：造两个测试目标各有一个失败用例的夹具（或等价的脚本级测试），一次门禁的汇总里两个都列出；汇总含失败用例名。
2. B：用脚本级测试覆盖——只改 `apps/web/` 下一个文件时 Rust 测试步骤标为沿用；只改 `crates/` 下一个文件时受影响的步骤（含 Web 测试）全部执行；只改 `docs/` 时只执行声明了该输入的步骤；改 `scripts/ci-local.sh` 时全跑；顶层新增未归属路径时全跑且守卫测试失败；强制全跑开关有效；在 worktree 内伪造通过记录不被采信。
3. B：失败 → 修一个文件 → 再跑，第二次只执行输入变了的步骤；日志逐步骤写明执行 / 沿用。
4. C：e2e（真实内核 + 假 CLI）——实现轮改动一个测试文件并让它失败，快检当轮退回，失败摘要带用例名；本轮没碰的测试不跑；超预算时写明哪些没跑。未配置快检的项目行为与现在一致。
5. D：Web 测试步骤空闲机器墙钟时间不超过改动前的 50%（证据给出前后各 3 次的数据）；连续 5 次全绿；无残留进程；ENOTEMPTY 一项有结论。
6. 设计文档有改动前基线表，最终证据有同口径的改动后数据；给出建议的 `.autome/config.toml` `[gate]` 原文。
7. `cargo fmt --all -- --check`、`cargo clippy --all-targets -- -D warnings`、`sh scripts/ci-local.sh`（强制全跑）全绿。
