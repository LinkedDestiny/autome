## 背景与现状

### 门禁怎么跑（共同）

- `scripts/ci-local.sh`（158 行）是完整门禁：`run <名> <命令…>` 打印 `==> <名>`、执行、打印 `    ok (Ns)` /
  `    FAILED (Ns)`；末尾逐行 `  ok      <名>` / `  FAILED  <名>`，再一行「全部通过 / 有步骤未通过，用时 Ns。」。
  步骤：Format、Clippy、`Test (unit, end to end, adapter flags)`（第 83 行 `cargo test --workspace --all-targets -- --nocapture`）、
  Desktop install（缺 `node_modules` 时）、Desktop、Contract、Web install（缺 `node_modules` 时）、Web lint / typecheck /
  test / build；`--package` 另加三步。只认 `--package`、`-h`，其它参数退出 2。
- 内核 `gate::start`（`crates/automed/src/gate.rs:168`）用 `/bin/sh -c` 跑包装脚本，包装脚本以 `sh -c "$AUTOME_GATE_COMMAND"`
  执行项目命令，环境继承：`AUTOME_GATE_COMMAND/LOG/PID/EXIT`，以及 `run_gate_attempt`（`scheduler.rs:4836`）加的
  `AUTOME_TASK`、`AUTOME_HEAD`、`AUTOME_GATE_NODE`、`AUTOME_GATE_KIND`。作业文件在**主检出**
  `<项目>/.autome/output/gates/<任务>/<节点>-<head12>.{log,pid,exit,started,kind}`，cwd 是任务 worktree。
  `discard_stale`（`gate.rs:302`）在同一节点换 head 时删掉旧 head 的作业文件——**旧日志不长期保留**。
- 失败摘要：`gate.result.tail = gate::tail(log, 60)`（最后 60 行且 ≤ 6000 字节，`gate.rs:412`），退回时原文进 prompt。
- 失败指纹（`crates/autome-domain/src/gate_failure.rs:158`）：去空白后以 `FAILED`+空白开头、其后不是 `(` 的行是失败步骤名；
  `==> <名>` 划分步骤段；存在失败步骤段时只从失败段收关键行（`test … FAILED`、含 error 类词的行）。唯一按这个日志格式
  解析的代码就是它（`grep '==> '` 全仓库只命中它和它的测试）。
- 合并前门禁整次沿用上一次结果的条件含 `last["kind"] != "quick"`（`scheduler.rs:4697`）：内核层面快检永不替代合并前门禁。
- `.githooks/post-commit` 在主检出每次提交后后台跑 `ci-local.sh`，不带任何 `AUTOME_*` 变量；`.worktree/` 下直接退出。

### A：Rust 测试一次报全，汇总列出失败用例

1. `ci-local.sh` 的 Rust 测试命令改为 `cargo test --workspace --all-targets --no-fail-fast -- --nocapture`（A-R1）；`ci.yml`
   的 `Test`、`End to end`、`Adapter flags exist` 三步都加 `--no-fail-fast`（A-R2）。步骤名保持不变（指纹里的步骤名不变）。
2. 引擎执行每一步时把输出同时写进日志和一个临时文件（`{ "$@" 2>&1; echo $? > rc; } | tee out`，POSIX sh 没有 pipefail），
   步骤失败后按步骤声明的解析器提取失败用例：
   - `cargo`：按 `Running <路径> (target/debug/deps/<名>-<hash>)` 划分测试目标，收集每个目标 `failures:` 段之后、空行之前
     的 4 空格缩进名字（`--nocapture` 下 `test x ... FAILED` 行可能被输出打散，这一段不会）；目标名显示为
     `automed (lib)` / `end_to_end` 这种形式。
   - `vitest`：收集 `FAIL  <文件> > <套件> > <用例>` 行（含整文件失败 `FAIL  <文件> [ <文件> ]`）。
   - 其它步骤（Clippy、lint 等）不声明解析器，不出用例块。
3. 汇总格式（A-R3、B-R4，同时照顾两个读者）：

   ```text
   ==> 汇总
   ────────────────────────────────────────
     ok      Format
     沿用    Clippy  ← T-95/merge_gate@806910a9b823 11-13 21:03 · 输入 3f2a9c1d
     FAILED  Test (unit, end to end, adapter flags)
     ...
   失败用例 · Test (unit, end to end, adapter flags)（2）：
     - end_to_end: gate_quick_feature_x
     - automed (lib): scheduler::tests::y
   执行 9 步，沿用 2 步，失败 1 步。
   有步骤未通过，用时 432s。
   ```

   - `  ok      <名>`、`  FAILED  <名>` 两种行**逐字不变**（`FAILED` 行后面不加任何东西，否则指纹的步骤名与 `==> <名>` 对不上，
     作用域判断失效）。新增的行一律不以 `FAILED` 开头。
   - 汇总前加 `==> 汇总` 一行：它不是失败步骤名，所以汇总里的用例名、沿用说明永远不进指纹关键行（今天汇总落在最后一步
     的段里，只是碰巧没有关键词）。
   - 失败用例块紧挨结论行，总共最多 20 行，超出写「…另有 N 个，见上方日志」；每行截到 160 字符。这样即使 60 行 / 6000
     字节的 tail 从前面截掉部分步骤行，用例块和结论行仍在 tail 里（失败摘要一眼看全，C-R4 同样受益）。
4. 指纹兼容：`gate_failure_window.rs` 加一例——同一份失败日志加上新汇总块前后，指纹 id 与 `steps` 相同。

### B：输入没变的步骤不重跑

#### B.1 步骤声明（B-R1、B-R5）

`scripts/ci/steps.sh` 里三种声明，每种一行（顺序即执行顺序）：

```sh
GLOBAL_INPUTS='scripts .github .githooks .gitignore Cargo.toml Cargo.lock rust-toolchain.toml
  apps/web/package.json apps/web/package-lock.json apps/desktop/package.json apps/desktop/package-lock.json'
NO_GATE='docs .autome .claude AGENTS.md README.md'

step 'Format'  'crates'           cargo fmt --all -- --check
step 'Clippy'  'crates protocol'  cargo clippy --all-targets -- -D warnings
step 'Test (unit, end to end, adapter flags)' 'crates protocol' --cases cargo \
     cargo test --workspace --all-targets --no-fail-fast -- --nocapture
prep 'Desktop install' --if-missing apps/desktop/node_modules sh -c 'cd apps/desktop && { npm ci || npm install; }'
prep 'Build core'      cargo build -p automed -p autome-cli
step 'Desktop'   'apps/desktop crates protocol'  npm test --prefix apps/desktop
step 'Contract'  'crates/automed/src/dispatch.rs' sh -c '…（原文不变）'
step 'Scripts'   ''                              node --test scripts/test/*.test.mjs
prep 'Web install' --if-missing apps/web/node_modules sh -c 'cd apps/web && npm ci'
step 'Web lint'      'apps/web' npm run lint --prefix apps/web
step 'Web typecheck' 'apps/web' npm run typecheck --prefix apps/web
step 'Web test'  'apps/web crates protocol plugins apps/desktop/renderer' --cases vitest npm run test --prefix apps/web
step 'Web build'     'apps/web' npm run build --prefix apps/web
```

`--package` 的三步原样留在 `ci-local.sh`，仍用 `run`（总是执行、不沿用、不报告）。

- `step <名> <输入> [--cases cargo|vitest] <命令…>`：可沿用的检查步骤。**新增一步只写这一行**（X-4：T-96 的浏览器步骤
  就是 `step 'Web browser' 'apps/web crates protocol' <命令>`），全局输入、工具链、未归属路径自动并入。
- `prep <名> [--if-missing <路径>] <命令…>`：准备步骤，**其后有任一 `step` 要执行时才执行**，从不沿用、从不记录。
- 输入写路径前缀（目录或文件），按路径段匹配。表里的划分就是上一节「各步骤实际读什么」逐行落下来的：Web 测试与
  Desktop 跑真实内核，所以包含全部 Rust 输入 `crates protocol`；`plugins` 整个目录归 Web 测试（只有它读，宁宽勿漏）；
  Desktop 读的 `scripts/package.sh`、`.gitignore` 已在全局输入里；M-05 起 `end_to_end` 会读 `scripts/ci/lib.sh`，同样已在全局
  输入里。以后某个测试开始读新的跨目录路径，若该路径已归属别的步骤，必须同步加进本步骤的输入——这是本方案唯一靠人
  守住的点，写进 `steps.sh` 文件头注释，评审 / 审计按 X-3 检查。

#### B.2 输入键（B-R2）

开跑前引擎算一次工作区快照：把 git 的 index 复制到临时文件，`GIT_INDEX_FILE=<临时> git add -A && git write-tree` 得到
树 T——它是**磁盘上实际内容**（已提交、未提交、未跟踪未忽略的文件都算），与提交号无关。每一步的键是下面这段文本的
`git hash-object --stdin`：

```text
ci-local-key 1
step <名>
cmd <命令原文>
tool <工具链指纹>
unclaimed <未归属路径的哈希>
input <路径> <T 里该路径的树/blob id，或 absent>     ← 本步骤输入 ∪ 全局输入，排序
```

- **工具链指纹**：`rustc -vV`、`cargo -V`、`cargo clippy -V`、`rustfmt -V`、`node -v`、`npm -v`、`git --version`、`uname -sr`、
  `sw_vers -productVersion`（有就取）、环境变量 `RUSTFLAGS CARGO_BUILD_TARGET CARGO_TARGET_DIR NODE_OPTIONS` 的值、
  `apps/web/node_modules/.package-lock.json` 与 `apps/desktop/node_modules/.package-lock.json` 的 blob id（npm 装完写的实际
  依赖树，比 lockfile 更贴近「用的是哪套依赖」）。所有步骤共用一个指纹，宁可多失效。
- **未归属路径的哈希**：T 里不落在任何步骤输入、全局输入、`NO_GATE` 前缀下的路径，按「路径 blob」逐行拼起来再哈希；
  没有就是空串的哈希。它进每一步的键——**有未归属的改动，所有步骤都失效**（B-S1）。
- **全局输入**进每一步的键——`scripts/`、`.github/`、各 `package.json`/lockfile、`rust-toolchain.toml` 的任何改动让全部
  步骤失效（B-S2）。`.githooks/`、`.gitignore` 也放进来：它们极少改，放进来比论证「不影响结果」便宜。
- 为什么键里没有 HEAD：Rust 测试里两处读 HEAD（构建标识），断言的都是「二进制的标识与当时 HEAD 一致」——两边来自
  同一个 HEAD，结果只取决于构建机制的代码（在 `crates/` 里），与 HEAD 是哪个提交无关。把 HEAD 放进键会让 B-R3 的三种
  情形全部失效。
- 一步执行通过后，引擎**重算这一步的键**（再做一次快照，约 1 秒）；与开跑前一致才报告为通过，不一致（门禁运行期间
  worktree 被改了）就只算这次执行、不报告通过。

#### B.3 通过记录：只由内核写，存在账本里（B-S3、B-R3、B-R7）

通过记录不是脚本写的文件，而是**账本里 `gate.result` 事件的新字段 `passes`**，只有内核在门禁结束后写；脚本只读内核在
启动门禁前导出的快照。内核侧只做对任何项目都成立的事（N-6）：

- 启动门禁前（`gate::start` 里 `job.clear()` 之后、起进程之前），内核把「可沿用的通过」写进作业目录里的 `<节点>-<head12>.passes`，每行
  `<键>\t<任务>\t<节点>\t<head12>\t<时间>`，并导出 `AUTOME_GATE_PASSES=<该文件>`。来源只有两类：**本任务自己的门禁**，
  以及**本项目里已合并任务的门禁**（`TaskRecord.merge_commit` 有值）；只取最近 7 天、最多 5000 条，按时间新到旧。
- 同时导出 `AUTOME_GATE_REPORT=<节点>-<head12>.report`。门禁命令可以往里写逐行报告（格式见 B.6）；门禁结束（含失败、
  超时）后内核读它（上限 256 KiB，读不了或格式不对就当没有），给 `gate.result` 加
  `steps: {ran, reused, failed, not_run, unverified}` 计数与 `passes: [{step, key}]`（只取 `ran` 行）。没有报告文件的项目，
  `gate.result` 与今天逐字段相同（C-V2）。
- `job.clear()` 与 `discard_*` 一并删除 `.report`、`.passes`。

**信任边界（设计文档要求写明的部分）：**

1. 会话里跑 `ci-local.sh`（实现轮、审计轮自己验证、post-commit 钩子、手工运行）**没有** `AUTOME_GATE_PASSES`，引擎不沿用
   任何步骤、全部执行；也没有 `AUTOME_GATE_REPORT`，不写报告。会话自己跑出来的「通过」进不了账本。
2. 即使 `AUTOME_GATE_PASSES` 被设置，引擎也要求它是**不在当前 worktree（`git rev-parse --show-toplevel`）之内**的普通文件，
   否则整份忽略、全部执行，日志写「通过记录位于工作区内，不采信」。在 worktree 里放一份伪造的记录不会被读到（V-2 g）。
3. 要伪造一条跨任务可用的通过，只能往 SQLite 账本里插事件——在 worktree 之外，违反硬性边界，Codex 沙箱根本写不了。
4. 门禁脚本本身在 worktree 里，会话能改它——这一点今天就成立（把 `ci-local.sh` 改成 `exit 0` 就能让本任务的门禁通过），
   本方案不扩大它：被改过的脚本最多给**本任务**报告假通过；跨任务只采信**已合并**任务的通过，而合并意味着那份脚本
   过了评审、审计和合并前门禁。
5. 每次沿用都在日志与汇总里写出来源（任务 / 节点 / head / 时间）和输入键，对应账本里一条真实的 `gate.result`。报告里
   声称沿用、但键不在内核给的快照里的步骤计入 `steps.unverified`，时间线标红「沿用来源未核实 n 步」——做了能被发现。

三种情形共用这一套（B-R3）：只改一侧的任务——另一侧的键与 main 上已合并任务的通过相同；失败修复后重跑——本任务
上次门禁里通过的步骤键没变；rebase 到新 main——main 的那一侧来自刚合并任务的通过。

#### B.4 构建产物不陈旧（B-S4）

新增准备步骤 `Build core`（`cargo build -p automed -p autome-cli`，与 `ci.yml` web job 同一条），位于 Desktop 与 Web 测试
之前，**其后任一步要执行时就执行**、从不沿用。cargo 增量构建：二进制已是当前源码时约 1 s；`automed/build.rs` 以 HEAD
等为 `rerun-if-changed`，所以 rebase 之后的构建标识也是新的。Rust 测试被沿用时 Web 测试照样拿到当前源码构建的
`target/debug/{autome,automed}`；全部步骤都沿用时它不跑（不浪费）。`ci-config.test.ts` 的「本地门禁在 Web test 之前已构建
内核」改为断言 `prep 'Build core' cargo build -p automed -p autome-cli` 在 `step 'Web test'` 之前——比今天「靠 Rust 测试顺带
构建」更直接。

#### B.5 开关与模式（B-S5、X-5）

- `--all` 或 `CI_LOCAL_ALL=1`：强制全部执行（通过照样报告）。
- `--plan`：只算键、只打印每步的决定（`plan<TAB>执行|沿用<TAB><键><TAB><名>`），不执行任何命令、不写报告。供脚本级
  测试与人工排查。
- `--check-claims`：列出工作区里未归属的路径，有则退出 1。守卫测试就是在真实仓库上跑它（B-S1）。
- `--package` 保持原义；`-h` 帮助更新。不带参数、没有 `AUTOME_GATE_PASSES`：每一步都执行（X-5「全部步骤都被覆盖」）。
- GitHub CI 始终全跑：`ci.yml` 不调用 `ci-local.sh`，各 job 直接跑命令，环境里也没有 `AUTOME_GATE_PASSES`；新加的
  `scripts` job（macos-14，Node 22，先 `rustup show`——`ci-summary` 用例 ① 要真实 cargo）跑 `node --test scripts/test/*.test.mjs`。

#### B.6 日志与报告格式（B-R4）

- 执行的步骤：`==> <名>` … `    ok (Ns) · 输入 <完整键>` / `    FAILED (Ns) · 输入 <键>`（`FAILED (` 开头的行指纹本来就跳过）。
- 沿用的步骤：`==> <名>` 下一行 `    沿用 ← <任务>/<节点>@<head12> <时间> · 输入 <键>`，不执行命令。
- 报告文件（`AUTOME_GATE_REPORT`），首行 `autome-gate-report 1`，其后每步一行 `<状态>\t<键或->\t<名>`，状态取
  `ran`（执行且通过）、`reused`、`failed`、`partial`（子集运行，C 项用）、`not_run`（超预算没跑，C 项用）。名字里不允许
  出现 Tab。引擎每完成一步就追加一行，门禁中途被杀也能留下已完成的部分。

#### B.7 时间线（B-R6）

`task-timeline-model.ts` 的门禁条目：`gate.result` 带 `steps` 时摘要追加「· 执行 n 步 · 沿用 m 步」，`not_run > 0` 再加
「· 未跑 k 项」，`unverified > 0` 再加「· 沿用来源未核实 u 步」；不带 `steps` 时与今天逐字相同。整次沿用（`gate.reused`）
仍是「沿用已通过的结果」，与步骤级的「沿用 m 步」措辞分开。

### C：每轮在宿主上跑改动相关的测试

#### C.1 内核导出（C-R3）

`run_gate_attempt` 对需求任务的 `Gate` 节点、Bug 任务的 `FixGate` 节点再导出两个变量（单仓库项目；工作区项目不导出，
因为没有单一的 head）：

- `AUTOME_ROUND_START`：本轮会话开始时的 head——取最近一条实现会话（Bug：修复会话）`session.started` 的 `start_heads`。
  Bug 修复会话今天不记 `start_heads`，补上（事件字段只增）。
- `AUTOME_BASE`：`git merge-base <RepoSlot.base> HEAD`，任务基线提交。

两个变量只是环境，不改事件；没配快检的项目照常走 `gate.skipped`，逐事件不变（C-V2）。

#### C.2 快检脚本 `scripts/ci-quick.sh`（C-R1、C-R2、C-R4、C-R5）

1. 先跑与今天快检相同的静态检查，但用 `step` 声明（与 `ci-local.sh` 共用同一份输入声明，键一致）：Format、Clippy、
   `prep 'Web install'`、Web lint、Web typecheck。它们是**整步**，通过就报告 `ran`——合并前门禁可以沿用（C-R5）。
2. 改动集：`git diff --name-only $AUTOME_ROUND_START`（工作区对本轮起点，含已提交与未提交）∪ 未跟踪未忽略文件。
   没有 `AUTOME_ROUND_START` 时退到 `AUTOME_BASE`，再退到 `--since <rev>` 参数；都没有就不跑相关测试，在汇总写
   「未提供本轮起点，未跑改动相关的测试」。
3. 由改动集按固定优先级生成候选命令，依次执行：

   | 优先级 | 改动 | 候选命令 |
   |---|---|---|
   | 1 | `crates/<c>/tests/<t>.rs`（改或新增），`end_to_end` 以外 | 整个目标 `cargo test -p <c> --test <t> --no-fail-fast` |
   | 1 | `crates/automed/tests/end_to_end.rs` | 改动块全部落在 `#[test] fn` 体内时 `cargo test -p automed --test end_to_end --no-fail-fast -- <这些测试名>`；否则整套写进「未跑」（C.3） |
   | 1 | `apps/web/test/**` 或 `apps/web/` 其它源码 | 一条 `npm exec --prefix apps/web -- vitest related --run <这些路径>`（测试文件自身也在 related 结果里） |
   | 1 | `apps/desktop/**` | 整步 `Desktop`（全集，通过报告 `ran`；前面自动跑 `Build core`） |
   | 2 | `crates/<c>/src/**`、`crates/<c>/build*.rs`、`crates/<c>/Cargo.toml` | `cargo test -p <c> --lib --no-fail-fast` |
   | 2 | `protocol/**` | `cargo test -p automed --lib protocol` 与 `cargo test -p automed --test prompt_rendering` |
   | 2 | `crates/<c>/tests/` 下非 `.rs` 文件（golden、fixtures） | 该 crate 的 `--tests` |
   | 3 | `crates/autome-domain/src/**` | 依赖它的 crate 的 `--lib`（`automed`、`autome-cli`） |

   - Web 候选执行前先跑 `prep 'Build core'`（真实内核用例要用当前二进制，B-S4 同理）。
   - **预算**：相关测试阶段的墙钟预算 `CI_QUICK_BUDGET` 秒，缺省 120。每条候选**开始前**检查已用时间，超了就不再
     开始，剩下的逐条写进汇总 `  未跑    <命令>（超出快检预算 Ns，留给合并前门禁）` 并在报告里记 `not_run`。已开始的不打断；
     最坏情况由内核的 `quick_timeout_minutes`（10 分钟）兜底。
   - 相关测试是**子集**：报告里一律记 `partial`，从不记 `ran`；内核只把 `ran` 记成通过——子集结果不会让合并前门禁沿用
     `Rust 测试` 或 `Web test`（C-V3）。`Desktop` 是整步，例外地记 `ran`。
   - 失败的候选按 A 项的解析器出用例块，进 tail，快检退回当轮的现有流程不变（C-R4）。
4. 没有被改动集触发的测试一律不跑（V-4「本轮没碰的测试不跑」）。

#### C.3 用例粒度与预算的取值

依据设计轮实测（见基线表 Rust 一行）：

- `end_to_end` 整套 197 s（负载下按日志里 Rust 测试 360/292 的比例约 4 分钟），一个就吃掉 5 分钟上限的大半，**快检里不整套跑**：
  改动块都在测试函数体内时按名字只跑这些测试（258 个用例平均不到 1 s）；改了共用的辅助函数时整套写进「未跑」，留给合并前
  门禁。测试名用 `git diff -U0` 的改动行号映射到当前文件里包住它的 `#[test]` 函数（awk 实现，不依赖 `.gitattributes`）。
- `automed` lib 69 s：C-R1 要求「至少改动所在 crate 的单元测试」，所以改了 `crates/automed/src/` 就整跑 `--lib`；加上增量编译，
  这一类快检预计 100–130 s，略高于任务卡「中位数 90 s」的建议——如实接受，不拿模块名过滤去凑数（那就不再是「整个 crate 的
  单元测试」）。只改 Web 的轮次预计 20–40 s，只改文档的轮次与今天相同（约 8 s）。
- 预算 120 s 是「开始新候选」的截止线：已开始的跑完。最坏情况是 119 s 时开始 `automed --lib`，负载下约 150 s 跑完，加静态检查，
  合计约 5 分钟；内核的 `quick_timeout_minutes = 10` 兜底。M-05 的证据里给出实测的快检耗时（每类改动至少一次）。

### D：Web 测试并行

#### D.1 分组（D-R1）

设计轮串行实测（110 个文件、833 个用例全过，墙钟 518 s，逐文件耗时取自 vitest 输出）：**时间几乎全在起真实内核的
文件上**——`task-ops-real` 138.5 s、`notifier-real` 75.8、`task-merge-real` 38.2、`notifier-backfill-real` 36.6、
`task-detail-real` 35.3、`task-timeline-real` 31.2、`task-live-real` 28.2、`task-docs-real` 26.5，八个文件合计约 410 s（81%）；
72 个纯逻辑文件合计 4.4 s。所以只并行纯逻辑文件几乎不省时间，**必须让起内核的文件之间有限并行**；关键路径是最长的单个
文件 `task-ops-real`（约 27%），理论下限在改动前的 30% 左右，50% 目标有余量。

`vitest.config.ts` 改成三个 project（同一 `groupOrder`，三组同时开跑），成员用显式文件清单：

| project | 成员 | 并行度 |
|---|---|---|
| `unit` | 不起内核、不监听、不扫进程、不碰共享路径的文件（约 70 个） | 默认 `maxWorkers` |
| `kernel` | 起真实内核但不起 Vite dev server、不构建、没有墙钟断言的文件——上面八个重文件里除 `task-live-real` 外的七个，以及 `core-sidecar`、`core-supervisor`、`install-alignment`、`w9Kernel` 系列等 | `maxWorkers` 由 M-06 实测在 3–4 之间取定 |
| `exclusive` | Vite dev server、`npm run build`、production 模式读 `build/`、带墙钟断言、子 vitest（`logtail-live-cleanup`）的文件（串行合计约 90 s，与 `kernel` 组同时跑） | `fileParallelism: false` |

- `build/` 共享：加 `globalSetup` 在任何测试开始前跑一次 `npm run build`（Web build 中位 1 s），并导出一个标记变量；六个
  自己构建的套件改用共享的 `ensureBuilt()`——标记在就不再构建，单独跑某个文件时 `globalSetup` 同样先构建，
  「单独也能跑」不变。三个从不构建的 gateway 套件不再依赖文件顺序。
- 守卫测试 `test/test-groups.test.ts`（新）：每个 `test/*.test.ts` 恰好属于一个 project；源码出现内核 / 端口 / 进程 / 构建
  标记（`target/debug`、`CoreSupervisor`、`AutomedSidecar`、`w9Kernel`、`fixtures/*.sh`、`startServer(`、`createHttpServer(`、
  `createServer(`、`listen(`、`spawn('npm'`、`npm run build`、`ps -axo`、`process-leak`）的文件不得在 `unit`；`exclusive` 成员
  `fileParallelism` 为 false；配置里不出现按环境变量增减文件的写法。新加一个起内核的测试文件忘了归组，这条守卫当场红。
- 实测后可以调整成员（从 `exclusive` 下放到 `kernel`），但只能凭 M-06 证据里的实测结果，不按文件名猜。

#### D.2 指标与测法（D-R2）

主机常年有 2–3 个 Loop 在跑，没有真正的空闲时段。M-06 在同一时段**交替**跑「改动前配置」与「改动后配置」各 3 次
（改动前配置 = 旧 `vitest.config.ts` 原文，写到 `.autome/output/` 下，用 `--config` 指定、`--root apps/web`），每次记墙钟与
load average，比较中位数：改动后 ≤ 改动前 × 50%。随后改动后配置连续 5 次全绿，每次结束后按 `logtail-live-cleanup` 的方式
（`ps -axo pid=,ppid=,command=` 找命令行含本次私有 `TMPDIR` 的进程及后代，等 2 s 后要求为空）确认无残留。

#### D.3 ENOTEMPTY（D-R3）

先修夹具：`automed-pidfile.sh` 改为把参数传下去（`exec "$W3_REAL_AUTOMED" "$@"`），且 `--version` 不写 pid 文件。然后验证

## 建议的门禁配置

合并后由操作者手工应用（会话不改 `.autome/`）。只改 `quick` 一行：

```toml
[gate]
command = "sh scripts/ci-local.sh"
run = "before_merge"
timeout_minutes = 30
quick = 'if [ -f scripts/ci-quick.sh ]; then sh scripts/ci-quick.sh; else cargo fmt --all -- --check && cargo clippy --all-targets -- -D warnings && { [ -d apps/web/node_modules ] || (cd apps/web && npm ci); } && npm run lint --prefix apps/web && npm run typecheck --prefix apps/web; fi'
quick_timeout_minutes = 10
```

四种组合（另有内核新旧两种，同样成立）：

| 配置 \ 脚本 | 旧脚本（合并前切出的分支） | 新脚本 |
|---|---|---|
| 旧配置 | 现状 | 完整门禁：新内核导出快照就沿用、否则全跑；快检仍是旧四条命令 |
| 新配置 | `scripts/ci-quick.sh` 不存在，走 else 分支 = 旧四条命令；完整门禁不变 | 完整门禁带沿用；快检跑 `ci-quick.sh` |

- 新脚本 + 旧内核（本任务自己的门禁就是这样：跑门禁的是已安装的内核）：没有 `AUTOME_GATE_PASSES` / `REPORT`，全部执行、
  不写报告，与今天等价。旧脚本 + 新内核：多出的环境变量没人读，没有报告，`gate.result` 不多字段。
- 不用 `--quick` 参数而另起文件，是因为旧脚本见到不认识的参数退出 2，会让每一轮快检都失败；用 `||` 回退也不行——
  新快检失败时会去跑旧命令并可能「通过」。
