## 阻塞问题

### R1-P01：后续安装会改变已记录步骤的键，R19 的第二次全沿用与选定方案不能同时成立

- **类别：内部逻辑矛盾。**
- **违反的要求与条款：** B-1、验-4；设计「B-Q1」的 B-1 论证；M-03 新用例 R19「再跑：三步都是 reused」及 M-03 验收契约第一段。
- **设计位置：** 设计第 177–212 行（保留键组成，只为后续执行步骤更新生效键），第 324–328 行（R19）。
- **根因：** 每一个步骤的键都包含 Web、Desktop 两份已安装依赖标记的哈希。准备步骤后重算只影响之后执行的步骤，不能让此前已记录的通过键变成最终安装状态的键。

具体反例：

1. 按 R19 从没有 `node_modules` 开始。Before 成功时记录 `K_before(absent)`。
2. Web install 写入已安装标记；After A / After B 按设计使用安装后的键记录通过。
3. 第二次不做任何改动，`prepare` 算出的 Before 键是 `K_before(installed)`，与首跑报告里的键不同。因此 Before 必须「执行」，不可能如 R19 所要求「三步都是 reused」。

这不只影响 R19 中安装前的 Before。真实完整门禁的顺序是 Desktop install → Desktop / Contract / Scripts → Web install → Web 各步。两份依赖首次都需安装时，Desktop / Contract / Scripts 虽然已经位于一次安装之后，其通过键仍会被后面的 Web 安装改变，第二次无法沿用。快检在 Web install 前的 Format / Clippy 也有同类现象。

**源码与核验：**

- `scripts/ci/inputs.mjs:29` 的 `toolchain()` 无条件读取两份已安装标记；`calculate()` 把同一个工具链哈希纳入每一步的键。`scripts/ci/steps.sh:12` 起可核对上述准备顺序。
- 用未修改的现有算键器，在隔离仓库依次取得「两份都缺失」「只安装 Desktop」「两份都安装」的键，再严格按设计的记录时点生成外部通过记录。最终状态重新计划得到：Before **执行**、After Desktop **执行**、After Web **沿用**。另断言 R19 的 Before 安装前后键不同，成立。
- 复现脚本：`.autome/output/review1-key-probe.mjs`；输出：`.autome/output/review1-key-probe.log`。这是现有算键器实验与设计时序推导，不是对尚未实现方案的验收。

**处理要求：** 统一 B-1 的实现方案与 R19 的预期，并处理同一门禁多次安装造成的中间步骤失效。若认为安装前 Before 不属于 B-1，可单独纠正该断言，但还须解决安装后的 Desktop / Contract / Scripts 被后续安装失效的问题。不能把已执行步骤直接改挂到未测过的最终键下。检查范围为完整门禁、快检中所有安装前和两次安装之间的步骤。

### R1-P02：安装失败后的另一个成功准备步骤会重新认可失败安装留下的输入，违反 B-Q2 的失败分支

- **类别：内部逻辑矛盾。**
- **违反的要求与条款：** B-2、任务约束 7；设计「B-Q1」第 184–187 行与「B-Q2」第 219–222 行。后者明确承诺安装失败后「后续步骤的键仍是 prepare 时的键，失败的安装改了依赖树就报 partial」。
- **根因：** 重算条件是「本次准备成功（failed_count 没增加）」，没有保留此前依赖安装失败造成的不可复核状态。它适用于所有 `execute_prep`，包括紧随 Desktop install 的 Build core。

具体反例：

1. 首次计划得到键 `K0`。Desktop install 失败，但已经改变了 `node_modules/.package-lock.json`；门禁按现有约定继续执行。
2. 下一项 Build core 成功。它本次没有增加 `failed_count`，所以按 B-Q1 重算并写入所有后续步骤的键 `K1`，其中已包含失败安装留下的依赖状态。
3. 某个后续检查返回成功，期间输入未变。设计要求将跑后键与生效键 `K1` 比较，于是记录 `ran K1`；B-Q2 对同一情形要求的却是 `partial -`。
4. 「本轮门禁整体失败」不能隔离这个通过记录：`gate.rs::read_report` 收集所有 `ran`，`Store::gate_passes` 允许当前任务沿用失败门禁中的成功步骤。下次输入仍是失败安装留下的状态时，`K1` 可以命中；若后续步骤均命中，安装准备步骤也会被跳过。

**源码与核验：**

- `scripts/ci/steps.sh:12`、`:13` 确认 Desktop install 后就是 Build core。`scripts/ci/lib.sh:182`、`:193` 确认准备失败后继续执行及沿用分支。`crates/automed/src/gate.rs:162`、`crates/automed/src/store.rs:674` 确认失败门禁内的 `ran` 可进入当前任务的后续沿用记录。
- 同一隔离脚本让依赖准备写入不同标记后退出 7，随后让 Build core 返回 0。对未修改的 `execute_step` 分别传入原始键和设计规定重算后的生效键，报告分别为 **`partial -`** 与 **`ran <键>`**，此时 `failed_count=1`。
- 将后一条通过记录交给现有 `prepare` 再跑：安装与 Build core 均跳过，Consumer 沿用，结果为 **执行 0 步、沿用 1 步、失败 0 步**。实验只模拟方案规定的生效键选择，没有实现新 `keys` 模式或修改产品代码。
- 脚本与输出同 R1-P01。

**处理要求：** 定义依赖准备失败后哪些步骤不能产生可沿用记录，以及什么条件可以恢复可信计量；无关的成功准备步骤不能抹去该失败。按真实顺序加入「安装失败改变依赖 → Build core 成功 → 后续检查成功 → 再跑」的判别场景。检查范围包括完整门禁所有准备步骤，以及快检多次调用 Web install / Build core 的路径；不要求失败后停止其它检查。
