## 目标与非目标

**目标。**

1. 复盘轮（自动、手动两种入口）启动时，提示词里是本任务**当时**的指标表，含设计轮、实现轮、reopen 与门禁各项（A-1、验-1）。
2. 指标新增五项门禁数据，进 `METRIC_NAMES`，可以被 `predicted_impact.metric` 引用。口径与账本 `gate.result` 一致，最终计量包含
   复盘之后的门禁（A-2、验-2）。
3. 旧任务的指标里没有新字段时，新指标按缺失处理，不当 0、不进均值（A-3、验-3）。
4. 门禁在本次运行里装了依赖，**最后一次安装之后**通过的步骤照常记 `ran <键>`，下次输入不变时沿用。完整门禁与快检都覆盖
   （B-1、验-4）。最后一次安装之前跑过的步骤是在当时的依赖状态下测的，键记当时的状态，下次因依赖状态不同而执行一次、之后沿用，
   不改挂到没测过的键下（B-Q1「保证范围」）。
5. B-2、B-3、B-4 三条现有保证不放松，各有测试（验-5）。

**非目标。**

- 不改协议文本（仓库根 `protocol/` 与本任务副本都不改），不升账本 schema（保持 9），不动 `.autome/`。
- 面板不新增指标展示，`WARNING_METRICS` 不变（A-Q3）。`mean_request_input` 的怪处不处理（A-Q6，记 Backlog BL-01）。
- T-99 的 L-01…L-04 不做。
- 不改 `scripts/ci/steps.sh` 的步骤与顺序，不改 `install-node.sh`，不改通过记录的文件格式与 `ci-local-key` 版本。

## 方案

### A-Q1 复盘前计量放在哪：`start_session` 取值处现算

- 把 `write_task_metrics` 拆成两个函数：
  - `measure_task(ctx, task_id) -> Result<TaskMetrics>`：只算、不写。
  - `write_task_metrics`：调 `measure_task`，然后照旧 `set_task_metrics` + 发 `task.metrics` 事件。
- `start_session` 的复盘分支改成 `measure_task(ctx, &task.id)`。出错时记 `warn`，退回 `ctx.store.task_metrics`，再退回 `None`。
  这样计量失败不会挡住复盘轮启动。
- 自动、手动两个入口都经过这一处，所以都拿到现算值。
- 每次启动复盘都重算。T-98 那种失败一次复盘一次的任务，每轮复盘看到的都是当时的数。
- 手动复盘时任务若已 `Failed` / `Cancelled`，账本里已有最终值，但仍然重算。理由：
  - `start_retro` 要求 worktree 还在，状态块与证据文件可读，现算值不比最终值旧；
  - 旧内核记下的最终值没有门禁字段，现算才有。

  `measure_now` 不加「进入 `Node::Retro`」的分支。

### A-Q2 复盘前的值存不存：只交给提示词，不落账本

复盘时现算的值只传给 `LaunchSpec.task_metrics`，不写 `tasks.metrics`，也不发 `task.metrics` 事件。约束 4 列出的读取方因此都
不受影响：

- 版本页、移除实验基线：读 `tasks_with_metrics`。在途任务没有这一列，进不了均值与基线。
- `measure_now` 的 `Done` 分支：`task.metrics.is_none()` 的判断照旧成立。最终计量照常发生，它是唯一一次写入，「最终值覆盖复盘值」
  自然成立。
- 面板读 `task.metrics` 事件：在途期间没有这种事件，`task-stage-model.ts` 的退路不会把复盘时的值当最终值。
- `dispatch.rs` 任务回包的 `metrics` 与「`task.metrics` 是最终汇总」的注释，照旧成立。

E1 用例会钉住这几点：复盘期间 `tasks_with_metrics` 不含本任务，合并前没有 `task.metrics` 事件，合并后的最终值包含复盘之后的门禁。

### A-Q3 名称与分组

新增五个指标，`METRIC_NAMES` 从 12 项变成 17 项。新名字追加在末尾，旧顺序不变。

| 名字 | 含义 |
|---|---|
| `round_gate_runs` | 每轮门禁（实现轮 / 修复轮之后那次）跑完的次数 |
| `round_gate_failures` | 其中失败的次数 |
| `merge_gate_runs` | 合并前门禁跑完的次数 |
| `merge_gate_failures` | 其中失败的次数 |
| `gate_seconds` | 本任务所有门禁实际运行的总秒数 |

- 次数与失败数分开，因为 `predicted_impact` 一次只引用一个名字。
- 「每轮门禁」不叫「快检」：它按节点认定，项目没配快检时它就是完整门禁。本仓库这一组实际就是快检。
- 五个字段在 `TaskMetrics` 上都是 `Option`，带 `#[serde(default, skip_serializing_if = "Option::is_none")]`。
  - 新内核每次计量都写 `Some(n)`，包括 `Some(0)`：零是断言，缺失不是。
  - `value()` 对 `None` 返回 `None`。
- `WARNING_METRICS` 不加新项。任务卡没要求，加了会改变版本页的警告行为，记 Backlog BL-03。

### A-Q4 口径（全部在一个纯函数 `task_metrics::gate_counts` 里）

数据来源：新增 `Store::timed_events(subject_id, kinds)`，按 `seq` 返回本任务 `gate.started` / `gate.result` 事件的
`(seq, kind, payload, at_secs)`，其中 `at_secs = CAST(strftime('%s', at) AS INTEGER)`，读不出时为 `None`。
`write_task_metrics` 拿到后交给 `gate_counts`，结果经 `Counts` 进 `aggregate`。

| 事件 / 情形 | 计法 |
|---|---|
| `gate.result`，`node` ∈ {`gate`, `fix_gate`} | 每轮门禁 +1；`ok == false` 时失败 +1。超时与熔断时也是 `ok=false`，都算失败 |
| `gate.result`，`node` = `merge_gate` | 合并前门禁 +1；`ok == false` 时失败 +1 |
| `gate.result`，`node` ∈ {`repro_check`, `main_check`} | 不进两组，只计入耗时 |
| `gate.reused` / `gate.skipped` | 不算一次，不计耗时。宿主没跑，`timed_events` 也不取这两种事件 |
| 未配对的 `gate.started`（作业消失、HEAD 移动、仍在跑） | 不算一次，不计耗时。结果未知，不猜 |
| 同因熔断回放 | 不写新事件，所以自然不重复计数 |
| 耗时 | 对每条 `gate.result`，找它之前最近一条 `node` 与 `log` 都相同的 `gate.started`，取 `at` 之差，小于 0 按 0 算。找不到配对、或任一侧 `at_secs` 为 `None` 时，这条只计次数、不计耗时 |
| 排队时间 | 不含。`gate.started` 写在出队、作业启动之后。耗时含作业结束到内核轮询到的那段延迟（一个 tick 量级） |

- 分组按 `node`，不按 `kind`。原因：
  - 每轮门禁可能是 `quick` 也可能是 `full`；
  - Bug 的 `fix_gate` 可能是 `repro` 或 `quick`；
  - 在这些情形下，按 `kind` 分组会把同一个「实现后那次门禁」拆进不同组。
- Bug 任务的 `fix_gate` 算每轮门禁，它的 `merge_gate` 算合并前门禁。`repro_check` 本来就预期先红，不计失败。
- `main_check` 在合并之后、清理之前跑，所以会计入最终计量的耗时。复盘时它还没跑。
- 没有任何门禁事件的任务，五项都是 `Some(0)`。

- 整个指标缺失时，仍是现有那句「（本任务没有记录到指标。…）」。
- `{metric_vocabulary}` 由 `METRIC_NAMES.join(" / ")` 代入，自动带上五个新名字，不改协议文本。

### B-Q1 修法选型：(c) 准备步骤成功跑过之后重算其余步骤的键

候选方案的取舍如下：

- **(b) 不再把 `node_modules/.package-lock.json` 算进键，只靠锁文件。** 排除。T-97 把已装依赖树算进键，是为了让「装的是哪套
  依赖」决定能否沿用（T-97 设计「工具链指纹」一条）。去掉它，B-2 只能改由另一个判据保证。`.autome-lock.sha256` 管不住手工
  `npm install`；改判据又要动 `install-node.sh` 和标记格式。
- **(a) 一开始先装依赖再算键。** 排除。全沿用时也会去装，违反 B-4。
- **(c) 键的组成一字不改，只改算键时机。** 选这个。做法：
  - `inputs.mjs` 新增模式 `keys <steps 文件>`，按行输出每一行的键，`prep` 行输出空行。
  - `lib.sh` 的 `execute_prep` 跑完准备命令后，如果这次准备**成功**（`failed_count` 没增加），**并且本次运行里没有发生过任何
    准备失败**（`ci_prep_failed` 未置位），就调 `keys` 把当前键写进 `$ci_tmp/keys`：先写临时文件，再 `mv`。
    - 调用失败时，把 `$ci_tmp/keys` 写成单行 `unknown`。
    - 准备**失败**时：置位 `ci_prep_failed=1`，不重算。这个标志在本进程内**只增不减**：之后任何准备步骤（包括紧随其后、本身成功
      的 `Build core`，以及快检里第二次 `Web install`）都不再重算，`$ci_tmp/keys` 保持最后一次可信的内容（上一次成功重算的结果，
      或没有该文件、即 `prepare` 时的键）。这保持 `ci-reuse` 第 17 例的现行行为（失败后后续检查照旧执行）。
    - 被 `--if-missing` 跳过时不重算，本来什么都没变。
    - 失败标志的「恢复」条件：只有下一次门禁进程重新 `prepare`，按当时磁盘上的实际依赖状态算键。同一进程内不恢复，因为失败的安装
      可能改了依赖树，而同一进程内没有办法区分「失败的安装改了什么」和「后来成功的步骤改了什么」。
  - `execute_step` 的沿用分支不变，仍按 `prepare` 时的键与记录决定沿用（B-4 的基础）。
  - 执行分支要先定下**生效键**：
    - 有 `$ci_tmp/keys` 时，取第 `i+1` 行；
    - 文件内容是 `unknown`，或那一行为空时，生效键记为不可复核；
    - 没有这个文件时，用 `prepare` 传进来的键。
  - 执行分支跑完后：
    - 失败 → `failed <生效键>`；
    - 生效键可复核，且跑后重算的键与它相等 → `ran <生效键>`；
    - 其它 → `partial -`。
  - 日志里的「输入 <键>」也改用生效键。

  **保证范围。** 键里含两份已装依赖标记，所以每次安装都会改变其后所有步骤的键。记录的键永远是那一步**实际运行时**的依赖状态：
  - **最后一次安装之后**的步骤：生效键就是最终状态的键。同一 worktree 不改输入再跑，`prepare` 算出的键与它相同，沿用。
    这是 B-1、验-4 的保证，真实场景（只有 `Desktop install` 或只有 `Web install` 执行了 `npm ci`，如 T-99）完整落在此范围内。
  - **最后一次安装之前**的步骤（安装前的 `Before`；两份依赖都首次安装时，夹在 `Desktop install` 与 `Web install` 之间的
    `Desktop` / `Contract` / `Scripts`；快检里 `Web install` 之前的 `Format` / `Clippy`）：它们是在较早的依赖状态下测的，
    键也是那时的状态。**不**把它们改挂到最终状态的键下——它们没在最终状态下测过，改挂就是放松 B-2。下一次门禁里这些步骤因键
    不同执行一次，随后记在最终状态的键下，再下一次沿用。这是一次性收敛成本，不是回归：现状下它们同样要在安装后重跑，而且
    安装之后的步骤还一直不记录通过。BL-05 记录了「按步骤声明依赖标记」的省时优化，不在本任务内。

  这套做法对完整门禁（`prepare`）与快检（`quick-prepare`，含浏览器阶段的再次 `prepare('Web install')`）同时生效，因为两者都
  经过 `execute_prep` / `execute_step`。

逐条论证：

- **B-1。** `Desktop install` / `Web install` 成功后重算一次，之后每一步的生效键就是它实际运行时的键，键里含装好后的依赖树。
  跑完复核相等，记 `ran`。下一次门禁在同一 worktree 里，最后一次安装之后的步骤，其 `prepare` 算出的键与上次的生效键相同，于是
  沿用（验-4）；更早的步骤按上面「保证范围」处理。
- **B-2。** 键里照旧有两份已装依赖树的哈希，以及 `GLOBAL_INPUTS` 里的锁文件。
  - 没装（`absent`）、装的树变了（手工 `npm install` 会改写 `.package-lock.json`）、锁文件变了而没重装，这三种情况的键都和
    「按锁文件装好」时记下的键不同，所以不会命中。
  - 每条记录的键，都是那一步实际运行时的依赖状态，不会出现「没装时跑出来的通过」被记成「装好时的键」。
- **B-3。** 跑后重算与生效键比较，这一条不变。步骤运行期间改了源码或锁文件，仍报 `partial -`。
  - 准备步骤之后、下一步开始之前发生的改动会进生效键，记下的就是那一步实际测过的内容。这是内容寻址本来的含义，不是放松。
  - 重算失败按不可复核处理，报 `partial`，失败时一律不记录通过。
- **B-4。** 沿用决定与「`prep` 只在其后还有不能沿用的步骤时才写」都没改。全部能沿用时不执行准备步骤，也就不会重算。

### B-Q2 判定点

- 「已装依赖与锁文件是否一致」由键判定：已装依赖树的哈希与锁文件都在键里。沿用决定在 `prepare` 时做，看的就是当时的已装状态。
- 不一致时不沿用，计划里这些步骤是「执行」。执行前由准备步骤（`install-node.sh` 发现指纹不符就 `npm ci`）先装，装完重算键。
- 任何准备步骤（`Desktop install` / `Web install` / `Build core`）失败时：
  - 置位 `ci_prep_failed`，之后本进程不再重算，后续检查照旧执行（第 17 例）；
  - 后续步骤的生效键停留在最后一次可信的键（失败之前最后一次成功重算的结果，或 `prepare` 时的键）。失败的准备步骤若改了依赖树，
    步骤跑完后的复核键与生效键不等，报 `partial -`；若什么都没改，复核键相等，记 `ran`——此时记录的键描述的就是真实状态；
  - 紧随其后成功的无关准备步骤（如 `Desktop install` 之后的 `Build core`）**不能**抹去这次失败：标志只增不减；
  - 门禁整体失败。
- 哪些步骤不能产生可沿用记录：失败标志置位之后、依赖状态相对生效键发生了变化的步骤，即复核键与生效键不等的那些。
  可信计量只在下一次门禁进程里恢复。

### B-Q4 键版本

键的组成不变，`ci-local-key 1` 不升。

- 新旧脚本对同一状态算出同一个键，旧记录在新脚本下只会在状态完全相同时命中，不会错误命中。
- 在跑的其它任务分支用自己分支里的旧脚本，不受影响。
- 内核 `gate.rs::read_report` 只按 `ran <键>` 收集 `passes`，不解析键的组成，与键版本没有耦合。

  - 应对：E1 断言的是复盘提示词与最终指标里的数，以及它们与 `gate.result` 扫描结果相等，不断言会话总数。
  - 序列以实现期实测为准，写进证据。
  - 内核流转若让「3 次快检、2 次合并前门禁」凑不出来，就改夹具脚本的失败时机，不改断言的口径。
- **复盘启动时现算的开销。** 读状态块、证据目录与会话表，和合并前那次计量相同，毫秒到百毫秒量级。计量出错只记 `warn` 并退回，
  不挡复盘。
- **两次安装之间与安装之前的步骤要多跑一次。** 见 B-Q1「保证范围」。只发生在一个 worktree 两份依赖都首次安装的第一次门禁之后，
  收敛后稳定沿用；代价是一次，不是每次。
- **重算键的开销。** 每次准备步骤成功后多算一遍全部键：一次快照，加一轮工具链版本命令。完整门禁至多 2 次，快检至多 3 次，
  每次约 1–3 秒。
- **旧记录与混跑。** 键的组成与版本都不变，新旧脚本对同一状态算出同一个键，不存在错误命中。
- **回退。** 三个里程碑相互可单独回退：
  - M-02 回退后，复盘轮回到「没有记录到指标」；
  - M-01 回退要连同 M-02 一起回退；
  - M-03 回退后，回到装依赖后不记录通过的旧行为。

  新字段都可缺失，回退后旧内核读新 JSON 也能读：serde 默认忽略未知字段，`TaskMetrics` 没有 `deny_unknown_fields`。

- BL-01 `METRIC_NAMES` 里的 `mean_request_input` 是会话级字段，`TaskMetrics::value()` 永远返回 `None`。`predicted_impact` 引用它
  就永远测不出来。可以从词表里拿掉，或者在任务级汇总出它（A-Q6）。

- BL-04 重算键之后，可以顺手查一次通过记录：首次装依赖前判为「执行」的步骤，如果装后键已有记录，就改为沿用。这是省时优化，
  不影响正确性。

  `Format` / `Clippy` / `Desktop` 这类步骤不被无关的另一份安装改键，省掉 B-Q1「保证范围」里说的那一次重跑。这要改键的组成
  与 `ci-local-key` 版本，不在本任务内。
